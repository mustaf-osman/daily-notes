- [eMudhra 的 CA 私钥不是被偷的，是算出来的](https://github.com/mitmproxy/mitmproxy/commit/169234499088fc2c414644a67efaed3d64ae2e3b) — 146 分。这条看起来像个玩笑：mitmproxy 加了个 `--emudhra` 开关，直接拿已泄漏的 eMudhra 中间 CA 私钥签发证书，顺手把 certifi 里的 eMudhra 根从预编译包里移除。背后是本周最严重的安全事件：印度 CA eMudhra 的八张中间证书（六张 TLS、两张代码签名）私钥被确认泄漏。Google 安全团队的说法是这些密钥"不需要被偷"——2025 年 4 月的签发仪式随机性不足，生成了第二套弱密钥，而发布到根证书库的恰好是这一套，所以任何人都能从公开证书反推出私钥。Mozilla 收到报告后两小时内自己恢复了密钥，评论区有人贴出其中一张的私钥指数 d=4，穷举空间小到可以口算。处置速度罕见地快：Chrome 17 日 18:05 UTC 收到报告、19:45 推送 CRLSet，Firefox 22:59 完成 OneCRL；Go 在 20 日的安全版本里用 URGENT 通道封掉，没点名是哪家 CA。好消息是目前没有链到这六张 TLS 中间证书的证书进过 CT 日志，也就是说理论上还没有人能用它骗过浏览器。

- [PHP 两个 critical RCE，官方连夜发四个分支](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/) — 677 分，今日最高。8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 修掉 CVE-2026-109618 与 CVE-2026-109619，两个都能让未认证攻击者执行任意代码。前者是请求恰好撞上 memory_limit 时留下半初始化的内部结构，之后被当成合法数据使用——在 Apache + mod_php 上，默认配置就能在应用代码跑起来之前触发，已演示完整 RCE；后者是 fatal error 留下的悬空全局状态，同一个 worker 处理的下一个请求会踩到已释放内存（UAF），也在真实应用上打通过。两个洞都在内存管理和错误处理里，也就是每个请求都会走的地方——这既是它严重的原因，也是它难修的原因：动这里就可能破坏兼容性、拖慢性能、逼第三方扩展改代码。文章后半段讲的是流程：2024 年 PHP 做了多年来第一次外部审计（Sovereign Tech Agency 出钱、OSTIF 组织、Quarkslab 执行），以及靠这套机制一点点还安全债的过程。

- [LiteLLM 1.107.0 被投毒：装一次，机器就归别人](https://safedep.io/litellm-pypi-compromise-credential-stealer-backdoor/) — 434 分。PyPI 上的 litellm 1.107.0 七个 wheel（Linux / macOS / Windows 全中）里多了三个文件：`cook.pth` 让 Python 每次启动都 import `cook.py`，后者收集 SSH 私钥、云凭据、CI/CD secret、各家 AI 工具 token、浏览器密码和 LiteLLM proxy 数据库里的 provider key，加密后发到 www.litellm[.]dev；`sitecustomize.py` 再起一个常驻进程，每小时从一个 GitHub 文件读地址、重跑窃密、下指令。哪怕你的进程根本没 import litellm，只要环境里有 Python 就会执行。注入手法很干净：sdist 的 pyproject.toml 在 `[tool.maturin]` 下多了一行 `data = "cook"`，把 cook/ 目录塞进 wheel 的 purelib，而 sdist 本身不含 cook/，只看源码包看不出问题。更阴的是版本对不上——tag v1.107.0 指向的提交里 version 写的是 1.108.0，攻击者把版本号改回 1.107.0、把 litellm-proxy-extras / enterprise 的 pin 降回 rc2 的值，让依赖 diff 看起来正常。三个平台的 wheel 构建时间分别是 11:20 / 11:21 / 11:37 UTC，Windows 版所有 .py 都是 CRLF，像是从 Windows 上的 git checkout 打出来的。SafeDep 判断（中等偏高置信）是 BerriAI 自己的私有发布流水线用了被改过的源码，而不是外部拿 PyPI token 上传——这比"某个人账号被盗"严重得多。1.106.2、rc1、rc2 干净，1.107.0 已被 PyPI 下架。

## 💡 今日点评

**今天真正的主题不是"又有漏洞了"，而是"该验证的地方没人验证"。** 首页十条里五条是安全事件，而且没有一条是普通的"某个函数写错了"。eMudhra 的私钥不是被偷的，是签发仪式随机性不足、能从公钥反推出来的——整套 PKI 建立在"私钥真的随机"这个假设上，而这个假设在 2025 年 4 月到 2026 年 10 月之间没有任何人验证过，最后是一个外部研究者去看了一眼。LiteLLM 的攻击者没黑 GitHub，改的是构建产物，还把版本号和依赖 pin 调回去让 diff 看起来干净；PyPI 上这个版本连 provenance attestation 都没有，也就是说"这个包确实来自那个仓库"根本无从证明。Railway 的环境变量加密了，但攻击者拿到了其中一部分的明文——加密存储和"密钥没跟数据放在一起"是两件事，前者做到了，后者没有。三个事故，三种缺失，都是流程设计上就没人负责核对的那一格。

**AI 让"生产"变便宜的同时，让"辨别真假"变贵了。** PHP 那两条对照最清楚：一边是真实的 critical RCE，两个洞都在每个请求都会走的内存管理和错误处理路径上，mod_php 默认配置就能未认证触发；另一边是 GitHub 上上千个跑不通的假 PoC——LLM 把"写一个看起来像 exploit 的东西"的成本压到零，于是"这到底能不能打穿"成了最贵的问题。Elias 的方法论值得抄：自己起个 Docker，手动跑一遍，不信任何二手结论。这个习惯在 agent 时代比任何时候都值钱，因为我们马上要面对的代码，一半是模型写的，一半是模型评审的。

**对做机器人的直接启示：在这类设备上，pip install 约等于把 root 交出去。** LiteLLM 的手法（.pth + sitecustomize）不需要你 import 任何东西，只要装了包、机器上有 Python，进程一启动就执行。RK3588 和 RDK X5 这种设备长期在线、有网、有云凭据，上面还跑着一堆第三方推理库——这是最坏的组合。能做的很具体：锁版本、只用带 hash 的 lockfile、CI 里对 wheel 做一次 diff、别把云 key 明文写进环境变量（Railway 今天刚演示了后果）。安全不是写出来的，是每次装包时多看一眼换来的。
