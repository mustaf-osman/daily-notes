## 💭 技术随想：时间都去哪了——时区、DST 与时间戳的三个坑

时间大概是程序里最"反直觉"的数据类型：`1700000000` 这样一个冷冰冰的数字，在北京是凌晨六点，在纽约却是昨天下午五点。很多线上事故（订单"提前"发货、打卡时间差一天、定时任务少跑一次）追到底都是同一类问题——**没想清楚"时间"在计算机里到底是怎么表示的**。

计算机里的时间其实只有两种真身：**Unix 时间戳**（一个递增的秒数，全世界同一时刻只有同一个值）和**带时区的 datetime**（aware datetime）。其余的表示都是衍生品，坑也大多出在衍生品上：

1. **时区只是"显示层"的翻译。** 时间戳本身没有任何时区概念，`2023-11-14T22:13:20+00:00` 和 `2023-11-15T06:13:20+08:00` 是同一瞬间的两种写法。理解了这一点，"跨时区时间算错了"这类问题的解法就清晰了：**存储永远用 UTC（或整数时间戳），只在展示给用户时转换时区**。转换用 `zoneinfo`（Python 3.9+ 标准库），别再用 `pytz` 那套坑死人的 `localize/normalize`。

2. **DST（夏令时）让钟表出现"幽灵时间"。** 美国春令时切换那天，凌晨 2:00 直接跳到 3:00——**2:30 这个时刻在钟表上根本不存在**；秋令时回拨时，1:30 又会出现两次。Python 处理"不存在的时间"不报错，而是用 `fold` 参数悄悄选择跳变前/后：`fold=0` 把 2:30 理解成跳变后的 3:30（落 UTC 07:30），`fold=1` 理解成跳变前的 1:30（落 UTC 06:30）——同一个字面时间，UTC 相差整整一小时。排 DST 相关的诡异 bug 时，先查 `fold`。

3. **naive datetime 是"没有国籍的人"。** `datetime.now()` 不带时区信息，它到底是什么时间取决于运行它的机器——同一份日志，在 UTC+8 的服务器上是 09:14，在 UTC 上是 01:14。拿 naive datetime 做减法、序列化、跨服务传递，等于把"我住在哪个时区"这个隐含假设塞进了数据里，迟早翻车。判断标准很简单：`dt.tzinfo` 是 `None` 就是 naive，尽量在入口处就 `astimezone(timezone.utc)` 补上时区。

4. **计时要用的不是"时间"，是"单调时钟"。** `time.monotonic()` 从某个任意起点单调递增，系统改时间、NTP 校时、DST 切换都不影响它；而 `time.time()` 会随着系统时间被调前调后。测性能、算超时、做心跳，一律用 monotonic，否则用户手动改一次系统时间，你的超时逻辑就全乱了。

**心法：** 时间的本质是一个单调递增的数字，时区、日历、DST 都是人类叠加上去的"显示规则"。工程上一句话总结：**用 UTC 存，用 monotonic 测，用时区显示。** 想清楚每个 datetime 属于哪一层，时间类 bug 能少一大半。

## 🧩 今日代码片段：时间三坑演示 + timeago 小工具

```python
from datetime import datetime, timezone, timedelta
from zoneinfo import ZoneInfo

# 坑1：同一时刻，不同的钟表显示（时间戳是全世界的公约数）
ts = 1_700_000_000
moment = datetime.fromtimestamp(ts, tz=timezone.utc)
print("UTC     :", moment.isoformat())
print("北京时间:", moment.astimezone(ZoneInfo("Asia/Shanghai")).isoformat())
print("纽约时间:", moment.astimezone(ZoneInfo("America/New_York")).isoformat())

# 坑2：DST 夏令时——2026-03-08 纽约凌晨 2:00 直接跳到 3:00，2:30 根本不存在
ny = ZoneInfo("America/New_York")
d2 = datetime(2026, 3, 8, 2, 30, tzinfo=ny, fold=0)  # 理解成跳变后 3:30
d3 = datetime(2026, 3, 8, 2, 30, tzinfo=ny, fold=1)  # 理解成跳变前 1:30
print("fold=0 ->", d2.astimezone(timezone.utc).isoformat())
print("fold=1 ->", d3.astimezone(timezone.utc).isoformat())

# 坑3：naive vs aware——tzinfo 是 None 的时间没有"国籍"
print("naive:", datetime.now(), "-> tzinfo =", datetime.now().tzinfo)
print("aware:", datetime.now(timezone.utc), "-> tzinfo =", datetime.now(timezone.utc).tzinfo)

# 附：timeago——把时间戳翻译成人话（生产环境换成 i18n 库即可）
def timeago(ts: int, now: datetime | None = None) -> str:
    now = now or datetime.now(timezone.utc)
    secs = (now - datetime.fromtimestamp(ts, tz=timezone.utc)).total_seconds()
    for unit, n in [("分钟", 60), ("小时", 3600), ("天", 86400), ("周", 604800)]:
        if secs < n * 60:
            return f"{int(secs // n)} {unit}前"
    return "很久以前"

print(timeago(int(datetime.now(timezone.utc).timestamp()) - 3600))  # 1 小时前
```

**实际运行输出（本机 Python 3.11，系统时区 UTC+8）：**

```
UTC     : 2023-11-14T22:13:20+00:00
北京时间: 2023-11-15T06:13:20+08:00
纽约时间: 2023-11-14T17:13:20-05:00
fold=0 -> 2026-03-08T07:30:00+00:00
fold=1 -> 2026-03-08T06:30:00+00:00
naive: 2026-08-31 09:14:15.805980 -> tzinfo = None
aware: 2026-08-31 01:14:15.805980+00:00 -> tzinfo = UTC
1 小时前
```

**说明：**

- 同一时间戳三种写法里只有 UTC 的 `+00:00` 和北京时间 `+08:00` 差 8 小时、纽约 `-05:00` 差 5 小时——**时刻没变，变的只是翻译**。
- `fold=0` 与 `fold=1` 输出的 UTC 相差 3600 秒，证明 Python 对"不存在的 2:30"做了跳变方向的选择。回拨那天（秋天）同一个时间出现两次，也是靠 `fold` 区分。
- 本机输出 naive 是 09:14、aware 是 01:14，恰好差 8 小时——如果把这台机器的日志直接存进数据库，和 UTC 服务器一比就"穿越"了，这就是 naive 的祸根。
- `datetime.now(timezone.utc)` 在入口统一收口，配合 `fromtimestamp(ts, tz=timezone.utc)` 把时间戳还原为 aware 对象，全链路不再出现裸的 naive 时间。
- 前端展示时用 `Intl.DateTimeFormat` 或 `dayjs.tz` 按用户时区渲染；后端只认 UTC。两边各司其职，时区 bug 就没有藏身之处。
