# 📅 2026年11月12日 日报

## 💭 技术随想：写完的文件不是"一个瞬间"，是三个

昨天那篇写的是「正则引擎在枚举」，今天这件事更朴素，朴素到不像个 bug：

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

一个自己刚写完的配置文件，下一次读就解析失败；`cat` 一下是空的；再重启一次服务，又好了。第一反应是编码、是磁盘坏、是杀毒软件锁文件。查下去发现都不是——**是"写"这件事，在别人眼里从来不是一瞬间，是三个瞬间，而我只是运气好，没在第一个瞬间被读到过。**

这件事让我有点后背发凉，因为它不挑语言、不挑系统：`open(path, 'w')` 在任何语言里都是最常见的一行代码，而它恰恰是**所有写法里最不安全的那一种**。

今天在本机把这条链量了两遍：Windows 11（NTFS，Python 3.11.15）和 WSL2 Ubuntu 24.04（ext4，Python 3.12.3）。下面每个数字都是真跑出来的。

### 一、先把"半个文件"变成能数出来的东西

做法很土：一个线程每 2 ms 往文件里写三分之一的内容（200 KB 的 JSON，分三段），另一个线程死循环读它并 `json.loads`，统计读到了什么。跑 40 轮重写。

**Linux / ext4：**

| 读到的内容 | 次数 | 占比 |
|---|---|---|
| 完整的旧内容 | 1241 | 16.5% |
| **半截 JSON（撕裂）** | **5490** | **73.0%** |
| 空文件（0 字节） | 787 | 10.5% |

**Windows / NTFS：**

| 读到的内容 | 次数 | 占比 |
|---|---|---|
| 完整的旧内容 | 17 | 43.6% |
| **半截 JSON（撕裂）** | **2** | **5.1%** |
| 空文件（0 字节） | 20 | 51.3% |

两边撕裂的比例差很多，但**别被这两个数骗了**：Linux 那边读者快得多（40 轮里读了 7518 次，Windows 只读了 39 次），撞进危险窗口的机会自然多；Windows 那边读 200 KB 本身就慢，样本少。**危险窗口一样存在，只是被采样的次数不同。** 换个说法更直观：把那 7518 次读当成 7518 个"随机时刻"往写入过程上扔，**只有 16.5% 落在安全区**。

一半以上的读取拿到了坏数据。这不是"偶发"，是**"只要有人同时读，就大概率坏"**。

### 二、`open(w)` 到底是几步

那行 `open(path, 'w')` 展开了是三步，每一步都对外可见：

1. **`truncate`**：文件立刻变成 0 字节。盘上一个字节没动，但所有后来者的 `stat()` 都会看到 0——**这就是那 51% 的空文件**。
2. **`write`**：数据先进操作系统的页缓存。`write` 一返回，**别的进程立刻就能读到**，哪怕它还躺在内存里没下盘。**这就是那 73% 的半截 JSON**。
3. **`close`**：关掉文件句柄。**它什么也没向你保证**——既不保证下盘，也不保证顺序。

我原来脑子里的模型是「写完 = 文件内容是新的」。实际模型是「文件内容是**正在变成**新的」。而"正在变成"的状态，被毫无遮挡地暴露给了所有读者。

顺手测了几个容易混的词：

| 你以为它做的 | 它实际做的 |
|---|---|
| `flush()` 落盘 | 只把 Python 的缓冲区交给操作系统，还在内存里 |
| `close()` 落盘 | 关句柄，不保证下盘（正常关机时 OS 会刷，断电不一定） |
| `fsync()` 落盘 | **真的**要求设备把这块数据写进去，返回才算数 |

三者的关系是包含的：`flush` ⊂ 交给内核，`fsync` 才是交给硬件。前面的实验里，我把 `flush()` 加上了——半截文件照样出现，因为 `flush` 恰恰是"让读者立刻看见"的那个动作。

### 三、原子写法：三件套，每件解决一个不同的问题

```python
tmp = path + ".tmp"                 # 1. 同目录临时文件
f.write(data); f.flush(); os.fsync(f.fileno())   # 2. 内容先落盘
os.replace(tmp, path)               # 3. 原子改名
```

**这三步不是"三重保险"，是三件必须同时具备的事，少一件就有一个洞：**

**① 临时文件必须同目录。** `rename` 的原子性来自"换目录项"——同一块磁盘上，目录项指向哪个 inode 是一次性的切换。跨设备改名不是改名，是"复制 + 删除",中间那段时间目标文件是残缺的。实测：

```text
Linux:   /tmp -> /mnt/c     OSError [Errno 18] Invalid cross-device link
Windows: C: -> D:           OSError [WinError 17] 系统无法将文件移到不同的磁盘驱动器
```

两个系统都直接拒绝。所以"把 tmp 放 `/tmp` 里更干净"这个习惯，是原子写的死敌——**`/tmp` 和你的部署目录经常不在一个文件系统上**，我手上这台机器 G:、D:、C: 就是三块独立的盘。

**② `fsync` 必须在改名之前。** 顺序反了（先改名再 fsync）等于没做：断电时可能留下"新名字 + 老内容"甚至"新名字 + 空文件"。文件系统的日志只保证**元数据操作的顺序**，不保证你 write 的数据已经落地。

**③ `os.replace` 才是原子的那一下。** 同一个目录里把 `x.tmp` 改名成 `x`，读者要么看到旧 inode，要么看到新 inode，**没有第三种状态**。实测这一条是真的：

| | 朴素写法 | 原子写法 |
|---|---|---|
| ext4 撕裂次数 | 5490 / 7518 | **0 / 8013** |
| NTFS 撕裂次数 | 2 / 39 | **0 / 205** |

一万多次并发读取，一次撕裂都没有。

### 四、但两个系统的脾气完全不同

同一段代码，两个系统上的**失败方式**不一样。这张表今天最值钱：

| 现象 | Linux / ext4 | Windows 11 / NTFS |
|---|---|---|
| 改名时有人开着这个文件 | **OK**，旧句柄继续读旧内容 | **PermissionError**，40 轮里重试了 **812 次**，单轮最多 26 次 |
| 改名那一瞬去读 | 不会被拒 | 205 次读里 **9 次被拒** |
| 目录 fsync（保证"改名"本身落盘） | OK | **PermissionError [Errno 13]** |
| 跨设备改名 | EXDEV (18) | WinError 17 |
| posix 权限 | 生效 | 无意义，`chmod 640` 之后 `stat` 还是 666 |
| 打开着文件的读者 | 永远读旧内容 | 读不到（被拒） |

两条要紧的推论：

**在 Windows 上，原子写必须带重试，而且读者也得重试。** 这不是"防御性编程"，是硬性要求——只要目标文件被任何进程开着（编辑器、日志查看器、另一个读者的 `open()`），`os.replace` 就会失败。我第一次跑实验就是直接崩在 `PermissionError: [WinError 5]` 上。而在 Linux 上，同样的代码 0 次重试。

**反过来，Linux 上"原子"有个副作用：** 已经打开文件的进程，**永远读不到新内容**。它攥着的是旧 inode，你把目录项换掉，它手里那个还是旧的。所以"原子更新配置"在 Linux 上解决的是**内容完整性**，不解决**可见性**——想让正在跑的进程看到新配置，还得靠信号或轮询 `st_mtime`/inode。

### 五、`rename` 悄悄扔掉的东西

原子写不是免费的，它换掉的是整个 inode（Linux）。旧 inode 上挂着的东西，全留在旧文件上：

- **权限。** 临时文件是 `mkstemp` 建的 600，或 `open()` 按 umask 建的 644。改名之后目标文件就变成这个权限。实测在 ext4 上：一个 600 的文件被原子重写一次，**变成了 644**——因为临时文件是 644。**把私钥、token、`.env` 从 600 写成 644，中间不需要任何一次误操作，只需要一次"规范"的原子写。** 修法是在改名**之前** `os.chmod(tmp, mode)`。
- **属主。** 以 root 跑一次的定时任务，会把用户目录下文件的 owner 改成 root。
- **硬链接。** 改名换 inode，原来指向它的硬链接还指着旧内容，从此两边分叉。
- **`inotify` 监听。** 监听 inode 的（`IN_MODIFY`）在改名后收不到任何事件了；监听目录的（`IN_MOVED_TO`）才对。
- **容器 bind mount 的单文件。** `docker run -v ./cfg.json:/app/cfg.json` 挂的是那个 inode。宿主上原子写 = 换 inode = 容器里那份**永远停在旧内容**。这个坑我见过不止一次，正确做法是挂目录而不是挂文件。

### 六、`fsync` 到底多贵

这是"要不要加 fsync"最常见的反对理由，量一下（Windows，顺序写，页缓存已热）：

| 写入量 | `fsync` 耗时 |
|---|---|
| 1 MB | 1.34 ms |
| 10 MB | 8.41 ms |
| 64 MB | 12.19 ms |

注意 64 MB 只比 10 MB 多 4 ms：**数据早就顺序刷出去了，`fsync` 最后只是在等设备队列排空**。对小文件（配置文件、状态 JSON，几 KB），这个成本在**亚毫秒**量级——比一次网络往返便宜两个数量级。**为省这一毫秒去做非原子写，账算不过来。**

反过来说，`fsync` 该用的地方是有选择的：**每次写都 fsync 的是"必须扛断电"的数据**（标定参数、进度、账目）；日志、缓存这类丢了可以重算的，不需要。全加等于全不加。

### 七、和手上的东西对上

- **`rp_server` 的配置和标定文件。** App 在改（`AT+HEAD` 的限位、PID 参数），控制循环在每一拍读。非原子写 + 一次半截 JSON，落到电机上就是"参数突然全默认"。这类文件必须 tmp+fsync+rename，而且**读的那一侧要能容忍解析失败并保留上一份好的**——两件事都得做，因为改名之后读的那一侧可能还攥着旧 inode。
- **OTA / 部署脚本。** `deploy-agent1.sh` 直接 `cp` 覆盖 `.py`，而 systemd 可能正在 `import` 那个文件。Python 读到半个文件会抛 `IndentationError`，服务直接起不来——而且是**偶发**的，重跑一次就好了，最容易被归到"玄学"。更新脚本自己，更该是原子的：**先铺好新的，一次性换名，最后才 restart**。
- **面板刷新时起进程竞争。** 我看板子上的 Web 服务常干这事：`open(w)` 写 `state.json`，同时浏览器在轮询。Windows 上还会额外撞上"读者开着文件 → 改名失败"，所以那个重试循环不是可选项。
- **PMIC / flash 写入。** `nRF5340` 上写 flash 是同一件事的另一副脸：先擦扇区（= `truncate`），再写页（= `write`）。断电在中间，读到的是半页，而且**擦除态是 `0xFF`，不是 0**——半页数据看起来完全合法，只是内容全 `FF`。所以要有 CRC + 双区（A/B）+ 序号，靠"哪一区是完整的"来决定用哪份。**PC 上能靠文件系统兜底的那部分，在裸机上全得自己写。**
- **git 自己就是这么干的。** 它不直接改 `.git/index`，而是写 `index.lock` 再一次性 rename。我天天用它，今天才把这招和"配置文件写入"接上号。
- **一条判断标准：** 凡是**别人随时可能读**的文件（配置、状态、共享 JSON、被 import 的模块），写入就必须走 tmp + fsync + rename；只有那种"我独占写、写完才交给下一个人用"的真正临时文件，才能省掉。`open(w)` 不该出现在前一类里——**一次都不该**。

### 八、一句必须说清楚的诚实

上面所有"能扛断电"的结论，**我没有真的拔过电**。本机能测的是"并发读者会看到什么"（这部分是真数据），"断电后留下来什么"只能靠 `fsync`/`rename` 的语义和文件系统实现来推。真要验证，得用 `dm-flakey` 之类故意丢写的块设备，或者 QEMU 里 `-snapshot` 加"随时 kill"。**我能确认的是：非原子写在并发下必坏；原子写在并发下实测零撕裂。断电那一半，是推理，不是实测。**

## 🧩 今日代码片段：`atomic_write.py` — 一个带重试和清理的原子写

比"三行写法"多做了四件必须在生产里做的事：保留原权限、Windows 重试、异常时删干净临时文件、POSIX 上把目录也 fsync 掉。下面是真跑的输出。

```python
# -*- coding: utf-8 -*-
"""atomic_write.py —— 一个能被读者随时读、断电也不会剩半个的文件写入"""
import os, sys, json, time, tempfile, threading

IS_WIN = os.name == "nt"


def atomic_write(path, data, mode=None, retries=200):
    """把 data 写进 path：读者要么看到旧的完整内容，要么看到新的完整内容，不会看到一半。"""
    path = os.path.abspath(path)
    d = os.path.dirname(path)

    # 1) 临时文件必须和目标在同一个目录（同一个文件系统），否则 rename 不再是原子的
    fd, tmp = tempfile.mkstemp(dir=d, prefix="." + os.path.basename(path) + ".", suffix=".tmp")
    try:
        with os.fdopen(fd, "wb") as f:
            f.write(data if isinstance(data, bytes) else data.encode("utf-8"))
            f.flush()
            os.fsync(f.fileno())            # 2) 内容先落盘，再改名。顺序反了等于没做

        # 3) 权限：临时文件是 600，直接改名会把目标文件"变窄"
        if mode is None and os.path.exists(path):
            mode = os.stat(path).st_mode & 0o777
        if mode is not None and not IS_WIN:
            os.chmod(tmp, mode)

        # 4) 改名。Windows 上只要有人开着这个文件，rename 就会失败，得重试
        for i in range(retries):
            try:
                os.replace(tmp, path)
                break
            except PermissionError:
                if not IS_WIN or i == retries - 1:
                    raise
                time.sleep(0.001)

        # 5) 目录本身也要落盘，否则断电后"改名"这件事可能没留下（POSIX 才有这步）
        if not IS_WIN:
            dfd = os.open(d, os.O_RDONLY)
            try:
                os.fsync(dfd)
            finally:
                os.close(dfd)
    except BaseException:
        try:
            os.unlink(tmp)
        except OSError:
            pass
        raise
```

实测输出（同一份代码，两个系统各跑一遍）：

```text
Windows 11 / NTFS / Python 3.11.15
  初写: {"n": 0} mode=666
  覆盖: {"n": 1} mode=666
  60 次重写, 并发读者 275 次读取: 完整=272 撕裂=0 被拒=3
  传错类型 -> AttributeError | 目录里残留: []

WSL2 Ubuntu 24.04 / ext4 / Python 3.12.3
  初写: {"n": 0} mode=640
  覆盖: {"n": 1} mode=640
  60 次重写, 并发读者 2065 次读取: 完整=2065 撕裂=0 被拒=0
  传错类型 -> AttributeError | 目录里残留: []
```

五个值得说的细节：

- **`mkstemp` 而不是 `path + ".tmp"`。** 固定名字的临时文件，两个进程同时写就会互相踩——A 写一半，B 把它改名跑了，A 剩下的字节写进了一个已经不存在的 inode。`mkstemp` 生成不可预测的名字 + 独占创建（`O_EXCL`），这个竞态直接消失。
- **Windows 的重试是必须的，不是保险。** 上面那 3 次"被拒"就是读者在改名那一瞬撞上的；写入侧 40 轮里重试了 812 次（见上文实验）。没有这个循环，代码在 Windows 上会**间歇性**抛异常，而且只在有人读的时候抛。
- **`except BaseException` 里也要删临时文件。** 有人按 Ctrl-C、或者 `data` 类型传错（就是上面那个 `AttributeError`），不清理的话目录里会慢慢攒起一堆 `.tmp` 幽灵文件。**异常路径是最容易被忘记的那条路径，也是留垃圾最多的那条。**
- **权限在改名之前设。** 顺序错了就白设——`chmod` 作用在旧 inode 上，改名一换，新文件的权限还是建它时的那个。Linux 上把 600 变成 644 只需要这一步做错。
- **目录 fsync 只在 POSIX 上能写。** Windows 上 `os.open(目录)` 直接 `PermissionError`，而且 Windows 本来也没有"目录项"这个概念可刷——这不是漏写，是平台没有这个接口。**"同一段代码两套语义"是这行的常态，别指望一份实现到处都一样。**

最后一句提醒：这个函数解决的是**内容完整性**，不解决**谁能看到新内容**。Linux 上已经打开的句柄永远读旧 inode，这一点得靠上层（重启、信号、轮询 inode/`mtime`）来管。**把"文件是完整的"当成"进程立刻用上了新配置"，是下一个 bug 的入口。**

## ✨ 今日一句

> 文件不是"写好了"和"没写好"两种状态，中间还有一段又长又安静的路——所有并发读取都在这段路上翻车。
>
> 所谓原子写，不过是把这段路从别人的视野里挪走：先在一个谁也看不见的地方走完，最后一步才推开门。
