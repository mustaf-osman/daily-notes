## 💭 技术随想：CRC 校验——给数据盖一枚"防伪指纹"

调试串口、抓 CAN 报文的时候，总能在帧尾巴上看到一串"多余的"字节——CRC 或者校验和。每收一包都要算一遍、对一遍，不嫌麻烦吗？不嫌。因为**数据在线上跑的这段路，随时可能挨一拳**：电机一启动、继电器一吸合，电磁干扰就在线上掀起一阵小风暴，谁也不知道哪个 bit 会被打翻。校验码就是贴在包裹上的防伪指纹——发货前盖一个，收货时重盖一遍，对不上，整包拒收。

大白话：校验码就是"数据的防伪指纹"，按固定规则把整段数据揉成一个短号码，接收方照同一条规则再揉一遍，**两个指纹一样才算数**。其中最经典的是 **CRC（循环冗余校验）**：把整段数据当成一个巨大的二进制整数，拿一个约定的"除数"（生成多项式）去除它，除出来的**余数**就是校验码；接收方把"数据 + 校验码"一起再除一遍，能规规矩矩"除尽"才放行。注意这是二进制世界特供的除法——没有借位，减法就是异或（XOR），硬件里几个触发器加几个异或门就能实时算完，代价小到可以忽略。

那为什么不干脆把所有字节加起来当校验，多省事？因为**求和是"瞎"的：它只认总数，不认位置**。想三类经典事故就明白了：

- **一加一减**：一个字节被干扰成 +1，另一个被干扰成 −1——总和纹丝不动，求和校验举手放行；
- **调换顺序**：两个字节在路上被搞反了位置——总和依然一模一样，可"左电机"和"右电机"的参数就这么互换了，求和毫不知情；
- **两处翻转互相抵消**：一个 −2、一个 +2，同样的剧本再来一遍。

这三类错误，CRC **全部当场拿下**——它的数学本质（多项式除法的余数）对"哪个位置、什么顺序"敏感到骨子里。也正因如此，工业界宁可多算这几个字节：以太网帧尾部挂 **CRC-32**、CAN 总线每帧自带 **15 位 CRC**、ZIP/PNG 文件用 **CRC-32**、固件升级整包算 CRC 核对——凡是"数据要经过一段危险旅程"的地方，基本都有 CRC 站岗。

三条工程心得：① 校验只管回答"有没有坏"，不管"坏在哪、能不能修"——要修，那是 ECC / 纠错码的活，分工不同；② **别自己发明多项式**，用标准参数（CRC-8/0x07、CRC-16/CCITT、CRC-32 以太网），不然跟对端的库对不上；③ 接收端算完 CRC 再解析数据，**校验不过直接丢帧**——丢一帧只是少动一下，拿一帧坏数据去执行，可能是机器乱动一下。

## 🧩 今日代码片段：CRC-8 对决求和校验——专挑"漏网之鱼"

实验设计：给一帧 4 字节的控制数据（比如 4 个电机的目标位置低 8 位）分别算出求和校验与 CRC-8 两种"指纹"，然后模拟它上路挨了五种"打"，看谁抓得住、谁放行。**重点看 ③④⑤ 三行。**

```python
# ── CRC-8 小实验:同样的"防伪指纹",为什么比简单求和强 ──
import unicodedata

def crc8(data: bytes) -> int:
    """标准 CRC-8(多项式 0x07,初值 0x00):逐位异或移位,硬件里就是一个移位寄存器"""
    crc = 0x00
    for byte in data:
        crc ^= byte                       # 新字节并入寄存器
        for _ in range(8):                # 逐位处理 8 次
            if crc & 0x80:                # 最高位是 1:左移后异或多项式
                crc = ((crc << 1) ^ 0x07) & 0xFF
            else:                         # 最高位是 0:只左移
                crc = (crc << 1) & 0xFF
    return crc

def checksum(data: bytes) -> int:
    """最朴素的求和校验:所有字节相加,取低 8 位"""
    return sum(data) & 0xFF

def pad(s: str, w: int) -> str:           # 按显示宽度补齐(中文算 2 格),表格才对得齐
    return s + " " * max(0, w - sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in s))

# 一帧控制数据:4 个字节——比如 4 个电机的目标位置低 8 位
frame = bytes([0x12, 0x34, 0x56, 0x78])
ref_sum, ref_crc = checksum(frame), crc8(frame)
print(f"发送: {frame.hex(' ').upper()}   和校验={ref_sum:02X}   CRC-8={ref_crc:02X}\n")

# 传输路上可能挨的"几拳":
cases = [
    ("① 原样到达",    bytes([0x12, 0x34, 0x56, 0x78])),
    ("② 单bit翻转",   bytes([0x12, 0x34, 0x5E, 0x78])),   # 0x56 的 bit3 被干扰
    ("③ 一加一减",    bytes([0x13, 0x34, 0x56, 0x77])),   # 首字节+1 末字节-1,总和不变
    ("④ 调换顺序",    bytes([0x34, 0x12, 0x56, 0x78])),   # 前两字节互换,总和不变
    ("⑤ 两处翻转",    bytes([0x10, 0x36, 0x56, 0x78])),   # 一处-2 一处+2,总和不变
    ("⑥ 连翻4bit",    bytes([0x12, 0x34, 0x48, 0x78])),   # 0x56→0x48,连续 4 位被干扰
]
for name, got in cases:
    s, c = checksum(got), crc8(got)
    ok = lambda v, ref: "✓通过" if v == ref else "✗拒收"
    print(f"{pad(name, 12)}{got.hex(' ').upper()}   和={s:02X}{ok(s, ref_sum)}   CRC={c:02X}{ok(c, ref_crc)}")
```

**实际运行输出（本机 Python 3.11，逐条真实打印）：**

```
发送: 12 34 56 78   和校验=14   CRC-8=1C

① 原样到达  12 34 56 78   和=14✓通过   CRC=1C✓通过
② 单bit翻转 12 34 5E 78   和=1C✗拒收   CRC=B4✗拒收
③ 一加一减  13 34 56 77   和=14✓通过   CRC=27✗拒收
④ 调换顺序  34 12 56 78   和=14✓通过   CRC=98✗拒收
⑤ 两处翻转  10 36 56 78   和=14✓通过   CRC=E6✗拒收
⑥ 连翻4bit  12 34 48 78   和=06✗拒收   CRC=9D✗拒收
```

**说明：**

- ②⑥ 属"常规事故"：单个 bit 翻转、连续 4 个 bit 被干扰——求和校验和 CRC 都抓得住；真正的分水岭是 ③④⑤ 三行。
- ③ 一加一减：两个字节一个 +1、一个 −1，总和没变——**求和校验盖"通过"章，CRC 直接拒收**。这种"互相抵消"式干扰在真实电磁环境里一点也不罕见。
- ④ 调换顺序：前两个字节互换，总和不变——求和放行，CRC 拒收。**参数装错位置比参数算错更难查**，能当场拦下的都是恩情。
- ⑤ 两处翻转：一个字节 −2、另一个 +2，又是求和看不见的；CRC 依然全抓。8 位 CRC 只够演示，真实系统用 16/32 位，漏网概率低到工程上可以忽略。
- 公平对比一句：CRC-8 和求和校验**都是 8 位、一样长**——CRC 强的不在"位数"，在算法对位置和顺序敏感。同样的长度，拦下的错误差一个量级。
- `crc8()` 每一行都和硬件一一对应：`crc ^= byte` 是"把新字节并进移位寄存器"，`for _ in range(8)` 是逐位处理，最高位是 1 就"左移后异或多项式"——**逐位版看懂了，256 字节的查表法加速版就一目了然**（查表无非是把这 8 次循环提前算好、存起来）。
- 两个边界感：CRC 挡得住"意外坏"，挡不住"故意伪造"——那是加密签名的活；另外不少 MCU 自带硬件 CRC 外设，翻翻手头芯片的手册，能白嫖就别手算。

## ✨ 今日一句

> 干扰最狡猾的一招，不是把数据改烂，而是改得"看上去没变"：一个 +1、一个 −1，总数照旧。CRC 的意义，就是在"看上去没变"里，把变了的那一下揪出来。
