# 📅 2026年11月23日 日报

## 💭 技术随想：一个小数，其实是四个数

`0.1` 这个符号我敲了十几年，今天才算第一次看清它。起因很小：给一个输出「143 件 × 0.07 元」的账单，屏幕上打出来是 `10.010000000000021`。我以为是打印格式没截，改成两位小数，问题消失了——但也顺手把一个我一直没搞明白的东西翻了出来。

**「0.1」在这台机器上不是一个数，是四个：**

1. **你写的那个**：十进制字面量，理想中的 0.1。
2. **存进去的那个**：二进制里唯一离它最近的一个数，`0x3fb999999999999a`。
3. **打出来给你看的那个**：`repr()` 还给你 `'0.1'`，它其实不是你存的那个数。
4. **你以为四舍五入会得到的那个**：`round(2.675, 2)` 给你 `2.67`，而你想的是 `2.68`。

这四者之间每一处「不一样」，都是一类独立的 bug。今天全在这台机器上跑（Windows 11 / Python **3.14.9**），下面每个数字都是刚刚打出来的。

### 一、0.1 存不进去，因为 10 里面有一个 5

二进制能精确表示的小数，分母必须是 2 的幂：0.5、0.25、0.125、0.0625 都可以，因为它们分别是 1/2、1/4、1/8、1/16。

`0.1 = 1/10 = 1/(2×5)`。那个 **5** 是罪魁祸首——十进制里 1/3 除不尽，二进制里 1/5 也除不尽，于是 0.1 在二进制里是**无限循环小数**：

```text
0.1 (十进制) = 0.0001100110011001100...(1100 循环)₂
```

双精度只有 52 位尾数用来存它，剩下的一律截断并就近舍入。实测：

```text
hex                : 3fb999999999999a
符号位             : 0
指数位             : 1019  ->  实际指数 -4
尾数位             : 0x999999999999a          ← 一串 9，就是那个 1100 循环被舍入后的样子
Decimal(0.1)       : 0.1000000000000000055511151231257827021181583404541015625
```

存进去的那个数，比 0.1 **大**了大约 `5.55e-18`。它的邻居间距（ulp）是 `1.3877787807814457e-17`，也就是说在 0.1 附近，机器能分辨的最小台阶是 1.4e-17 量级。

更妙的是三个数「偏的方向」不一样：

```text
存下的 0.1 = 0.1000000000000000055511...   比 0.1 大
存下的 0.2 = 0.2000000000000000111022...   比 0.2 大
存下的 0.3 = 0.2999999999999999888977...   比 0.3 小
```

所以 `0.1 + 0.2` 算出来是 `0.30000000000000004`，而 `0.3` 本身略小于 0.3，两者永远对不上：

```text
0.1 + 0.2 = 0.30000000000000004
0.1 + 0.2 == 0.3  ->  False
0.1 * 3   = 0.30000000000000004
```

**这不是 Python 的错，是 IEEE 754 双精度的定义。** 换个语言、换个芯片，答案一模一样。

### 二、`repr()` 打出来的不是真值，是「能原样还原的最短字符串」

如果打印的是真值，那 `print(0.1)` 该打出 55 位小数。它没有，因为 Python 3.1 之后 `repr` 用**最短往返表示**：在所有能重新变回同一个 double 的字符串里，挑最短的那个。

```text
repr(0.1)       = '0.1'
'%.15g' % 0.1   = '0.1'
'%.17g' % 0.1   = '0.10000000000000001'      ← 真容开始露出来
```

标准给的保证是**17 位有效数字足以无损往返**（我这个值 16 位也够，但不是所有 double 都这么幸运）。

这条的实用价值在**存档**上：把浮点数写进 CSV/JSON/配置文件时，用 `.15g` 或 `str()` 会安静地丢掉最后那一两位的信息；用 `repr()` 或 `.17g` 才能做到「写出去、读回来、一个 bit 不差」。反过来，如果只是给人看，`.2f` 就够了——**但要清楚那是「格式化」，不是「这个数就是这个值」。**

### 三、浮点数不是一根连续的数轴，是疏密不均的尺子

double 的尾数固定 52 位，所以**指数越大，相邻两个可表示数之间的台阶越宽**。台阶（ulp）实测：

| 数量级 | ulp（能分辨的最小增量） |
|---|---|
| 1 | 2.2e-16 |
| 10³ | 1.1e-13 |
| 10⁶ | 1.2e-10 |
| 10⁹ | 1.2e-07 |
| 10¹² | 0.00012 |
| 10¹⁵ | **0.125** |
| 10¹⁶ | **2** |
| 10¹⁸ | **128** |

两个直接的后果：

```text
1e16 + 1      == 1e16    ->  True        ← 加了个 1，等于没加
2**53         = 9007199254740992          ← 能精确表示的最大连续整数
float(2**53+1) == 2**53  ->  True        ← 9007199254740993 存进去就变成 ...992
```

**这条对我的活儿是硬约束：** Unix 纳秒时间戳现在是 `1.79e18` 量级，ulp 是 **256**。也就是说，纳秒时间戳一旦存成 float，硬件给你的最后 8 位二进制是假的，抖动最高到 256 纳秒。实测把此刻的 `time.time_ns()` 过一遍 float：

```text
int       : 1795400875442529500
float->int: 1795400875442529536      偏差 36 ns
```

这次只偏了 36 ns，但那是运气——**上限就是 256 ns，与你写在代码里的「纳秒精度」是两个概念。** 时间戳一律用 int，别用 float，一秒钟都不要犹豫。

### 四、加法不满足结合律，连 Python 的 `sum()` 都偷偷改过

同一组数，换个加的顺序，结果就不一样：

```text
(0.1 + 0.2) + 0.3  =  0.6000000000000001
0.1 + (0.2 + 0.3)  =  0.6
```

误差还会累积。朴素循环累加 100 万次 0.1：

```text
1e6 次累加 = 100000.00000133288        差 1.33e-06
```

**这里有个今天才发现的事：Python 3.12 起，内置 `sum()` 换成了补偿求和（Neumaier）。** 同一份数据，手写循环和 `sum()` 现在给出不同的答案：

```text
sum([0.1]*10)
  手写 +=    : 0.9999999999999999
  sum()      : 1.0                   ← 补偿求和，把误差抵掉了
  math.fsum(): 1.0

[1e16, 1.0, -1e16, 1.0]
  手写 +=    : 1.0                   ← 1.0 被 1e16 吞了
  sum()      : 2.0
  math.fsum(): 2.0
```

这有两层意思。好的一面：**普通代码里的浮点求和比过去准了。** 坏的一面：**如果你的老代码和测试用例是按旧的 `sum()` 行为写死的，升级 Python 3.12 后可能悄悄变成另一个值**——而且变得更「对」，只是跟你的预期不一样。

还有一层更细的：`sum()` 变准，不等于变得「符合人心」——

```text
[19.99, 0.07, 0.03, 0.01]
  手写 += : 20.1                    ← 撞对了
  sum()   : 20.099999999999998      ← 更接近「真实的二进制和」
```

**补偿求和逼近的是「这串浮点数的精确和」，而「精确和」本身就不等于 20.10。** 想要 20.10，只有一个办法：别用浮点算钱。

### 五、`round()` 不是四舍五入，是「就近取偶」

这条大概是最多人被坑过、又最少人意识到的一条。内置 `round()` 用的是**银行家舍入（half-to-even）**：正好卡在中间时，往偶数那边走。

```text
round( 0.5) =  0      round( 1.5) =  2      round( 2.5) =  2
round( 3.5) =  4      round( 4.5) =  4      round(-0.5) =  0
round(-1.5) = -2      round(-2.5) = -2
```

`round(2.5)` 给的是 **2**。做报表、做结算、做评分，这一条足够让人来问你一次。

而且 `round(x, 2)` 更阴——它是「**先看那个二进制值离谁近，再就近取偶**」，所以它不是在你写的十进制数上舍入：

```text
round(2.675, 2) = 2.67        ← 因为存的 2.675 其实略小于 2.675
round(1.005, 2) = 1.0         ← 1.005 存成了 1.00499999...
round(0.125, 2) = 0.12        ← 0.125 二进制精确，于是标准半偶数：往 2 走
```

**格式化也一样逃不掉**，因为 `%.2f` 拿到的也是同一个二进制值：

```text
'%.2f' % 2.675  = '2.67'
'%.2f' % 1.005  = '1.00'
'%.2f' % 0.615  = '0.61'
'%.2f' % 10.235 = '10.23'
```

四个全是「人算该进位、机器没进位」。这不是 bug，是**你在十进制里想的，和它在二进制里存的，本来就不是同一个数**。

### 六、钱怎么办：整数分，或者从字符串进 Decimal

两条路，都可靠。

**第一条（推荐）：金额永远用整数分。** 加、减、乘全在整数域做完，只在最后显示时拼小数点：

```text
143 件 × 0.07 元
  float 累加 : 10.010000000000021
  float 相乘 : 10.010000000000002
  整数分     : 1001 分 -> 10.01        ← 一分不差
```

**第二条：`Decimal`，但必须从字符串构造。** 这是最容易错的一步：

```text
Decimal(2.675).quantize(0.01)   ->  2.67     ← 已经从 float 带进误差了
Decimal('2.675').quantize(0.01) ->  2.68     ← 从字符串进，才是你以为的 2.675
```

`Decimal(2.675)` 的真实值是 `2.67499999999999982236431605997495353221893310546875`。**把 float 塞进 Decimal，等于把误差一起搬进去了，白忙一场。** 另外 `quantize` 默认也是半偶数，要人味的四舍五入得显式写 `ROUND_HALF_UP`。

### 七、判等：`==` 几乎总是错的，`isclose` 也有一半是错的

```text
0.1 + 0.2 == 0.3          ->  False          差 5.551115123125783e-17
math.isclose(0.1+0.2, 0.3) ->  True           相对容差 1e-9 兜住了
```

`math.isclose` 的默认是 `rel_tol=1e-9, abs_tol=0.0`。**相对容差对 0 完全无效**（0 的百万分之一还是 0）：

```text
math.isclose(1e-13, 0)                        ->  False
math.isclose(1e-13, 0, abs_tol=1e-12)         ->  True
```

所以「跟 0 比」的时候必须显式给绝对容差。这条在传感器数据上天天踩：一个理论上该是 0 的偏差、一个本应为 0 的速度分量，用相对容差判它「不为零」，然后进 `if` 分支做了一堆不该做的事。

顺带把特殊值也钉一下：

```text
float('nan') == float('nan')  ->  False
float('inf') - float('inf')   ->  nan
0.0 * float('inf')            ->  nan
max(1, float('nan'), 2)       ->  2          ← max 会跳过 nan，不报错
1e308 * 10                    ->  inf
1 / 0                         ->  ZeroDivisionError（不是 inf！）
```

最后一条值得单独记：Python 的 `1/0` 抛异常，但 `1.0/0.0` 也抛异常——**想拿 inf 得显式写 `float('inf')`**，别指望除零给你。

### 八、对着手上的东西看

- **电机位置/速度指令。** 用 float 做「每帧加一点」的累加，误差会一直往里贴。要么发绝对值（由控制器算），要么在本地维护 int 微米/微弧度，只在发指令那一瞬间转成 float。
- **时间戳。** 一律 int。纳秒用 int64（到 2262 年才溢出），微秒用 int64 甚至 int32 都够。**float 存纳秒，等于自己给自己加 256 ns 的抖动。**
- **账单/流水。** 生鲜超市那种按分结算的，从 Excel 读出来立刻转整数分，别在中间留 float。比较、求和、结余全在整数域。
- **`round()` 出现在金额代码里就是红旗。** 换成 `Decimal(str(x)).quantize(..., ROUND_HALF_UP)`，或者直接整数分。
- **`==` 出现在两个 float 之间也是红旗。** 除非你在比 `0.0` 这种精确值，否则用 `isclose` 并想清楚容差是相对还是绝对。
- **CSV 里的浮点列。** 存的时候用 `repr()`，别用 `'%.2f'`——后者把误差永久写进了文件，下一个人读回来会以为那是精确值。

### 九、一句必须说清楚的诚实

- **属于规范/硬件事实的**：IEEE 754 双精度是 1+11+52 位；ulp 随指数线性增长；17 位有效数字保证往返；`round` 是 half-to-even（文档明写）；Python 3.12 起 `sum()` 改用补偿求和（release notes 明写）。
- **属于这台机器这一次的实测**：`0.1` 的 hex `3fb999999999999a`、55 位真值、`1e6` 次累加差 `1.33e-06`、纳秒时间戳偏差 36 ns（**这个数每次跑都不一样，上限才是 256**）、`round(2.675,2)=2.67` 这类具体输出。
- **没有实测的**：`sum()` 的补偿实现在不同小版本之间是否还有微调——我只验了 3.14.9 这一个版本，跨版本行为请以自己环境为准。
- **最要紧的一句**：`0.1 + 0.2 != 0.3` 不是「精度不够」，是「0.1、0.2、0.3 这三个数在二进制里根本不存在」。你写的是十进制，机器存的是二进制，**中间那一步转换是不可逆的有损压缩**。想清楚这一点，剩下所有规则都是它的推论。

## 🧩 今日代码片段：`money.py` —— 四个把「小数」当小数用的工具

`to_cents` 把金额从字符串直接落到整数分，`from_cents` 在最后一步才拼小数点，`round_half_up` 给出人味的四舍五入，`almost_eq` 补上 `math.isclose` 在零附近的窟窿。

```python
# -*- coding: utf-8 -*-
"""money.py —— 四个把「小数」当小数用的工具"""
import math
import time
from decimal import Decimal, ROUND_HALF_UP


def to_cents(text) -> int:
    """金额一律从「字符串」进，转成整数分，绝不让它路过 float。
    Decimal('2.675') = 2.675；Decimal(2.675) = 2.67499999999999982236..."""
    d = Decimal(str(text)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
    return int(d * 100)


def from_cents(cents: int) -> str:
    """整数分 -> '12.30'。加减乘全在整数域做完，最后一步才拼字符串。"""
    sign = "-" if cents < 0 else ""
    c = abs(cents)
    return f"{sign}{c // 100}.{c % 100:02d}"


def round_half_up(x, ndigits=0) -> float:
    """真·四舍五入。内置 round() 是「就近取偶」：round(2.5) 给 2，报表上会被人追着问。"""
    q = Decimal(1).scaleb(-ndigits)
    return float(Decimal(str(x)).quantize(q, rounding=ROUND_HALF_UP))


def almost_eq(a, b, rel=1e-9, abs_=1e-12) -> bool:
    """判等。相对容差在「和 0 比」时完全失效（0 的 1e-9 还是 0），
    所以必须同时给一个绝对容差 —— 这是 math.isclose 默认 abs_tol=0.0 埋的坑。"""
    return math.isclose(a, b, rel_tol=rel, abs_tol=abs_)


if __name__ == "__main__":
    print("1) 143 件 0.07 元:")
    naive = 0.0
    for _ in range(143):
        naive += 0.07
    print("   float 累加 :", repr(naive))
    print("   float 相乘 :", repr(143 * 0.07))
    print("   整数分     :", 143 * to_cents("0.07"), "分 ->", from_cents(143 * 7))

    print("2) round vs round_half_up (ndigits=2):")
    for v in (2.675, 1.005, 0.615, 10.235):
        print(f"   {v!r:>7}  round={round(v, 2)!r:<6} fmt={'%.2f' % v:<6} half_up={round_half_up(v, 2)!r}")

    print("3) Decimal 从哪进:")
    print("   Decimal(2.675)  ->", Decimal(2.675).quantize(Decimal("0.01")))
    print("   Decimal('2.675')->", Decimal("2.675").quantize(Decimal("0.01")))

    print("4) 判等:")
    a, b = 0.1 + 0.2, 0.3
    print("   a == b        :", a == b, "| 差:", abs(a - b))
    print("   isclose(1e-13,0) 默认:", math.isclose(1e-13, 0), "| almost_eq:", almost_eq(1e-13, 0))

    print("5) 纳秒时间戳别用 float 存:")
    ns = time.time_ns()
    print("   int      :", ns)
    print("   float->int:", int(float(ns)), "| 偏差", abs(ns - int(float(ns))), "ns")
```

实测输出（Windows 11 / Python 3.14.9）：

```text
1) 143 件 0.07 元:
   float 累加 : 10.010000000000021
   float 相乘 : 10.010000000000002
   整数分     : 1001 分 -> 10.01
2) round vs round_half_up (ndigits=2):
     2.675  round=2.67   fmt=2.67   half_up=2.68
     1.005  round=1.0    fmt=1.00   half_up=1.01
     0.615  round=0.61   fmt=0.61   half_up=0.62
    10.235  round=10.23  fmt=10.23  half_up=10.24
3) Decimal 从哪进:
   Decimal(2.675)  -> 2.67
   Decimal('2.675')-> 2.68
4) 判等:
   a == b        : False | 差: 5.551115123125783e-17
   isclose(1e-13,0) 默认: False | almost_eq: True
5) 纳秒时间戳别用 float 存:
   int      : 1795400911972237200
   float->int: 1795400911972237312 | 偏差 112 ns
```

四个细节值得单独说：

- **`to_cents` 一进来就 `str()`，这是整套的命门。** 调用方可能传 `0.07`（float）也可能传 `"0.07"`（字符串），`str()` 让两条路都能走，但**传 float 的那条已经在路上丢过误差了**——`str(0.07)` 得到 `'0.07'` 只是因为 `repr` 做了漂亮的往返，不代表你没损失。真正干净的用法是从源头的文本、或者整数分开始。
- **`from_cents` 用 `//` 和 `%`，不用 `/`。** `/` 会立刻变回 float，前面所有的努力当场作废。负数靠 `sign` 单独拎出来，`-c // 100` 的取整方向是另一个坑。
- **`round_half_up` 从 `str(x)` 进。** 所以它是「在你写的那个十进制数上舍入」，所以 `2.675 -> 2.68`——这是「符合人预期」，也是「和 IEEE 754 的真实值不一致」。这两件事你只能选一个，**做账选预期，做数值计算选真实**。
- **`almost_eq` 的 `abs_=1e-12` 是我自己拍的。** 它必须跟你业务的最小有意义单位挂钩：电机位置有效到 1e-6 rad，那 `abs_tol` 就该是 1e-9 而不是 1e-12，否则「确实动了 0.5 微弧度」会被判成「没动」。

一句话收这段：**浮点数不是一个精确的十进制小数，而是「离那个小数最近的一个二进制值」；你写出 0.1、打印出 0.1，都不代表机器里躺着 0.1。**

## ✨ 今日一句

> `0.1 + 0.2 != 0.3` 不是精度不够，是 **0.1 这个数在二进制里根本不存在**。
>
> 你写的是十进制，机器存的是二进制，中间那一步是**不可逆的有损压缩**——想明白这一点，`round` 为什么会「算错」、为什么钱不能用 float、为什么时间戳要用 int，全都只是它的推论。
