## 💭 技术随想：Python 类型提示——从"装饰品"到"生产力武器"

很多人觉得 Python 的类型提示（type hints）就是给编辑器看的装饰品，写了也不强制检查，不如不费那个功夫。这是一个误解。

**类型提示真正的价值不在"写的时候"，而在"读的时候"和"重构的时候"。**

三件事彻底改变了我的看法：

1. **`mypy` 在 CI 里能拦住多少低级 bug。** 有一次我重构了一个函数签名，忘了一处调用点。`mypy --strict` 直接在 CI 报红，省了我 20 分钟调试。那个 bug 是典型的 `Optional[str]` 传给了只接受 `str` 的函数——运行时不一定爆，但一定是隐患。

2. **`TypedDict` 和 `Protocol` 是文档。** 当你从 JSON API 拿到一个嵌套 4 层的字典，`TypedDict` 不仅让 IDE 可以自动补全，更重要的——6 个月后你自己回来看代码，不用再 `print(resp.keys())` 猜结构了。

3. **类型即契约。** 团队协作时，一个人改了一个函数的返回类型但忘记改调用方，类型检查器会告诉你。没有类型提示，你只能在运行时靠运气。

```python
# ❌ 这段代码藏了一个 bug —— 你能一眼看出来吗？
def get_user_ids(users: list[dict]) -> list[int]:
    return [u["id"] for u in users]

# 某个调用方传了 None
users = fetch_users()  # 可能返回 None
ids = get_user_ids(users)  # 💥 TypeError at runtime
```

加上类型提示后，`mypy` 在你不运行代码的情况下就能发现：

```python
from typing import Optional

def fetch_users() -> Optional[list[dict]]: ...

def get_user_ids(users: list[dict]) -> list[int]: ...

users = fetch_users()  # mypy: ❌ Optional[list[dict]] != list[dict]
```

**建议的渐进式引入路径：**
- 新文件：加 `# mypy: strict`
- 旧文件：先给公共函数加，内部函数慢慢补
- 用 `pyright` 的 `typeCheckingMode: "basic"` 起步，逐步提升到 `"strict"`

## 🧩 今日代码片段：TypedDict + 数据校验 = 活文档

```python
from typing import TypedDict, Literal
import json

# 定义 API 返回的数据结构
class UserProfile(TypedDict):
    id: int
    name: str
    role: Literal["admin", "editor", "viewer"]
    metadata: dict[str, str]  # 至少知道 key/value 都是 str

# 解析 JSON 时带上类型，IDE 立刻能补全字段
def handle_response(raw: str) -> None:
    data: UserProfile = json.loads(raw)
    # 现在 IDE 知道 data["role"] 只能是那三个值
    if data["role"] == "admin":
        print(f"管理员: {data['name']}")  # 自动补全 data['name']

# 批量处理的类型提示也很清晰
def get_admin_names(profiles: list[UserProfile]) -> list[str]:
    return [p["name"] for p in profiles if p["role"] == "admin"]
```

**说明：** `TypedDict` 在运行时就是普通 `dict`，零性能开销。它纯粹是给 `mypy`/`pyright` 和 IDE 用的。结合 `json.loads` 使用时，它能防止你拼错字段名——这是 JSON 处理中最常见的 bug。
