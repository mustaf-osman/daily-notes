## 💭 技术随想：毫秒计数器那一圈——49.7 天翻一次"里程表"，程序为什么不会迷路

每个固件里都藏着这么一个小东西：开机起，每毫秒 +1，一刻不停。你几乎天天跟它打交道——Arduino 里叫 `millis()`，STM32 的 HAL 里叫 `HAL_GetTick()`，Zephyr 里叫 `k_uptime_get_32()`。它就是一个里程表，记录"开机以来的时间"。

里程表也有跑满的时候：32 位无符号整数，上限 4294967295 毫秒——**约 49.71 天**。第 49.71 天的某一个毫秒，它从 0xFFFFFFFF 翻回 0x00000000，像计程器跳到一串 9 之后哗地变回 0。此时如果你正在用它计时，就会看到诡异的一幕：本该"时间在流逝"，计数器却突然"变小"了几十亿。

大多数写代码的人一辈子没被它坑过；但每年总有一批设备，稳定运行 49 天左右后开始莫名其妙：定时器提前触发、任务不再执行、"重启一下就好"。锅基本都在这里——**不是回绕本身，而是比较时间的那一行写法**。

先把"对"的写法放在这：`if (now - start >= timeout)`——记住起点 start，想知道等没等够，就用"现在减起点"，看流逝量是否达标。秘密在于无符号减法的隐藏能力：当 now 已经小于 start（回绕之后），计算机不会给你负数，而是**借位绕到环的另一端**，把结果算成"从 start 沿环前进到 now 的真实距离"。在模 2³² 的世界里，减法算的从来不是"两个数谁大"，而是"环上走了多远"。

为什么这能成立？把 2³² 想象成一条环形跑道：计数器就是跑者，回绕 = 跑过终点线接着跑。`now - start` 问的是"从 start 这个刻度出发往前跑了多少"，只要没跑满一整圈，答案永远精确——哪怕中途跨过了终点线。跑道上的距离，从来不知道什么叫"起点在终点后面"。

再看不靠谱的写法：`if (now >= start + timeout)`——比较"截止时刻"。日常用着好像也对，手感还更直觉。但回绕一到就原形毕露：`start + timeout` 先被截断到环的另一头（0xFFFFF000 + 5000 = 0x00000388），而"现在"还是个几十亿的大数——于是第一毫秒就"觉得"早就到点了，定时器当场错触发，后面怎么走怎么乱，偶尔碰巧对一次。

进一步说，**连"减法"也不是无条件的靠谱**。今天的代码里做了个边界扫描：真实流逝量从 1 毫秒一路扫到 49.71 天，观察"减出来的数"从什么时候开始跟真实值分道扬镳——两条线很关键：24.85 天（2³¹ 毫秒）处，有符号解释会先翻车（2147483648 变 -2147483648），Linux 内核里 `time_after()` 那套"有符号技巧"处理回绕的写法就是卡在这条线上；到了 49.71 天整圈，连无符号减法也只能"绕圈"——"49.71 天 + 1 小时"和"1 小时"算出同一个数，任何比较都再也分不清了。

工程结论只有两条，记住能用一辈子：

1. **永远比较间隔，不比较绝对时刻。** `now - start >= timeout`——超时判断、去抖计时、心跳判定、任务周期，全用这个形状；
2. **间隔必须远小于 2³¹ 毫秒（24.85 天）。** 这是所有写法的安全分界线；实在要测更长的东西，换 64 位计数器（Zephyr 的 `k_uptime_get()` 干脆返回 int64——几亿年才回绕，等于永别这个问题）。

顺带一提，这个规律跟位宽无关：16 位微秒计数器（一圈只有 65.5 毫秒）在小单片机里天天见，同一个减法换个 mask 照样精确。今天演示里反复出现的 `& 0xFFFFFFFF` 也不是装饰——Python 整数是无限精度的，没有天然的"回绕"，得手动给它戴上手铐；而 C 里 `uint32_t` 天生就是这圈跑道，是白送的。无符号定宽整数，算是 C 语言里少见的"白送福利"：定义变量那一刻，你就自动拥有了一个懂环形距离的算术。

## 🧩 今日代码片段：模拟 32/16 位计数器——三个实验看清"回绕不是问题"

三段对照实验：① 让定时器正好跨过回绕点（0xFFFFFFFF → 0）计 5000ms，两种写法逐行对比；② 边界扫描——真实流逝从 1ms 扫到 49.71 天，看"减法"何时开始说谎；③ 同一公式换到 16 位微秒计数器（一圈 65.5ms），验证"只跟模有关、跟位宽无关"。

```python
# -*- coding: utf-8 -*-
"""定时器回绕演示：32 位毫秒计数器 49.7 天绕一圈，为什么定时器从不迷路（真实可运行）"""
import sys
try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

MASK = 0xFFFFFFFF
def u32(x): return x & MASK
def h32(x): return f"0x{x:08X}"

# 两种写法
def done_naive(now, start, timeout):        # 直觉写法：比较"绝对时刻"
    deadline = u32(start + timeout)
    return now >= deadline

def done_correct(now, start, timeout):      # 可靠写法：比较"走了多远"
    return u32(now - start) >= timeout

print("=" * 68)
print("实验1：定时器要在'跨过回绕点'的当口计时（0xFFFFFFFF → 0x00000000）")
print("=" * 68)
START, TIMEOUT = 0xFFFFF000, 5000
print(f"起点 start = {h32(START)}（再过 {0x100000000-START}ms，计数器就翻回 0）")
print(f"想等 timeout = {TIMEOUT}ms")
print(f"直觉写法算出的截止值 = start + timeout = {h32(u32(START+TIMEOUT))}  ← 被截断到环的另一头")
print()
print(f"{'流逝(ms)':>8} | {'now':>12} | {'减出来 = now-start':>16} | 减法判断 | 直觉判断")
print("-" * 74)
for el in (0, 1, 2048, 4095, 4096, 4999, 5000, 5001):
    now = u32(START + el)
    raw = u32(now - START)
    c = "✔ 触发" if done_correct(now, START, TIMEOUT) else "  等待"
    n = "✔ 触发" if done_naive(now, START, TIMEOUT) else "  等待"
    mark = "   ← 计数器在这里归零，回绕发生" if el == 4096 else ""
    print(f"{el:>8} | {h32(now)} | {raw:>16} | {c}   | {n}{mark}")
print()
print("→ 减法写法：4999ms 还在等，5000ms 准时触发——回绕从它眼皮底下过去了，毫无影响。")
print(f"→ 直觉写法：0ms 就触发了（start+{TIMEOUT} 被截断成小数，'巨大'的 now 当然 ≥ 它），")
print("   随后一路乱答，直到 5000ms 才又碰巧碰上——错不在'不触发'，而在错误的时间触发。")

print()
print("=" * 68)
print("实验2：边界扫描——'减法'从多大的量级开始也会说谎？")
print("=" * 68)
DAY = 86_400_000
print(f"{'真实流逝':<20} | {'unsigned 结果':>14} | {'当有符号看':>14} | 结论")
print("-" * 74)
for label, el in [("1ms", 1), ("1秒", 1000), ("1小时", 3_600_000), ("1天", DAY),
                  ("24.85天 = 2^31ms", 2**31), ("30天", 30 * DAY),
                  ("49.71天 = 2^32ms", 2**32), ("49.71天+1小时", 2**32 + 3_600_000)]:
    raw = el & MASK
    signed = ((raw + 2**31) & MASK) - 2**31
    v = []
    v.append("unsigned 精确" if raw == el else "unsigned 绕圈")
    v.append("signed 精确" if signed == el else f"signed 错位({signed:+d})")
    print(f"{label:<20} | {raw:>14} | {signed:>14} | {' / '.join(v)}")
print()
print("→ 流逝 < 2^31ms（≈24.85天）：两种解释都精确，随便怎么写都行；")
print("→ 到 2^31 这一档，有符号解释先翻车（变成负数）——Linux 内核 time_after() 那种")
print("   '有符号技巧'处理回绕的写法，代价就是必须保证间隔 < 2^31；")
print("→ 到 2^32ms，连 unsigned 减法也不得不绕圈：49.7天+1小时 和 1小时 算出同一个数，")
print("   任何比较都再也分不清这两件事——这是'一圈'给算术划下的硬边界。")

print()
print("=" * 68)
print("实验3：同一个公式，换到 16 位微秒计数器（一圈只有 65.5ms）")
print("=" * 68)
def u16(x): return x & 0xFFFF
def h16(x): return f"0x{x:04X}"
def done16(now, start, t): return u16(now - start) >= t
s16, t16 = 0xFF00, 700
print(f"起点 0xFF00，想等 700µs；start+700 = {h16(u16(s16+700))} ← 又是截断")
print()
for el in (0, 200, 255, 256, 512, 699, 700, 701):
    now = u16(s16 + el)
    mark = "   ← 回绕发生" if el == 256 else ""
    c = "✔ 触发" if done16(now, s16, t16) else "  等待"
    n = "✔ 触发" if now >= u16(s16 + t16) else "  等待"
    print(f"  {el:>4}µs | now = {h16(now)} | 减法: {c} | 直觉: {n}{mark}")
print()
print("→ 连公式都不用改结构，换个 mask、换个单位，同一个减法在 16 位世界里同样准确。")
print("→ 一句话：别问'现在是几点'，只问'走了多远'——回绕算什么，距离不知道什么叫回绕。")
```

**说明：**

- 实验 1 是整件事的缩影：第 0 行和第 4096 行都值得盯着看——0ms 时"直觉写法"就已宣布超时（因为它拿"几十亿"去比"被截断的几百"）；4096ms 处计数器当着你的面从 0xFFFFFFFF 跳回 0x00000000，而减法写法的回答依旧平静而准确。
- 减法为什么精确？因为无符号定宽整数的减法在数学上是**模 2³² 运算**，它天然回答的就是"环上的距离"。C 里 `uint32_t a, b; a - b` 一行指令、没有分支没有异常；换成有符号还可能踩未定义行为，反而更糟。
- 实验 2 把"安全区"画了出来：流逝量 < 2³¹ms 时怎么写都对；≥ 2³¹ 有符号解释翻车；≥ 2³² 连无符号也画不出区别（"49.71 天 + 1 小时" ≡ "1 小时"）。所以工程红线：**任何基于这种计数器的计时，间隔都别超过 24.85 天**。
- 两个边界各有出处：2³¹ 来自"有符号差值"写法（Linux 内核 `time_after(a, b)` 就是 `(long)(b - a) < 0`，用符号位判断环上前进方向）；2³² 是"整圈"的硬边界，谁来都救不了。
- 实验 3 说明"只跟模有关、跟位宽无关"：16 位 µs 计数器一圈只有 65.536ms，小 MCU 上天天见；同一个减法换 mask 直接复用。反过来，混用位宽（16 位计数器减到 32 位变量里再比较）才是真的危险——两边模不一致，环就对不上了。
- 再说一句 Python 侧的细节：演示里所有 `& MASK` 都是刻意的——Python 整数无限精度，**不会**自动回绕，是在手动模拟"C 的 32 位无符号"；写嵌入式测试脚本时这点常坑人：你测的是"逻辑"，但真实设备跑的是"定宽算术"。
- 落地清单：① 比较一律写 `now - start >= timeout`；② 编译期/静态检查确保时间常量 < 2³¹；③ 想跑几十天的看门狗、长周期任务，直接用 64 位时间源；④ 测试时把起点挑到 0xFFFFF000 附近跑一遍——用 50 行代码覆盖"49 天才会出现"的现场，比真跑 49 天便宜太多。
- 顺带一提，这个题眼在 CAN 总线、机器人状态机里也通用：任何"计时判定"（心跳超时、动作超时、节拍周期）都该是这个形状——上周心跳那篇如果接着往下写，下一层就是它。

## ✨ 今日一句

> 计数器每 49.7 天归零一次，像一个环形跑道；别问它"现在是几点"，只问"走了多远"——在"距离"的定义里，从来就没有"回绕"这个概念。
