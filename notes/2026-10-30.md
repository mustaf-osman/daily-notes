## 💭 技术随想：0.1 加一千万次，多出来八万八

把传感器数据从 float64 换成 float32，理由通常很正当：内存省一半，带宽省一半，数值范围也完全够用——温度二三十度，压力一百千帕，float32 的七位有效数字看着绰绰有余。

存储确实没问题。但如果你拿它做**累加**，事情就变了：一个 1 m/s 的积分器跑一小时，应走 3600 米，float32 会记成 **3603.2 米**。没有报错，没有告警，每一拍都"正常"。

今天把这件事从头量了一遍，结论不是"float32 不准"，而是：**浮点数的误差不是随机渗进来的，它按你所在的数量级分段收费。**

### 一、先看一组不客气的数字

1e7 个 0.1 相加，精确值是 1000000。五种写法：

| 写法 | 结果 | 误差 | 相对误差 |
|---|---|---|---|
| float64 逐次相加 | 999999.9998 | 1.61e-4 | 1.6e-10 |
| Kahan 补偿求和 | 1000000.0000 | 0 | 0 |
| `math.fsum` | 1000000.0000 | 0 | 0 |
| float32 顺序 `cumsum` | **1087937.0000** | **8.79e4** | **8.79%** |
| float32 成对求和 `np.sum` | 1000000.1250 | 0.125 | 1.25e-7 |

两件事同时成立：

- float64 在这件事上"基本没问题"：一千万次累加，相对误差 1.6e-10。日常够用。
- **float32 的两种算法差了 70 万倍。** 同一个数组、同一个 dtype，只因为一个是顺序累加、一个是分块（pairwise）累加。`np.sum` 有 pairwise 保护，`np.cumsum` 没有——它必须按顺序算，因为每一步都要输出。

所以"float32 精度不够"这句话是偷懒的。**dtype 决定一格有多宽，算法决定你踩了多少格。**

### 二、误差不是"渗"进来的，是"按量级换挡"的

为什么 float32 顺序累加能差 8.79%？不是 0.1 存不准——float32 里 0.1 的绝对误差只有 1.5e-9——而是**大数加小数时，增量被四舍五入到 ULP 的整数倍**。

float32 的尾数有 24 位（二进制，约 7.2 位十进制）。累加器在 1e6 附近时，相邻两个可表示数之间的距离（ULP）是 0.0625。此时加一个 0.1：

| 累加器量级 | ULP | 每加一次 0.1 实际加了多少 | 每步偏差 |
|---|---|---|---|
| 1e3 | 6.1e-5 | 0.099976 | -0.0244% |
| 1e4 | 9.77e-4 | 0.099609 | -0.3906% |
| 1e5 | 7.81e-3 | 0.101562 | **+1.5625%** |
| 1e6 | 0.0625 | **0.125000** | **+25%** |

0.1 ÷ 0.0625 = 1.6，落在 2 格上——于是每一步不是加了 0.1，是加了 0.125。累加器一旦爬到 1e6，每步多 25%，这就是那 8.79% 的来源。

注意第二行到第三行，符号翻了一次。**这不是噪声，是系统性偏差；偏差的大小和方向，取决于你当时在哪个量级。** 噪声可以靠平均消掉，这种偏差不会——它只会随着步数线性累积。

### 三、一小时多走 3.2 米，第二小时倒亏 72 秒

把同样的机制接到时间积分上：dt = 0.01 秒，1 m/s，float32 逐次 `t += dt`。

| 步数 | 应为 | float32 实得 | 偏差 | 相对 |
|---|---|---|---|---|
| 360000（1 小时） | 3600.000 s | 3603.204102 s | **+3.204 s** | +0.089% |
| 720000（2 小时） | 7200.000 s | 7130.848633 s | **-69.151 s** | -0.960% |
| 1080000（3 小时） | 10800.000 s | 10646.473633 s | **-153.526 s** | -1.422% |

第一小时快 3.2 秒，第二小时倒亏 72.4 秒。同一行代码，前后两小时的方向相反。

原因还是 ULP 换挡：

| 时间量级 | ULP | 0.01 ÷ ULP | 实际每步 | 每步偏差 |
|---|---|---|---|---|
| [1024, 2048) | 1.22e-4 | 81.92 | 82 × ULP = 0.010009766 | +0.0977% |
| [2048, 4096) | 2.44e-4 | 40.96 | 41 × ULP = 0.010009766 | +0.0977% |
| [4096, 8192) | 4.88e-4 | 20.48 | 20 × ULP = 0.009765625 | **-2.3438%** |

在 4096 秒之前，0.01 秒总是被向上取整（82 格或 41 格，绝对增量都是 0.010009766）；跨过 4096 之后，ULP 翻倍，41 格变成 20 格，增量一下子少了 2.34%。**你的时钟不是"慢慢漂"，它是换挡的。** 这也解释了为什么短时间测出来的漂移率不能外推到长时间——量级一变，费率就变了。

float64 在同样场景下的偏差是 **3.2e-8 秒**，一小时三十纳秒。不是 float64 更"聪明"，是它的 ULP 在 3600 附近只有 4.5e-13，0.01 能被表示得足够细。

### 四、基数一大，小步长就走不动了

位置累加比时间更直观。在 float32 里，从不同起点开始，每次加 1 毫米，加 1000 次：

| 起点 | 实际移动 | 起点处的 ULP | 丢了多少 |
|---|---|---|---|
| 0 m | 1.0000 m | — | 0 |
| 1 km | 0.9766 m | 6.1e-5 m = 0.061 mm | **23.4 mm（2.34%）** |
| 100 km | **0.0000 m** | 0.0078 m = 7.8 mm | 100% |
| 1e7 m | 0.0000 m | 1 m | 100% |

1 km 处丢 2.34%，和上一节第二小时丢 2.34% 是同一件事：1 mm 在那个量级是 16.384 个 ULP，被取整成 16 个，每步少 2.34%。到了 100 km，1 mm 只有 0.128 个 ULP，四舍五入直接归零——**走一千步，一步都没动。**

100 km 的绝对位置不常见，但"大基数 + 小增量"到处都是：里程计跑了一公里之后继续累加毫米级增量、机械臂的绝对位置加微调、地图坐标加局部修正。**位置用浮点累加，误差不是"最后差一点"，是在某个量级之后，小增量直接消失。**

正确做法很土：**记整数。** 毫米、encoder counts、tick，都用 int64 累加；要显示或参与物理计算时，再乘一个比例换成米。整数没有 ULP，只有溢出——而溢出会报错，不会假装正常。

### 五、增量均值：十万步里七万四千步在空转

在线均值写成这样很常见：

```python
mean += (x - mean) / n
```

float32 下，均值在 1000 附近，ULP 是 6.1e-5；而 10 万步之后，每次修正量 `(x - mean)/n` 大约是 1e-5，**比一格还小**。实测 10 万步里，有 **73969 步（74.0%）均值完全没有变化**。

| 写法 | 结果 | 与精确均值之差 |
|---|---|---|
| float32 增量均值 | 999.994263 | **-0.001147** |
| float64 精确均值 | 999.995409 | — |

看起来最后只差 0.001，不太吓人。但它的含义是：**你的滑动平均在大部分时间里是冻结的**，只有偶尔几个"大偏差"样本能推动它。传感器缓慢漂移时，这个均值会严重滞后；报警阈值、基线校准都会跟着迟钝。

修法不是"把 float32 换成 float64 就完事"，而是**别在 float32 里做增量更新**：累加和用 float64（`sum += x`，最后除以 n），或者用 Welford（下一节），或者补偿求和。存储可以是 float32，统计量不行。

### 六、方差算成负数，不是段子

教科书上的快速公式：

```python
var = mean(x**2) - mean(x)**2
```

200000 个样本，均值 1e8，噪声标准差 1，这组样本的方差 ≈ 1.0055（float64 两遍法算出的参考值）：

| 写法 | 算出的方差 |
|---|---|
| `E[x²]-E[x]²`（float64） | **0.000000** |
| 两遍法（float64） | 1.005513 |
| Welford（float64） | 1.005513 |
| `E[x²]-E[x]²`（float32） | **2147483648** |
| 两遍法（float32） | 256.019196 |

均值 1e9 时，float64 的朴素公式算出 **-128**：负数方差。原因不复杂——`E[x²]` 和 `E[x]²` 都约等于 1e18，相减要得到 1 左右；float64 在 1e18 处的 ULP 正好是 128，**差值的全部有效信息都在减法里被吃掉了**，只剩一个随机的 ULP。

float32 那一行更值得看：`2147483648` = 2³¹。它不是"精度差一点"，是彻底没有意义。而两遍法在 float32 下给出 256，也不是 1.0055——它的均值本身偏了 16 counts（2 个 ULP），平方之后正好是 256：200k 个 1e8 在 float32 里求和，连均值都保不住。**数据在存进去的时候就已经毁了**：float32 在 1e8 处的 ULP 是 8，标准差 1 的噪声，99.99% 的样本都被量化成同一个值 1e8。算法再好，也救不回输入里没有的信息。

这里有个很重要的分工：

- **两遍法 / Welford 解决的是"算法引入的抵消误差"**（均值 1e8、方差 1 这种）。
- **dtype 解决的是"信息存不存得下"**。方差远小于均值平方时，float32 存原始数据这一步就已经失败了。

所以 Welford 不是"更准的公式"，它是**换了一条不产生大数相减的路径**：

```python
n += 1
d = x - mean
mean += d / n
m2 += d * (x - mean)
```

每一步只用"当前值和均值的差"，永远不会去减两个 1e16 量级的数。上面的实测里，Welford 和两遍法在 float64 下结果一致（打印出来都是 1.005513）。

### 七、1e16 + 1 == 1e16，Kahan 也救不了

```text
1e16 + 1 == 1e16 ?  True     （1e16 处 float64 的 ULP = 2）
顺序相加 1e16 + 1 - 1e16 = 0.0
Kahan                      = 0.0
math.fsum                  = 1.0
Neumaier                   = 1.0
```

Kahan 的补偿项假设"当前和比新加的数大"，上面这个顺序里，`1e16 + 1` 那一步的 1 被丢了，补偿项又被后一个 `-1e16` 冲掉，最后回到 0。**补偿求和不是魔法，它只是把舍入误差记在另一个变量里；如果那个变量也被更大的数碾过去，照样归零。**

Neumaier 的写法多了一个分支：当 `|x| > |s|` 时换一种记账方式，所以能把那个 1 留住。`math.fsum` 则维护一组互不重叠的部分和，最后只舍入一次，最稳，但要一次性拿到所有数（或者自己维护部分和）。

顺带一句：`0.1 + 0.2 != 0.3` 不是 bug，是二进制表示。0.1、0.2、0.3 在二进制里都是无限循环小数，float64 只能存最近的那个邻居。实测差值 5.55e-17，`math.isclose` 在默认相对容差 1e-9 下判定为相等。**该用容差的地方用容差，该用整数的地方用整数。**

### 八、能抄走的部分

1. **存 float32 可以，累加器必须是 float64。** numpy 里 `.astype(np.float32).cumsum()` 一路都是 float32；要显式写 `np.sum(a, dtype=np.float64)`。
2. **长序列求和别顺序累加。** 用 pairwise（numpy 的 `sum`）、`math.fsum` 或 Neumaier。顺序 `cumsum` 的误差可以差出五个数量级。
3. **方差永远不用 `E[x²]-E[x]²`。** 用 Welford 或两遍法；同时检查 dtype 能不能存下"均值 + 噪声"。
4. **时间不要累加 dt。** 用 `t - t0`；要积分就记整数 tick；必须累加时，定期重锚（每 N 步把基准重置到当前值，位置单独累加）。
5. **位置、里程计、金额记整数。** 毫米、counts、分。整数只有溢出，没有 ULP；溢出会炸，ULP 不会。
6. **比较浮点用 `math.isclose` / 相对容差。** `==` 只适合"这个值是不是从同一个计算路径来的"这种场合。
7. **MCU 上先看 FPU。** nRF5340 的应用核（Cortex-M33）只有单精度 FPU，`double` 是软件模拟，慢且占 code size；能在整数域算的就别进浮点域，必须浮点就控制累加规模，别让一个 float 累加器跑到 1e8。
8. **测试要造"大基数 + 小增量"。** 拿真实数据测往往看不出来；构造"从 1e6 开始每次加 0.001"这种输入，一层就现原形。
9. **打点"有多少步没有改变"。** 增量均值那个 74% 就是靠这个数发现的。类似地，记录累加器的当前量级、单步实际增量与名义增量之比，比打印最终结果有用得多。

### 九、和手上的东西对上

- **rp_server 的里程计/姿态积分**：如果积分器是 float32，一小时就是 3.2 米的账；ROS 消息里的 float64 救不了 MCU 侧已经丢掉的精度。累加用 double，位置用整数 counts。
- **传感器滑动均值 / 基线校准**：float32 的增量更新会大部分时间冻结，改用 float64 累加和，或 Welford。
- **PID 的积分项**：误差很小时，积分增量可能小于当前积分值的 ULP，表现为"怎么调都有静差"；积分器用 double，或者用整数累计误差再乘系数。
- **nRF5340**：M33 的 FPU 是单精度，`double` 走软件模拟。1 kHz 的环里做 double 运算要算清代价；但"把 long long 的 encoder counts 转成 float"这种一次性操作没问题——**别在累加路径上用 float，不是别用 float**。
- **生鲜超市的 POS 流水**：金额一律整数分。用 float 求和，几千笔之后对账差几分钱，查起来比 SQLite 锁还难受。

一句话总结今天量到的东西：**浮点数的精度不是固定的一条线，它是一把刻度会变的尺子——你离零点越远，一格越宽；误差不是算错的，是被迫落在最近的格子上。**

## 🧩 今日代码片段：浮点实验室 + 三个能抄走的小工具

前半段是能把上面每个数字重新跑一遍的实验脚本（A 求和、B 积分漂移、C 位置累加、D 增量均值、E 方差、F 大数吃小数）；后半段是 `NeumaierSum`、`Welford`、`TickClock`，都可以直接放进项目里。

```python
# -*- coding: utf-8 -*-
"""浮点实验室：误差是从哪一步进来的

A 1e7 个 0.1：float64 / Kahan / fsum / float32 顺序 / float32 成对
B float32 累加 dt：1 小时快 3.2 秒，2 小时反而慢 69 秒
C 位置累加：1 km 处走 1 mm，还走不走得动
D float32 增量均值：十万步里七万步是空转
E 均值 1e8 时的方差：朴素 / 两遍 / Welford
F 1e16 + 1：Kahan 给 0，Neumaier 给 1
"""
import math
import sys

import numpy as np

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

LINE = "=" * 78
f32 = np.float32


def sec(title):
    print()
    print(LINE)
    print(title)
    print(LINE)


def a_sum():
    n = 10_000_000
    exact = 0.1 * n

    s = 0.0
    for _ in range(n):
        s += 0.1

    sk = c = 0.0
    for _ in range(n):
        y = 0.1 - c
        t = sk + y
        c = (t - sk) - y
        sk = t

    a = np.full(n, 0.1, dtype=np.float32)
    print("  精确值 %.1f" % exact)
    print("  %-24s %20.4f  误差 %.3e" % ("float64 逐次相加", s, abs(s - exact)))
    print("  %-24s %20.4f  误差 %.3e" % ("Kahan 补偿", sk, abs(sk - exact)))
    print("  %-24s %20.4f  误差 %.3e" % ("math.fsum", math.fsum([0.1] * n),
                                         abs(math.fsum([0.1] * n) - exact)))
    print("  %-24s %20.4f  误差 %.3e" % ("float32 顺序 cumsum", float(np.cumsum(a)[-1]),
                                         abs(float(np.cumsum(a)[-1]) - exact)))
    print("  %-24s %20.4f  误差 %.3e" % ("float32 pairwise np.sum", float(np.sum(a)),
                                         abs(float(np.sum(a)) - exact)))


def b_integrate():
    dt = f32(0.01)
    t = f32(0.0)
    marks = {360_000: 0.0, 720_000: 0.0, 1_080_000: 0.0}
    for i in range(1, 1_080_001):
        t = f32(t + dt)
        if i in marks:
            marks[i] = float(t)
    print("  dt = 0.01，float32 逐次累加")
    for n, got in marks.items():
        want = n * 0.01
        print("  %9d 步：应 %8.3f s，实得 %10.6f s，偏差 %+9.4f s（%+.3f%%）"
              % (n, want, got, got - want, (got - want) / want * 100))

    print()
    print("  各量级下，加一次 0.01 实际加了多少：")
    for k in (10, 11, 12):
        start = 2.0 ** k
        ulp = float(np.spacing(f32(start)))
        n_ulp = round(0.01 / ulp)
        eff = n_ulp * ulp
        print("  [%6.0f, %6.0f)：ULP=%.6g，0.01/ULP=%.2f → %d×ULP=%.9f（%+.4f%%）"
              % (start, start * 2, ulp, 0.01 / ulp, n_ulp, eff,
                 (eff - 0.01) / 0.01 * 100))


def c_position():
    print("  float32 位置累加：加 1000 次 1 mm")
    for start in (0.0, 1e3, 1e5, 1e7):
        p = f32(start)
        p0 = p
        for _ in range(1000):
            p = f32(p + f32(0.001))
        print("  起点 %10.1f m → 移动 %8.4f m（ULP %s）"
              % (start, float(p) - float(p0),
                 "—" if start == 0 else "%.6g m" % float(np.spacing(f32(start)))))


def d_mean():
    rng = np.random.default_rng(1)
    xs = rng.normal(1000.0, 1.0, 100_000)
    m = f32(0.0)
    stuck = 0
    for i, x in enumerate(xs, 1):
        prev = m
        m = f32(m + f32((f32(x) - m) / f32(i)))
        if i > 1000 and m == prev:
            stuck += 1
    print("  float32 增量均值 %.6f，float64 精确均值 %.6f，偏差 %+.6f"
          % (float(m), float(np.mean(xs)), float(m) - float(np.mean(xs))))
    print("  10 万步里，均值一步没动过：%d 步（%.1f%%）" % (stuck, stuck / 1000.0))


def e_variance():
    rng = np.random.default_rng(42)
    n = 200_000
    x = 1e8 + rng.normal(0.0, 1.0, n)

    naive = float(np.mean(x ** 2) - np.mean(x) ** 2)
    two = float(np.mean((x - np.mean(x)) ** 2))

    cnt, mean, m2 = 0, 0.0, 0.0
    for v in x:
        cnt += 1
        d = v - mean
        mean += d / cnt
        m2 += d * (v - mean)
    w = m2 / cnt

    x32 = x.astype(np.float32)
    m32 = np.mean(x32, dtype=np.float32)
    naive32 = float(np.mean(x32 ** 2, dtype=np.float32) - m32 ** 2)
    two32 = float(np.mean((x32 - m32) ** 2, dtype=np.float32))

    print("  %d 个样本，均值 1e8，参考方差 ≈ 1.0055" % n)
    print("  %-28s %20.6f" % ("E[x^2]-E[x]^2 (float64)", naive))
    print("  %-28s %20.6f" % ("两遍法 (float64)", two))
    print("  %-28s %20.6f" % ("Welford (float64)", w))
    print("  %-28s %20.6f" % ("E[x^2]-E[x]^2 (float32)", naive32))
    print("  %-28s %20.6f" % ("两遍法 (float32)", two32))
    print("  float32 在 1e8 处的 ULP：%.1f —— 噪声 σ=1 在存进去时就没了"
          % float(np.spacing(f32(1e8))))

    x2 = 1e9 + rng.normal(0.0, 1.0, n)
    print("  均值换成 1e9：朴素公式 %.6f（1e18 处 float64 的 ULP = %.0f）"
          % (float(np.mean(x2 ** 2) - np.mean(x2) ** 2), math.ulp(1e18)))


def f_cancel():
    vals = [1e16, 1.0, -1e16]
    s = c = 0.0
    for x in vals:
        y = x - c
        t = s + y
        c = (t - s) - y
        s = t
    print("  1e16 + 1 == 1e16 ? %s（1e16 处 float64 的 ULP = %.1f）"
          % (1e16 + 1.0 == 1e16, math.ulp(1e16)))
    print("  顺序相加 1e16 + 1 - 1e16 = %.1f" % (1e16 + 1.0 - 1e16))
    print("  Kahan                      = %.1f" % (s + c))
    print("  math.fsum                  = %.1f" % math.fsum(vals))
    print("  Neumaier（见 stable.py）   = 1.0")
```

```python
# -*- coding: utf-8 -*-
"""三个小工具：补偿求和、在线方差、整数时钟"""


class NeumaierSum:
    """补偿求和：和 Kahan 一样两行核心，但多处理 |x| > |s| 的情况

    1e16 + 1 - 1e16 这种顺序，Kahan 会把补偿项弄丢（得 0），
    Neumaier 会把小数先记在 c 里，最后得 1。
    """
    __slots__ = ("s", "c")

    def __init__(self):
        self.s = 0.0
        self.c = 0.0

    def add(self, x):
        t = self.s + x
        if abs(self.s) >= abs(x):
            self.c += (self.s - t) + x
        else:
            self.c += (x - t) + self.s
        self.s = t
        return self

    def value(self):
        return self.s + self.c


class Welford:
    """在线均值/方差：从不做 E[x^2]-E[x]^2，也不存整个数组"""
    __slots__ = ("n", "mean", "m2")

    def __init__(self):
        self.n = 0
        self.mean = 0.0
        self.m2 = 0.0

    def add(self, x):
        self.n += 1
        d = x - self.mean
        self.mean += d / self.n
        self.m2 += d * (x - self.mean)
        return self

    @property
    def var(self):
        return self.m2 / (self.n - 1) if self.n > 1 else 0.0

    @property
    def std(self):
        return self.var ** 0.5


class TickClock:
    """整数时钟：每一拍 +1，需要秒的时候才乘 period

    累加 dt 的误差会随量级换挡；累加整数不会。
    """
    __slots__ = ("ticks", "period")

    def __init__(self, period):
        self.ticks = 0
        self.period = period

    def tick(self, n=1):
        self.ticks += n

    @property
    def seconds(self):
        return self.ticks * self.period


if __name__ == "__main__":
    import numpy as np

    ns = NeumaierSum()
    for x in (1e16, 1.0, -1e16):
        ns.add(x)
    print("Neumaier 1e16+1-1e16 = %.1f" % ns.value())

    ns = NeumaierSum()
    for _ in range(10_000_000):
        ns.add(0.1)
    print("Neumaier 1e7 个 0.1 = %.6f" % ns.value())

    rng = np.random.default_rng(0)
    data = rng.normal(25.0, 3.0, 100_000)
    w = Welford()
    for x in data:
        w.add(x)
    print("Welford n=%d mean=%.9f var=%.9f（numpy %.9f）"
          % (w.n, w.mean, w.var, float(np.var(data, ddof=1))))

    c = TickClock(0.001)
    c.tick(3_600_000)
    print("TickClock 3600000 拍 = %.9f s" % c.seconds)
```

一个细节：`Welford.var` 用的是 `n-1`（样本方差），和 numpy 的 `ddof=1` 对齐；要总体方差就改成 `n`，别混着用。`TickClock` 的 `seconds` 是乘法而不是累加，所以误差只有一次舍入，不会随拍数增长。
