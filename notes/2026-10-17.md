## 💭 技术随想：重发一次，机器人多走 10 厘米——"恰好一次"是骗局，"恰好一次的效果"不是

控制链路上跑的是 UDP：手柄 App 一帧一帧发，rp_server 收到后转给虚拟手柄，再往下走到电机。选 UDP 的理由很充分——旧帧没用，新帧才重要，丢一帧不值得等重传（前面聊 UDP 与 TCP 的那篇说过这件事）。但"不值得等"不等于"不需要确认"：一条"点动 10 厘米"的指令如果丢了，操作员会再按一次；如果客户端还带了自动重发，故事就更微妙了。

设想一个再普通不过的下午：操作员点了一下"前进 10cm"，数据包到了，服务端执行了，轮子转了；回程的 ACK 在半路被干扰吃掉。客户端的定时器一响："没收到确认，重发。" 服务端又收到一条一模一样的"+100mm"，它没有任何理由怀疑——于是轮子再转一圈。操作员看到的是"我只按了一下，它走了 20 厘米"。

这不是哪一方的 bug。客户端没错：不重发就没有可靠性。服务端也没错：它收到的是一条语法合法、语义明确的指令。错的是这条链路上少了一样东西——**一个能让服务端认出"这两条其实是同一次意图"的标记**。

下面这套实验，就是想把这 10 厘米的来龙去脉摆到桌面上。

### 三种送达语义，只有两种是真的

**最多一次（at-most-once）**：发出去就不管，丢了算运气。UDP 本身就是这个语义。优点是永远不会重复，缺点是"到底到没到"没人知道——账最不准。

**至少一次（at-least-once）**：收不到 ACK 就重发，直到收到为止。这是工程上唯一能落地的"可靠"：只要链路还有一线希望，消息总能挤过去。代价是：**重发会产生副本，而副本和正本长得一模一样，服务端分不出来**。

**恰好一次（exactly-once）**：听起来最理想，但在"链路可能丢包"的前提下，传输层做不到。这不是工程水平问题，是数学问题——1975 年就有论文把它讲清楚了，后来被称为"两军问题"：两支军队要靠信使约定总攻时间，信使可能被俘；A 发出确认，需要 B 再确认"我收到了你的确认"，这个确认又需要 A 再确认……**最后一条确认永远无法被确认**，双方永远无法同时确信"我们已经约好了"。换成 RPC：客户端发出请求，服务端执行完发回响应；响应丢了，客户端重发；服务端怎么知道这是重发还是新请求？客户端又怎么知道服务端是没收到、还是执行了但响应丢了？**这个问题在协议层无解**。

所以工程界换了个问法：既然"消息只送达一次"做不到，那就让"消息送达多次"和"送达一次"的效果一样。这叫**幂等**。行业里说的"exactly-once semantics"（Kafka 的 idempotent producer、事务消息），指的从来不是"消息不重复"，而是"重复被吃掉了，业务效果只有一次"。

一句话总结这三个词的关系：**可靠性 = 重试 + 去重。只做重试，是把"丢消息"换成了"重复执行"；只做去重，是把"重复"换成了"丢消息"。**

### HTTP 早就把答案写在语义里了

RFC 9110 把方法分成两类：**safe**（GET/HEAD，只读）和 **idempotent**（PUT/DELETE，连同所有 safe 方法）。PUT 的语义是"把资源变成这个样子"——执行一次和执行十次，结果一样；DELETE 是"确保它不存在"，删两次和删一次一样。而 POST 是"请处理这件事"，天然不幂等：提交两次订单，就是两笔订单。

但注意，HTTP 给的只是**语义承诺**，不是实现。你在接口上写 `PUT /robot/position`，服务端却实现成"当前位置 += 请求里的偏移量"，那它照样不幂等。**幂等是服务端的行为，不是方法名的装饰。**

真正把这件事工程化的模板是 Stripe：请求头里带一个 `Idempotency-Key`，服务端把第一次的处理结果存下来（默认保留 24 小时），同一个 key 再来，就把当初的响应原样回放——连错误响应也回放。客户端因此可以放心重试：它拿到的永远是"那一次"的答案。

### 幂等键的五个坑

**一、key 必须代表"一次意图"，而不是"一次发送"。** 客户端在第一次发送前生成 key，之后所有重试都复用同一个。最常见的错误是在重试循环里 `uuid4()`——每次重试都是新 key，去重表一次也命中不了，白建。

**二、占坑必须是原子的。** 先查后写（`if key not in store: ...`）在并发下必然翻车：两个重发同时到达，都查到"没有"，都去执行。正确做法是 `SET key value NX PX 86400000`（Redis）、`INSERT ... ON CONFLICT DO NOTHING`（Postgres），或者干脆给 key 建唯一索引，让数据库替你仲裁。

**三、存结果，不只存"处理过"。** 只记一个布尔标记，重复请求回来只能得到"处理过了"，拿不到当时的结果——客户端还是不知道该信什么。要存的是**那一次的响应**，包括失败。

**四、要能表达"处理中"。** 两个请求同时到达时，第二个不能也去执行，也不能直接说"重复"——第一次可能还没跑完。它应该等，或者返回 409/202 让客户端稍后再查。同时，"处理中"这个状态必须有超时回收：进程崩了，占坑不能永远占着。

**五、TTL 要比客户端的重试窗口长。** 客户端可能坚持重试几分钟，key 却 60 秒就过期了——过期之后来的重发就是一条全新请求。Stripe 的 24 小时是个可参考的量级；至少要让"最坏情况下的重试链"落在 TTL 里面。另外 key 的作用域要绑上设备/账户和接口，别让两台设备的 key 撞在一起。

还有一个反模式值得单独说：**用请求体的哈希当 key**。看着很聪明——内容一样就是重复嘛。但用户真的想连按两次"前进 10cm"呢？两条请求体一模一样，哈希也一样，第二条会被当成重复吃掉。**幂等键表达的是"这是同一次意图的重试"，不是"这两个请求长得一样"**。这两件事只有客户端分得清。

### 机器人这一课：最便宜的去重，是改指令的语义

上面所有办法都要加存储、加 TTL、加清理任务、加并发状态机。还有一条更省事的路：**把指令设计成重复执行也无害的样子**。

- 增量指令——"再走 10cm"、"再转 5 度"、"再往上抬一点"——天生不幂等。执行两次就是两个 10cm。
- 绝对指令——"去 x=400mm"、"目标速度 0.3m/s"、"关节角转到 30°"——天生幂等。执行两次，第二次发现"我已经在 400mm 了"，动作量为零。

所以在控制链路上，能发"目标状态"就别发"增量"。丢包、乱序、重复、重发，全都不怕：后到的目标覆盖先到的，最终状态只由最后一条指令决定。这也是为什么大多数 CAN 伺服驱动器接受的是"目标位置/目标力矩"而不是"走一步"——控制周期里反复下发同一个目标，本来就是常态，重复是免费的。

只有一类操作躲不开增量语义：点动（jog）、步进、标定时的微调。这时才需要老老实实上序号 + 去重窗口。而更高频的流（比如摇杆），要的其实不是"去重"而是"新鲜度"：每帧带个递增序号，收到旧帧直接丢——旧数据不该覆盖新数据，这和"同一次意图只执行一次"是两种不同的语义，别混用。

这就是今天最想记下来的一句：**在协议里消灭重复，比在代码里检测重复便宜得多**。前者只需改一句指令的定义，后者要建表、设 TTL、处理并发、写清理任务，还得祈祷没人绕过它。

### 三个反直觉的点

**一、重试不是可靠性的补丁，是重复的来源。** 想可靠就必须重试，想不重复就必须去重——这是一对必须同时设计的动作，只做一半，等于把一种故障换成另一种。实验里"裸奔"多走 200mm，"最多一次"少走 100mm，两个方向都错。

**二、客户端永远无法自己判断"没执行"还是"执行了但回执丢了"。** 这个不确定性不能靠"多试几次"消除：试得越多，重复的概率越大。它只能由服务端用一个 key 收敛成一个确定答案——两军问题的工程解不是"更强的确认"，是"让重复无害"。

**三、"恰好一次"是效果，不是传输。** 任何声称"消息只送达一次"的中间件，拆开看都是"至少一次 + 去重"。想清楚这一点，很多"消息重复"的线上问题就不神秘了：不是中间件坏了，是它从来没承诺过你以为它承诺的东西。

### 放远一点

TCP 那一层其实已经替我们吃掉了很多重复：重传、去重、按序，都是内核在做。但 TCP 管不了业务层的重试——请求送到了、服务端处理慢、客户端 3 秒超时重发，第二条照样会到。**传输层的可靠，不等于业务层的幂等**。这也是为什么在 TCP 之上还要幂等键，在 UDP 之上更要。

（顺带一句：Kafka 的 idempotent producer 用的是同一个思路——生产者 ID + 分区内递增序号，broker 记住"这个生产者这个分区处理到第几条了"，重复的直接丢。名字叫幂等，骨子里是去重表。）

## 🧩 今日代码片段：幂等实验室——同一份网络，四种策略

真机上演不了"ACK 恰好丢一次"，所以写了个确定性模拟器：一条轨道上的小车，客户端要它走 4 段、每段 100mm（目标 400mm）。网络剧本是写死的——第 1 条数据到达但 ACK 丢失，第 2 条第一次发送丢包，第 3 条一次到底，第 4 条又丢 ACK。同一份网络剧本，跑四种策略：

- **① 裸奔**：收到就执行，重发就再执行（最朴素的实现）
- **② 最多一次**：客户端发一次就不管（不重试）
- **③ 幂等键**：服务端记住 key，重发只回放结果
- **④ 绝对指令**：指令是"去 x=400"，重复执行天然无害

最后附一段"先查后写"的并发现场：两个重发同时到达，去重表是查得到还是查不到，全看时序。

纯标准库，本机 Python 3.11.15 真实运行；输出为真实运行结果。

```python
# -*- coding: utf-8 -*-
"""幂等实验室：同一条指令，网络抖一下，机器人到底走了多远？

纯标准库、确定性模拟（每次运行一字不差）。
场景：小车在轨道上，客户端要它向右走 4 段，每段 100mm（目标 400mm）。
网络：UDP，会丢包；客户端收不到 ACK 就重发（最多 3 次）。
四种策略：
  ① 裸奔      —— 收到就执行，重发就再执行一次
  ② 最多一次  —— 发一次就不管了（丢了就丢了）
  ③ 幂等键    —— 服务端记住 key，重发只回放结果，不再执行
  ④ 绝对指令  —— 指令是"去 x=400"，重复执行等于没执行
附：去重表也怕"先查后写"——两个重发同时到达的样子。
"""
import sys
import unicodedata

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

LINE = "=" * 66
MAX_SENDS = 3

# 每条指令的"网络剧本"：(数据是否到达, ACK 是否回到客户端)
FATES = {
    "ack_lost": [(True, False), (True, True)],
    "data_lost": [(False, False), (True, True)],
    "clean": [(True, True)],
}

COMMANDS = [
    (1, "ack_lost"),
    (2, "data_lost"),
    (3, "clean"),
    (4, "ack_lost"),
]


def pad(s, width):
    w = sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in s)
    return s + " " * max(0, width - w)


class Robot:
    def __init__(self):
        self.pos = 0
        self.t = 0
        self.log = []
        self.moves = 0          # 真正产生位移的执行次数

    def event(self, msg):
        self.t += 1
        self.log.append((self.t, msg))

    def move_rel(self, d, tag):
        before = self.pos
        self.pos += d
        self.moves += 1
        self.event(f"{tag} 执行「+{d}mm」：{before} → {self.pos} mm")

    def goto(self, target, tag):
        before = self.pos
        self.pos = target
        if before == target:
            self.event(f"{tag} 执行「去 x={target}」：已在目标，位移 0（重复执行无害）")
        else:
            self.moves += 1
            self.event(f"{tag} 执行「去 x={target}」：{before} → {self.pos} mm")


class Server:
    def __init__(self, robot, mode):
        self.robot = robot
        self.mode = mode
        self.store = {}

    def handle(self, no, tag):
        r = self.robot
        if self.mode in ("naive", "at_most_once"):
            r.move_rel(100, tag)
            return "OK"
        if self.mode == "idempotent":
            key = f"move-{no}"
            if key in self.store:
                r.event(f"{tag} 命中幂等键 {key} → 不执行，回放上次结果（{self.store[key]}）")
                return self.store[key]
            r.move_rel(100, tag)
            self.store[key] = f"位置={r.pos}mm"
            return self.store[key]
        if self.mode == "absolute":
            r.goto(no * 100, tag)
            return "OK"
        raise ValueError(self.mode)


def run_command(server, no, fate, retry, tag):
    """返回 (客户端是否认为成功, 实际发送次数)"""
    robot = server.robot
    script = FATES[fate]
    sends = 0
    for attempt in range(MAX_SENDS):
        data_ok, ack_ok = script[attempt] if attempt < len(script) else (True, True)
        sends += 1
        if not data_ok:
            robot.event(f"{tag} 第 {sends} 次发送：数据包丢了（服务端没收到）")
            if not retry:
                robot.event(f"{tag} 不重发 → 这条永远没执行；客户端只知道“失败”")
                return False, sends
            robot.event(f"{tag} 超时，重发（客户端不知道第一次的结果）")
            continue
        robot.event(f"{tag} 第 {sends} 次发送：服务端收到")
        result = server.handle(no, tag)
        if not ack_ok:
            robot.event(f"{tag} ACK 丢了 → 客户端不知道到底执行没执行")
            if not retry:
                robot.event(f"{tag} 不重发 → 客户端记“失败”，服务端其实已经执行了")
                return False, sends
            robot.event(f"{tag} 超时，重发（客户端不知道第一次的结果）")
            continue
        robot.event(f"{tag} 收到 ACK（{result}）→ 客户端记为成功")
        return True, sends
    robot.event(f"{tag} 重试 {MAX_SENDS} 次仍无 ACK，放弃")
    return False, sends


def run(mode, title, retry, note, verbose=False):
    print(LINE)
    print(title)
    print(LINE)
    robot = Robot()
    server = Server(robot, mode)
    rows = []
    ok = 0
    for no, fate in COMMANDS:
        tag = f"第{no}条"
        before_pos, before_moves = robot.pos, robot.moves
        good, sends = run_command(server, no, fate, retry, tag)
        ok += good
        rows.append((tag, sends, robot.moves - before_moves,
                     f"{before_pos} → {robot.pos} mm", "成功" if good else "失败"))
    print("  " + pad("指令", 6) + pad("发送", 6) + pad("位移", 6) + pad("位置变化", 18) + "客户端")
    for tag, sends, execs, span, verdict in rows:
        print("  " + pad(tag, 6) + pad(f"{sends}次", 6) + pad(f"{execs}次", 6)
              + pad(span, 18) + verdict)
    print()
    print(f"  → 位置 {robot.pos} mm（目标 400），产生位移 {robot.moves} 次，客户端记成功 {ok}/4")
    if verbose:
        print("  —— 事件流水 ——")
        for t, msg in robot.log:
            print(f"  [t={t:02d}] {msg}")
    print(f"  {note}")
    print()
    return robot.pos, robot.moves, ok


def handler(name, store, robot, key, atomic):
    seen = store.get(key)
    yield f"{name}: 查 key={key} → {('有：' + seen) if seen else '没有'}"
    if seen:
        yield f"{name}: 直接回放结果（{seen}），不执行"
        return
    if atomic:
        ok = key not in store
        if ok:
            store[key] = "处理中"
        yield f"{name}: 原子占坑 key={key} → {'成功' if ok else '失败（有人在处理）'}"
        if not ok:
            yield f"{name}: 不执行，等对方的结果（或返回 409，稍后再查）"
            return
    before = robot.pos
    robot.pos += 100
    robot.moves += 1
    yield f"{name}: 执行「+100mm」→ {before} → {robot.pos} mm"
    store[key] = f"位置={robot.pos}mm"
    yield f"{name}: 写结果 key={key} = {store[key]}"


def race_demo():
    print(LINE)
    print("附：去重表也怕“先查后写”——两个重发同时到达的样子")
    print(LINE)
    for atomic in (False, True):
        robot = Robot()
        store = {}
        print()
        print("  " + ("原子占坑：put_if_absent（等价于 Redis SET NX / 数据库唯一索引）" if atomic
                      else "先查后写：if key not in store: 执行；store[key] = 结果"))
        gens = {
            "A": handler("A", store, robot, "move-9f2c", atomic),
            "B": handler("B", store, robot, "move-9f2c", atomic),
        }
        order = ["A", "B", "A", "B", "A", "A"] if atomic else ["A", "B", "A", "B", "A", "B"]
        for name in order:
            try:
                print("    " + next(gens[name]))
            except StopIteration:
                pass
        print(f"    → 机器人位置 {robot.pos} mm（本该 100），服务端执行 {robot.moves} 次")


print(LINE)
print("幂等实验室：4 条「+100mm」，网络抖两下，最后走到哪？")
print(LINE)
print("  网络剧本（每条指令的前两次尝试）：")
for no, fate in COMMANDS:
    if fate == "ack_lost":
        desc = "数据 OK，ACK 丢 → 客户端必然重发"
    elif fate == "data_lost":
        desc = "第 1 次数据丢了 → 重发才到"
    else:
        desc = "一次到底"
    print(f"    第{no}条  {desc}")
print()

run("naive", "① 裸奔：来一条执行一条（客户端老实重发）", True,
    "多走 200mm：重复执行的不是“错误请求”，是“正确请求的副本”。", verbose=True)
run("at_most_once", "② 最多一次：发了就不管（丢了就丢了）", False,
    "少走 100mm；客户端记“失败”的 3 条里，有 2 条服务端其实已经动了——账对不上。")
run("idempotent", "③ 幂等键：重发命中 key，只回放结果", True,
    "分毫不差：重复的是“发送”，不是“动作”。", verbose=True)
run("absolute", "④ 绝对指令：指令本身就是“去 x=400”", True,
    "分毫不差：重复执行天然无害——幂等写在指令语义里。")
race_demo()
print()
print(LINE)
print("一句话：网络只能保证“至少一次”，动作的“恰好一次”得靠服务端自己挣。")
print(LINE)
```

**今天收获清单：**

- **三种送达语义：** 最多一次会丢、至少一次会重、恰好一次在传输层不存在。所谓"恰好一次语义"，全都是"至少一次 + 去重"包装出来的效果。
- **可靠性 = 重试 + 去重。** 只做重试，是把"丢消息"换成"重复执行"；只做去重，是把"重复"换成"丢消息"。实验里裸奔多走 200mm、最多一次少走 100mm，两个方向都错。
- **幂等键五条：** key 由客户端生成且重试不变；占坑必须原子（`SET NX` / 唯一索引 / `ON CONFLICT`）；存结果不只存标记；"处理中"要有并发语义和超时回收；TTL 覆盖重试窗口，作用域绑设备与接口。
- **先查后写 = 并发下的双执行。** 实验里 A、B 都查到"没有"，位置跑到 200mm；换成 `put_if_absent`，B 当场退让，位置停在 100mm。
- **反模式：拿请求体哈希当 key。** 它会把两次合法的相同操作合并成一次——幂等键表达的是"同一次意图的重试"，不是"两个请求长得一样"。
- **机器人最优解：绝对指令。** 目标位置/速度/角度天生幂等，重复执行等于没执行，比任何去重表都便宜；增量指令（点动、步进）才需要序号 + 去重窗口。
- **高频流要的是新鲜度，不是去重。** 摇杆这类连续帧带递增序号，旧帧直接丢——"旧数据不覆盖新数据"和"同一次意图只执行一次"是两种语义，别混用。
- **TCP 解决链路重传，不解决业务层重试。** 传输层的可靠不等于业务层的幂等，所以 TCP 之上照样要幂等键，UDP 之上更要。

## ✨ 今日一句

> 网络只能承诺"至少一次"，"恰好一次"是应用层自己挣来的。而最优雅的实现，不是把去重表修得更厚，而是把话说成"去 x=400"——让"多做一次"这件事，从一开始就不成立。
