## 💭 技术随想：布隆过滤器——一个"糊里糊涂"却省下几个 GB 的聪明结构

有个问题困扰过几乎每个后端工程师：**如何判断一个元素是否在集合里，而集合大到塞不进内存？** 比如几十亿条 URL 去重、几千万个用户的缓存穿透防护。直觉答案是哈希表，可算一笔账就傻眼了：1 亿个 16 字节的 key，哈希表连桶带指针轻松吃掉 3~5 GB——而且大部分查询的结果是"不存在"，钱全花在存垃圾上了。

**布隆过滤器（Bloom Filter）的回答是：我可以"糊涂"一点。** 它用一个位数组 + k 个哈希函数，对任何查询只给两种答案：**"一定不存在"**，或者**"可能存在"**。它允许假阳性（说"可能有"其实没有），但**绝不允许假阴性**（说"没有"就一定没有）——这个不对称性恰好是工程上的金矿：

- **缓存穿透防护**：请求打进来先问布隆过滤器，它说"一定不存在"就直接返回，不用查 Redis、不用打数据库。那些拿随机 ID 刷接口的攻击瞬间失去意义。
- **爬虫去重**：几十亿 URL 只需几 GB 内存，不必为每个 URL 存一条记录。
- **数据库底层**：LevelDB、RocksDB、Cassandra 都用它减少无效的磁盘读取。

**性能代价一目了然：** 存 100 万个元素、接受 1% 误报率，位数组只要约 **1.4 MB**——同等规模哈希表要几百 MB。它靠两个公式过日子：位数组大小 `m = -n·ln(p) / (ln2)²`，哈希个数 `k = (m/n)·ln2`。p 是你能容忍的误报率，想要更准就多掏内存，永远可以谈判。

**几个使用须知：**
1. **不能删除元素。** 一个 bit 可能被多个元素共用，清零会误伤。要删除请上 Counting Bloom Filter，每个位置换成计数器。
2. **误报率是"满员"时的承诺。** 塞入的元素超过设计容量 n，误报率会加速恶化——容量要按峰值预估。
3. **哈希要快。** 这里不需要密码学强度，用 `murmur3`/`xxhash` 这类快速哈希；甚至可以只算两个基础哈希，用"双哈希技巧"线性组合出 k 个，CPU 省一半。

**心法：** 布隆过滤器是"空间换精度"的典范——它放弃的只是"100% 确定"，换来的是数量级级别的内存节省。工程上的大部分难题，答案都不是"更准"，而是"**在多准才够用**"上找到那个可以谈的平衡点。

## 🧩 今日代码片段：30 行手写一个布隆过滤器

```python
import math
import hashlib


class BloomFilter:
    """布隆过滤器：只回答"一定不存在 / 可能存在"，用 KB 级内存挡掉海量无效查询"""

    def __init__(self, capacity: int, false_positive_rate: float = 0.01):
        # m = -n·ln(p) / (ln2)^2  位数组长度
        self.m = math.ceil(-capacity * math.log(false_positive_rate) / (math.log(2) ** 2))
        # k = (m/n)·ln2  哈希函数个数
        self.k = math.ceil((self.m / capacity) * math.log(2))
        self.bits = bytearray((self.m + 7) // 8)   # 位数组，1 万个元素只需十几 KB

    def _hashes(self, item: str):
        """双哈希技巧：只算两个基础哈希，线性组合出 k 个位置，省一半 CPU"""
        h1 = int.from_bytes(hashlib.sha256(("s1:" + item).encode()).digest()[:8], "big")
        h2 = int.from_bytes(hashlib.md5(("s2:" + item).encode()).digest()[:8], "big")
        for i in range(self.k):
            yield (h1 + i * h2) % self.m

    def add(self, item: str):
        for pos in self._hashes(item):
            self.bits[pos >> 3] |= 1 << (pos & 7)

    def __contains__(self, item: str) -> bool:
        # 所有位都是 1 才算"可能存在"；只要有一位是 0，就"一定不存在"
        return all(self.bits[pos >> 3] >> (pos & 7) & 1 for pos in self._hashes(item))


bf = BloomFilter(capacity=10_000, false_positive_rate=0.01)
print(f"存 1 万个元素：位数组 {bf.m / 8 / 1024:.1f} KB，{bf.k} 个哈希函数（哈希表同样规模要上百 KB~MB）")

for i in range(10_000):
    bf.add(f"user:{i}")

# 存过的元素：100% 判"存在"，绝不漏报
assert "user:42" in bf and "user:9999" in bf

# 没存过的元素：允许少量假阳性，但观察值和理论值 1% 高度吻合
fp = sum(1 for i in range(100_000, 200_000) if f"user:{i}" in bf)
print(f"10 万次陌生查询误报 {fp} 次，实际假阳性率 {fp / 100_000:.3%}（理论 1%）")
```

**说明：**

- `bytearray` 充当位数组：第 `pos` 位落在第 `pos >> 3` 个字节、第 `pos & 7` 个 bit 上，`|=` 置位、`& 1` 读位。
- 双哈希技巧：`h1 + i*h2 mod m` 生成的序列在 m 为质数时分布足够均匀，工程上不必真算 k 个哈希。
- 生产环境建议直接上现成库（Python 的 `pybloom-live`、Redis 的 `BF.RESERVE`/`BF.ADD` 命令），别重复造轮子——但手写一遍，你才真正懂它"省"在哪里。
- 把它套进你的缓存层：查 Redis 前先问布隆过滤器，命中的"一定不存在"直接返回，数据库 QPS 立降一个数量级。
