# 📅 2026年11月16日 日报

## 💭 技术随想：「一行」不是一个东西，是三个

昨天数的是「一个字符的长度」，今天轮到了「一行」——结果更乱：**同一份文件，`wc -l` 说是 3 行，Python 说是 3 行，中间隔着一个字节的 `\r`，而 git 说这份文件「改了」，`git diff` 偏说「没改」。**

起因很小：我给这个日报仓库做体检，随手敲了 `git ls-files --eol`，发现自己 141 个文件里，**有 2 个跟其他 138 个不一样**——它们的工作区副本末尾多了一个看不见的 `\r`。于是今天把「换行」这个从没正眼看过的符号，从头到尾量了一遍。下面每个数字都是真跑出来的（Windows 11 / Python 3.14.9 / git 2.53.0.windows.3）。

### 一、一个换行，两种字节

- `\n`（LF，`0x0A`）：**1 个字节**，Unix/Linux/macOS 的规矩。
- `\r\n`（CRLF，`0x0D 0x0A`）：**2 个字节**，DOS/Windows 留下的规矩。

别小看这多出来的一个字节。今天生成一份 399,999 行、每行 16 个字符的文本，两种写法实测：

```text
LF    14,288,889 字节
CRLF  14,688,888 字节    多 399,999 字节（+2.80%）
```

**多出来的字节数正好等于换行个数——每行一个 `\r`，一个不多一个不少。** 一个 14 MB 的日志文件，就因为行尾风格，白胖 2.8%。

### 二、「这个文件有几行」——四个工具，四个答案

我造了七个文件，每个只差行尾，然后同时问 `wc -l`、Python 的 `readlines()` 和 `splitlines()`：

| 文件 | 字节 | `\n` | `\r\n` | 裸 `\r` | `wc -l` | `readlines()` | `splitlines()` |
|---|---|---|---|---|---|---|---|
| `a\nb\nc\n` | 6 | 3 | 0 | 0 | 3 | 3 | 3 |
| `a\nb\nc`（末尾无换行） | 5 | 2 | 0 | 0 | **2** | 3 | 3 |
| `a\r\nb\r\nc\r\n` | 9 | 3 | 3 | 0 | 3 | 3 | 3 |
| `a\rb\rc\r`（老 Mac） | 6 | 0 | 0 | 3 | **0** | 3 | 3 |
| `a\nb\r\nc\rd`（混着来） | 8 | 2 | 1 | 1 | **2** | **4** | **4** |
| 空文件 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 只有一个 `\n` | 1 | 1 | 0 | 0 | 1 | 1 | 1 |

看懂这张表，行尾的事就懂一半了：

- **`wc -l` 数的不是「行」，是「`\n` 这个字节」。** 所以「老 Mac 换行」的文件，它数出 **0 行**；末尾没换行的最后一行的，它**少算一行**。它不是错了，它只是**只认 `\n`**。
- **Python 的文本模式默认开了「通用换行」（universal newlines）**：`\r\n`、`\r`、`\n` 一律当换行。所以那个「老 Mac」文件它老老实实数出 3 行，而 `wc -l` 说是 0。
- **同一个文件，同一个问题，两个工具给两个数。** 谁都没错——**「几行」这个词本身没定义清楚：你数的是换行符，还是被人眼认作一行的那段东西？**

还有更实在的一个：仓库里 `news/2026-08-12.md` 这个文件，9942 字节、**一个换行都没有**（一行到底）。`wc -l` 数出 0——「9942 字节的文件有 0 行」，这话不假，只是废话。git 对它的判定也是特立独行的 `i/none w/none`。

### 三、最阴的坑：读一遍、写回去，文件就永久变了

这是今天最值钱的一条。在本机（Windows），Python 的**文本模式写**会把 `\n` 翻译成 `\r\n`：

```text
open(p,'w').write('x\ny\n')                -> b'x\r\ny\r\n'   ← \n 被换成了 \r\n
open(p,'w',newline='').write('x\ny\n')     -> b'x\ny\n'
open(p,'w',newline='\n').write('x\ny\n')   -> b'x\ny\n'
open(p,'wb').write(b'x\ny\n')              -> b'x\ny\n'
```

于是「用文本模式读一遍、再写回去」这个看起来完全无害的操作，会把文件**改掉**：

```text
原始 LF 文件    b'a\nb\nc\n'        6 字节
读一遍再写回去  b'a\r\nb\r\nc\r\n'  9 字节   ← 长了 3 个字节

第 2 次往返     9 字节（稳住了）
第 3 次往返     9 字节
```

第一遍直接把你 6 字节的文件撑成 9 字节，之后稳定——**因为读的时候 `\r\n` 被翻译回 `\n`，写的时候又被翻译成 `\r\n`，从此它是一个「自洽」的 CRLF 文件了。** 你不是「读了一下」，你是**改写了它**。

而**读的时候你根本看不见**：

```text
open(p,'r').read()               -> 'hello\nworld\n'          ← \r 被吃掉了
open(p,'rb').read()              -> b'hello\r\nworld\r\n'      ← 原形
open(p,'r',newline='').read()    -> 'hello\r\nworld\r\n'       ← 只有这么写，\r 才现形
```

**默认的文本模式读，会把「这个文件是 CRLF」这件事当场抹掉**——你拿到一个干净的字符串，善意地处理一下再写回去，就把它变成了另一个文件。

### 四、git：存的永远是 LF，看见的可能是 CRLF，报的是一个 ` M` 加一个空 diff

这个仓库 `core.autocrlf = true`，`git ls-files --eol` 的全量统计：

```text
138 个  i/lf  w/lf     索引里 LF，工作区也 LF
  2 个  i/lf  w/crlf   索引里 LF，工作区却是 CRLF   ← 就这两个例外
  1 个  i/none w/none  一个换行都没有的那个 9942 字节文件
```

那两个「例外」是谁？`news/2026-08-06.md` 和 `notes/2026-10-19.md`。它们**静静地躺着，`git status` 一片干净**——因为决定「该是什么样」的不是文件本身，是索引里那条记录。

把差的字节算一下，你就知道那多出来的是什么：

```text
notes/2026-10-19.md   工作区 27,928 字节   索引 blob 27,437 字节   差 491
                      该文件 \r\n 段数 = 491 / 492 段        ← 对得上，一个不差
news/2026-08-06.md    工作区  4,400 字节   索引 blob  4,366 字节   差  34
                      该文件 \r\n 段数 = 34                  ← 也对得上
```

**多出来的每一个字节，都是那些 `\r`。** git 交上去（blob）的，永远是 LF。

下面是我在一份临时仓库里做的对照实验，翻来覆去只改行尾：

```text
A) 用 LF 提交（i/lf w/lf）→ 工作区改成 CRLF：
   git status --porcelain   =  M f.txt      ← git 说：改了
   git diff --numstat       = （空）        ← git 说：没改
   git diff --ignore-cr-at-eol --numstat = （空）

B) 用 CRLF 提交 → ls-files 给 i/lf w/crlf → status 一片干净
   rm f.txt && git checkout -- f.txt → 写出来的还是 b'a\r\nb\r\n'（CRLF）
```

于是**同一份文件、同一时刻，三个工具三个答案**：

| 工具 | 它说 |
|---|---|
| `git status` | 这个文件改了（` M`） |
| `git diff` | 什么都没改（空输出） |
| `sha256sum` | 改了：`8f9e9933…` vs `4a1e67f2…` |

`git diff` 会把「只差行尾」当成噪音过滤掉，`status` 又会把它当成一次改动——**它俩吵起来的时候，只有哈希说了实话。** `git add` 也一肚子话：

```text
warning: in the working copy of 'lf_new.txt', LF will be replaced by CRLF
         the next time Git touches it
```

「下次 git 碰它的时候」——所以别以为现在字节是什么样，将来还是什么样。

### 五、Shell 里翻车最快的一次：`read` 会把 `\r` 留在变量里

写个循环读 CRLF 文件，`\r` 会**跟着值一起被赋给变量**（因为 shell 只认 `\n` 是行结束符）：

```text
$ printf 'alpha\r\nbeta\r\ngamma\r\n' > crlf_demo.txt
$ while IFS= read -r line; do printf '读到: [%s]\n' "$line"; done < crlf_demo.txt
读到: [alpha\r]
读到: [beta\r]
读到: [gamma\r]
```

终端里那个 `]` 会被 `\r` 拽到行首、把前面的字吃掉——**看上去像乱码，其实是光标被按回了行首。** 后果不止是难看：

```text
$ while IFS= read -r n; do [ "$n" -gt 2 ] ...; done < crlf_demo.txt
  比较失败: n=[alpha\r] 不是整数              ← 数值比较直接失败

$ while IFS= read -r n; do n=${n%$'\r'}; ...; done < crlf_demo.txt
  修好后 n=[alpha] 长度=5                     ← 剥掉 \r 就正常了

$ printf 'a,b,c\r\n1,2,3\r\n' | cut -d, -f3 | cat -A
c^M$                                          ← 最后一列永远多一个 ^M
```

**规律很朴素：凡是「按行读、取最后一个字段、做等值比较、做数值转换」的地方，CRLF 都会咬你一口。** `${n%$'\r'}`、`tr -d '\r'`、`dos2unix`、或者干脆统一 LF——四个办法随便挑一个，但**必须挑一个**。

这里要老实说一句：这台机器上的 MSYS `grep` 对 CRLF 是**宽容**的（`grep -c 'beta$' crlf_demo.txt` 返回 1，能匹配上，说明它自己把 `\r` 处理掉了）。**同一个 `grep`，换台机器、换个版本，结论可能就相反。** 所以这个坑不能靠「我这儿试了没问题」来排除——**只能靠字节说话**。

### 六、行尾在协议里不是风格，是规格

文本文件里 CRLF/LF 是「习惯」，到了协议里就是「规矩」——HTTP 规定头部必须以 CRLF 结束。我在本机起了个 HTTP 服务器，用原始 socket 发三种请求：

```text
GET / HTTP/1.1\r\nHost: 127.0.0.1\r\n\r\n   ->  'HTTP/1.0 200 OK'
GET / HTTP/1.1\nHost: 127.0.0.1\n\n         ->  'HTTP/1.0 200 OK'   ← 居然也过了
GET / HTTP/1.1\rHost: 127.0.0.1\r\r         ->  没有任何响应
                                               （服务端抛 ValueError: Bad request version）
```

第三行最直观：**没有 `\n`，行就永远不结束**，请求行里塞进了后面所有东西，服务器直接判定版本号非法；而且它想回一个 400 的时候，客户端已经把连接掐了。第二行则是个诚实的反例：**RFC 要求 CRLF，但 Python 这个服务器在实现上是「按 `\n` 断行、顺手去掉 `\r`」，所以纯 LF 也放过。** 「规格怎么写」和「对面能不能忍」，是两回事。

顺手量了文本模式读的代价（14,288,889 字节全量读入，取最好一次）：

```text
open(p,'rb').read()                    6.1 ms
open(p,'r',encoding='utf-8').read()   11.4 ms    ← 换了文本模式，多花 88%
open(p,'r',encoding='utf-8',newline='').read()  11.7 ms
```

**「通用换行」不是免费的**：它要扫描、判 `\r`、翻译，14 MB 上就是 5 毫秒的差价。按行切也一样（400,000 行、同样数据）：

```text
bytes.split(b'\n')   17.6 ms     str.split('\n')   21.4 ms
str.splitlines()     23.6 ms     file.readlines()  40.4 ms
```

`readlines()` 最慢——它既要解码、又要按三种行尾断行、还要把每行做成独立对象。**要快就走字节层，要方便就走文本层，两边别混着抱怨。**

### 七、对着手上的东西看

- **`rp_server` 读配置/参数。** 配置文件只要被 Windows 上的编辑器碰过一次，最后一行（或每一行）就可能带着 `\r` 上板子。`int("115200\r")` 直接炸，或者更坏——它没炸，`"115200\r"` 被当成字符串塞进了 `AT+` 报文里发出去。**解析入口统一 `strip()`，或者干脆只收 LF。**
- **AT 报文本身。** 板子和 App 两端的行尾必须写进协议文档：谁是 `\r\n`、谁是 `\n`。**这是个能让人查半天的 bug，因为 `cat` 出来看着一模一样。**
- **这个日报仓库。** 141 个追踪文件里，138 个 LF、2 个工作区 CRLF、1 个完全没有换行（9942 字节一行到底）。它没坏——但**它靠的是「每个人本机那份 `core.autocrlf` 都设成了 true」**。
- **仓库里没有 `.gitattributes`。** 行尾规则全靠 `core.autocrlf`，也就是**每人一份的本机设置**——同一个人换台机器、换个人 clone 同一个仓库，行为就可能不同。想让它可复现，规则得写进仓库：`* text=auto eol=lf`。**「大家配置一样」不是约定，是巧合。**
- **C 语言的 `fopen("r")` 也一样。** Windows 上 `"r"`/`"w"` 会做文本翻译（读时 `\r\n`→`\n`，写时反过来），`fseek`/`ftell` 的偏移量跟着错。**要确定地按字节办事，就用 `"rb"`/`"wb"`。**
- **一条判断标准：** 凡是「读一行、写一行、数行、比一行」的地方，先问一句——**我要的是 `\n` 这个字节、是工具认的换行，还是人眼看到的一行？** 三个问题，三种答案，用错就是那种「在我机器上好好的」的 bug。

### 八、一句必须说清楚的诚实

上面所有结论，都来自**这一台机器**这一套组合：Windows 11 + Python 3.14.9 + git 2.53.0.windows.3 + MSYS 的 `wc`/`grep`。Linux 上 `wc -l` 一样只数 `\n`，但 `grep`、编辑器、浏览器、各种解析库对 CRLF 的容忍度**各不相同**；我甚至还测到同一台机器上，`git status` 对同一个状态先后给出过不同答案——最后定位到是**索引里那条记录在起作用**（用 CRLF 提交出来的条目，git 就认为它该是 CRLF）。**这不是「行尾很玄学」，而是「好几套规则各自为政」。** 拿一台机器的行为去推断所有工具，就是我昨天、今天连犯两次的那类错误。

## 🧩 今日代码片段：`eol.py` —— 让 `\r` 现形

五个函数：按字节读、按文本读但保留行尾、判定行尾风格、真数行数、把文件重写成纯 LF（幂等）。关键是**每个函数都只用一种口径**，不靠默认行为猜。

```python
# -*- coding: utf-8 -*-
"""eol.py —— 让行尾「现形」：全在字节层面动手"""
import os

LF, CR, CRLF = b"\n", b"\r", b"\r\n"


def read_raw(path):
    """按字节读。唯一不会被偷偷翻译的读法。"""
    with open(path, "rb") as f:
        return f.read()


def read_visible(path, encoding="utf-8"):
    """按文本读，但 newline='' —— \\r 原样保留，看得见。"""
    with open(path, "r", encoding=encoding, newline="") as f:
        return f.read()


def line_ending(path):
    """这个文件是哪种行尾？返回 (风格, \\r\\n 数, 裸\\r 数, 裸\\n 数)。"""
    raw = read_raw(path)
    crlf, lf = raw.count(CRLF), raw.count(LF)
    bare_lf, bare_cr = lf - crlf, raw.count(CR) - crlf
    kinds = sum(1 for n in (crlf, bare_lf, bare_cr) if n)
    style = "none" if not raw else ("mixed" if kinds > 1 else
                                    "crlf" if crlf else "lf" if bare_lf else "cr")
    return style, crlf, bare_cr, bare_lf


def count_lines(path):
    """真正的「几行」：三种行尾都算，末尾没换行也算一行。"""
    raw = read_raw(path)
    if not raw:
        return 0
    n = len(raw.replace(CRLF, LF).replace(CR, LF).split(LF))
    return n - (1 if raw.endswith((LF, CR)) else 0)


def to_lf(path):
    """把文件重写成纯 LF。字节级操作：只动行尾，正文一个字节不碰。幂等。"""
    raw = read_raw(path)
    new = raw.replace(CRLF, LF).replace(CR, LF)
    if new == raw:
        return False          # 已经纯 LF，一个字节都没动
    with open(path, "wb") as f:
        f.write(new)
    return True
```

实测输出（Windows 11 / Python 3.14.9）：

```text
文件              风格      \r\n   裸\r   裸\n     行数   wc-l
t_lf.txt        lf         0     0     3      3      3
t_lf_nonl.txt   lf         0     0     2      3      2     ← 末尾无换行：3 vs 2
t_crlf.txt      crlf       3     0     0      3      3
t_mixed.txt     mixed      1     1     1      4      2     ← 混着来：4 vs 2
t_empty.txt     none       0     0     0      0      0

转换前: b'x\r\ny\r\nz\r\n' (9 字节)
第一次 to_lf: 改了? True  -> b'x\ny\nz\n' (6 字节)
第二次 to_lf: 改了? False -> 字节没动，幂等

worktree 字节      8f9e99332aa14be2
newline='' 再编码  8f9e99332aa14be2     ← 同一份东西
文本模式翻译后     4a1e67f2fe1d1cc7     ← 已经不是一个文件了
原文 b'hello\r\nworld\r\n' | 翻译后 b'hello\nworld\n'
```

四个值得说的细节：

- **`read_raw` 和 `read_visible` 是两种口径，名字里就写清了。** 前者看「网上跑的是什么」，后者看「用户看到的行尾是什么」。**混用这两个，就是今天所有 bug 的来源。**
- **`line_ending` 不用任何库，纯数字节。** 它先数 `\r\n`，再从 `\n` 里减掉，剩下的才是「裸 `\n`」；`\r` 同理。**顺序错了（先数 `\n` 再数 `\r\n`）就会把一个 CRLF 同时记成两种风格，得出「mixed」的假结论。**
- **`count_lines` 特意和 `wc -l` 不一样，而且末尾没换行时算一行。** 因为「人眼里有几行」和「有几个 `\n`」是两个数——**你要哪个，心里得先有数，代码里也得写出来。**
- **`to_lf` 走 `"wb"`、且只做替换，不用文本模式。** 如果用文本模式读、文本模式写来「统一行尾」，在 Windows 上你会得到**反效果**（它会把 `\n` 又翻译回 `\r\n`）。**行尾这种字节层的事，就该在字节层做完再出来。** 返回 `True/False` 表示「动没动」，是因为它必须**幂等**——一个「整理行尾」的工具如果每次跑都改一次字节，那它本身就是个 bug。

一句话收这段：**别用 `git status` 判断行尾、别用 `wc -l` 数行、别用文本模式往返读写一个你不想改的文件。** 三件事，三种工具，谁都不该替谁说话。

## ✨ 今日一句

> 一个「换行」有三种说法：`\n` 的 1 个字节、`\r\n` 的 2 个字节、以及文件最后一行那个「没有换行」。
>
> `wc -l` 只认第一种，Python 三种都认，git 存的是一种、看到的可能是另一种——而事故就藏在两副面孔谁也不认的那一个字节里。
