## 💭 技术随想：HTTP 代理与 CONNECT 隧道——一次 git push 失败的排障记录

今天 `git push` 突然报错：`Failed to connect to github.com port 443`。于是走了一遍教科书式的网络排障流程：`nslookup` 查 DNS（结果指向一个陌生的 IP，典型的解析污染）、`netstat` 看端口（本地代理没在监听）、`curl` 直连测试（连接被重置）——最后发现是本地代理进程没起来。整个过程其实都在和 **HTTP 代理的 CONNECT 隧道**打交道，值得把它讲清楚。

很多人以为代理是"中间人"转发明文，其实 **HTTPS 走代理依赖的是一个叫 CONNECT 的方法**：客户端先和代理建立 TCP 连接，然后发送一行 `CONNECT github.com:443 HTTP/1.1`，代理连上目标并回一句 `HTTP/1.1 200 Connection established`，之后这个连接就变成一条**透明的字节隧道**——客户端和 github.com 在里面直接做 TLS 握手。所以代理只看到"目标域名+端口"和一堆密文，这就是为什么走代理不需要给代理装证书（除非代理做 TLS 劫持，那才是真·中间人）。这条隧道正是墙内外"科学上网"的通用底座，理解了它，SS/VMess 这类协议只是换了条更隐蔽的隧道而已。

排障时顺手积累的几条经验：

- **代理配置有三层优先级**：环境变量 `http_proxy/https_proxy` → git config 的 `http.proxy`（又分 `--local/--global/--system`）→ 命令行 `-c` 临时覆盖。排查时先 `git config --get-regexp proxy` 看哪一层设了值——今天仓库 `.git/config` 里就残留着一个旧代理端口，这正是"网络通了 git 却连不上"的常见坑。
- **测代理最快的方式是 `curl -x`**：`curl -s -o /dev/null -w "%{http_code}" -x http://127.0.0.1:7890 https://github.com`，返回 200 就说明代理链路通了，不用先折腾 git。
- **区分三种失败**：`Connection refused`（端口没进程，代理没开）、`Connection timed out`（被防火墙丢包）、`Connection reset`（被主动重置，常见于直连被封锁的站点）。三种失败对应的排查方向完全不同。
- **`no_proxy` 别漏了**：公司内网环境加上 `no_proxy=localhost,127.0.0.1,.internal`，否则访问本机服务也会被绕去代理转一圈。
- **DNS 污染和 IP 封锁是两回事**：前者换公共 DNS（DoH）能解，后者只能走代理。`nslookup` 返回的 IP 和官方 IP 对不上，就是污染的信号。

**心法：** 网络问题永远先分层定位——是 DNS、TCP、TLS、代理还是应用配置？每排除一层，问题的位置就缩小一半。今天这个坑，本质就一句话：**代理没开，但 git 以为它开了。**

## 🧩 今日代码片段：代理探针 + 手工 CONNECT 握手

**① 一眼看懂 CONNECT 隧道长什么样（手工构造握手）：**

```python
import socket


def connect_tunnel(proxy_host, proxy_port, target_host, target_port=443, timeout=5):
    """通过 HTTP 代理对目标建立 CONNECT 隧道，返回隧道 socket 和代理的响应"""
    s = socket.create_connection((proxy_host, proxy_port), timeout=timeout)
    req = f"CONNECT {target_host}:{target_port} HTTP/1.1\r\n" \
          f"Host: {target_host}:{target_port}\r\n\r\n"
    s.sendall(req.encode())
    resp = s.recv(4096).decode(errors="replace")
    return s, resp


s, resp = connect_tunnel("127.0.0.1", 7890, "github.com")
print(resp.splitlines()[0])   # 期望输出: HTTP/1.1 200 Connection established
s.close()                     # 拿到这条隧道后，就可以在上面做 TLS 握手了
```

**② 批量代理探针——排障时用来快速找出"哪个代理端口是活的"：**

```python
import time
import urllib.request
import urllib.error

TARGET = "https://github.com"
CANDIDATES = ["http://127.0.0.1:7890", "http://127.0.0.1:7897", None]  # None 表示直连


def probe(proxy, target=TARGET, timeout=8):
    handler = {"http": proxy, "https": proxy} if proxy else {}
    opener = urllib.request.build_opener(urllib.request.ProxyHandler(handler))
    t0 = time.perf_counter()
    try:
        with opener.open(target, timeout=timeout) as resp:
            ms = (time.perf_counter() - t0) * 1000
            return f"✅ {proxy or '直连':<24} HTTP {resp.status}  {ms:.0f}ms"
    except urllib.error.HTTPError as e:
        return f"⚠️  {proxy or '直连':<24} HTTP {e.code}（通了但非 2xx）"
    except Exception as e:
        return f"❌ {proxy or '直连':<24} {type(e).__name__}: {e}"


for p in CANDIDATES:
    print(probe(p))
```

**实际运行输出（本机今天的状态）：**

```
HTTP/1.1 200 Connection established
✅ http://127.0.0.1:7890      HTTP 200  492ms
❌ http://127.0.0.1:7897      URLError: WinError 10061（端口无进程，拒绝连接）
❌ 直连                        URLError: timed out
```

**说明：**

- 片段①只用了标准库 `socket`，就把代理的核心机制演示出来了——`CONNECT` 请求成功后的 socket 就是一条透明隧道，TLS 层在隧道内正常工作，这就是 HTTPS 代理不需要装证书的原因。
- 片段②可以换成任意候选端口列表，几秒钟就能定位哪个代理可用、延迟多少；比在 git 里反复 `pull` 试错快得多。
- 如果隧道建立成功但 TLS 失败，问题就出在更上层（证书、SNI、目标端口被代理规则拦截），再往上查应用层即可。
- 排障工具箱里常备：`curl -x`、`netstat -ano | findstr 端口`、`git config --get-regexp proxy`，再加这份探针脚本，大部分代理类问题十分钟内能定位。
