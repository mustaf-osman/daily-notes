# 📅 2026年11月17日 日报

## 💭 技术随想：`is` 问的不是「一样」，是「同一个」

前两天分别量了「长度」和「一行」，今天轮到一个更根本的问题：**两个东西，到底什么叫「一样」？**

Python 给了两个运算符，一个问「是不是同一个」（`is`），一个问「是不是一样」（`==`）。以前我觉得这是语法课第一周的内容，直到我把这几件事实测了一遍：`257 is 257` 有时真有时假、`() is ()` 居然是真、删掉的对象会把 `id` 让给下一个、而 `1`、`1.0`、`True` 在同一本字典里会**互相顶掉**——`{1: 'int', True: 'bool', 1.0: 'float'}` 实测只剩一条。下面每个数字都是刚跑出来的（Windows 11 / Python **3.14.9** / win32）。

### 一、两个问题，`relation()` 一句话回答

先把「两个对象的关系」穷举成三种：**同一个对象**、**只是相等**、**两者都不是**。

```text
relation(257, 257)                  -> 同一个对象          ← 同一个常量被编译期合并了
relation(1000, int("1000"))         -> 相等，但不是一个对象
relation("a", "a")                  -> 同一个对象
relation("hello", "".join(["hel","lo"])) -> 相等，但不是一个对象
relation(nan, nan)                  -> 既不相等，也不是同一个
```

第二行和第一行是同一种「内建不可变数」——**为什么一个相同、一个不同？** 这就是今天全部内容的入口。

### 二、257 和 256 之间有一条线，但那不是承诺

CPython 预先造好了 `-5` 到 `256` 这些整数对象，运行时新建的小整数直接复用它们：

| 表达式（运行时各建一次） | 结果 |
|---|---|
| `int(str(-6)) is int(str(-6))` | **False** |
| `int(str(-5)) is int(str(-5))` | True |
| `int(str(-1)) is int(str(-1))` | True |
| `int(str(0)) is int(str(0))` | True |
| `int(str(255)) is int(str(255))` | True |
| `int(str(256)) is int(str(256))` | True |
| `int(str(257)) is int(str(257))` | **False** |
| `int(str(1000)) is int(str(1000))` | **False** |

**这条线在 `-5` 和 `256` 上**，一边缓存一边不缓存。但它**不是语言规定的**——它是 CPython 这个实现的选择。换个解释器（PyPy、MicroPython），结论可能就变了。

更绕的是**同一个代码块里的字面量**：

```text
257 is 257                        -> True      ← 同一份代码对象里的两个常量，编译期就合并成一个对象
eval("257") is eval("257")        -> False     ← 每次 eval 各自编译，两个对象，且 257 不在缓存里
eval("256") is eval("256")        -> True      ← 256 在缓存里，于是又「是同一个」了
a = 257; b = 257; a is b          -> True      ← 同一个代码对象里，同一份常量
```

所以「`257 is 257` 是 True 还是 False」这个问题，**答案取决于这两次 257 分别是谁造的**。写成一行比较，是真实代码里最容易骗人的地方——它现在对，只是因为这几个字面量恰好在同一个函数体里。

### 三、字符串驻留：也是「造它的人」说了算

```text
"hello" is "hello"                            -> True
("hel" + "lo") is "hello"                     -> True    ← 字面量拼接在编译期就算完了
"".join(["hel", "lo"]) is "hello"             -> False   ← 运行时拼出来的，是个新对象
sys.intern("".join(["hel", "lo"])) is "hello" -> True    ← 只有显式驻留，才是保证
"hello world!" is "".join(["hello"," world!"])-> False   （内容相等：True）
"hello_world"  is "".join(["hello","_world"]) -> False   （内容相等：True）← 就算是「标识符形状」也一样
```

规律是：**字面量（常量）会驻留，运行时拼出来的一律不驻留**。哪怕拼出来的字符串长得完全像变量名。

`sys.intern` 是唯一能靠的保证，但它有代价：被驻留的字符串是「不朽」的，**生命周期跟解释器一样长**——拿它去驻留成千上万条运行期拼出来的字符串，等于主动做一个永久内存泄漏。这行代码上一句还在修 bug，下一句就在造 bug。

### 四、`()` 是单例，`[]` 不是

```text
[] is []            -> False
{} is {}            -> False
set() is set()      -> False
() is ()            -> True
tuple() is ()       -> True
None is None        -> True
```

为什么空元组是单例？**因为它不可变**——里面没东西，也就没状态，全世界共用一份完全无害。相反，`[]` 和 `{}` 每建一个就多一份可变状态，绝不能共用。

（顺带：`id(())` 连着问两次完全相同，`id(()) == id(tuple())` 也是 True。）这条也是实现细节，但它解释了一个我一直没想通的习惯：**可变的东西不能被「保存下来再用」，只能每次新造**。

### 五、`id()` 会被回收再利用——这是今天最值钱的一条

```text
x = [1, 2, 3];  i1 = id(x)         -> 2172554414208
del x
y = [4, 5, 6];  i2 = id(y)         -> 2172554414208     ← 一模一样
i1 == i2 -> True            但 a_snapshot == y -> False
id([1]) == id([2])                -> True               ← 两个临时对象的 id「相同」
```

`id()` 是**这一段内存的地址**。对象一死，地址就被下一个对象接手。于是「两个 id 相同」**完全不能推出「是同一个对象」**——除非你确定前一个还活着。

我用这个做了个「按 id 缓存」的实操——这是真实项目里出现过很多次的写法：

```text
第一次: [1, 2, 3]    -> 6     现算            ← 缓存里记下 id -> 6
（对象被删掉，缓存条目还留着）
第二次: [10, 20, 30] -> 6     命中缓存         ← id 被复用了，拿到的是别人的答案
```

**注意它一声不响地给了个错误答案，还没报错。** 这就是这类 bug 最难的地方：没有异常、没有警告，只是一次「缓存命中」。修法只有两个方向——**要么按值当键**（`functools.lru_cache` 要求参数可哈希，就是在逼你这么做），**要么让缓存真的持有那个对象**（强引用 / `weakref.WeakValueDictionary`），别让 id 有机会被别人接手。

### 六、`True`、`1`、`1.0` 是同一把钥匙

```text
True is 1                        -> False      ← 身份不同
True == 1                        -> True
isinstance(True, int)            -> True
hash(True), hash(1), hash(1.0)   -> 1 1 1
```

**哈希相同、又相等，于是它们在字典和集合里就是同一把钥匙：**

```text
{1: 'int', True: 'bool', 1.0: 'float'}  -> {1: 'float'}
{0: 'int', False: 'bool'}               -> {0: 'bool'}
len({1, 1.0, True})                     -> 1
1 in {True}                             -> True
True in {1.0}                           -> True
[1] == [True]                           -> True
```

三条实用的推论：

1. **后写的值会覆盖先写的值，但键留下的是最早插入的那个对象。**（`{1:'int', True:'bool'}` 里键实测是 `int` 类型的 `1`，值是 `'b'`。）
2. **`"1"` 和 `1` 是两把钥匙，`1` 和 `true` 不是。** 实测 `"1" in {1: 'x'} -> False`，`1.0 in {1: 'x'} -> True`。所以一份 JSON 配置里如果 `{"threshold": "1"}` 写成了字符串，你拿整数 `1` 去查**就是查不到**；反过来如果有人往同一个键表里一会儿塞 `1` 一会儿塞 `True`，会**悄悄合并**。
3. 用自定义类当键时，规矩是「**哈希 + 相等**」，跟身份没关系：

```text
class K:  __hash__ 固定返回 1，__eq__ 永远返回 True
d[k1] = 'a'; d[k2] = 'b'   ->  表里还剩 1 条，取 k1 得到 'b'，取 k2 也得到 'b'
留下的键是最早插的那个对象吗 -> True
k1 is k2 -> False  但  k1 == k2 -> True
```

一个「跟谁都说相等」的对象，会在字典里把所有键吸成一条——**这是键盘表、缓存表里最省事也最危险的 bug**。

### 七、NaN：不等于自己，但能被「同一个」救回来

```text
nan1 == nan1                -> False      ← 连自己都不等于
nan1 is nan1                -> True       ← 但它当然是「自己」
hash(nan1), hash(nan2)      -> 169444936141  169444936137     ← 每个 nan 对象哈希都不同
t = (nan1,);  t == t        -> True
[nan1] == [nan1]            -> True       （同一个对象）
[nan1] == [nan2]            -> False      （两个不同的 nan 对象）
nan1 in [nan1]              -> True       |  nan2 in [nan1]  -> False
{nan1: 'a'}.get(nan1)       -> 'a'        |  {nan1: 'a'}.get(nan2)  -> 查不到
```

这里藏着一条我原来不知道的规则：**容器/字典比「相等」的时候，先比身份，再比值。** 所以 `[nan1] == [nan1]` 是 True（同一个对象，直接放过），而 `[nan1] == [nan2]` 是 False（不同对象，再比 `==`，结果 False）。同一个 nan 躺进字典里、又用**它自己**去查，是查得到的；换一个字面量新建的 nan 去查永远查不到。

**结论：判 NaN 只有 `math.isnan()` 一种正确问法。** 拿 `==`、拿 `in`、拿字典键去碰它，得到的都是「看起来像答案的巧合」。

### 八、`==` 会跑到别人的代码里去，`is` 不会

```text
class AlwaysEqual:  __eq__ 永远返回 True
w == None   -> True      ← 假的「相等」：一个对象宣称自己等于 None
w is None   -> False     ← 真的答案
w == 123    -> True
w in [1,2,3]-> True      ← in 和 == 都是这个对象的 __eq__ 说了算

class Strict:  __eq__ 直接抛异常
s is s      -> True
s == s      -> 抛异常: 别拿 == 比较我
```

`==` 是**调用方交给对方执行**的（`a == b` 可能跑 `a.__eq__(b)`，也可能跑 `b.__eq__(a)`），所以对方想让它是真是假都行，甚至可以让它直接炸。**判单例（`None` / `True` / `False` / 自己的哨兵）只能用 `is`**——`is` 不做调度，不跑任何用户代码，答案是确定的。

**再往前一步，`==` 的返回值根本不必是布尔**——我拿一个「`__eq__` 返回列表」的对象实测：

```text
class Fake:  __eq__ 返回 [True, False]
f == None    -> [True, False]   ← 不是 True 也不是 False，是个列表
f is None    -> False
if f == None: -> 进入分支        ← 非空列表按真值规则算「真」，于是走进了一个「明明不是 None」的分支
```

**它没抛异常、没报警告，就这么走错了分支。** 判单例（`None` / `True` / `False` / 自己的哨兵）只能用 `is`：`is` 不做调度、不跑任何用户代码、返回值永远是布尔，答案是确定的。

### 九、快慢只是顺带的

```text
5,000,000 次 is None : 140.1 ms
5,000,000 次 == None : 177.6 ms     倍数 1.27x

2,000,000 次（列表推导）: is 73.4 ms / == 86.2 ms
```

`is` 确实快一点，但**只有 1.27 倍**——如果哪篇教程告诉你「用 `is` 更快所以要换」，那是在拿一个不重要的理由做一个重要的决定。**选 `is` 的理由永远是语义（同一个 / 单例），不是性能。**

### 十、连解释器都劝你别这么写

跑第一版实验时，脚本自己吐了 7 条警告（第二版又 3 条）：

```text

SyntaxWarning: "is" with 'str' literal. Did you mean "=="?

```

而且**可以在编译期就把它变成硬错误**：


**解释器在警告一件事：用 `is` 比较字面量，本身就说明你在测试「实现细节」，而不是在写逻辑。** 这条警告想被 CI 当成错误挡下来，加一个 `-W error::SyntaxWarning` 就够了。

### 十一、对着手上的东西看

- **`rp_server` 的参数解析。** `arg is None` 是对的写法。如果某天换成一个「会重载 `__eq__`」的参数对象，`arg == None` 就会变成别的东西——**这个坑不报错，只是分支走错**。
- **「缺省」不能拿 `None` 当哨兵。** 用 `None` 表示「没传」，那「传了 None」就永远表达不出来。要区分这两种情况，就自己造一个：`MISSING = object()`，然后 `if x is MISSING`。**这不是风格问题，是「能不能表达」的问题。**
- **AT 报文和配置解析里的 `0` / `False`。** 板子回 `0`、App 回 `False`、配置文件写 `"0"`——`{0, False, "0"}` 在「相等」这件事上不是三个不同的东西。要是拿它们当字典键做「已处理」标记，实测会合并成两条。**解析入口把类型先钉死（要么全 `int`、要么全 `str`），别让它们有机会混在同一张键表里。**
- **任何「按 `id()` 缓存 / 去重」的代码。** `rp_server` 里如果有「对象 id -> 状态」的映射，一定要问一句：**这个对象在我查之前，会不会已经死了？** 会的话，id 会被下一个对象接手，你会拿到别人的值——**而且没有任何报错**。
- **`is` 用在哪、不用在哪，一条判断标准：** 只跟「世界上只有一份」的东西比——`None`、`True`、`False`、自己造的哨兵、以及模块级的单例。除此之外一律 `==`。**拿 `is` 比数值、字符串、容器，就是在赌实现细节。**

### 十二、一句必须说清楚的诚实

这十二条里，**只有「单个实例用 `is` 判」是语言层面能依赖的**。小整数缓存范围（-5..256）、字符串驻留、空元组单例、常量合并、容器比较的身份捷径、`hash(nan)` 的实现——**全都是 CPython 的实现细节**，换个版本、换个解释器就可能不一样。我上面每个数字都来自**这一台机器这一次运行**（Python 3.14.9 / Windows 11）；`is` 的答案甚至能因为「这段代码在同一个函数里还是分散在两行」而变化。**这不是「Python 很玄学」，而是「同一个问题有好几个层面：身份、值、哈希、缓存」——`is` 只回答第一个，`==` 只回答第二个。** 想清楚自己要问哪个，这十件事就都变成常识了。

## 🧩 今日代码片段：`identity.py` —— 分清「是不是同一个」

四个函数，每个只干一件事：一句话说清两个对象的关系；判断一个字符串是否已驻留；用**专属哨兵**区分「没有这个键」和「值是 None」；找出那些「类型不同却相等」的键。

```python
# -*- coding: utf-8 -*-
"""identity.py —— 分清「是不是同一个」和「是不是一样」"""
import sys


def relation(a, b):
    """一句话说清 a 和 b 的关系：同一个 / 只是相等 / 都不是。"""
    if a is b:
        return "同一个对象"
    try:
        equal = (a == b)
    except Exception as e:                     # __eq__ 自己会炸的对象
        return f"比较失败: {type(e).__name__}"
    if not isinstance(equal, bool):            # 返回数组之类的"不是布尔"
        return f"相等性给不出布尔: {type(equal).__name__}"
    return "相等，但不是一个对象" if equal else "既不相等，也不是同一个"


def same_value_copy(s):
    """造一个「内容一模一样、身份肯定不同」的字符串。"""
    return (s + "\x00")[:-1]


def is_interned(s):
    """这个字符串是不是已经在驻留表里那份？副作用：不在的话会把新副本塞进去。"""
    if not isinstance(s, str):
        raise TypeError("只对 str 问这个问题")
    probe = same_value_copy(s)
    return sys.intern(probe) is s


MISSING = object()                             # 专属哨兵，不是 None


def config_get(cfg, key, default=MISSING):
    """按 key 取值。用专属哨兵，才能区分「没这个键」和「值就是 None」。"""
    if key in cfg:
        return cfg[key]
    if default is MISSING:
        raise KeyError(key)
    return default


def colliding_keys(keys):
    """找出那些「类型不同却相等」的键——放进同一个 dict 里会互相顶掉。"""
    out = []
    for i, a in enumerate(keys):
        for b in keys[i + 1:]:
            if a is not b and a == b and type(a) is not type(b):
                out.append((a, type(a).__name__, b, type(b).__name__))
    return out


if __name__ == "__main__":
    print("-- relation --")
    print("257 与其副本:", relation(257, 257))
    print("1000 与 int('1000'):", relation(1000, int("1000")))
    print("'a' 与 'a':", relation("a", "a"))
    print("'hello' 与 join 出来的:", relation("hello", "".join(["hel", "lo"])))
    print("nan 与自己:", relation(float("nan"), float("nan")))

    print("-- is_interned --")
    print("字面量 'hello':", is_interned("hello"))
    print("运行时拼出来的:", is_interned("".join(["hel", "lo"])))
    print("拼的这份再问一次:", is_interned(sys.intern("".join(["hel", "lo"]))), "(已经驻留了)")

    print("-- config_get --")
    cfg = {"port": None, "name": "rp_server"}
    print("port =", config_get(cfg, "port"), "| 值真的是 None，但键在")
    print("bogus =", config_get(cfg, "bogus", "缺省"))

    print("-- colliding_keys --")
    keys = [1, True, 1.0, "1", 0, False, 2]
    for a, ta, b, tb in colliding_keys(keys):
        print(f"  {a!r}({ta}) == {b!r}({tb})  → 同一个字典里会互相顶掉")
    print("  直接塞进去看看:", {1: "int", True: "bool", 1.0: "float", "1": "str"})
```

实测输出（Windows 11 / Python 3.14.9）：

```text
-- relation --
257 与其副本: 同一个对象
1000 与 int('1000'): 相等，但不是一个对象
'a' 与 'a': 同一个对象
'hello' 与 join 出来的: 相等，但不是一个对象
nan 与自己: 既不相等，也不是同一个
-- is_interned --
字面量 'hello': True
运行时拼出来的: False
拼的这份再问一次: True (已经驻留了)
-- config_get --
port = None | 值真的是 None，但键在
bogus = 缺省
-- colliding_keys --
  1(int) == True(bool)  → 同一个字典里会互相顶掉
  1(int) == 1.0(float)  → 同一个字典里会互相顶掉
  True(bool) == 1.0(float)  → 同一个字典里会互相顶掉
  0(int) == False(bool)  → 同一个字典里会互相顶掉
  直接塞进去看看: {1: 'float', '1': 'str'}
```

四个值得说的细节：

- **`relation()` 里的 `try/except` 不是多余的。** `==` 可能抛异常（`Strict`），也可能返回非布尔（数组）。**一个「判断关系」的函数如果会被对方弄崩，那它就没资格叫判断函数。** 所以我把它降级成了一句「比较失败」，而不是让调用者去猜。
- **`is_interned()` 为什么要先造一个副本？** 因为直接 `sys.intern(s) is s` 恒为真（不在表里时它会把 `s` 自己塞进去再返回 `s`），测不出任何东西。只有拿一个**内容相同、身份不同**的新对象去问「表里那一份是不是原来那个」，才能得到真答案。**注意副作用：这一问会把副本永久留在驻留表里**——所以这函数是诊断用的，别放进热路径。
- **`MISSING = object()` 这一行是整个文件最实用的地方。** `object()` 不带任何 `__eq__`，只可能被 `is` 认出；`None` 则同时背着「缺省」和「值就是 None」两种含义。**能表达清楚的状态，就别用模糊的哨兵去替代。**
- **`colliding_keys()` 只挑「类型不同却相等」的**（加了 `type(a) is not type(b)`），因为「两个 int 相等」是正常业务，「`1` 和 `True` 相等」才是要报警的事。**报告一条真实存在的碰撞，比报告一堆噪音有用。**

一句话收这段：**`is` 回答「是不是同一个」，`==` 回答「是不是一样」，`hash()` 决定「它们在表里坐不坐同一个位置」。** 三个问题，三套规则，混着用就是那种「没有报错、只是答案不对」的 bug。

## ✨ 今日一句

> 大多数 bug 不是因为「答错了」，而是因为「问错了问题」。
>
> `is` 问的是「你是不是它」，`==` 问的是「你像不像它」——而 `1`、`1.0`、`True` 在字典里共用一个座位，`id` 会在原主人死后转交给下一个人。
