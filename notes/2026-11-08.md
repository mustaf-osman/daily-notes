# 📅 2026年11月08日 日报

## 💭 技术随想：你算的不是时间，是某个时钟的刻度

前几天在日志里看到一条心跳：周期设的 1 ms，实际打出来的间隔在 0 / 16 / 32 ms 之间跳。第一反应是 CPU 被抢了、或者 sleep 不准。查下去发现两件事都不对——**是我用来算间隔的那个时钟，根本没有 1 ms 的分辨率。**

这件事很值得记一笔。因为「计时」在代码里长得太人畜无害了：`now()`、`time.time()`、`elapsed = b - a`，看起来只是减法。但减法的两个操作数各有各的刻度，而刻度以下的真实经过时间，**不是被四舍五入，是被丢掉**。你以为在测 200 µs，实际上常常读到 0。

今天在本机把三个时钟量了一遍（Windows 11 / Python 3.11.15），每个数字都是真跑出来的。

### 一、三个时钟，三种刻度

同一台机器、同一个进程，`time` 模块给的三个「现在」：

| 时钟 | 读一次 | 最小步进 | 本质 |
|---|---|---|---|
| `time.time()` | 27 ns | **约 0.5 ms** | 墙钟，1970 起的秒数，会被校时改动 |
| `time.monotonic()` | 25 ns | **15.6 ms** | 单调，不回退，但在这台机器上**很粗** |
| `time.perf_counter()` | 53 ns | **100 ns** | 单调 + 最高精度，硬件计数器 |

注意第三行和第二行的对比：`perf_counter` 读一次贵一倍，刻度细 **15 万倍**。

这张表最反直觉的是第二行。很多文档会说「测耗时用 monotonic，别用 time.time，因为后者会被 NTP 改」。这句话是对的，**但它只说了「会不会跳」，没说「看不看得清」。** 在 Windows 上，CPython 的 `time.monotonic()` 底下是 `GetTickCount64()`——一个以系统 tick 计的毫秒计数器。实测对齐（ctypes 直接调 kernel32）：

```text
GetTickCount64=40226.015  time.monotonic=40226.015  diff=+0.000 ms
GetTickCount64=40226.015  time.monotonic=40226.015  diff=+0.000 ms
（5 次全为 0.000 ms，且两次读数之间值没变过）
QPC frequency = 10000000 Hz -> 100.0 ns/tick
```

而 `perf_counter()` 走的是 `QueryPerformanceCounter`，本机频率 10 MHz，**一步 100 ns**。所以「单调 → 用 monotonic」这个口诀在这里是错的：**要单调又要精度，用 perf_counter。**

### 二、看不见的 200 µs

拿一段已知长度、用 `perf_counter` 卡出来的约 200 µs 忙等，分别用三个钟去量它（各 200 次）：

| 量它用的钟 | 中位数读数 | 读到 0 的比例 | 最小非零读数 |
|---|---|---|---|
| 真实长度 | 200.2 µs | — | — |
| `time.time` | **0.0 µs** | 79% | 507 µs |
| `time.monotonic` | **0.0 µs** | **98%** | **15000 µs** |
| `time.perf_counter` | **200.2 µs** | 0% | 200 µs |

`time.monotonic` 那行最能说明问题：**98% 的测量结果正好是 0**，剩下 2% 一次跳到 15 ms。也就是说，用它测任何短于 15 ms 的东西，你拿到的不是一个带误差的数，而是「零，或者一个差了 75 倍的数」。**刻度以下的内容不是变模糊，是整块消失。**

补一句适用面：这不是「Windows 才有的毛病」。Linux 上 `CLOCK_MONOTONIC` 是纳秒级的，`time.monotonic()` 也就够用。**同一个函数名，在两个平台上差 6 个数量级**——所以「在我机器上是好的」这句话，跨平台时一文不值。

### 三、1 ms 节拍：中位间隔 0 µs，p99 是 16 ms

我照着那条第 4 节的写法复现了一下：用**该时钟自己**算 deadline、1 ms 一拍、跑 300 拍。

| 判超时用的钟 | 间隔中位数 | p1 | p99 | 最大 | 迟到（>1.5 ms） |
|---|---|---|---|---|---|
| `time.monotonic` | **0 µs** | 0 | 16 ms | 16 ms | **18 / 295** |
| `time.perf_counter` | 1009 µs | 397 | 1638 | 2140 | 7 / 295 |

`time.monotonic` 那个「中位 0 µs」不是 bug：因为 deadline 和现在用的是同一个粗刻度，`target - now` 经常算出**一个负数或零**，于是 `time.sleep(0)` 立刻返回，这一拍照样算「到点了」。**18/295 的拍子迟到超过 1.5 ms，还有一批拍子间隔是 0**——用这种节拍跑控制环，等于给系统喂了一串时间戳在抖的样本。上面那篇采样定理讲的东西会立刻接上：**时间戳抖，等于采样点在抖；采样点抖，等于你在做非均匀采样，而所有基于 FFT 的分析都默认它是均匀的。**

### 四、墙钟会跳，跳的方式有两种

用 1 kHz 的模拟循环跑 1 s 超时，在 0.4 s 时给时钟加一个 ±500 ms 的跳变：

| 跳变 | 墙钟版实际等待 | 单调版实际等待 |
|---|---|---|
| −0.5 s（校时往回拨） | **1.501 s** | 1.000 s |
| +0.5 s（校时往前拨） | **0.500 s** | 1.000 s |

两个方向都要命，而且**症状完全不同**：

- **往回拨 → 超时变长。** 逻辑上更危险：`while now < deadline` 会多转大半圈。如果这个循环里没有别的东西兜底，卡住的时间是「拨回去多少就多等多少」。表现是「偶发卡一下」，日志里什么都没记——因为它没报错，它只是在等一个已经过去又被拨回来的时刻。
- **往前拨 → 超时变短，甚至负数。** `deadline - now` 一夜之间变成负的，超时立即触发，所有重试逻辑同时认为「又超时了」。表现是一阵雪崩式的重试风暴。

真实系统里这种跳变不来自「有人手动改时间」，而来自 **NTP 校准、虚拟机快照恢复、容器迁移、RTC 电池没电冷启动**。前三个在云上和 RK3588 这类板子上都不罕见。

**所以规则很简单，但要说清边界：**

- 凡是问「**过了多久**」的（超时、心跳、节拍、重试间隔、耗时统计、速率）→ **单调钟**，且要够细 → `perf_counter` / `CLOCK_MONOTONIC_RAW`。
- 凡是问「**是哪一刻**」的（日志时间戳、文件名、文件 mtime、缓存过期、跟外部系统对时）→ **墙钟**，因为只有它跟别人对得上。
- **两者不要混着算。** `time.time() - monotonic()` 这个差值本身在漂，实测 3 秒内极差就到了 **15.2 ms**——正好是那个粗刻度加上墙钟刻度的台阶。用它当「时间基准」做减法，误差就是这个量级。

### 五、32 位的钟，1.2 小时转一圈

嵌入式这边更原始：给「现在」的常常只是一个自增计数器。

| 计数器 | 回绕周期 |
|---|---|
| 32 位微秒 | **1.193 小时** |
| 32 位毫秒 | 1193 小时（49.7 天） |
| 32 位 100 ns | **0.119 小时（7.2 分钟）** |

第一行和第三行不是理论值，是很多人踩过的坑：nRF5340/STM32 上拿一个 32 位 µs 计数做时间戳，**跑 72 分钟后回绕**；TI 的某些 100 ns 单元甚至 7 分钟一圈。

回绕本身不可怕（无符号减法照样对），真正会出事的是这三种写法：

- **有符号比较**：`if (int32_t)(now - last) > 0` 在回绕点前后翻符号，判定直接反掉。
- **直接比大小**：`if (now > deadline)`。回绕之后 `now` 立刻小于任何未来时刻，超时永不触发——和 NTP 往回拨是同一个症状。
- **µs 存进 float**：float32 只有 24 位有效位，在第 1677 万微秒（约 16.7 s）之后，`+1 µs` 就加不动了。**16.7 秒以后，计数器对你来说就停了。**

正确写法永远是 `(uint32_t)(now - last) >= span`，用无符号减法让回绕自己消掉，并且 **span 必须小于半圈**（对 32 位 µs 计数就是 35 分钟以内）。

### 六、`sleep` 从来不是「按时」

顺便把 `time.sleep` 也量了（各 200 次）：

| 请求 | 实际 p50 | p99 | 均值误差 | 超过 2 倍的次数 |
|---|---|---|---|---|
| 0.5 ms | **1.01 ms** | 1.77 ms | +0.55 ms | 21 / 200 |
| 1 ms | **1.53 ms** | 3.53 ms | +0.51 ms | 4 / 200 |
| 2 ms | 2.50 ms | 5.96 ms | +0.48 ms | 3 / 200 |
| 5 ms | 5.46 ms | 6.28 ms | +0.40 ms | 0 / 200 |
| 10 ms | 10.42 ms | 11.88 ms | +0.41 ms | 0 / 200 |

三句话：

1. **每次 sleep 都至少多睡半个 tick（约 0.5 ms）。** 这不是抖动，是偏置——恒定往一边偏。
2. **偏置会累积。** 一个「sleep(2ms) 再干活」的循环，200 拍下来：应 0.4000 s，实耗 **0.4748 s**，**漂了 19%**。跑到第 5000 拍，你的「1 kHz 采样」实际是 840 Hz。
3. **所以固定节拍不能靠 sleep 累加，要靠绝对 deadline。** 每次醒来重新看表、对齐到「第 i 拍应该开始的时刻」，误差就只跟最后一拍有关，不会滚雪球。

### 七、对着手上的东西看

- **`rp_server` 的心跳和超时**：心跳超时、UDP 重传、连接判活，全是「过了多久」。用 `time.time()` 算的话，RK3588 上只要 systemd-timesyncd 校一次时就可能触发一轮假超时。**换 `perf_counter`/`monotonic`，一个字的改动。**
- **控制链的时间戳**：App → UDP:9000 → `rp_server` → 虚拟手柄 → `joy_node` → `inference_node` → 电机。这条链上每一跳都在算「延迟」，如果各跳用的是不同精度的钟（比如 ROS 节点用 `rclpy` 的系统时间，脚本用 `time.time()`），**你量到的端到端延迟里混着两个钟的刻度差**。实测这个差在 3 秒内就能到 15 ms——比你想测的延迟本身还大。
- **ROS 2 的 `use_sim_time`**：一旦开了仿真时间，节点听到的是 `/clock` 话题，**它的时间会被发布者任意跳**（开机从 0 开始、暂停、快进）。那些用「时间戳差」做超时的节点，在仿真里表现正常、上真机反而出问题——因为真机上时间戳是单调的，仿真里不是。**反过来也一样。别让业务逻辑依赖「时间戳不会跳」这个假设。**
- **nRF5340 的定时器**：RTC 计数是 24 位（约 8 秒 @32.768 kHz，或按 prescaler 更长），`k_uptime_get()` 给的是 64 位毫秒、但要看你有没有把它塞进 32 位变量。**用 `k_uptime_get()` 而不是自己读 RTC 计数**，这是 Zephyr 已经替你处理过回绕的那一层。
- **日志时间戳**：用墙钟（要跟别人对得上），但「这条日志离上一条多久」要**另存一个单调时间**。两者都记，才有办法事后分清「系统卡了 300 ms」和「时钟被拨了 300 ms」——**这两种情况在只看墙钟的日志里长得完全一样。**
- **cron 任务**：它是墙钟驱动的，所以它会因为时区、夏令时、校时、机器休眠而漏跑或跑两次。这就是为什么定时任务里要记录「上次成功运行的时间」而不是假设「每次都会按时来」。
- **测试机是 Windows 的时候**：`time.monotonic()` 有 15.6 ms 台阶这件事，会让「在我本机跑得好好的」变成一句谎话。**测时间相关代码，先在目标平台上量一次刻度。**

一句话收今天：**「现在几点」和「过了多久」是两个问题，用两个钟；而「过了多久」这个问题，还要再问一句「你的钟看得见这么短吗」。**

## 🧩 今日代码片段：绝对 deadline 的固定节拍器

`Ticker`：用 `perf_counter` 做绝对 deadline，sleep 睡到「大致到点」再忙等最后一小段躲开 sleep 粒度，**迟到就丢拍、从当前时刻重新对齐，绝不补跑**。下面的输出是真跑出来的。

```python
# -*- coding: utf-8 -*-
"""tick.py —— 固定节拍器：绝对 deadline + 高精度单调钟 + 跳拍不补"""
import time


class Ticker:
    """period_s: 节拍周期；clock: 必须是单调且够细的钟。

    关键点只有三条：
      1. deadline 是「第 i 拍应有的绝对时刻」，不是「上一拍 + 周期」；
      2. 最后一段用忙等，躲开 sleep 的 tick 粒度；
      3. 迟到了就重新对齐，丢掉漏掉的拍 —— 控制环补跑等于让旧指令排队。
    """

    def __init__(self, period_s, clock=time.perf_counter):
        self.period = period_s
        self.clock = clock
        self.next_t = clock() + period_s
        self.tick = 0
        self.skipped = 0

    def wait(self):
        now = self.clock()
        if now < self.next_t:
            time.sleep(self.next_t - now)          # 粗睡
            while self.clock() < self.next_t:      # 精等（本机 100 ns 一格）
                pass
        else:
            # 迟到了：算清漏了几拍，然后把 deadline 挪到「现在 + 一拍」
            self.skipped += int((now - self.next_t) // self.period) + 1
            self.next_t = now + self.period
            return None
        self.next_t += self.period
        self.tick += 1
        return self.tick
```

实测（Windows 11 / Python 3.11.15）：

```text
--- 500 Hz 跑 200 拍 ---
实耗 0.4000 s（应 0.4000），拍数 200，迟到丢弃 0
间隔 µs: 中位 2009 | p1 1496 | p99 2501 | 最大 2518 | 标准差 189.8

--- 同样的 2 ms 节拍，用 time.sleep(0.002) 朴素写法 ---
实耗 0.4748 s（应 0.4000），累计漂移 +74.8 ms
间隔 µs: 中位 2487 | p99 2608 | 最大 2656

--- 故意卡 50 ms，看丢拍行为 ---
正常拍 60 个，因卡顿丢掉 50 拍，总耗时 0.222 s（不补跑）
```

四个值得说的细节：

- **总时长精确到小数点后四位（0.4000 对 0.4000 之外的 0.4748）。** 因为 deadline 是绝对的，每拍的「多睡 0.5 ms」在下一次对齐时被自动吃掉，误差不累积。这就是「绝对 deadline」和「相对 sleep」的全部差别：**一个是还债，一个是复利。**
- **抖动（标准差 190 µs）是躲不掉的，但它不累积。** 抖动和漂移是两个不同的病：抖动是「这一拍早一点晚一点」，漂移是「越跑越偏」。**实时控制怕的是漂移，而不是抖动**——抖动可以通过滤波和留余量吸收，漂移会把你的相位慢慢转过去。
- **`skipped` 要计数，不能静默。** 控制环里丢拍是允许的，但「丢了多少」是必须上报的指标。否则你会在某个现场发现「模型看到的 100 Hz 数据，其实是 60 Hz」，而没人知道是什么时候开始的。
- **忙等只等最后一小段（通常 < 1 ms）。** 全程忙等会把一个核吃满；全程 sleep 精度又不够。**用 sleep 熬过 95% 的时间，用忙等覆盖最后那 5%**——这是所有硬实时循环的标准配方。

再补一句为什么不用 `time.monotonic`：上面第一张表里它在这台机器上 15.6 ms 一格，`wait()` 里的 `while self.clock() < self.next_t` 会变成**一个转 15 ms 的忙等**（因为读数一格格跳），2 ms 的节拍直接塌成 15 ms 一拍。**换 `perf_counter` 之后，同一个循环 p99 从 16 ms 掉到 2.5 ms。**
