## 💭 技术随想：0.1 + 0.2 为什么不等于 0.3——计算机的"数法"和你不一样

打开 Python 敲一句 `0.1 + 0.2`，它会回你 `0.30000000000000004`。别急着怪 Python：换成 C、Java、JavaScript，答案一样会歪——这不是语言的毛病，而是 IEEE 754 标准划下的规矩，全世界统一执行。真相也不是"算错了"，而是 0.1 和 0.2 这两个数，计算机从一开始就存不下精确值：它拿到手时就各欠着一点账，加起来，欠账落在 0.3 旁边最近的一格上。

为什么存不下？回到小学：十进制里写 1/3 = 0.3333…，永远写不完，因为 3 除不尽 10。计算机用二进制，只认 2 的幂——分母是 2、4、8、16… 的分数才有"有限位"。而 0.1 = 1/10，分母 10 = 2×5，那个 5，就是二进制除不尽的"3"。于是 0.1 的二进制是 0.0001100110011…："1001"从第 5 位起无限循环，永远没有收尾。

写不完，可内存的格子是有限的：float64 只给 52 位尾数。怎么办？和你拿一把只有毫米刻度的尺子量 1/3 厘米一样——量不出精确值，就报一个离得最近的读数。存 0.1 时，计算机把无限循环的二进制截到第 55 位、在最末尾凑一次整，塞进去的实际是 0.1000000000000000055511151231257827021181583404541015625。看着离谱，但这确实是双精度内存里离 0.1 最近的那个数，误差约 5.6×10⁻¹⁸。

所以 `0.30000000000000004` 翻译成人话就是：0.1 的替身 + 0.2 的替身，落在 0.3 的替身旁边一点点。差值 5.55×10⁻¹⁷——恰好是这个数量级区间的一格（ULP），不多不少。浮点世界里没有"等于"，只有"离多远"：这句话不是修辞，是那行输出里的字面事实。

浮点数的位布局就是"二进制的科学计数法"——十进制里你写 1.23×10⁻⁴，二进制里它写 ±1.xxx×2^e。float64 = 1 位符号 + 11 位指数 + 52 位尾数（约 15~16 位十进制有效数字），float32 = 1+8+23（约 7 位）。这把尺子的刻度还不均匀：1 附近一格是 2.2×10⁻¹⁶，1e6 附近一格是 1.2×10⁻¹⁰，到 1e16 附近，一格粗到 2.0——只有偶数站得住，`1e16 + 1` 直接等于 1e16，那个 1 被吞了。float64 能"连号数数"的上限是 2^53（约 9×10¹⁵），float32 只有 2^24（1677 万）。MCU 上（比如 nRF5340 的硬件 FPU 只做单精度、double 靠软件模拟），“大整数转 float32”的坑多半就埋在 2^24 这条线附近：24 位计数值转得动，25 位就要出事。

误差还会攒、还会挑站位。1e6 个 0.1 挨个加，漂出 1.3×10⁻⁶；更戏剧的是顺序——`[1e16, -1e16, 1.0]` 得 1.0，`[1e16, 1.0, -1e16]` 得 0.0。1.0 的命运取决于它站在谁旁边：撞上 1e16 时那里只剩偶数格，它落在半格处，被"向偶取整"退了回去，从此消失。两剂解药：Kahan 补偿求和（每次舍入丢掉的"零头"记在账上，下一步补回来）和 math.fsum（精确舍入，与顺序无关）。

比表示误差更狠的是算法雷区：灾难性相消。sqrt(x²+1)−x 在 x=1e9 时直接算得 0.0——两个 16 位有效数字的数相减，前面 15 位一模一样、全部抵消，答案的可靠位数所剩无几；换成代数等价的 1/(sqrt(x²+1)+x)，5×10⁻¹⁰ 稳稳到手。同一个公式、数学恒等，数值上一个归零、一个完好——"重新配方"这门功夫，值钱就值在这里。

落到工程上的规矩其实不多：别用 == 比浮点（用 isclose 或容差）；钱用整数"分"结算（0.1 元 × 3 用浮点会得 0.30000000000000004，用分就是利落的 30 分）；大批量累加用 fsum / Kahan；要无损打印，float64 给 17 位、float32 给 9 位；NaN 用 isnan 判（它连自己都不等于自己，还会把碰过的整条计算链传染成 NaN）。

想想上一篇采样定理，其实是同一个故事的两面：采样定理说"有限张快照装不下连续世界"，浮点数说"有限的二进制格子装不下 1/10"——都被迫给出"最近的解释"，误差都从"表示能力有限"这四个字里长出来。理解刻度，就知道它哪里差、差多少、什么时候可控；剩下的事，就是别让关键判断（控制、对账、比较）站在这些误差上。

```python
def f32(x):
    """压成 float32（单精度）再取回来——模拟 MCU 里的 float 运算"""
    return struct.unpack("f", struct.pack("f", x))[0]


def bits64(x):
    return struct.unpack(">Q", struct.pack(">d", x))[0]


def bits32(x):
    return struct.unpack(">I", struct.pack(">f", x))[0]


def kahan(vals):
    """Kahan 补偿求和：替每次舍入开一本"零钱账"，最后统一找补"""
    s = 0.0
    c = 0.0
    for v in vals:
        t = s + v
        if abs(s) >= abs(v):
            c += (s - t) + v
        else:
            c += (v - t) + s
        s = t
    return s + c
```

```
    2^53 + 1 = 9007199254740992   ->  (2^53 + 1.0) == 2^53 ?  True
    1e16 + 1 = 10000000000000000   ->  == 1e16 ?  True

  float32（单精度，MCU 上的常客）：1 位符号 + 8 位指数 + 23 位尾数
    (float32)0.1 的位模式 = 0x3DCCCCCD
    (float32)0.1 的真身   = 0.100000001490116119384765625
    存 0.1 的误差：float64 = 5.551e-18，float32 = 1.490e-09（单精度约是双精度的 2.7e+08 倍 ≈ 2.7 亿倍）
    float32 连号整数上限 2^24 = 16777216：
      (float32)(2^24 + 1) = 16777216  ->  等于 2^24 ?  True

  嵌入式视角：nRF5340 这类 MCU 的硬件 FPU 只做单精度，double 是软件模拟（慢几十倍），
  所以控制/传感器代码里 float32 是主流——而它的尾数只有 23 位，刚过双精度的一半。

============================================================================
实验4：误差会攒起来——一百万次累加，外加'小值的命运'
============================================================================
  1e6 个 0.1 相加（模拟传感器长期积分/流水累加），参考值 100000.0：
    朴素循环 s += v        = 100000.00000133288
    Kahan 补偿求和         = 100000.0
    math.fsum（精确舍入）  = 100000.0
    与 100000.0 的误差：   朴素 +1.333e-06 | Kahan +0.000e+00 | fsum +0.000e+00

  10 个 0.1 的经典对照：
    sum([0.1]*10)        = 0.9999999999999999   == 1.0 ?  False
    math.fsum([0.1]*10)  = 1.0   == 1.0 ?  True

  小值的命运，取决于它站在谁旁边（同样的三个数，换个顺序换个结果）：
    [1e16, -1e16, 1.0]  先抵消掉两个大数，再 +1.0 → 1.0
    [1e16, 1.0, -1e16]  1.0 先撞上 1e16（只剩偶数格，落在半格处被退回）→ 0.0
    math.fsum 两种顺序都给出  1.0 / 1.0   （补偿算法不吃顺序的亏）

============================================================================
实验5：三个经典雷区
============================================================================
  ① 大数吃小数：相加前先'对齐指数'，够不着的小数位直接被挤出格子
     (1e16 + 1.0) - 1e16 = 0.0

  ② 灾难性相消：两个相近的大数相减，有效数字几乎清零
     sqrt(x² + 1) - x  （x = 1e9）：
       直接算：              0.0
       换个写法 1/(sqrt(x²+1)+x)： 5.000e-10
       精确值 ≈ 5e-10——同一个公式，数学上等价，数值上一个归零、一个完好。

  ③ NaN 六亲不认，连自己都不认：
     nan == nan       ->  False
     math.isnan(nan)  ->  True   （判断 NaN 只能用这个）
     inf - inf = nan，0.0 * inf = nan

============================================================================
实验6：正确姿势
============================================================================
  [√] 比较用 math.isclose：isclose(0.1+0.2, 0.3) -> True
      或手动容差：abs((0.1+0.2) - 0.3) < 1e-9 -> True
      （实际差值 = 5.551e-17；想要几位靠谱，容差就取到那一位）

  [√] 钱不用浮点，用整数（分）：
      0.1元 × 3 = 0.30000000000000004 元   ← 浮点版
      10分 × 3 = 30 分 = 0.30 元   ← 整数版，精确

  [√] 要无损打印浮点，17 位有效数字起步（双精度往返的最少位数）：
      repr(0.1)            = 0.1
      format(0.1, '.17g')  = 0.10000000000000001
      55 位全展开的真身     = 0.1000000000000000055511151231257827021181583404541015625
      17 位打印再读回，完整往返：float(format(0.1+0.2, '.17g')) == 0.1+0.2 -> True

一句话：浮点不是坏掉的十进制，而是'另一本数系'——懂它的刻度，才知道
        哪些数它给得起、哪些数它只能给你'最近的邻居'。
```

**说明：**

- **核心一句话**：0.1、0.2、0.3 在十进制里是有限小数，到了二进制全是无限循环小数（分母里带着一个 5）；内存只能存"最近的邻居"。0.1+0.2 = 0.30000000000000004 与 0.3 的差是 5.55×10⁻¹⁷ = 2⁻⁵⁴——恰好是那个区间的一格 ULP。这不是"乱错"，是"最接近策略"下的确定行为。
- **亲手可验的 55 位**：内存里的 0.1，二进制展开到第 55 位就"没了"（前导 3 个 0 + 52 位尾数 = 55 位）；而数学真值是"1001"无限循环、永远没有收尾。0.1 的 64 位真容 0x3FB999999999999A，按 1/11/52 拆开，能亲眼看到截断+凑整发生在哪一位。
- **两把尺子**：float32 存 0.1 的误差约是 float64 的 2.7 亿倍；连号数数的上限 2^24（1677 万）对 2^53（约 9×10¹⁵）；1e16 + 1 = 1e16。MCU 上（nRF5340 的 FPU 单精度硬算、double 软件模拟）优先整数/定点（Q 格式），关键计数别超过 2^24 再转浮点。
- **累加三对照**：朴素循环 1e6 次漂出 1.3×10⁻⁶；Kahan 补偿求和、math.fsum 全部归零。Kahan 的思路一句话：把每次舍入丢掉的零头记在账上，往后补回来。批量求和（统计、积分、流水对账）值得上 fsum。
- **顺序会改结果**：同样三个数，[1e16, -1e16, 1.0] → 1.0；[1e16, 1.0, -1e16] → 0.0（半格处被向偶取整退回）。fsum 两种顺序都给 1.0——补偿算法不吃顺序的亏。
- **灾难性相消**：sqrt(x²+1)−x 直算 0.0，改写 1/(sqrt(x²+1)+x) 得 5×10⁻¹⁰。看到"相近大数相减"先想换形式：分子有理化、配方（求根公式的稳定写法和方差的两遍法都是这么救回来的）。
- **打印三档**：repr = 最短且能往返（0.1 → '0.1'）；17 位 = 完整往返的安全位数；55 位 = 真身全展开。别用默认打印断案，也别让日志里"看起来相等"骗过比较。
- **NaN**：NaN != NaN，判断只能用 isnan；inf−inf、0×inf 都出 NaN；碰过的整条表达式全被传染。协议解析、数据校验层先想清楚它。
- **落地清单**：① 浮点比较一律走容差（isclose），容差至少高于 ULP 数个量级；② 批量累加用 fsum/Kahan，留意顺序敏感；③ 账目用整数"分"，不碰 float；④ MCU 上整数/定点优先，float32 盯住 2^24；⑤ 时间累计用整数 tick（呼应 9-17 那篇毫秒计数器），别拿浮点秒当积分器。

## ✨ 今日一句

> 计算机没算错 0.1 + 0.2：它只是只会说二进制，而 0.1 恰好是它说不出口的那个音——每一次，它都从给得起的数里挑了离你最近的邻居。误差从这里来，可控也从这里来。
