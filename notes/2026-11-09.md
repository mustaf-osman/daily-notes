# 📅 2026年11月09日 日报

## 💭 技术随想：`len()` 数的是字符，网线里跑的是字节

前天写定时器，说「你以为在测 A，其实在测 B」。今天这件事是同一个毛病的另一副脸：**你以为在数字符，其实在数字节；或者反过来。**

它在代码里长得极其无辜——`len(s)`、`s[:40]`、`if name == "张三"`。三个都是「一次就懂」的写法。但只要这段代码跟字节打过一次交道（串口、UDP、BLE、文件名、CSV、HTTP 头、定长协议字段），**「一个字符」和「一个字节」之间的那 2 倍差距，就会变成「字段被截成半个字」「名字查不到」「日志里全是娓╁害」。**

今天在本机（Windows 11 / Python 3.11.15 / 文件系统编码 utf-8）把这条链上的坑挨个量了一遍，数字都是真跑出来的。

### 一、两个长度，差 3 倍

同一个字符串对象，`len()` 给的是**码位数**，`.encode()` 给的是**字节数**：

| 字符串 | `len()` | UTF-8 字节 | GBK 字节 |
|---|---|---|---|
| `"abc"` | 3 | 3 | 3 |
| `"café"` | 4 | 5 | 5 |
| `"中文"` | 2 | **6** | 4 |
| `"한글"` | 2 | 6 | **编码不了** |
| `"🙂"` | 1 | **4** | **编码不了** |
| `"e" + U+0301` | **2** | 3 | 编码不了 |

三行就能看出问题的形状：

- **ASCII 是 1:1，所以「我本机测过没问题」永远是谎话。** 英文测出来的 `len(s)==len(s.encode())`，换成中文立刻变成 1:3。
- **同一个汉字，UTF-8 是 3 字节，GBK 是 2 字节。** 所以「按 40 字节切字段」这件事，在两种编码下能装的汉字数不一样——**而报文里不会写它用的是哪种编码**。
- 第三行那个 `é` 是**两个码位**（e + 组合尖音符），显示出来跟单个 `é` 一模一样，`len` 是 2 不是 1。这条后面单独说。

还有个更隐蔽的：`len()` 是 O(1)，`len(s.encode())` 是 O(n)。本机拿一个 5 MB 的字符串量了一下：**`len()` 单次 149 ns，`encode()` 单次 10.9 ms——差 7 万倍。** 所以别在循环里反复 `s.encode()` 求长度，那是在每帧里重新序列化一遍整段文本。

### 二、定长字段里装不下中文

协议里「定长 40 字节的用户名字段」看着很宽松。实测：

| 字段宽度 | ASCII 能装 | 汉字能装 | emoji 能装 |
|---|---|---|---|
| 16 字节 | 16 字 | **5 字** | 4 个 |
| 32 字节 | 32 字 | **10 字** | 8 个 |
| 40 字节 | 40 字 | **13 字** | 10 个 |

一个「40 字节」的字段，装得下 37 个字符的英文标识符 `"ZhangSan_2026_robot_arm_controller_v2"`，却只装得下 13 个汉字。而 `"东北大学通信工程2023级本科生"` ——16 个字、**恰好 40 字节，一个字节不剩**，再加一个字就直接溢出差错。

于是现场就出现两种经典现象：

1. **名字被截成半个字**——按字节切，最后一个汉字只剩前 2 个字节，解码直接抛异常，或者屏幕上多个 `�`。
2. **数据库里存进去的比界面上看到的短**——界面按「字符」给了 40 个字的输入框，后端按「字节」截到 40，用户看着自己输完了，存下来少一半。

**规则：凡是跨进程/跨设备传文本，长度一律以字节计，而且要在文档里写明编码。** 光写「字段长 40」是不够的，那个 40 在 ASCII 和 UTF-8 下是两个完全不同的容量。

### 三、66% 的截断点会炸，而 `ignore` 让你看不出炸过

拿一句真实的中文（`"温度传感器读数异常，请检查连接"` 重复 3 次，135 字节），把**每一个可能的截断位置**都试一遍：

```text
136 个截断点里有 90 个会抛异常（66%）
```

三分之二的截断点会 `UnicodeDecodeError: unexpected end of data`。这个比例不是巧合：中文 3 字节一个字，**随便一刀，只有 1/3 的概率正好落在字符边界上**。

而处理方式会决定这个 bug 是「立刻炸」还是「静默错」：

| 处理方式 | 结果 | 危险程度 |
|---|---|---|
| 直接 `decode()` | 抛异常，日志里看得见 | 低（吵，但诚实） |
| `errors="ignore"` | **静默丢掉那半个字**，长度对不上，没人知道 | **高** |
| `errors="replace"` | 留一个 `�`，至少肉眼能看出 | 中 |
| 按字符边界截断 | 正确 | — |

实测 `decode("utf-8", "ignore")` 把 19 字节切成 `'温度传感器读'`——**看起来完全正常的一句话，只是最后一个字没了。** 这种 bug 在上层不会报错，只会表现为「字段偶尔少一个字」，然后在三个月后变成一句「有时候名字显示不全，偶发」。

### 四、UTF-8 能自同步，GBK 不能

看一下真实的字节形状：

```text
温   E6 B8 A9      lead=11100110
度   E5 BA A6      lead=11100101
A    41            lead=01000001
🙂   F0 9F 99 82   lead=11110000
b    62            lead=01100010
```

UTF-8 的规矩是硬的：

- `0xxxxxxx` → 1 字节（ASCII）
- `110xxxxx` → 2 字节开头
- `1110xxxx` → 3 字节开头
- `11110xxx` → 4 字节开头
- `10xxxxxx` → **只能是后续字节，永远不会出现在字符第一位**

最后那条就是「自同步」：**任何一个高位是 `10` 的字节，必定是某个字符的尾巴。** 所以哪怕你从流的中间开始读，也能在一两个字节内重新对齐——这正是 UTF-8 在无帧边界的串口流上还能救回来的原因。

**GBK 没有这个性质。** 它的首字节是 `0x81–0xFE`，尾字节是 `0x40–0x7E` 和 `0x80–0xFE`——**尾字节范围里包含 ASCII 的 `A`、`0`、`|`。** 意思是：一个孤立的、看起来像 ASCII 的字节，可能只是上一个汉字的半个身子。于是：

- 「遇到 ASCII 就当帧头」在 GBK 文本里会切错；
- `0x7C`（`|`）作为分隔符，在 GBK 里也可能是某个汉字的第二字节——用 `|` 拼协议在中文环境下是个真坑；
- 丢了一个字节之后，**后面的全部错位，而且错位后依然「合法」**，能一路解出满屏乱码而不抛一个异常。

### 五、乱码不是异常，是「解码成功」

这条最要命。把 UTF-8 的中文按 GBK 解，实测：

| 原文 | UTF-8 字节 | 当 GBK 解出来 |
|---|---|---|
| 温度 | `e6b8a9 e5baa6` | **娓╁害** |
| 连接 | `e8bf9e e68ea5` | **杩炴帴** |
| 数据 | `e695b0 e68dae` | **鏁版嵁** |
| 中文 | `e4b8ad e69687` | **涓�鏂�** |

如果你在 Windows 的 cmd、某个国产串口助手、或者老版本的日志系统里见过「娓╁害」「鏁版嵁」这种字——**那不是玄学，就是 UTF-8 的字节被当 GBK 解了。** 而且注意最后一行：`涓` 后面跟了个 `�`，因为 `0xAD` 在 GBK 里是非法尾字节，**只有 3/4 的行会抛异常，还有一部分会「完全成功地」解成一堆合法但没意义的字。**

更狠的是 `latin-1`：

```text
utf-8 片段 b'\xe4\xb8\xad\xe6'
  utf-8    -> UnicodeDecodeError: unexpected end of data
  gbk      -> UnicodeDecodeError: illegal multibyte sequence
  latin-1  -> 'ä¸\xadæ'      回编码一致: True
```

**`latin-1` 能把任意字节流解成字符串，且再编码回来一模一样。** 所以「我的代码没抛异常」这个信号，对它毫无意义。

**结论：靠 try/except 检测编码错误，只能在「错得离谱」时救你；错得「不太离谱」时，它一声不响。** 判断编码只能靠外部信息（协议文档、BOM、HTTP 的 `Content-Type`、或者明确的配置项），不能靠猜。

### 六、看起来一样的两个字

```text
'café'  vs  'café'      ← 屏幕上完全一样
len 4 vs 5 | == False
bytes b'caf\xc3\xa9'  vs  b'cafe\xcc\x81'
```

左边是 `é`（U+00E9，一个码位），右边是 `e` + U+0301（组合尖音符，两个码位）。**看起来一模一样，比较不相等，长度差一，字节完全不同。**

后果是三种非常难查的 bug：

- **字典查不到**：`users["café"]` 和你手里的 `"café"` 是两个键；
- **去重失效**：同一个名字在数据库里存了两条；
- **定长字段超长**：界面上 40 个字，字节数多出几个。

修复只有一句：**在入口处做规范化**，`unicodedata.normalize("NFC", s)`。实测 NFC 之后两者相等（`True`）。

还有一层 NFC 管不了的：**全角/半角**。`"ＡＢＣ１２３"` 里每个字符都是全角码位，`==` 比较、`.lower()`、正则 `[A-Z0-9]` 全部不认。要 `NFKC` 才会折叠成 `'ABC123'`。手机输入法、Excel 粘贴、微信转发——全角字符混进配置文件的概率比想象中高得多。

顺便说个不可能靠规范化解决的：**排序**。`sorted(["张三","李四","王五","阿明","赵六"])` 出来的首字顺序是 `张李王赵阿`——按 Unicode 码位排的。想要拼音序得 `locale.strxfrm` 或者 pypinyin，**默认的字符串比较和「中文排序」根本不是一回事。**

### 七、两个小坑，各占一行

**换行。** 同样写 `"a\nb\nc"`（5 个字符）：

```text
mode w   磁盘字节数 = 7
mode wb  磁盘字节数 = 5
```

Windows 的文本模式把 `\n` 悄悄换成 `\r\n`。所以「文件里 5 个字符」和「文件 7 字节」可以同时成立，算偏移量、算协议长度、算校验和的时候，**用文本模式读进来的长度和实际字节数差了几个字节**。

**内存。** `sys.getsizeof`：`'a'`=50、`'中'`=76、`'🙂'`=80。CPython 3.3 之后按「最宽的字符」选紧凑表示，一个字符串里混进一个 emoji，整串都按 4 字节/字符存——**100 万个汉字里插一个 emoji，内存从 2 MB 涨到 4 MB。**

### 八、对着手上的东西看

- **`rp_server` 的 JSON/UDP 报文**：`AT+HEAD=<pan>,<tilt>` 这类命令是纯 ASCII 的，没问题；但只要有一个字段会带中文（设备名、备注、错误消息），**长度校验就必须按字节算**，且要在 `encode()` 之后量。
- **串口/蓝牙读数据**：一次 `read()` 回来的东西可能断在字符中间。**用 `codecs.getincrementaldecoder`，不要对每个包单独 `decode()`。** 今天实测：20800 字节切成 5273 个随机小包，朴素写法失败 **4592 次**、只剩 **1207/7600** 个字符（还原率 16%）；增量解码器 0 失败、7600 字符全对，而且更快（5.4 ms vs 6.9 ms，省掉了异常的开销）。
- **定长字段（BLE、CAN 载荷、老式文本协议）**：写 `pad_field()` 那样的函数，按字节补齐/截断，**永远不要用 `s[:40]` 切可能含中文的字符串**。补空格后解析回来记得 `rstrip`，但别 `strip` 掉正文里的空格。
- **nRF5340 / Zephyr 的日志**：`LOG_INF` 里带中文，一条日志的字节数会比字符数大 3 倍，日志缓冲区（默认很小）会提前截断——表现是「中文日志到最后总缺一块」。
- **Obsidian 文件名 / 双链**：macOS 存文件名用 NFD，Windows 和 Linux 用 NFC。同一个「café.md」跨机器同步过来，可能变成两个文件或者链接点不开。**这是规范化的锅，不是同步软件的锅。**
- **`sorted` 里放中文**：想按拼音排就别用默认比较，默认是码位序。
- **和微信/Excel 交互的 CSV**：GBK、UTF-8、UTF-8 带 BOM 三种都有人给。Excel 打开 UTF-8 CSV 不乱码的唯一稳妥办法是**加 BOM**（`utf-8-sig`）；反过来，读别人给的文件时**先看前 3 个字节是不是 `EF BB BF`**。

一句话收今天：**字符是给人看的单位，字节是给机器传的单位。中间那层转换，编译器不会提醒你，运行时也只在「错得够离谱」时才吭声。**

## 🧩 今日代码片段：`bytestext` — 三个必须按字节处理的函数

一个 30 行的模块，解决上面三类事故：安全截断、定长字段、流式解码。下面的输出是真跑出来的。

```python
# -*- coding: utf-8 -*-
"""bytestext.py —— 按字节处理文本：安全截断 / 定长字段 / 增量解码"""
import codecs


def truncate_bytes(s: str, limit: int) -> str:
    """按 UTF-8 字节数截断，绝不切在多字节字符中间。

    只丢掉「装不下的那半个字」，前面的内容一个不坏。
    """
    raw = s.encode("utf-8")
    if len(raw) <= limit:
        return s
    return raw[:limit].decode("utf-8", "ignore")


def pad_field(s: str, width: int, pad: bytes = b" ") -> bytes:
    """定长字段：长度恰好 width 字节，永远不超、永远不断字。"""
    body = truncate_bytes(s, width).encode("utf-8")
    return body + pad * (width - len(body))


class TextStreamDecoder:
    """串口 / TCP 分片喂进来，一个汉字被拆在两个包里也不会炸。

    朴素做法是对每个包单独 decode()，断在字符中间就抛异常或者丢字；
    增量解码器会把「没拼完的那半个字」留在内部，等下一个包补上。
    """

    def __init__(self, encoding: str = "utf-8"):
        # errors="replace"：遇到真的非法字节留一个 �，而不是抛异常打断整个流
        self._d = codecs.getincrementaldecoder(encoding)(errors="replace")

    def feed(self, chunk: bytes) -> str:
        return self._d.decode(chunk)

    def flush(self) -> str:
        """流结束时调用：把内部残留的半个字符吐出来（会成为 �）。"""
        return self._d.decode(b"", final=True)
```

实测（Windows 11 / Python 3.11.15）：

```text
[1] 定长 32 字节字段
   id    b'\xe6\xb8\xa9\xe5\xba\xa6\xe4\xbc\xa0\xe6\x84\x9f\xe5\x99\xa8-01              ' len=32 (应 32)
   name  b'\xe4\xb8\x9c\xe5\xa4\xa7\xc2\xb7\xe9\x80\x9a\xe4\xbf\xa1                  ' len=32 (应 32)
   note  b'OK                              '                          len=32 (应 32)

[2] 原文 7600 字符 / 20800 字节，切成 5273 个随机包（1~7 字节）
   朴素 decode : 失败 4592 次，还原 1207 字符，不一致，耗时 6.9 ms
   增量 decoder: 失败 0 次，还原 7600 字符，一致，耗时 5.4 ms

[3] 喂 b'\xe4\xb8\xad\xe6' -> '中' （看不见的那半个字被留住）
   再喂剩下的 1 字节    -> '文' （拼回来了）

[4] 136 个截断点里有 90 个会抛异常（66%）
```

四个值得说的细节：

- **`truncate_bytes` 的第二行是全函数的重点：`if len(raw) <= limit: return s`。** 没超长就原样返回，不重新构造——省一次编码，也避免把「本来就合法」的字符串又过一遍水。
- **`errors="ignore"` 在这里是安全的，因为在别处都危险。** 区别在于：截断这个场景我们**故意**只丢最后一个残字；而「把收到的整段字节解成文本」这个场景用 `ignore`，就是静默丢数据。同一个参数，两种语境，判断标准是「丢的是不是已知的那一个」。
- **`pad_field` 返回 `bytes` 而不是 `str`。** 定长字段最终是要写进报文/文件里的，返回 `str` 会诱使调用方再 `.encode()` 一次，而那次编码可能换编码、可能加 BOM——**在边界上，类型本身就是文档。**
- **增量解码器比朴素写法还快（5.4 vs 6.9 ms）。** 抛 4592 次异常的成本，比维护一小块内部缓冲贵得多。**「更正确的写法通常也更快」这件事，在字符串和异常上经常成立。**

再补一句为什么不自己实现「找到最后一个字符边界」：手写循环判 `0x80 <= b < 0xC0` 看着简单，但漏掉 4 字节字符、漏掉非法首字节的处理，就会在 emoji 上翻车。**标准库已经把「不完整序列」这件事建模成状态机了，用它。**
