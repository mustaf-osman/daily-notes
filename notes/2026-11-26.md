# 📅 2026年11月26日 日报

## 💭 技术随想：一个时钟不够 —— `time.time()` 会跳，`monotonic` 不会

起因是一段很短的日志。一个控制循环本该每帧跑 5 毫秒，日志里却出现了一帧 `-2731 ms`，还有一帧 `60012 ms`。没有崩溃、没有重启，程序自己从头跑到尾。查到最后不是代码的问题：**中间机器跟 NTP 对了一次表，把时钟往回拨了 2.7 秒，又往前跳了 60 秒。** 我的「耗时」是用 `time.time() - t0` 算的，而那两行日志量的根本不是耗时，是「墙上那个数字变了多少」。

**「现在几点」和「过了多久」是两个问题，需要两个不同的钟。** 前者要能对得上日历、要能被校准，所以它必须允许被拨动；后者要保证只往前走、谁都不许动它，所以它干脆不代表任何日期。今天把这件事在这台机器上从头跑了一遍（Windows 11 / AMD64 / Python **3.14.9**），下面每个数字都是刚打出来的。

### 一、这台机器上有五个「现在」，分辨率差一倍还多

连续取 20 万次，记下「最小非零增量」和「出现过多少个不同的值」：

```text
time.time              min delta = 2.384185791015625e-07   distinct/200k = 199999
time.monotonic         min delta = 1.9999424694105983e-07  distinct/200k = 200000
time.perf_counter      min delta = 1.9999424694105983e-07  distinct/200k = 200000
time.time_ns           min delta = 100                      distinct/200k = 200000
time.perf_counter_ns   min delta = 100                      distinct/200k = 200000
```

三件事一眼可见：

- `time.time()` 的最小台阶是 **238 ns**，而 `time.time_ns()` 是 **100 ns**——**同一个时钟，返回 float 的那版比返回 int 的那版粗了近 2.4 倍。**
- `time.monotonic()` 和 `time.perf_counter()` 在这台机器上数值一模一样（下面会说为什么）。
- 20 万次里 `time.time` 只出现过 199999 个不同的值，撞了一次——因为它的台阶比采样间隔还粗。

操作系统到底提供了什么，`get_clock_info` 说得明明白白：

```text
time          : GetSystemTimePreciseAsFileTime()  monotonic=False  adjustable=True   resolution=1e-07
monotonic     : QueryPerformanceCounter()          monotonic=True   adjustable=False  resolution=1e-07
perf_counter  : QueryPerformanceCounter()          monotonic=True   adjustable=False  resolution=1e-07
process_time  : GetProcessTimes()                  monotonic=True   adjustable=False  resolution=1e-07
```

关键在 **`adjustable`** 这一列。`time.time()` 是唯一一个 `adjustable=True` 的——**它是唯一一个允许被别人改的钟。** 也正因为它是唯一一个能被校准、能对得上日历的钟（另三个连「今年是哪年」都不知道）。

### 二、`time.time()` 的精度不是操作系统给的，是 float 给的

这是今天最漂亮的一条，我原来一直以为 `time.time()` 的分辨率就是系统时钟的分辨率。实测：系统给的 `resolution` 是 `1e-07`（100 ns），可 `time.time()` 的最小增量是 `2.384185791015625e-07`。**为什么差了 2.38 倍？**

因为 `time.time()` 返回的是 **float**，而 float 在 `1.79e9` 这个量级上，相邻两个可表示数之间就只有这么宽：

```text
now          = 1795654969.7889245
log2(now)    = 30.74          -> 指数位是 30，尾数 52 位
ulp          = 2**(30-52) = 2**-22 = 2.384185791015625e-07
math.nextafter(now, inf) - now = 2.384185791015625e-07       ← 实测同一个值
ulp == 实测最小增量 ?  True
time.time() 每秒最多能分辨 1/ulp = 4194304 个格子
```

**`time.time()` 现在的精度上限是 2⁻²² 秒，由 float 的尾数决定，跟硬件无关。** 现在是 4,194,304 格/秒；再等 8 年（秒数翻倍到 2³¹），ulp 也翻倍，只剩两百万格/秒。这不是 bug，是「用一个 53 位有效数字的数去装一个已经用了 31 位的整数部分」的必然结果——和 11 月 23 号那篇里「float 存纳秒时间戳会抖 256 ns」是同一个病根：

```text
time.time_ns() 现在 = 1795655062254917600
2**53 = 9007199254740992  ->  float 能精确表示的整数上限
2**53 ns = 9.007e6 秒 = 104.25 天          ← float 只能精确装下「纪元后 104 天以内」的纳秒
ulp(float(ns)) = 256.0 ns                  ← 现在的纳秒戳存进 float，台阶是 256 ns
```

**结论很直白：要精度就返回 int 的 `*_ns`，要「几点」就用 `time.time()`，但别指望它比 238 ns 更细。**

### 三、`sleep()` 只会睡长，从来不会睡短

请求的时长和实际睡出来的时长，各采样 200 次：

| 请求 `sleep(x)` | 实际中位 | 实际最小 |
|---|---|---|
| 0（让出时间片） | 0.001 ms | 0.001 ms |
| 0.0001 s | 0.631 ms | 0.430 ms |
| 0.001 s | 1.636 ms | 1.061 ms |
| 0.005 s | 5.526 ms | 5.115 ms |
| 0.01 s | 10.529 ms | 10.109 ms |
| 0.05 s | 50.635 ms | 50.123 ms |

两件事：

- **请求 0.1 ms，实际睡了 0.63 ms——多出 6 倍，全是没有要求的那部分。** 越短越不准，因为「醒过来」这件事本身要走一遍调度器，那段时间不归 `sleep` 管。
- **最小值和请求值之间总有一个固定开销**（0.001 请求 → 最小 1.061，多出 0.06 ms；0.05 请求 → 最小 50.123，多出 0.123）。这个「多出来的零头」才是 `sleep` 的真实代价。

所以「`sleep(0.001)` 循环 1000 次就是 1 秒」这种写法永远偏慢——这次实测偏了 60% 以上。要精确的固定频率，得用**绝对时间点**推下一次该醒的时刻（`deadline += period`），而不是「每次睡一小段」：

```text
错误：每帧 sleep(5ms) -> 误差累加，漂移肉眼可见
正确：下一帧的 deadline = 上一帧 deadline + 5ms，sleep 到点为止
```

### 四、三个钟各管一件事，别混用

| 钟 | 单调? | 可调? | 起点有意义? | 用来干什么 |
|---|---|---|---|---|
| `time.time()` | 否 | **是** | 是（Unix 纪元） | 打日志时间、落盘的时间戳 |
| `time.monotonic()` | 是 | 否 | **否**（任意） | 超时、间隔、测量时长 |
| `time.perf_counter()` | 是 | 否 | 否 | 基准测试、性能计时（最高分辨率） |
| `time.process_time()` | 是 | 否 | 否 | 只算 **CPU 时间**，不算等待 |

`monotonic` 和 `perf_counter` 在前三列完全一样，区别只在**用途约定**：`perf_counter` 是给你「测性能」用的，保证在可用时钟里分辨率最高；`monotonic` 是给你「算间隔」用的。在 Windows 上两者底层都是 `QueryPerformanceCounter()`，所以数值一模一样（上面那张表也印证了）。**在 Linux 上它们才分成两组：`monotonic` 走 `CLOCK_MONOTONIC`，`perf_counter` 也走它，但 `process_time` 走 `CLOCK_PROCESS_CPUTIME_ID`——这条来自文档，今天这台 Windows 没法验。**

最直观的差别是 `process_time`：

```text
忙循环 300 万次:  墙钟 0.6006 秒  |  CPU 时间 0.5938 秒        ← 几乎相等：CPU 一直在干活
sleep(0.3)   :   墙钟 0.3008 秒  |  CPU 时间 0.0 秒           ← CPU 一点没干
```

**`sleep(0.3)` 的「CPU 时间」是 0。** 因为睡觉期间 CPU 不在为这个进程干活。所以「这个函数耗了多少 CPU」和「这个函数花了多久」是两个数，量错了会得出完全相反的结论：一个大部分时间在等 IO 的函数，用墙钟看是「慢」，用 CPU 时间看可能是「几乎不费资源」。

还有一条要记住：**`monotonic` 的值没有意义。** 这台机器现在是 `50506.6`——

```text
time.monotonic() = 50506.6229269      ← 只能跟「另一个 monotonic 读数」相减
time.time()      = 1795654970.690666  ← 能换成 2026-11-26
机器醒着: 14:03:04
```

`50506` 秒除以 3600 是 **14 小时**——从开机到现在。**别拿它去存数据库、别拿它当 ID、别指望它跨重启还是同一个量。** 它是「这一觉睡了多久」，不是「现在几点」。

### 五、拿墙钟做超时、做锁、做心跳，是定时炸弹

回到开头那个 bug。用墙钟做超时的形状长这样：

```python
t0 = time.time()                 # 开始
while True:
    if time.time() - t0 >= 10:   # 「超过 10 秒就超时」
        break
    do_work()
```

只要中间发生一次 NTP 校时（或者运维手动改表、或者虚拟机快照恢复），这个时间差就会瞬间变成一个跟真实经过时间无关的数。模拟一遍（把钟在第 5 步往前拨 60 秒）：

```text
第 5 步就判定超时（真实只过了不到 2 秒）
```

**程序「多等 10 秒」这个意图，被一次校时变成了「立刻放弃」。** 反过来把钟往回拨，超时会永远不触发——一个挂死的任务在你眼里是「还在正常跑」。

同样的病会出现在所有「用时间戳表达先后」的地方：

- **租约/锁的过期时间。** 用墙钟存 `expire_at = time.time() + 30`，机器一校时全乱。
- **`cache` 的 TTL。** 往回拨表，缓存永远不过期；往前跳，缓存被瞬间清空。
- **限流 / 令牌桶。** 「每秒最多 N 个」如果按墙钟秒算，一次校时就能让整秒的额度凭空多出来或消失。
- **CAN / 传感器时间戳的差值。** 如果时间戳来自 `time.time()`，跨校时的两帧差值是假的。

**规矩只有一条：凡是「过了多久」的问题，一律 `time.monotonic()`；凡是「哪一刻」的问题，才用 `time.time()`。** 超时、间隔、重试退避、心跳间隔、测耗时——全是前者。

### 六、`datetime` 的坑：看着相等的两个时刻，差了 3600 秒

这一条是今天最反直觉的。美东 2026-11-01 是夏令时结束的日子，凌晨 2:00 回拨到 1:00，于是 **01:30 这个钟点出现了两次**——一次在 EDT（-04:00），一次在 EST（-05:00）。`datetime` 用 `fold` 区分它们：

```text
fold=0 : 2026-11-01 01:30:00-04:00 | 时间戳 1793511000.0
fold=1 : 2026-11-01 01:30:00-05:00 | 时间戳 1793514600.0
UTC    : 2026-11-01 05:30:00+00:00 vs 2026-11-01 06:30:00+00:00
时间戳差 3600.0 秒
```

但接下来这行值得盯着看：

```text
amb == amb.replace(fold=1)  ->  True          ← 说是相等
两者的 timestamp() 差        ->  3600.0 秒    ← 差了一小时
```

**`==` 给你 `True`，时间戳告诉你差了一小时。** 原因是：两个 aware datetime 如果 `tzinfo` 是**同一个对象**，Python 比较时**只比墙上钟面（年/月/日/时/分秒），根本不看 `fold`**。所以同一个钟点的两个瞬间被判成了「相等」。

这直接埋了一个 bug：**用「本地钟点」做去重/建索引，DST 回拨的那一小时里，两个真实不同的时刻会撞成同一个 key**——一条被覆盖。反过来，春季前拨时，某些本地钟点**根本不存在**（02:30 那天没发生），`datetime` 照样能构造出来，只是它的 `utcoffset` 是猜的：

```text
2026-03-08 02:30（春季跳过点） -> 2026-03-08 02:30:00-05:00   ← 一个从未存在过的时刻
```

修法同样简单，但必须做：

- **存盘、比较、去重，一律用 UTC**（`datetime.now(timezone.utc)`），显示的时候才转本地。UTC 没有 DST，没有歧义。
- **真要处理本地时间，先看它是不是 DST 的边界**（下面 `clockkit.py` 里的 `wall_clock_kind` 就是干这个的），歧义了就拒绝或要求用户挑一个。
- **`datetime.now()`（naive，无时区）出现在落盘代码里就是红旗。** 它不知道自己是哪个时区的，两个不同机器上的 naive 时间戳没法比。

顺手把本机的时区参数也打出来，`time` 模块这套约定挺反直觉的：

```text
datetime.now().astimezone().tzinfo = 中国标准时间
time.timezone  = -28800 秒   ← 注意是 UTC 偏移的【相反数】：东八区是 -28800
time.altzone   = -32400 秒
time.daylight  = 0            ← 咱们不用夏令时
time.tzname    = ('中国标准时间', '中国夏令时')
```

**`time.timezone` 的符号是反的**（东八区给 `-28800`），而且 `daylight=0` 时 `altzone` 仍然有值——它是「如果要用夏令时偏移是多少」，不是「现在是不是夏令时」。别拿它去算时差。

### 七、时间戳的单位和纪元，也得说死

`time.gmtime(0)` 给出这个：

```text
time.gmtime(0) -> tm_year=1970 tm_mon=1 tm_mday=1 tm_hour=0 tm_min=0 tm_sec=0 tm_wday=3
```

`tm_wday=3` 是星期四——1970-01-01 确实是星期四。这就是 Unix 纪元。（顺带一提，`time.gmtime(0)` 在 Windows 上给的是 1970，历史上某些 Windows 平台的 `gmtime(0)` 会失败——**这条我没在这台机器上复现，就不算了**。）

时间戳的单位永远是必须先问清的问题：

```text
秒     : 1795655048        10 位（到 2286 年才变 11 位）
毫秒   : 1795655048787     13 位
微秒   : 1795655048787000  16 位
纳秒   : 1795655048787000000  19 位
```

**只看到一串 10 位数字，先想「这是秒还是别的」再动手。** 混用一次就是把时间差乘了 1000 倍。还有那个老问题：

```text
32 位有符号秒上限 2**31-1 -> 2038-01-19 03:14:07+00:00
今年 2026，还有 12 年
```

嵌入式设备如果用了 32 位 `time_t`，2038 就会变成 1901。`time.time_ns()` 用 int64，能到 2262 年；**真正该担心的从来不是 2038，而是「这个字段当初是按多少位存的」。**

### 八、对着手上的东西看

- **机器人控制循环的耗时。** `time.time()` 算耗时，校时那次会给你负数或天文数字。换成 `time.perf_counter()`。
- **超时/看门狗。** 一律 `time.monotonic()`。看门狗尤其危险：拿墙钟做「多久没心跳就重启」，一次校时可能直接把好好的系统重启了。
- **日志时间戳。** 用 `time.time_ns()` 或带时区的 datetime，**别用 `time.time()` 的 float 秒**——那 238 ns 的台阶在「按时间排序 + 去找两件事的先后」时会让本该有序的日志出现同值。
- **CAN / 传感器帧的时间戳。** 硬件给什么单位就用什么，**在入口统一成整数纳秒或整数毫秒**，别混。跨设备比时间戳之前，先确认两边的钟是不是同一个（NTP 同步没有？同步源一致吗？）。
- **RK3588 上的定时任务。** `cron`/`systemd-timer` 用的是墙钟（它就得跟日历对齐），但**任务内部的超时**要用单调钟——两种时间在同一个程序里共存是正常的，别把它们当成一种。
- **PMIC / 固件的 `time_t`。** 确认它是 32 位还是 64 位；32 位就得记着 2038。
- **「待机多久后休眠」这类逻辑。** 用单调钟；用墙钟的话，用户手动往前调个表就能把设备「调进」休眠。
- **任何 `datetime.now()`（无 tzinfo）。** 出现在跨机器、跨进程、落盘的地方就是红旗，补上 UTC。

### 九、一句必须说清楚的诚实

- **属于标准/文档的**：`time.time()` 依赖系统实时钟、可被调整；`monotonic` 保证不倒流但起点任意；`process_time` 只计 CPU 时间；Windows 上 `perf_counter`/`monotonic` 都是 `QueryPerformanceCounter`；Linux 上 `process_time` 走 `CLOCK_PROCESS_CPUTIME_ID`；两个 aware datetime 共享同一 `tzinfo` 对象时比较**忽略 `fold`**；Unix 纪元是 1970-01-01 UTC；2038 是 32 位有符号 `time_t` 的边界。
- **属于这台机器这一次的实测**：上面所有分辨率数字（238 ns / 100 ns / 4194304 格）、`sleep` 那张表的每一个值、`0.6006/0.5938/0.0` 那组 CPU 时间、`fold=0/1` 的两个时间戳与 `== 给 True` 那条、`gmtime(0)` 的 `tm_wday=3`。
- **没有实测的**：真正的 NTP 校时跳变——我**没法**在这台机器上把系统钟拨着玩（也**不该**），所以第 5 节那个「超时提前触发」是**按机制的模拟**，不是真实诱发；Linux 上 `CLOCK_MONOTONIC` 与 `CLOCK_MONOTONIC_RAW`（后者不受 NTP 频率微调）的差别，来自文档；`gmtime(0)` 在旧版 Windows 上可能失败，也只是文档结论。
- **最要紧的一句**：**「现在几点」和「过了多久」是两道题，`time.time()` 只会答前一道。** 你把它拿去答第二道，它平时看起来也对——只在机器跟世界对了一次表的那一瞬间，安静地给你一个错得离谱的数。而这个数不报错、不告警，只会出现在日志里，等着某天有人`grep`到。

## 🧩 今日代码片段：`clockkit.py` —— 把两个钟分开放

`stopwatch` 用 `perf_counter` 量耗时，`deadline`/`expired` 用 `monotonic` 做超时，`epoch_ms` / `from_epoch_ms` 用**整数**算时间戳，`uptime_str` 把单调钟说成「醒着多久」，`wall_clock_kind` 揪出 DST 的重复/跳过。

```python
# -*- coding: utf-8 -*-
"""clockkit.py —— 两个钟：一个告诉你「几点」，一个告诉你「过了多久」。别拿错。"""
import time
import datetime
from contextlib import contextmanager

EPOCH = datetime.datetime(1970, 1, 1, tzinfo=datetime.timezone.utc)


@contextmanager
def stopwatch(label="耗时"):
    """量耗时只用 perf_counter：它单调、分辨率最高，且不受 NTP 校时影响。"""
    t0 = time.perf_counter()
    try:
        yield
    finally:
        print(f"{label}: {(time.perf_counter() - t0) * 1000:.3f} ms")


def deadline(seconds):
    """超时的终点用 monotonic 算。墙钟会在你没察觉时被拨动。"""
    return time.monotonic() + seconds


def expired(dl):
    return time.monotonic() >= dl


def epoch_ms(dt=None):
    """毫秒时间戳用整数算，别 int(dt.timestamp()*1000) —— 那是把误差四舍五入进日志。"""
    dt = dt or datetime.datetime.now(datetime.timezone.utc)
    d = dt - EPOCH
    return (d.days * 86400 + d.seconds) * 1000 + d.microseconds // 1000


def from_epoch_ms(ms, tz=datetime.timezone.utc):
    return (EPOCH + datetime.timedelta(milliseconds=ms)).astimezone(tz)


def uptime_str():
    """机器「醒着多久」是单调钟的事，跟任何日期无关。"""
    return str(datetime.timedelta(seconds=time.monotonic()))


def wall_clock_kind(dt_local):
    """这个本地钟点是正常、重复（秋回拨）还是不存在（春前拨）？靠 fold 前后比。"""
    a, b = dt_local.replace(fold=0), dt_local.replace(fold=1)
    if a.utcoffset() == b.utcoffset():
        return "正常（这个钟点只出现一次）"
    return "重复（同一钟点有两个瞬间）" if a.timestamp() < b.timestamp() else "不存在（被跳过）"


def measure_stable(n=4):
    """连续测短间隔，并断言单调钟绝不倒流。"""
    out, prev = [], time.monotonic()
    for _ in range(n):
        s = 0
        for i in range(20000):
            s += i                      # 一点真实负载
        cur = time.monotonic()
        assert cur >= prev, "单调钟倒流了！"
        out.append((cur - prev) * 1000)
        prev = cur
    return out


if __name__ == "__main__":
    print("== 1) 两个钟不是一个东西 ==")
    print("  time.time()   =", time.time(), "-> 能换成日期")
    print("  time.monotonic() =", time.monotonic(), "-> 只代表「过了多久」")
    print("  机器醒着:", uptime_str())

    print("\n== 2) 量耗时 ==")
    with stopwatch("  sleep(0.05)"):
        time.sleep(0.05)
    ms = measure_stable(4)
    print("  四段负载(ms):", [round(x, 3) for x in ms], "-> 严格递增、从不倒流")

    print("\n== 3) 超时 ==")
    dl = deadline(0.1)
    time.sleep(0.05)
    print("  过了 50ms，超时了吗:", expired(dl))
    time.sleep(0.08)
    print("  再过了 80ms，超时了吗:", expired(dl))

    print("\n== 4) 整数毫秒时间戳 ==")
    now = datetime.datetime.now(datetime.timezone.utc)
    ms = epoch_ms(now)
    print("  现在 ms 戳 :", ms)
    print("  转回时间   :", from_epoch_ms(ms).isoformat())
    print("  往返一致   :", epoch_ms(from_epoch_ms(ms)) == ms)

    print("\n== 5) DST 歧义（需要 tzdata） ==")
    try:
        from zoneinfo import ZoneInfo
        tz = ZoneInfo("America/New_York")
        amb = datetime.datetime(2026, 11, 1, 1, 30, tzinfo=tz)
        print("  2026-11-01 01:30 NY:", wall_clock_kind(amb))
        print("    fold=0 ->", amb.astimezone(datetime.timezone.utc).isoformat(),
              "| fold=1 ->", amb.replace(fold=1).astimezone(datetime.timezone.utc).isoformat())
        print("    但 amb == amb.replace(fold=1) 是", amb == amb.replace(fold=1),
              "—— 看着相等，其实差", amb.replace(fold=1).timestamp() - amb.timestamp(), "秒")
    except Exception as ex:
        print("  跳过（本机没 tzdata）:", type(ex).__name__)
```

五个值得单独说的细节：

- **`stopwatch` 里只有一行 `time.perf_counter()`，这就是全部。** 它没有 `try/except` 去兜「时钟倒退」，因为单调钟**不可能**倒退——你不需要为一件被保证的事写防御代码。反过来，凡是需要 `if elapsed < 0: ...` 兜底的地方，那个钟一定用错了。
- **`deadline` 返回的是一个「单调钟读数」，不是一个时刻。** 所以它**不能存盘、不能跨进程传**（重启后 `monotonic` 会归零重来）。超时的 deadline 只在**同一个进程存活期间**有意义——这不是缺陷，是它正确的适用范围。跨进程的租约另说，那需要「带单调性校正的墙钟」，是另一件更麻烦的事。
- **`epoch_ms` 故意绕开 `dt.timestamp()*1000`。** `timestamp()` 返回 float 秒，乘 1000 再 `int()` 会把 float 的误差四舍五入进你的时间戳——在 1.79e9 这个量级上，`timestamp()` 的台阶就有 238 ns，乘 1000 是 0.238 µs。用 `timedelta` 的 `days/seconds/microseconds` 做整数运算，得到的毫秒数是**精确**的，往返也一致（实测 `True`）。
- **`uptime_str` 用的是 `time.monotonic()` 而不是系统启动时间。** 它算出来的是「Python 这个进程看到的机器醒着的时间」——对 Windows 上 `monotonic` 走的是 QPC，QPC 的零点一般是**系统启动**，但这是实现细节，不该依赖。用来显示「已经跑了多久」是安全的；用来算「上次重启是哪天」就不安全。
- **`wall_clock_kind` 是这套里唯一处理「歧义」的。** 它靠「`fold=0` 和 `fold=1` 的 `utcoffset` 是否相同」判断边界，再比时间戳判断是「重复」还是「不存在」。**这类检查应该发生在「解析用户输入的本地时间」的那一刻**，而不是等程序跑出错误结果再回头怀疑。

一句话收这段：**`time.time()` 回答的是「世界现在发生了什么」，`time.monotonic()` 回答的是「我这个进程自己走了多远」。前者会因为你无法控制的原因跳变，后者不会——你要的是哪个，先想清楚。**

## ✨ 今日一句

> `time.time()` 和 `time.monotonic()` 就像一个挂在墙上的钟和一块秒表：**钟能告诉别人「现在几点」，但别人也能来把它拨一拨；秒表不能告诉任何人现在几点，但它从头到尾只认「过了多久」。**
>
> 计时用错了哪一块都不会立刻出事——它只在有人来拨钟的那一秒，安静地给你一个错数，然后回到正常，让你永远查不出原因。
