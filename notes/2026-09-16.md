## 💭 技术随想：CAN 总线仲裁——几十路信号同时开口，为什么从来不会撞车

一条 CAN 总线，两根细线，挂着一整串节点：控制器、电机驱动器、传感器、急停按钮……没有任何一个是"老大"，谁想发就发。按常识，这种"无领导的共享信道"应该是混乱的：以太网的解法就是出了名的"先撞了再说"——两组数据撞在一起，双方随机等一段时间再重试，赌的是概率。

但 CAN 走了另一条路：**它不是在撞车之后处理冲突，而是在撞上的那几微秒里，当场把谁先说话给定了**。而且输的那一方一个字节都不会损失——它只是安静退下，等下一轮。

秘密藏在两条看起来平平无奇的规则里。

**第一条，总线是"线与"逻辑。** CAN 上的 0 叫显性位（dominant），是强势的一方：谁都可以主动把总线拉下去；1 叫隐性位（recessive），是默认状态。只要有一家拉了 0，整条总线读出来就是 0——说 1 的人一旦发现总线变成 0，就等于听到有人"改了口"，而这个改口的人不可能是自己。

**第二条，ID 从最高位往最低位一位一位发。** 而每个发送者一边发、一边拿自己发出的位和总线上真实读到的位做对比。一旦发现"我想发的 1 被某个 0 顶掉了"，它就知道：有人在和自己抢，而且对方 ID 在这一位上比我更强势。于是它当场停手，从发件人变回安静的接收者——这个动作有个优美的名字：**非破坏性仲裁**。赢家甚至不知道旁边有人和自己抢过，它只感觉一路畅通。

两条规则一叠加，顺手推出了一条铁律：**ID 数值越小，优先级越高**。因为 MSB 先比 + 0 更强，任意两条 ID 的第一个分歧位上，数值小的那个必然是 0——它在那一局赢，并且永远赢。这不是约定俗成，是二进制比较的自然结果。所以在 CAN 世界里，ID 不只是"名字"，是写在名字里的地位：设计 ID 分配表的时候，工程师等于在给所有报文排生死——急停、安全帧拿 0x0xx 档，周期控制帧排中段，调试诊断这类"有没有都行"的帧扔到 0x7xx 档。机器人关节总线、汽车 ECU 网络里，几百种报文共用一对线却不打架，靠的就是这张"用数值编码的秩序表"。

和"撞了再退避"的以太网相比，CAN 的聪明在于把不确定性提前消灭：仲裁不消耗任何重传，总线利用率趋近 100%；更关键的是——输家的最坏等待时间是**可以算出来的**（当前帧的时长 + 仲裁的几十微秒），而不是随机退避、听天由命。对实时控制系统来说，可计算的延迟比更低的平均延迟值钱得多。

一个小而重要的收尾：这一切成立的前提，是总线上所有节点"位时间"严格一致——大家都是同一个波特率、采样点对齐，逐位比较才有意义。所以 CAN 里"统一波特率"不是惯例，是物理前提。

## 🧩 今日代码片段：60 行模拟一个 CAN 仲裁器——三个实验

把仲裁规则缩写成 60 行 Python：先给两个节点（A=0x120、B=0x0A3）开一场"逐位赛跑"，打印每一位的总线电平和谁被顶掉；再让五路报文同时排队，看没有任何调度器时总线自己排出什么顺序；最后测一测"两条 ID 越像，仲裁越晚分手"。

```python
# -*- coding: utf-8 -*-
"""CAN 总线「非破坏性仲裁」演示：为什么 ID 越小，优先级越高（真实可运行）"""
import sys
try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

N = 11  # 标准帧：11 位标识符（真实帧 ID 前还有 1 位 SOF 同步位，原理不变）


def bits_of(arb_id):
    """11 位 ID → 比特列表，MSB 在前（CAN 先发高位，这一点是全部秘密的一半）"""
    return [(arb_id >> i) & 1 for i in range(N - 1, -1, -1)]


def id_str(arb_id):
    return f"0x{arb_id:03X}"


def run_race(frames, trace=False):
    """frames: [(名字, ID), ...] 同时想发。返回获胜者。
    规则（线与总线）：任一节点发 0(显性)，总线就是 0；
    某节点想发 1(隐性) 却读回 0 → 它输了，立即退出、转为接收。"""
    node = [{"name": n, "id": i, "bits": bits_of(i), "lost": 0} for n, i in frames]
    for pos in range(N):
        contenders = [c for c in node if c["lost"] == 0]
        if len(contenders) <= 1:
            if trace and len(contenders) == 1 and any(c["lost"] for c in node):
                print(f"  —— 只剩 {contenders[0]['name']} 一家，第 {pos+1}~{N} 位它独自发完 ——")
            break
        bus = min(c["bits"][pos] for c in contenders)  # 线与：有一个 0 就是 0
        for c in contenders:
            if c["bits"][pos] == 1 and bus == 0:
                c["lost"] = pos + 1
        if trace:
            row = "  |  ".join(
                f"{c['name']}({id_str(c['id'])}) 发{c['bits'][pos]}"
                + (" →被顶掉出局✗" if c["lost"] == pos + 1 else " →继续同步✓")
                for c in contenders)
            print(f"  第 {pos+1:>2} 位  总线={bus}   {row}")
    return next(c for c in node if c["lost"] == 0)


print()
print("=" * 70)
print("实验1：A(0x120) 和 B(0x0A3) 同一微秒开抢——逐位看 A 怎么输")
print("=" * 70)
print("两家想发的 ID 比特（高位在前，严格按这个顺序往总线上发）：")
la = f"  A {id_str(0x120)}  "
lb = f"  B {id_str(0x0A3)}  "
print(la + " ".join(map(str, bits_of(0x120))))
print(lb + " ".join(map(str, bits_of(0x0A3))))
print(" " * (len(la) + 4) + "↑ 第 3 位：两家第一次意见不合")
print()
w = run_race([("A", 0x120), ("B", 0x0A3)], trace=True)
print()
print(f"→ 胜者 B（{id_str(w['id'])}）。A 在第 3 位刚想发 1，就听到总线被 B 拉成了 0：")
print("  当场停手、切回接收——这个帧没被破坏，A 只管等总线空闲再自动重发。")

print()
print("=" * 70)
print("实验2：五路报文同时排队——没有任何调度器，总线自己排出先后")
print("=" * 70)
pending = [("急停指令", 0x000), ("关节1命令", 0x0A3), ("关节2命令", 0x120),
           ("传感器上报", 0x300), ("调试诊断", 0x7FF)]
rnd = 1
while pending:
    w = run_race(pending)
    print(f"  第 {rnd} 轮竞争：{w['name']}（{id_str(w['id'])}）获胜 → 上总线，其余各家整队重试")
    rnd += 1
    pending = [(n, i) for n, i in pending if i != w["id"]]
print("  → 自动排出的顺序，恰好就是 ID 从小到大——优先级不用任何人管。")

print()
print("=" * 70)
print("实验3：ID 越接近，仲裁越晚才分手（第一次不同的位决定一切）")
print("=" * 70)
pairs = [(0x000, 0x7FF), (0x0A3, 0x120), (0x0A3, 0x0A4), (0x123, 0x123)]
for a, b in pairs:
    ba, bb = bits_of(a), bits_of(b)
    diff = next((k + 1 for k in range(N) if ba[k] != bb[k]), None)
    if diff is None:
        print(f"  {id_str(a)} vs {id_str(b)}：11 位全程相同 → 仲裁永远分不出胜负")
        print("        （现实含义：同一个 ID 撞车 = 配置错误——数据段两家同时开口，直接撞出错帧）")
    else:
        w = a if ba[diff - 1] == 0 else b
        prefix = "没有共同前缀" if diff == 1 else f"前 {diff-1} 位相同"
        tag = {1: "第 1 位就分手，最快", 9: "缠到第 9 位才分手，较慢"}.get(diff, f"第 {diff} 位分手")
        print(f"  {id_str(a)} vs {id_str(b)}：{prefix}，{tag} → {id_str(w)} 胜")
print("  → 仲裁「耗时」= 两条 ID 第一个不同的位的位置；两条 ID 越像，越晚分出胜负。")
```

**说明：**

- 实验1 里第 3 位是整个原理的缩影：A"发 1 却读到 0"。这不是 A 出了问题，而是线与逻辑在通知它"有人比你强势"。真实 CAN 控制器就在这一位的采样点之后立刻切换状态——停发、转接收，全程硅片内完成，固件一行都不用写。
- "非破坏性"是它和以太网的本质区别：以太网撞车后双方都要随机退避重发，等多久掷骰子决定；CAN 逐位比 ID，落差一出现就自动分好序，不损坏任何一帧、不浪费一次重传。实时系统里"最坏情况可计算"比"平均值好看"重要得多。
- 为什么"ID 小 = 优先"不是约定而是必然：MSB 先发 + 0（显性）覆盖 1（隐性）。任意两条不同的 ID，第一个分歧位上数值小的那个必然是 0——它赢下那一局，并且只要赢一次就赢到底。
- 顺带一提，MSB 先发这个方向也不是随便定的：只有高位先比较，"数值小 = 优先"的直觉才成立；要是反过来 LSB 先发，优先级会变成按位反转的怪序，调度直觉全毁。
- 仲裁的长度 ≠ 帧的长度：只有 ID（标准帧再加 1 位 RTR）参与"比"，一旦分出胜负，输家全部静默，赢家把数据段、CRC 一口气发完，没人再打扰它。两条 ID 越接近、要"缠"的位越多（实验3），但代价天花板极小：1 Mbps 下 11 位 ≈ 11µs。
- 唯一"比不出胜负"的情况是 ID 撞车（实验3 里 0x123 vs 0x123）：两个节点会在数据段同时开口、电平互相打架 → 位错误 → 错误帧。所以同 ID 只允许"数据一致的广播"用法；一个报文类型一个唯一 ID，是配置铁律。
- RTR 位彩蛋：标准帧的仲裁场是"11 位 ID + 1 位 RTR"，数据帧 RTR=0（显性）、远程帧 RTR=1——同 ID 时数据帧赢远程帧，还是"0 更强"的延伸。演示为看清主线只模拟了 11 位 ID。
- 固件视角：bxCAN / MCAN 这类控制器把"逐位对比、输了转接收、空闲自动重发"全做在硬件里，固件看到的结果只有一个"发送完成"（或静默重试后成功）。把原理装进脑子，用处在于：给 ID 分配表排优先级、看懂错误计数器和 bus-off 状态、以及排障时明白"刚才总线上到底谁抢赢了"。
