# 📅 2026年10月21日 日报

## 💭 技术随想：二分法穿上 git 的外套

"上周还好好的，怎么今天就坏了？"

这句 bug 报告最难查。从"上周"到"今天"，中间躺着几百个提交。最笨也最常见的做法是手动回滚：退一个版本、编译、试、再退一个……500 个提交里有一个凶手，最坏要试 500 次。而 `git bisect` 只要 9 次。

不是因为它更聪明，是因为它把"找凶手"换成了另一个问题：**"这个提交坏不坏？"** 前者要靠推理和记忆，后者只要一次实验。剩下的，交给二分。

### 一、它只做减法

bisect 的全部工作是：给一个已知 good 的提交、一个已知 bad 的提交，每次挑中间那个问"坏不坏"，然后扔掉一半。N 个提交要几次？

| 提交数 | 需要的测试次数（上界） |
|---|---|
| 10 | 4 |
| 100 | 7 |
| 1,000 | 10 |
| 10,000 | 14 |
| 100,000 | 17 |
| 1,000,000 | 20 |

这就是对数的分量：一百万次提交，二十次实验。而且这个数字跟代码多复杂、bug 多隐蔽都没关系——它只跟提交个数有关。

bisect 不懂你的代码，不懂 Python 也不懂 C。它只认三样东西：一个 good 的提交、一个 bad 的提交、一个能对任意提交回答 good/bad 的命令。

**所以它找到的从来不是"bug 的那个提交"，而是"你的判定脚本第一次变红的提交"。这两者之间的距离，才是调试的真功夫。**

### 二、三个实验，三种翻车方式

昨天在数编码器的四个状态，今天在数提交。三个实验都在真的 git 仓库里跑，不是模拟。

**实验 A：干净的一刀。** 64 个提交，第 41 个把 `fee()` 的边界从 `<` 改成 `<=`——200 分整这一档从"收 10 分"变成了"不收"。判定脚本 7 条用例，特地把 199 / 200 / 201 三个点都覆盖了。真实的 bisect 日志：

```text
Bisecting: 31 revisions left to test after this (roughly 5 steps)
PASS
Bisecting: 15 revisions left to test after this (roughly 4 steps)
FAIL: fee(200)=0 应为 10
Bisecting: 7 revisions left to test after this (roughly 3 steps)
PASS
Bisecting: 3 revisions left to test after this (roughly 2 steps)
FAIL: fee(200)=0 应为 10
```

六次测试，指认第 41 个提交，一次不差。注意 31 → 15 → 7 → 3 → 1 → 0 这个阶梯：每一行是"还剩多少、大概几步"。人肉回滚时你只能看见"又一个不对"，bisect 让你看见搜索空间在缩短。

**实验 B：同一个仓库，判定脚本漏掉 200 这个边界。** 用例只剩 100 / 201 / 999 / 1000。六次测试全部 PASS。你猜它怎么报？

```text
Bisecting: 0 revisions left to test after this (roughly 0 steps)
PASS
f154de8641f8bca3b7ac650b4ef8722ae7c5e0b4 is the first bad commit
指认：feat: 计费模块第 64 次迭代（真凶是第 41 个）
```

它指认了 HEAD——那个测试全绿的最后一次提交。不是因为它觉得 HEAD 可疑，而是因为它必须在 good 和 bad 之间收敛到一条边界：你把 HEAD 声明成 bad，脚本又从没说过谁 bad，那"第一条 bad"就只能是 HEAD。

**bisect 从不说"我找不到"，它只会把边界当成答案交给你。** 一个理直气壮的错答案，比一句"没找到"贵得多——你会拿着它去 review 一个无辜的提交。

这也顺带说明：写判定脚本时，用例不是在测代码，是在测**你自己对"坏"的定义**。

**实验 C：中间夹着 4 个编译不过的提交。** 第 48~51 个提交是半成品（函数头少个冒号），import 就炸。判定脚本捕获 `SyntaxError` 后返回 125：

```text
SKIP: 这个提交连 import 都过不去 -> SyntaxError
Bisecting: 15 revisions left to test after this (roughly 4 steps)
```

最后仍然指认第 41 个，全程八次测试，两次 SKIP。125 是 bisect 留给"这个提交测不了"的专用出口：不用你手动跳，也不会污染结论。如果脚本在这里直接崩掉，Python 的退出码是 1——bisect 会把它当成"确凿的坏提交"，后面的推理全歪。

### 三、判定脚本的四条纪律

1. **退出码就是契约。** 0 = good，1~127（除 125）= bad，125 = 跳过，其它（含 ≥128）= 中止。

   | 退出码 | bisect 的理解 |
   |---|---|
   | 0 | good |
   | 1 ~ 127（除 125） | bad |
   | 125 | 这个提交没法测，跳过 |
   | 其它（128 及以上、负数） | 中止整个 bisect |

   这条契约里最阴的一条是：**Python 脚本抛未捕获异常，退出码就是 1，bisect 会当成"这个提交是坏的"。** 依赖没装、端口被占、路径写错，全会变成一条"确凿"的坏提交。所以判定脚本要把"环境问题"和"结论"分开：import 失败、服务连不上 → 125，别让异常飞出去。另外 `exit(-1)` 在 shell 里是 255，属于"其它"，直接中止；126/127 是 shell 自己的"命令找不到 / 不可执行"，同样中止。
2. **确定性。** 固定随机种子，不依赖时钟、网络、磁盘上的残留、执行顺序。一个很便宜的自检：同一个提交连跑 20 次，看结论稳不稳定。**bisect 对噪声没有免疫力，它只会把噪声忠实地放大成结论。**
3. **快。** 单次测试时间 × 步数就是总成本：8 分钟的集成测试跑 20 步，是 2 小时 40 分。先用最便宜的断言（单元级、不起服务）把范围收窄，再拿重测试确认。二分不是免费，它只是把 N 次重测试换成了 log N 次。
4. **只读。** 判定脚本别改工作区、别留缓存、别提交。它是温度计，不是手术刀。

### 四、bisect 会骗人的时候

- **历史不单调。** bug 修好又被改回来、功能被开关关掉再打开，历史里就有多个 good→bad 跳变。bisect 只保证找到"一个"跳变，不保证是你关心的那个。用 `git bisect log` 看看它到底走过哪些提交。
- **merge 提交。** 默认 merge 也会被测试；合并一多，指认点经常落在某个 merge 上。`git bisect start --first-parent` 让它只沿第一父提交走——代价是分支内部再也不看，merge 提交本身成了"引入点"。选哪种，取决于你想知道"哪天坏的"还是"哪个改动坏的"。
- **提交粒度。** 一个提交改了 40 个文件，bisect 只能指到提交。剩下 40 个文件里是哪一个，还得 `git show` 慢慢看。**bisect 缩小的是搜索空间，不是理解成本。**
- **历史被改写。** rebase / squash 过的分支，本地 bisect 出来的提交和线上那个二进制未必对得上。用 tag 或发布分支当 good 边界，比"我记得上周三还行"可靠一个数量级。
- **工作区是脏的。** bisect 会反复 checkout 历史提交，没提交的改动要么被 stash、要么在 checkout 时挡住整个流程。开始时先 `git stash` 或提交，别让工作区参与实验。

### 五、手边备忘

```bash
git bisect start
git bisect bad                  # 不带参数默认当前 HEAD
git bisect good v1.2.0          # 用 tag，别用"我记得"
git bisect run python check.py  # 全自动：跑脚本、判 good/bad、继续二分
git bisect log > /tmp/b.log     # 记录路径，出错了可以复盘
git bisect replay /tmp/b.log    # 从日志恢复现场
git bisect reset                # 千万别忘：结束前工作区还停在某个历史提交上
```

几个不常用但值钱的：

- `git bisect skip <范围>`：整段提交都不可测（比如某次重构期），一次跳过。
- 找性能回归：`git bisect start --term-old=fast --term-new=slow`，然后 `git bisect fast <sha>` / `git bisect slow`。术语换成"快/慢"，判定脚本返回的不是对错，而是"有没有超过阈值"。
- `--no-checkout`：不切换工作区，只更新 `BISECT_HEAD` 引用，适合测试跑在别处（产物、容器、另一台机器）的场景。

忘记 `git bisect reset` 的下场很具体：你以为自己在改今天的代码，其实工作区停在 2019 年的某个提交上，改了半天，commit 完才发现历史乱了。

### 六、放远一点

- Linux 内核邮件列表里的 `bisected to <commit>` 是比任何猜测都硬的证据。一个能 bisect 的 bug 报告，质量直接高一个档次——因为它把"我觉得是那次改的"变成了"只剩这一个没被排除"。
- 同一个思路在别处：二分答案、ddmin（把让测试失败的输入一点点删到最小）、二分定位是哪一段网线/哪一台交换机坏了。二分的对象可以是提交、输入、配置、网络段——只要你能对"一半"给出可靠的判定。
- 绕不过去的前提是：**你得有一个能重复的判定。** 没有它，二分只是把猜测包装得更科学。
- 反过来用也成立：想让别人快速定位你引入的问题？把提交切小、保证每个提交能编译、写一条能复现的脚本。你在替未来的所有人（包括未来的自己）省掉那 9 次编译。

## 🧩 今日代码片段：bisect 实验室——三个实验，全是真的 git

这个脚本不模拟 bisect，它真的建仓库、真的提交 64 次、真的埋 bug、真的调 `git bisect run`。三个实验共用一套历史生成器，只换判定脚本和历史形状：

- **实验 A**：干净历史 + 覆盖边界的判定脚本 → 六次测试精确指认第 41 个；
- **实验 B**：同一个仓库，判定脚本漏掉 200 这个边界 → 全绿，却指认 HEAD；
- **实验 C**：第 48~51 个提交编译不过，判定脚本返回 125 → 跳过它们，仍然指认第 41 个。

Windows 细节：`git bisect run` 是把命令交给 shell 执行的，NTFS 没有可执行位，所以这里写 `python check_fee.py` 而不是 `./check_fee.py`；判定脚本放在工作区但不提交，属于 untracked 文件，每次 checkout 都不会被动到。跑完自动删临时目录。

```python
# -*- coding: utf-8 -*-
"""git bisect 实验室：干净定位 / 测试太窄 / 中间夹着编译不过的提交"""
import os
import shutil
import subprocess
import sys
import tempfile

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

PYDIR = os.path.dirname(os.path.abspath(sys.executable))
ENV = os.environ.copy()
ENV["PATH"] = PYDIR + os.pathsep + ENV.get("PATH", "")
ENV["GIT_AUTHOR_NAME"] = ENV["GIT_COMMITTER_NAME"] = "Leo"
ENV["GIT_AUTHOR_EMAIL"] = ENV["GIT_COMMITTER_EMAIL"] = "leo@example.com"
ENV["GIT_TERMINAL_PROMPT"] = "0"

LINE = "=" * 72

CALC = '''# 计费模块 —— 第 {i} 次迭代
# 规则：前 200 分（含）以内不收手续费，超过部分按 5% 向下取整
VERSION = {i}


def fee(cents):
    """返回手续费（分）"""
    if cents {op} 200:
        return 0
    return cents // 20
'''

CHECK = '''# -*- coding: utf-8 -*-
"""判定脚本：这个提交的计费边界对不对
退出码约定：0 = good，1 = bad，125 = 跳过
"""
import os
import sys

sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))

try:
    import calc
except (SyntaxError, ImportError) as e:
    print("SKIP: 这个提交连 import 都过不去 -> " + type(e).__name__)
    sys.exit(125)

CASES = {cases}

bad = []
for cents, want in CASES:
    got = calc.fee(cents)
    if got != want:
        bad.append("fee(%d)=%d 应为 %d" % (cents, got, want))

if bad:
    print("FAIL: " + "; ".join(bad))
    sys.exit(1)
print("PASS")
sys.exit(0)
'''

FULL = [(0, 0), (100, 0), (199, 0), (200, 10), (201, 10), (999, 49), (1000, 50)]
NARROW = [(100, 0), (201, 10), (999, 49), (1000, 50)]


def sh(repo, *args, check=True):
    p = subprocess.run(
        ["git", *args], cwd=repo, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
        text=True, encoding="utf-8", errors="replace", env=ENV,
    )
    if check and p.returncode != 0:
        raise SystemExit("git %s 失败:\n%s" % (" ".join(args), p.stdout))
    return p


def make_repo(root, name, n, bug_at, broken=()):
    repo = os.path.join(root, name)
    os.makedirs(repo)
    sh(repo, "init", "-q", "-b", "master")
    first = last = None
    for i in range(1, n + 1):
        src = CALC.format(i=i, op="<=" if i >= bug_at else "<")
        if i in broken:
            src = ("# 半成品：正在改计费规则\nVERSION = %d\n\n\n"
                   "def fee(cents)\n    return cents // 20\n" % i)
        with open(os.path.join(repo, "calc.py"), "w", encoding="utf-8") as f:
            f.write(src)
        sh(repo, "add", "-A")
        sh(repo, "commit", "-q", "-m", "feat: 计费模块第 %d 次迭代" % i)
        sha = sh(repo, "rev-parse", "HEAD").stdout.strip()
        if i == 1:
            first = sha
        last = sha
    return repo, first, last


def write_check(repo, cases):
    with open(os.path.join(repo, "check_fee.py"), "w", encoding="utf-8") as f:
        f.write(CHECK.format(cases=repr(cases)))


def show(title, desc, repo, n, bug_at, cases):
    print(LINE)
    print(title)
    print(LINE)
    print("  " + desc)
    print()
    first = sh(repo, "rev-list", "--max-parents=0", "HEAD").stdout.strip()

    sh(repo, "bisect", "start")
    head = sh(repo, "bisect", "bad", "HEAD").stdout
    start = sh(repo, "bisect", "good", first).stdout
    for chunk in (head, start):
        for l in chunk.splitlines():
            if l.startswith("Bisecting:"):
                print("    " + l.strip())

    p = sh(repo, "bisect", "run", "python", "check_fee.py", check=False)
    verdict = None
    steps = skips = fails = 0
    for l in p.stdout.splitlines():
        l = l.strip()
        if l.startswith("Bisecting:"):
            print("    " + l)
        elif l.startswith(("PASS", "FAIL:", "SKIP:")):
            print("    " + l)
            steps += 1
            skips += l.startswith("SKIP")
            fails += l.startswith("FAIL")
        elif "is the first bad commit" in l:
            print("    " + l)
            verdict = l.split()[0]
        elif l.startswith("error") or "only 'good' commits" in l:
            print("    " + l)
    print()
    print("  判定脚本执行 %d 次：%d 次 FAIL，%d 次 SKIP" % (steps, fails, skips))
    if verdict:
        subj = sh(repo, "log", "-1", "--format=%s", verdict).stdout.strip()
        idx = sh(repo, "rev-list", "--count", "%s..%s" % (first, verdict)).stdout.strip()
        print("  指认：%s（历史上第 %s 个提交；真凶是第 %d 个）" % (subj, int(idx) + 1, bug_at))
    else:
        print("  指认：无")
    print()
    sh(repo, "bisect", "reset", "-q", check=False)


def main():
    root = tempfile.mkdtemp(prefix="bisect-lab-")
    print("临时仓库根目录：%s" % root)
    print()
    try:
        a, first, last = make_repo(root, "demo-a", 64, 41)
        write_check(a, FULL)
        show("实验 A：干净的一刀",
             "64 个提交，第 41 个提交把 fee() 的 200 分边界从 `<` 改成了 `<=`；"
             "判定脚本 7 条用例，覆盖 199/200/201", a, 64, 41, FULL)

        write_check(a, NARROW)
        show("实验 B：同一个仓库，判定脚本漏掉 200 这个边界",
             "用例只剩 100 / 201 / 999 / 1000 —— 每个提交看起来都\"对\"", a, 64, 41, NARROW)

        c, _, _ = make_repo(root, "demo-c", 64, 41, broken=(48, 49, 50, 51))
        write_check(c, FULL)
        show("实验 C：中间夹着 4 个 import 就炸的半成品提交",
             "第 48~51 个提交函数头少个冒号，判定脚本返回 125 跳过它们", c, 64, 41, FULL)
    finally:
        shutil.rmtree(root, ignore_errors=True)
        print("临时目录已清理。")


if __name__ == "__main__":
    main()
```

**今天收获清单：**

- **bisect 只做减法。** 它不需要知道 bug 长什么样，只需要一个 good、一个 bad、一个能回答"坏不坏"的命令。64 个提交 → 6 次测试；1,000,000 个提交 → 20 次。
- **它找到的不是 bug，是判定脚本第一次变红的提交。** 判定脚本写得窄，它就会认真地指认一个无辜的 HEAD（实验 B：6 次全 PASS，最后报第 64 个）。
- **退出码是契约：** 0 = good，1~127（除 125）= bad，125 = 跳过，其它 = 中止。Python 未捕获异常就是 1，环境问题会被当成"确凿的坏提交"，必须先接住再返回 125。
- **编译不过的提交不用手动跳过。** 返回 125，bisect 自己绕过去（实验 C：2 次 SKIP，仍然指认第 41 个）。
- **假设是"单调 + 可判定 + 可重复"。** 历史里修过又坏、被开关屏蔽过，就有多个跳变，它只保证找到其中一个。
- **成本 = 单次测试时间 × log N。** 8 分钟的集成测试跑 20 步是 2 小时 40 分——先用便宜断言收窄，再用重测试确认。
- **merge 会吃掉精度。** `--first-parent` 让 merge 提交当引入点，够快，但看不到分支内部。
- **结束后 `git bisect reset`。** 不然你的工作区会一直停在某个历史提交上。

## ✨ 今日一句

> bisect 从不告诉你"是谁干的"，它只告诉你"剩下的这一个人还没被排除"。调试里最贵的从来不是找到答案，而是把那些看着都像答案的可能，一个一个划掉。
