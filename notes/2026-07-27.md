## 💭 技术随想

今天聊两个 Git 的「保命」功能——**`git bisect`（二分查找）** 和 **`git reflog`（引用日志）**。

先说 `git bisect`。项目大了以后，某个版本突然出了 bug，但不知道是哪个 commit 引入的。你当然可以一个一个手动 `git checkout` 测试，但如果有 100 个 commits，平均要测 50 次。`git bisect` 用二分查找算法将这个复杂度降为 **O(log n)**——100 个 commits 最多只需要 7 步。它的原理就是二分法：标记一个好版本、一个坏版本，Git 自动切到中间 commit，你测试后告诉它是好是坏，如此反复，最后精准定位到罪魁祸首。

另一个神器是 `git reflog`。Git 不会真正删除任何东西（除非你手动 `git gc` 清理），所有操作都会被记录在 `.git/logs/` 下的 reflog 中。你以为 `git reset --hard` 之后丢失的代码、`git rebase` 搞乱的历史、不小心 `git branch -D` 删掉的分支——只要操作发生在 90 天内，都可以从 reflog 里找回来。**reflog 就是你 Git 操作的「时光机」**。

两者结合使用效果最佳：先跑 bisect 定位出有问题的 commit，然后用 reflog 在出问题之前的历史里找到你需要恢复的内容。Git 的「近乎不删数据」设计哲学，让这两把武器在关键时刻可以救命。

## 🧩 今日代码片段

一个实战脚本：**自动化 git bisect，帮你找到引入 bug 的 commit**。同时也展示 reflog 的恢复用法。

```bash
#!/usr/bin/env bash
# git-bisect-demo.sh — 自动二分查找 bug 来源
set -euo pipefail

# --- 1. 手动二分查找流程（演示）---
# 假设当前在 main 分支上，已知 v2.0 正常，v3.0 有 bug
echo "=== 开始二分查找 ==="
git bisect start
git bisect bad          # 当前版本有 bug
git bisect good v2.0    # v2.0 是好的
# Git 会 checkout 中间的 commit，然后你跑测试：
# 如果当前版本有 bug:  git bisect bad
# 如果当前版本正常:   git bisect good
# 重复 5-7 次后，Git 会告诉你第一个坏 commit 的 hash
git bisect reset        # 结束 bisect，回到原来的分支

# --- 2. 自动 bisect（全自动！）---
# 写一个 test script，返回 0（好）或 非0（坏）
cat > /tmp/test_bug.sh << 'EOF'
#!/usr/bin/env bash
# 测试某个行为是否正常
python -c "
# 假设 bug 表现：某个函数在 v3.0 之后返回值错误
import importlib, sys
# 这里放你的真正测试逻辑
result = __import__('your_module').your_function()
sys.exit(0 if result == expected else 1)
"
EOF
chmod +x /tmp/test_bug.sh

# 让 Git 自动跑 bisect
git bisect start
git bisect bad HEAD      # 当前有 bug
git bisect good v2.0     # v2.0 正常
git bisect run /tmp/test_bug.sh   # 自动二分！
git bisect reset

# --- 3. reflog 恢复「已丢失」的代码 ---
echo ""
echo "=== reflog 恢复演示 ==="
# 场景：不小心 reset --hard 丢了工作
git reflog | head -5     # 看看最近的 Git 操作记录
# 输出会类似：
#  abc1234 HEAD@{0}: reset: moving to HEAD~1
#  def5678 HEAD@{1}: commit: important work
# 恢复方法：
#  git cherry-pick def5678           # 把那个提交捡回来
#  git checkout -b recovered-branch  # 或者开个新分支指向它

# 所有历史都在，不必惊慌
```

**小贴士**：养成好习惯——复杂的 `git reset` 或 `git rebase` 操作前，先 `git tag checkpoint-$(date +%Y%m%d)` 做个标签，或者简单的 `git branch backup-before-rebase`。但即使忘了，reflog 也会在 90 天内保护你。
