# 📅 2026年11月02日 日报

## 💭 技术随想：dict 是 O(1)，但你的键不是

两件事前后脚撞在一起。

第一件：一个状态查询接口里写了 `if dev in device_list`，设备几百个，前端每秒刷几次，看着没事；等设备表涨到几万条，那个接口开始吃掉半个核。

第二件：一个带参数的缓存，命中率一直是 0。日志显示键"看起来一样"，`cache_info` 里 hits 永远是 0，misses 一路涨。加了几行打印才发现，键里有一个字段在调用之间被改过。

一个是"该用哈希表的地方用了列表"，一个是"用了哈希表，但键在背后变了"。表面上两件不相干的事，底下是同一张表。

今天把 dict 从头量了一遍。结论不是"dict 很快"——这句话没有信息量；而是：**O(1) 不是哈希表送的礼物，是它跟你签的一份合同：键在表里期间，它的哈希值和相等性都不能变。合同一破，常数时间还在，答案没了。**

环境：Windows 11 / Python 3.11.15 / CPython。绝对值换机器会变，比例关系是结构决定的。

### 一、先把 O(1) 量出来

同一批整数，分别放进列表、集合、字典，做命中/未命中各半的成员检查，取 3 次最快值：

| N | 查询数 | `in list` | `in set` | `in dict` |
|---|---|---|---|---|
| 1,000 | 2,000 | 4.089 µs | 0.0281 µs | 0.0285 µs |
| 10,000 | 2,000 | 31.598 µs | 0.0301 µs | 0.0319 µs |
| 100,000 | 2,000 | 463.020 µs | 0.1496 µs | 0.0928 µs |
| 1,000,000 | 100 | **25,420.301 µs** | 0.0570 µs | 0.0940 µs |

（表里是**每一次查询**的平均耗时，已经除过查询数。）

读这张表的三件事：

- **列表是线性的，而且很诚实地线性**：1,000 → 10,000 → 100,000，4.1 → 31.6 → 463 µs，十倍十倍地涨。100 万那行因为只查了 100 次，单次 25.4 ms，和前面的斜率对得上。
- **集合和字典几乎是一条平线**：0.028 → 0.030 → 0.15 → 0.057。中间那个 0.1496 是噪声（只查了 2000 次，p50 附近抖一抖就翻倍），不是"10 万比 100 万慢"。**看这一列要看量级，不要看最后一位。**
- **100 万行上，差 44.6 万倍。** 不是"慢一点"，是"一个接口能不能扛住每秒一百次"的区别。

集合和字典在成员检查上是一回事——`set` 就是"只有键、没有值的 dict"。所以后面只讲 dict，结论对 set 一样成立。

### 二、O(1) 的真正含义：不随 n 涨，不是不花钱

0.03 µs 是三十纳秒，大约一百条指令。这些钱花在哪：

1. 算 `hash(key)`（整数就是它自己，字符串要走一遍字符）；
2. 用哈希的低位取模，找到索引表里的槽（`i = hash & mask`，掩码是 `2^k - 1`，所以是位与不是除法）；
3. 顺着槽去看 entries 数组里那一条，先比哈希、再比 `is`、最后才调 `__eq__`。

第二步是关键：**表长永远是 2 的幂，取模就是一次位与。** 这也是为什么扩容不是"涨 10%"，而是"翻倍"——只有翻倍，掩码才仍然是 `2^k - 1`。

所以准确的说法不是"哈希表查找只要一步"，而是"**不管表里有一千条还是四百万条，它都只走那三步**"。这就是常数时间：代价固定在哈希函数和一次探测上，与 n 无关。

### 三、哈希冲突：把所有键的 hash 写成 0，两倍数据四倍时间

O(1) 有个前提：**哈希得把键分散开。** 我造了一个所有键 `__hash__` 都返回 0 的类，其余正常，往 dict 里塞：

| N | 建表 | 全查一遍 | `__eq__` 调用次数 | int 键建表 / 查一遍 |
|---|---|---|---|---|
| 1,000 | 0.099 s | 0.091 s | 499,500 | 0.00010 / 0.00002 s |
| 2,000 | 0.396 s | 0.409 s | 1,999,000 | 0.00026 / 0.00008 s |
| 4,000 | 1.619 s | 1.577 s | 7,998,000 | 0.00066 / 0.00013 s |
| 8,000 | **6.560 s** | **6.537 s** | 31,996,000 | 0.00122 / 0.00036 s |

四件事：

1. **数据翻倍，时间四倍。** 0.099 → 0.396 → 1.619 → 6.560，每一行都是上一行的 4 倍。这是标准的二次曲线，和"在循环里 `+=` 拼字符串"是同一种形状。
2. **比较次数正好是 `N(N-1)/2`。** 1000 给 499,500，2000 给 1,999,000，一个不多一个不少。说明每次插入都要把已经在表里的全部键比一遍——一次都没省。
3. **8,000 个键要 6.5 秒，而正常 int 键是 1.2 毫秒——差 5,377 倍。** 查一遍更狠：6.537 s 对 0.00036 s，**一万八千倍**。
4. **代码一行没改，只是键的哈希函数坏了。** 这正是这一类 bug 难查的原因：字典还在工作，`d[k]` 还能返回正确结果，只是慢。你不会看到报错，你会看到"CPU 有点高"。

机制一句话：CPython 的 dict 是**开放寻址**。槽被占了，它就按一个固定序列往后探（再哈希、扰动、线性探测），直到找到空槽或匹配。所有键的哈希相同，它们就排在**同一条探测链**上——第 n 个键要探 n 次，总共 n²/2 次。表再大也没用，因为起点永远是同一个槽。

这条对自定义对象很实在：`__hash__` 写得草率（比如 `return 0`、`return self.id % 4`、只返回某一位）不会让程序错，只会让它在对数个月后变成"这个接口偶尔很慢"。

### 四、几条不能靠直觉的 hash 事实

```text
hash(1)        = 1
hash(-1)       = -2          ← -1 被留作错误码，映射到 -2
hash(-2)       = -2          ← 和 -1 撞了，这是故意的
hash(True)     = 1
hash(1.0)      = 1
hash(False)    = 0
hash(0.0)      = 0
hash(2**61-1)  = 0           ← 模 2^61-1 的梅森素数哈希，正好归零
hash(10**30)   = 465258685558744706
hash(None)     = -9223363241783493680
hash((1,'a'))  = -1175938143325277571
hash(frozenset({1,2,3})) = -272375401224217160
```

前几行不是冷知识，是**契约的现场证据**：`1 == 1.0 == True`，所以它们的哈希必须相同（Python 保证数值相等就同哈希）。后果很直接：

```python
d = {1: "int"}
1.0 in d      # True
True in d     # True
d[True]       # 'int'

d[1.0] = "float"
d             # {1: 'float'}   ← 整数键被覆盖了
```

**字典里没有"整数键 1"和"浮点键 1.0"两个东西，只有一个槽。** 拿 `True` 当键去查，查到的也是它。

`hash(2**61-1) == 0` 这条更值得记：整数哈希取的是 `n mod (2^61-1)`。所以 `2^61-1` 的倍数全都哈希到 0——如果有人拿时间戳（毫秒级，恰好接近这个量级）直接当哈希，就会得到一批系统性撞车的键。

### 五、契约的三种崩法

`__hash__` 和 `__eq__` 的约定只有两句：**相等的对象必须同哈希；参与哈希的字段不能在对象存活期间改变。** 破坏它的方式有三种，危险程度完全不同。

**第一种：只写了 `__eq__`，没写 `__hash__`。** Python 会把 `__hash__` 自动置成 `None`：

```text
EqOnly.__hash__ = None
hash(EqOnly(1)) → TypeError: unhashable type: 'EqOnly'
```

这是**最好的**一种崩法：立刻报错，位置明确。`@dataclass(eq=True)` 默认就是 `frozen=False`，也不生成 `__hash__`——所以 mutable 的 dataclass 不能当键，这是设计，不是遗漏。

**第二种：参与哈希的字段被改了。** 这是最坏的一种，因为它一声不响：

```text
d = {BadKey(1): '值'}，len(d) = 1
k in d → True

k.v = 2                # 改了参与 __hash__ 的字段
k in d → False
len(d) 还是 1
d[k]   → KeyError
表里现在躺着：[<BadKey object at 0x...>]
```

**键还在表里，`len` 数得到它，但你再也够不着它。** 因为它现在哈希到别的槽去了，查找顺着新槽走，走到头也找不到那条记录。

再补一刀：

```text
d[BadKey(2)] = '新'
len(d) = 2             # 一个够不着的僵尸键 + 一个真的新键
```

于是你会看到内存一路涨、`len` 一路涨、命中率一路掉——三个症状指向三个不同的地方，其实是一个原因。今天那个"缓存命中率 0"的 bug 就是这一种。

**第三种：两个对象相等，但哈希不同。** 这是第二种的静态版本：

```text
a == b → True，hash(a)=100，hash(b)=200
d = {a: 'a'}
b in d → False
```

**字典先按哈希找槽，再用 `__eq__` 确认。哈希指错了地方，它连比较的机会都没有。** 所以"我重写了 `__eq__`，为什么查不到"这个问题的答案永远是：你只写了一半。

一句话记住顺序：**哈希决定去哪一排找，`__eq__` 决定是不是同一个人。** 排错了，人再对也没用。

### 六、`is` 不是 `==`，字典只认后者

顺手把身份和相等分清，因为这两件事在 dict 里离得很近：

```text
int('256') is int('256')  → True    （-5..256 被缓存，同一个对象）
int('257') is int('257')  → False
'sensor' is 'sensor'      → True    （标识符样字符串被驻留）
''.join(['sen','sor']) is 'sensor' → False
但 == 是 True，hash 也相同
```

`is` 比的是"是不是同一块内存"，`==` 比的是"值是否相等"。**字典只在乎后者**（内部有一个 `is` 快路径，但那只是优化，不改语义）。

所以别用 `is` 比字符串、比数字：它在小整数和驻留字符串上"看起来能用"，一旦换成长字符串或运行时拼出来的值就立刻翻车——而且翻得没有规律，比彻底坏掉更难查。

### 七、插入顺序是规范，但"有序"不等于"排序"

3.7 起，dict 保证按插入顺序迭代，删掉中间的元素也不会重排：

```text
{'a','b','c','d','e','f'} → 删 'c'、加 'g'
['a', 'b', 'd', 'e', 'f', 'g']      ← 新键永远追加到末尾
```

这条很实用：日志按插入顺序输出、配置项按声明顺序序列化、`json.dumps` 出来的字段顺序稳定——都可以靠它，不用再排一次。

但两个坑：

- **它记的是"插入顺序"，不是"任何有意义的顺序"。** 想按值排还是得 `sorted(d.items(), key=...)`。
- **set 没有这个承诺。** 同样的元素、同样的构造方式，迭代顺序可能和你想的不一样，也可能跨版本变化。要稳定输出就 `sorted(s)`。

另外，dict 的键在 `del` 之后不会立刻收缩——entries 数组留着位置，新的插入可以复用它。所以"反复增删同一个键"不会让表无限长大，但"反复增删大量不同的键"会让 `sizeof` 停在峰值附近。

### 八、可哈希性决定能不能进缓存

`functools.lru_cache` 的键就是参数元组，所以参数必须可哈希：

```text
f([1,2,3])   → TypeError: unhashable type: 'list'
f((1,2,3))   → 6      （元组可哈希）
```

这条人人都会背，但真正踩坑的是另一半：**"可哈希"不等于"能正确命中"。** 用一个 `__hash__`/`__eq__` 都正确的自定义对象当参数，缓存是能命中的：

```text
g(BadKey(1)) → 1
g(BadKey(1)) → 1
cache_info: hits=1, misses=1, currsize=1     ← 两次调用，只算了一次
```

而只要那个对象的哈希依赖一个会变的字段，就会变成第五节第二种：`misses` 一路涨、`currsize` 一路涨、内存一路涨，永远命中不了。

**判断标准很简单：一个值能不能当字典键，就看它"是不是一个值"。** 数字、字符串、元组、frozenset、frozen dataclass 是值；list、dict、set、mutable 的对象是"容器"或"实体"，它们的内容会变，不能拿来当身份证。

### 九、扩容是摊还线性的：4M 个键，每键 147 纳秒

| N | 建表 | 每键 | `sys.getsizeof(dict)` |
|---|---|---|---|
| 10,000 | 0.001171 s | 117.1 ns | 294,992 |
| 100,000 | 0.014145 s | 141.5 ns | 5,242,960 |
| 1,000,000 | 0.128656 s | 128.7 ns | 41,943,128 |
| 4,000,000 | 0.586677 s | 146.7 ns | 167,772,248 |

数据量涨 400 倍，单键成本从 117 涨到 147 纳秒——涨了 25%，不是 400 倍。**这就是"摊还"**：扩容那一次确实要重排所有键，但它发生在容量翻倍时，前面的插入把成本摊掉了。摊到每个键上，就是常数。

内存那一列更值得看：4M 个键值对占 168 MB，**折合每个条目 42 字节**，而这还不含键和值对象本身（4M 个 Python int 自己还要一百多 MB）。所以"用 dict 做缓存"的时候，账要这么算：一条缓存 42 字节起步，加上键和值的对象开销，一条通常一百多字节。十万条就是十几 MB——在 RK3588 上不算什么，在 nRF5340 的 512 KB RAM 上就是天文数字。

顺带一个反应：`{i: i for i in range(N)}` 这种"键值同一个对象"的写法，4M 条只用 168 MB 的表；如果值另建对象，内存会翻倍。

### 十、字符串哈希跨进程会变——这不是 bug

```text
默认（连跑三次）：-6785426295506647997  →  3960505434323197766  →  3481437884851365714
PYTHONHASHSEED=0：-2096571579003691106（固定）
```

字符串和字节的哈希每次启动都换一个盐。这是 **PYTHONHASHSEED 随机化**，目的是防"哈希洪泛攻击"：攻击者构造一批同哈希的键，把你的字典打成 O(n²)，一个请求拖死服务器。

三个实际后果：

1. **`hash()` 的结果不能落盘、不能跨进程比较。** 想存"内容的指纹"用 `hashlib.sha256`，别用 `hash()`。
2. **同一个 dict 在两个进程里，`repr` 一样，但内部槽位不同。** 只要你不依赖 `hash()` 的返回值，行为就完全一致。
3. **整数哈希是稳定的**（`hash(n) == n`），所以整型键的字典行为跨进程可复现。这也是为什么"用整数 ID 当键"比"用字符串当键"更省心——不只是快，还可预测。

### 十一、能抄走的部分

1. **循环里做成员检查，先把容器换成 set 或 dict。** 100 万条上是 44.6 万倍的差距，这不是优化，是能不能用。
2. **`__hash__` 必须和 `__eq__` 一起写。** 只写一个的两种结果：报 `TypeError`（幸运），或者产生查不到的僵尸键（不幸）。
3. **能当键的字段，一律设成不可变。** `@dataclass(frozen=True)` 是最省事的写法，它同时给你正确的 `__eq__`、`__hash__` 和"改就报错"。
4. **自定义 `__hash__` 要分散。** `return 0`、`return self.x % 8` 这类写法会让字典退化成链表；用 `hash((a, b, c))` 把多个字段组合起来。
5. **别拿 float 当键。** `0.1 + 0.2 != 0.3`，累计出来的浮点值当键，命中率会莫名其妙地低。要按时间分桶就用整数 tick 或 `round(t, 3)` 之后转成整数。
6. **别拿 `is` 比字符串和数字。** 小整数缓存和字符串驻留会让它在测试里通过，在生产里随机失败。
7. **dict 的顺序可以依赖，set 的不行。** 要稳定输出就 `sorted()`。
8. **`len(d)` 不能当"我存了多少条有效数据"看，除非键真的不变。** 僵尸键会一起被数进去。
9. **`hash()` 不落盘。** 要指纹用 `sha256`；要可复现的哈希用 `PYTHONHASHSEED=0`，但那只是调试手段。
10. **打点三个数：`len(d)`、`sizeof`、命中率。** 三个一起涨、命中率不涨，基本就是键在变（或者 `__eq__` 写错了）。

### 十二、和手上的东西对上

- **rp_server 的设备表**：`if dev in device_list` 这种写法，在几百个设备时看不出来，几千个就开始吃 CPU。换成 `dict[(device_id, channel)]`，用元组当键——元组可哈希，前提是两个字段都不变。
- **CAN 报文的去重/计数**：键用 `(can_id, 整数 tick)`，不要用浮点时间戳。同一帧在两次接收里时间戳不会严格相等，用它当键等于每次都是新键。
- **nRF5340 上的 C**：没有 dict，但机制一样——固定桶数的哈希表，哈希函数必须把 key 散开，装载因子超过 0.7 就扩容。`hash(& 0x3F)` 这种写法在小表上没问题，表一大就是今天第三节那条曲线。
- **POS 流水按商品名聚合**：`"苹果"` 和 `"苹果 "`（尾随空格）、全角 `"Ａpple"` 和半角 `"Apple"`，是四个不同的键、四个不同的哈希。聚合前先 `strip()` + `normalize("NFC")`，和 11-01 那篇的 `fold_key` 是同一件事。
- **带参缓存**：参数里有 list/dict 就先 `freeze` 成元组（今天的代码片段），否则 `lru_cache` 直接 `TypeError`；参数里有会变的对象，就要在调用前快照它的值，别把活的引用塞进去。

一句话总结今天量到的东西：**哈希表用"键永远不变"换来了常数时间。这条合同绝大部分时候没人看，直到某一天你的键变了——代码不报错，表还在长，答案没了。**

## 🧩 今日代码片段：hashkit — 把任意结构变成可哈希的键

`freeze`（递归把 list/dict/set 折成元组，顺序无关）、`frozen dataclass`（自动拿到正确的 `__eq__` / `__hash__`）、以及把它们接到 `lru_cache` 上的用法。下面这段是真跑过的，输出贴在后面。

```python
# -*- coding: utf-8 -*-
"""hashkit：把任意嵌套结构变成可哈希的键，给缓存和去重用"""
import functools
import sys
from dataclasses import dataclass

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass


def freeze(obj):
    """把 list / tuple / dict / set 递归转换成可哈希的元组。

    dict  → ('d', (键, 值) 排序后的元组)   把字典当"内容"比，而不是当对象比
    set   → ('s', 排序后的元组)
    list  → 元组（list 不能当键，元组可以）
    其余  → 原样返回（要求本身可哈希）

    排序是为了让 {'a':1,'b':2} 和 {'b':2,'a':1} 折成同一个键。
    """
    if isinstance(obj, dict):
        items = [(freeze(k), freeze(v)) for k, v in obj.items()]
        items.sort(key=repr)
        return ("d",) + tuple(items)
    if isinstance(obj, (set, frozenset)):
        items = sorted((freeze(x) for x in obj), key=repr)
        return ("s",) + tuple(items)
    if isinstance(obj, (list, tuple)):
        return tuple(freeze(x) for x in obj)
    return obj


@functools.lru_cache(maxsize=None)
def summarize(query):
    """带参计算：query 是 freeze 过的键，可以放心进缓存"""
    return "len=%d, fields=%d" % (
        len(query), sum(len(p) for p in query if isinstance(p, tuple)))


@dataclass(frozen=True)          # frozen=True 自动生成正确的 __eq__ 和 __hash__
class Reading:
    device: str
    channel: int
    value: float


if __name__ == "__main__":
    print("1) freeze：任意嵌套结构 → 可哈希")
    a = {"device": "imu", "axes": [1, 2, 3], "tags": {"x", "y"}}
    b = {"tags": {"y", "x"}, "axes": [1, 2, 3], "device": "imu"}
    fa, fb = freeze(a), freeze(b)
    print("   a 的键 =", fa)
    print("   字典顺序不同、集合顺序不同，折成的键相同：", fa == fb)
    print("   可哈希：是（%d）" % hash(fa))

    print()
    print("2) 用 freeze 之后，带参计算能进 lru_cache")
    print("   summarize(freeze(a)) →", summarize(freeze(a)))
    print("   summarize(freeze(b)) →", summarize(freeze(b)))
    print("   cache_info:", summarize.cache_info(), " ← 两次调用、只算了一次")

    print()
    print("3) frozen dataclass：自动拿到正确的 __hash__ / __eq__")
    r1, r2, r3 = Reading("imu", 0, 23.5), Reading("imu", 0, 23.5), Reading("imu", 0, 24.0)
    print("   r1 == r2 →", r1 == r2, "| hash 相同 →", hash(r1) == hash(r2))
    print("   r1 == r3 →", r1 == r3)
    print("   放进 set：", len({r1, r2, r3}), "个元素（r1/r2 去重）")
    try:
        r1.value = 99
    except Exception as e:
        print("   改字段 → %s: %s  ← 不可变，键永远稳定" % (type(e).__name__, e))
```

实测输出：

```text
1) freeze：任意嵌套结构 → 可哈希
   a 的键 = ('d', ('axes', (1, 2, 3)), ('device', 'imu'), ('tags', ('s', 'x', 'y')))
   字典顺序不同、集合顺序不同，折成的键相同： True
   可哈希： 是（1030365392191883425）
   直接 hash({'a':1}) → TypeError: unhashable type: 'dict'

2) 用 freeze 之后，带参计算能进 lru_cache
   summarize(freeze(a)) → len=4, fields=6
   summarize(freeze(b)) → len=4, fields=6
   cache_info: CacheInfo(hits=1, misses=1, maxsize=None, currsize=1)  ← 两次调用、只算了一次

3) frozen dataclass：自动拿到正确的 __hash__ / __eq__
   r1 == r2 → True | hash 相同 → True
   r1 == r3 → False
   放进 set： 2 个元素（r1/r2 去重）
   改字段 → FrozenInstanceError: cannot assign to field 'value'  ← 不可变，键永远稳定
```

三个值得说的细节：

- **`freeze` 里那个 `("d",)` 前缀不能省。** 它是类型标签：没有它，`freeze({"a": 1})` 和 `freeze([("a", 1)])` 会折成同一个元组，两个语义不同的东西在缓存里撞成一条。同理 `("s",)` 和普通元组要分开。
- **`items.sort(key=repr)` 是故意的。** 键可能是混合类型（`1` 和 `"1"`），直接 `sort()` 会 `TypeError`；按 `repr` 排虽然不好看，但**稳定、总序、不会抛异常**。代价是 `freeze` 的结果依赖 `repr` 的写法——它只用来当键，不落盘，所以可以接受。
- **`frozen=True` 的 dataclass 连 `__hash__` 都替你写对了**，而且字段一改就抛 `FrozenInstanceError`。这不是"更严格"，是**把契约变成语言强制**——今天第五节那三种崩法，它一种都不给你机会。
