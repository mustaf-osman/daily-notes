# 📅 2026年11月18日 日报

## 💭 技术随想：程序结束不是「一个瞬间」，是三层

昨天判「两个东西是不是同一个」，今天干脆问一个更狠的问题：**一个进程「结束」，到底发生了什么？**

我原以为答案是「函数返回了，进程就没了」——一句话。实测下来，这句废话背后是三件独立的事同时在发生：

1. **一个数字**：退出码，给外面人看的（可分 8 位、32 位，还有负数）
2. **一串清理**：`finally` 跑不跑、`atexit` 跑不跑、缓冲区里的字节吐不吐出去
3. **一个方式**：自己走的、被信号请走的、还是被强杀的——这三者的差别在 Windows 上甚至看不见

下面每个数字都是刚在这台机器上跑出来的（Windows 11 / Python **3.14.9** / MSYS bash）。有几处我第一版量错了，原因也写进去了——**错的那一遍比对的更有教学价值**。

### 一、退出码只有低 8 位：256 变成 0

```text
$ python3 -c "import sys; sys.exit(n)"; echo $?
  n=0     -> $?=0
  n=1     -> $?=1
  n=255   -> $?=255
  n=256   -> $?=0        ← 256 被砍掉了上面的位，变成「成功」
  n=257   -> $?=1
  n=300   -> $?=44       ← 300 减 256
  n=512   -> $?=0
  n=-1    -> $?=127      ← 负数绕了一圈
```

**这条规则是一颗定时炸弹的形状**：一个「失败」的退出码，只要数值是 256 的倍数，到了外面就变成「成功」。

真到哪儿会踩？脚本里写 `sys.exit(status)`，而这个 `status` 是从别处**原封不动搬来**的数字（老 C 代码里的 `wait()` 状态、硬件寄存器值、某次 `>> 8` 之前的东西）。运行的那一步返回 1，搬到脚本出口就可能是 256，然后 CI 亮绿灯。

### 二、同一个数字，四个「看的人」四个答案

这是今天最意外的一条。同一个 `sys.exit(256)`：

| `sys.exit(n)` | 原生 API 看（`subprocess`） | MSYS bash 看（`$?`） |
|---|---|---|
| `1` | `1` | `1` |
| `255` | `255` | `255` |
| `256` | **`256`**（0x100） | **`0`** |
| `300` | **`300`**（0x12c） | **`44`** |
| `-1` | **`4294967295`**（0xffffffff） | **`127`** |

同一台机器、同一个进程、同一个瞬间，两个「看的人」给的是两个数。**因为退出码压根不是一个数，是一个「约定」**：Windows 的进程退出码是 32 位无符号数（所以 `-1` 变成 4294967295），POSIX 的 shell 只保留低 8 位（所以 256 变成 0），bash 再额外把「被信号杀」编码成 128+信号。

三条实用的推论：

1. **退出码只能表达 0-255 这几个状态**，超出的部分不是被丢掉就是变形成另一个意思。
2. **别拿退出码当数据通道**。要传状态就写 stdout / 写文件 / 写日志；退出码只回答一个问题：「成功了吗」。
3. 老 C 代码里 `wait()` 之后要 `WEXITSTATUS(status)` 才拿得到真正的退出码——Python 的 `subprocess` 已经帮你做完了这件事（所以它给你的 `256` 是原值，不是被砍过的 0）。**跨语言对照的时候，这就是「同一个数字」对不上的原因。**

### 三、Windows 上「被信号杀」看不出来

在 Linux 上，Python 用**负数**表示「进程被信号杀了」，`-15` 就是 SIGTERM。同一行代码在 Windows 上：

```text
$ python3 -c "import os, signal; os.kill(os.getpid(), signal.SIGTERM)"
  子进程拿到的 returncode = 15        ← 正数，跟「正常退出、退出码 15」一模一样
```

所以「进程为什么没了」这件事，在 Windows 上是**问不出来的**：`15` 既可能是「自己 `sys.exit(15)`」，也可能是「被 TerminateProcess 干掉」。在 Linux 上这两件事长得完全不同（`15` vs `-15`）。

**写跨平台的进程管理代码时，绝不能靠 returncode 的正负号判断「是不是被杀的」。** 想区分就得自己记日志、或者用父进程侧的信号发送记录。

### 四、谁先跑：`finally` → `atexit`（后进先出），`os._exit` 全都跳过

一个进程「正常结束」的清理次序，实测是这样的：

```text
main start
inside try
finally 跑了                    ← try/finally，最早
atexit #2                      ← atexit 是「后注册的先跑」（栈）
atexit #1
$?=7                           ← 前面 return 的 7 一路传到外面
```

四个点值得记住：

- **`finally` 在 `atexit` 之前**。语法层面的清理，优先于「注册钩子」层面的清理。
- **`atexit` 是栈，不是队列**：后注册的先执行（实测 `#2` 在 `#1` 前面）。
- **`return 7` 的 7 会完整传到外面**（这台机器上 `$?=7`），清理动作不改变退出码——**除非清理过程中自己 `sys.exit(别的数)`**，那就会顶掉原来的。
- **`os._exit(0)` 是「什么都不做直接消失」**：

```text
进 try
（finally 没跑、atexit 没跑）
$?=0                            ← 而且是 0：一个「假装成功」的结束
```

用 `os._exit` 的理由通常是「不想让子线程/清理逻辑拖住退出」，代价是**日志、临时文件、锁、socket 全都不收尾，还对外宣布成功**。想「快速退出」但保留清理，正确做法是先 `sys.stdout.flush()` / `logging.shutdown()` 再 `os._exit`，而不是直接跳。

### 五、信号：Windows 上它只是个编号，进程是被「抹掉」的

我给子进程注册了 `SIGTERM`、`SIGINT`、`SIGBREAK` 三个 handler，handler 里**写一个标记文件**——这样「handler 跑没跑」是可以查证的，不用猜。然后从六个方向「杀」它：

```text
发送方式                               returncode   标记文件里有什么
terminate()                            1            ready pid=…        ← handler 没跑
send_signal(SIGTERM)                   1            ready pid=…        ← handler 没跑
send_signal(SIGINT)                    ValueError: Unsupported signal: 2
CTRL_BREAK_EVENT（新建进程组）          1            ready pid=…        ← handler 没跑
CTRL_C_EVENT（新建进程组）              1            ready pid=…        ← handler 没跑
taskkill /F /PID                       1            ready pid=…        ← handler 没跑
```

**六次里，handler 一次都没跑。** 标记文件里永远只有进程启动时写的那一行。

原因不神秘：Windows 没有真正的信号。所谓「发信号」在原生 API 层面就是 `TerminateProcess`——**从外面把进程抹掉，不给你进去执行任何代码的机会**。`send_signal(SIGTERM)` 不是「通知」，是「删除」，所以注册 handler 只是让代码看起来跨平台，实际在 Windows 上**静默无效**。

同一件事在 MSYS bash 里那条路上更绕：我从 bash 里 `kill` 一个原生 Windows Python，bash 报的退出码倒是标准得很：

```text
kill -TERM  -> $?=143   （128+15）
kill -INT   -> $?=130   （128+2）
kill -9     -> $?=137   （128+9）
```

但注意：**这三条里子进程注册的 handler 也没跑**（标记文件同样是空的），因为 MSYS 走到最后还是用 `TerminateProcess` 收尾。所以「退出码看起来是 143，很像被优雅地请走」——**它其实是被抹掉的**。这就是这类 bug 的味道：外面的数字很对，里面的收尾一行没做。

**反过来，能靠得住的只有一件事：进程自己决定什么时候走。** 想要优雅退出，就别指望信号，要靠自己检查一个「该退出了」的标志位（或队列里的消息），并且保证**关键状态是「随时可以死」的**——写一条就落盘一条，而不是攒在内存里等退出时统一写。

### 六、被强杀时丢的正是「最后一段」：缓冲区实测

`print` 之后，内容**不是立刻到别人眼里的**。写文件实测（每行 14 字节）：

| 写了 | 别人（另一个进程）看到 | 还压在缓冲区里 |
|---|---|---|
| 100 行（1,400 字节） | **0 字节** | 1,400 |
| 1,000 行（14,000 字节） | **0 字节** | 14,000 |
| 5,000 行（70,000 字节） | **0 字节** | 70,000 |
| 10,000 行（140,000 字节） | 122,960 字节 | 17,040 |
| 50,000 行（700,000 字节） | 614,780 字节 | 85,220 |
| 100,000 行（1,400,000 字节） | 1,352,510 字节 | 47,490 |
| 200,000 行（2,800,000 字节） | 2,705,010 字节 | 94,990 |
| 400,000 行（5,600,000 字节） | 5,532,980 字节 | 67,020 |

三条读法：

- **写了 7 万字节，别人一个字都看不见。** 教科书说「8 KB 缓冲」，实测这台机器上是 **7 万字节还没吐**，而写到几十万字节时，**任何时刻都还有 1.7 万到 9.5 万字节压在里面**。这个阈值是实现细节（随版本、平台变），所以别记数字，**记结论：没有上限假设，只有「flush 之前谁都看不见」**。
- 所以**「程序里 print 过了」和「日志里能看到」是两件事**。崩溃现场最要紧的那几行——`最后处理到第几个包`、`哪个参数是 None`——恰好就在那压着的几万字节里。
- 强杀实测：写 10 行、没 flush，被强杀后文件是 **0 字节**；同样的 10 行调过 `f.flush()`，强杀后 230 字节**全都在**。

对照组的 `f.flush()` 更值得说：写 200,000 行后调一次 `flush()`，别人立刻看到完整的 **2,800,000 字节**。**一行 `flush=True` 换来的不是性能，是「死的时候还能说话」。**

### 七、`f.tell()` 会顺手 flush（我第一版就是被它骗的）

我第一次量「缓冲区里压了多少」时，得到的是**全部为 0**——看起来「Python 根本没缓冲」。原因在最后一行：

```text
写 10 行后 不调用 f.tell()：1 秒时另一个进程看到   0 字节
写 10 行后 调用   f.tell()：1 秒时另一个进程看到 140 字节
```

`tell()` 必须知道「我现在写到哪了」，为此它**先把缓冲区吐给操作系统，再回答你的问题**。所以「量一下位置」这个看起来完全无副作用的动作，把整个实验的前提改掉了。

**`tell()` 能当 `flush()` 用，这件事本身就是个坑**：一段代码里出现 `f.tell()`（哪怕只是打日志用），前面所有「缓冲会不会丢」的判断就都不成立了。要判断缓冲状态，就去看 `os.fstat(f.fileno()).st_size`——**它不 flush，只报告操作系统的看法。**

### 八、`print` 完 ≠ 别人看得见：管道实测

同样是输出到**管道**，下游什么时候能看到第一行：

```text
默认缓冲              三行全部在 3.08 秒才到     ← 进程退出那一刻才吐出来
python -u             前两行 0.09 秒到，最后一行 3.1 秒（它那时才被打印）
PYTHONUNBUFFERED=1    前两行 0.08 秒到
```

那个 `3.08 秒` 是关键：**子进程在 0.1 秒时就把「第一行」写进了自己的缓冲区，但下游干等了 3 秒，直到进程正常退出才一起收到。** 上游自己的时间线（0.1 秒就写完了）和下游的时间线（3 秒后才看见）可以差出几十倍。

顺带一个我自己踩的坑：**读的那一侧也有缓冲。** 我第一版用 `p.stdout.read(64)` 去读，结果三种情况都报 `0.00 秒`——因为 `BufferedReader.read(n)` 会**一直等到读满 n 字节或者遇到 EOF**，它把「等不到数据」伪装成了「立刻拿到数据」。换成 `read1()` 之后，才看到真实的到达时刻（0.00 秒 / 3.08 秒 的差别）。

**所以「延迟看不见」往往不是没有延迟，而是你的量法自己吞掉了延迟。**

还有一条免费收获：`stderr` 是行缓冲（实测 `line_buffering=True`），`stdout` 不是（接管道、接文件都是 `line_buffering=False`）。**同样的 `print`，一条走 stdout 会攒着，一条走 stderr 立刻出去。** 这也是为什么「日志已经打出来了，但报错信息出现得更早」——不是日志慢，是走的路不同。

（终端的情况我这次没有实测：定时任务里没有真正的终端。Python 的规则是「接终端时 stdout 行缓冲」，这条来自文档，不在今天的实测数据里。）

### 九、shell 侧：退出码在哪五处被吃掉

```text
false;                     -> $?=1
false && echo "不该出现"    -> $?=1     ← && 短路，$? 是 false 的
true  || echo "不该出现"    -> $?=0
false | true               -> $?=0     ← 整条管道只看最后一个命令
set -o pipefail; false|true-> $?=1     ← 打开它才看整条管道
(exit 3); (exit 4)         -> $?=4     ← 两条独立命令，只记最后一条
if false; then :; fi       -> $?=0     ← if 把失败吃掉了
nosuchcmd_xyz              -> $?=127   ← 命令不存在
```

「五处被吃掉」分别是：

1. **管道**：`|` 之后只有最后一个命令的退出码被保留，前面失败了也看不见。
2. **`;` 串起来**：只记最后一条。
3. **`&&` / `||`**：`$?` 是「短路后实际执行的那条」的。
4. **`if` / `while` 的条件**：失败是被设计成「正常」的，不会中断脚本。
5. **128+n 的编码**：`130`/`143`/`137` 这种「大数字」不是程序自己给的，是 shell 在说「它被信号杀了」。

最要紧的是第 1 条，因为它藏在最常见的写法里：**`python build.py | tee build.log` 这条命令的退出码永远是 `tee` 的 0**。构建失败了，脚本照样往下走。

### 十、管道断了：生产者被投诉，但没有被判罪

```text
$ python3 -c "for i in range(200000): print(i)" | head -3
0
1
2
管道退出码 $?=0（取 head 的）
被测程序自己的 stderr:
    BrokenPipeError: [Errno 32] Broken pipe
    Exception ignored while flushing sys.stdout:
    OSError: [Errno 22] Invalid argument
```

下游 `head` 拿了 3 行就走，管道断了，生产者写不下去——**它自己被投诉了（stderr 里两条错），但整条管道的判决书是 0。** 这跟上一节是同一条规则的两种表现：**管道的退出码属于最后一个人，生产者的痛苦只写到 stderr。**

### 十一、对着手上的东西看

- **`rp_server` 的启动脚本 / 服务定义。** systemd 的 `Restart=on-failure` 判的是「退出码非零」和「死因」——所以两件事要盯：**① `os._exit(0)` 式的假成功会让它不重启**（实测：清理全跳过、退出码 0）；**② 被信号杀掉时的退出码在 Linux 上是负数/或 128+n**，systemd 有一份「算干净」的信号清单（`SIGHUP`/`SIGINT`/`SIGTERM`/`SIGPIPE`），这条来自文档，我这台机器上没有 systemd 可测，真要确认就 `systemctl show -p ExecMainStatus` 现场看一眼。**别凭记忆改 unit 文件。**
- **烧录 / 部署脚本。** 只要出现 `| tee`、`| grep`、`| tail`，**前面那步的失败就没了**（实测 `false | true` 是 0）。修法就一行：脚本开头写 `set -euo pipefail`。特别是「先编译、再烧录、再验证」的链子，中间任何一步被管道挡住都可能被当成成功。
- **日志的「最后一段」。** 实测压着的可以有 9 万字节——**崩溃前那几行往往就在里面**。关键路径上的日志（状态切换、收到什么报文、进入哪一步）用 `flush=True`，或者说清楚 `logging` 里 `StreamHandler` 的 `flush()` 行为。热循环里别用，一条一条一系统调用的代价是真的。
- **跨进程传状态。** 退出码只能表达 0-255，`256 → 0`（实测）。要传「具体是哪种失败」，用 stdout 的 JSON / 退出码 + 日志文件，别把硬件寄存器值或 C 那边的原始 status 直接 `sys.exit()` 出去。
- **`finally` 里别再 `sys.exit()`。** 实测清理动作不改变退出码，但清理里自己退一次就会顶掉原来的——**「本来要报警的 1，变成了清理逻辑给的 0」**，而这件事没人会注意到。
- **「我在 Windows 上注册了 SIGTERM handler」这句话要打问号。** 实测六种杀法 handler 一次都没跑。要么接受「Windows 上就是硬杀」，要么把「该退出了」做成自己的标志位检查，别把优雅退出寄托在信号上。

### 十二、一句必须说清楚的诚实

- **确定属于「规定」的**：`finally` 早于 `atexit`、`atexit` 后进先出、`os._exit` 跳过清理（语言层面）；POSIX shell 只保留 8 位、`128+n` 表示信号（约定层面）；`-N` 表示信号杀（Python 在 POSIX 上的约定）。
- **属于「这台机器这一次」的实现细节**：缓冲区到底压到 7 万还是 9 万字节才吐（我实测的浮动区间是 17,040 到 94,990 字节，没有固定值）、文本层往二进制层搬的节奏、`os.kill(SIGTERM)` 在 Windows 上给 15、MSYS 报的 127/143 里面有多少是 MSYS 自己的换算。
- **没有实测的**：Linux 上的真实信号行为（我是在 MSYS bash + Windows 原生 Python 上量的）、systemd 的干净信号清单、真终端下的行缓冲（定时任务里没有终端）。
- 所以上面每一张表都标了出处：**「实测」的就是刚跑出来的，「来自文档」的我在句子里写明**。这两类不能混着说——昨天讲「身份/值/哈希是三套规则」，今天这个道理是一样的：**「结束」也是三套规则：退出码（约定）、清理（语言）、死因（操作系统），混着看就得出「它明明成功了啊」这种结论。**

## 🧩 今日代码片段：`exitkit.py` —— 三件跟「结束」有关的小工具

四个东西，每个解决今天暴露的一个问题：**把 `returncode` 翻译成人话**、**跑命令并说清是失败还是被杀**、**每写一行立刻落盘的日志**、**量出「我说写了多少 / 别人看到多少」的差额**。

```python
# -*- coding: utf-8 -*-
"""exitkit.py —— 三件跟「进程怎么结束」有关的小工具"""
import atexit
import os
import signal
import subprocess
import sys


def describe(returncode):
    """把 returncode 翻译成人话。负数在 POSIX 上表示「被信号 N 杀掉」。"""
    if returncode is None:
        return "还在跑"
    if returncode < 0:
        try:
            name = signal.Signals(-returncode).name
        except ValueError:
            name = "未知信号"
        return f"被信号杀掉：{name}（{128 + (-returncode)} = 128+{(-returncode)}）"
    if returncode == 0:
        return "正常退出（0）"
    return f"正常退出，但退出码是 {returncode}"


def run(cmd, timeout=30):
    """跑一条命令，返回 (退出码, 人话, 最后三行输出)。不动 shell，不做字符串拼接。"""
    p = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout)
    text = (p.stderr.strip() or p.stdout.strip())
    tail = text.splitlines()[-3:]
    return p.returncode, describe(p.returncode), tail


class Journal:
    """每写一行立刻落盘的日志。

    默认的 print(file=f) 会把内容压在缓冲区里（实测压到 9 万字节还没吐），
    进程被强杀时这一段就没了。写「关键日志」时用 flush=True，
    代价是每行一次系统调用；只在关键时刻用，别放进热循环。
    """

    def __init__(self, path):
        self.path = path
        self.f = open(path, "a", encoding="utf-8")
        atexit.register(self.close)

    def write(self, *parts):
        print(*parts, file=self.f, flush=True)   # ← flush 是唯一保证
        return self

    def close(self):
        if not self.f.closed:
            self.f.flush()
            self.f.close()


def pending_bytes(f, written):
    """written 是你自以为写进去的字节数，返回「还压在缓冲区里、别人看不见」的量。

    注意：绝对不要在这里用 f.tell()——tell() 会顺手 flush，量出来的永远是 0。
    fstat 不 flush，它只报告操作系统的看法。
    """
    return written - os.fstat(f.fileno()).st_size


if __name__ == "__main__":

    for args in (["-c", "pass"],
                 ["-c", "import sys; sys.exit(3)"],

                 ["-c", "import sys, os, signal; os.kill(os.getpid(), signal.SIGTERM)"]):
        rc, human, tail = run([sys.executable] + args)
        print(f"  rc={rc:<6} {human}")

    print("== pending_bytes()：写完不算数，落盘才算数 ==")
    f = open("exitkit_demo.txt", "w", encoding="utf-8")
    written = 0
    for i in range(5000):
        line = f"line-{i:07d}\n"
        f.write(line)
        written += len(line.encode("utf-8"))
    print(f"  我说我写了 {written} 字节，别人看到 {os.fstat(f.fileno()).st_size} 字节，"
          f"压住 {pending_bytes(f, written)} 字节")
    f.flush()
```

实测输出（Windows 11 / Python 3.14.9）：

```text
== describe() 对着真实子进程 ==
  rc=0      正常退出（0）
  rc=3      正常退出，但退出码是 3
  rc=256    正常退出，但退出码是 256          ← 原生 API 不砍 8 位
  rc=15     正常退出，但退出码是 15           ← 其实是「被 SIGTERM 抹掉」（Windows 上分不出来）
== pending_bytes()：写完不算数，落盘才算数 ==
  我说我写了 65000 字节，别人看到 0 字节，压住 65000 字节
  flush() 之后，别人看到 70000 字节
== Journal：立刻落盘 ==
  别的进程现在能读到 58 字节：'第一行：立刻就在磁盘上了\n第二行：同样'
```

四个值得说的细节：

- **`rc=256` 和 `rc=0` 是同一个进程的两种「看法」。** `describe()` 故意不在函数里做 `>> 8` 或 `& 0xff`——**它只报告「原生 API 看到的数」，因为它不知道外面那个看的人是 bash、systemd 还是另一段 Python。** 要砍 8 位就写在调用点，并且写上注释说明为什么。
- **`rc=15` 那行是今天最该被记住的一条。** 在 Linux 上它会打印「被信号杀掉：SIGTERM」；在 Windows 上它只能说「退出码 15」。**同一个函数、同一行代码，两台机器给出两种诊断能力**——这不是 `describe()` 写得不好，是 Windows 上「被信号杀」这件事本身没留下痕迹。
- **`pending_bytes()` 里的注释比代码重要。** 这个函数唯一的坑是「拿什么去问操作系统」，而 `f.tell()` 看起来是最自然的选择——它会顺手 flush，让函数恒返回 0，**看起来一切正常**。所以要注释的是「别用 tell」，不是「用 fstat」。
- **`Journal` 的 `flush=True` 换的是「会不会丢遗言」，不是速度。** 实测每行一次系统调用；所以它只在「状态切换、收到报文、进入某一步」这种真正需要复盘的点上用。另外它把 `close` 挂在 `atexit` 上——**即使没人调用 `close()`，正常退出时也会收尾**（而强杀时收不收无所谓，每行已经落盘了）。

一句话收这段：**「退出」有三套规则——退出码是给外面看的约定（只有低 8 位有效）、清理是语言层面的顺序（`finally` → `atexit` → 缓冲）、死因是操作系统的说法（Windows 上根本不说）。** 三套混着看，就会得到「它明明成功了啊」和「日志怎么少了两百行」这两种最费时间的 bug。
