# 📅 2026年11月15日 日报

## 💭 技术随想：一个字符串的「长度」，其实是三个数

昨天写时间，发现「一个 `time()`」里藏着两个量。今天轮到字符串——一模一样的坑，而且更隐蔽。

在这台机器上（Windows 11 / Python 3.14.9），`len("👨👩👧👦")` 返回 **7**。可你眼睛看到的，是 **1 个人**（一家四口）。而它落到文件里、发到网线上，是 **25 个字节**。

同一个字符串：**人眼 1 个、`len()` 7 个、字节 25 个。** `len()` 给你的只是中间那个，它既不等于你数出来的字，也不等于它占的空间。今天把这条链从头量到尾，下面每个数都是真跑出来的。

### 一、先把三个数一次摆出来

| 字符串 | 人眼看到的字 | `len()`（码点） | UTF-8 字节 | UTF-16 码元 |
|---|---|---|---|---|
| `café`（预合成 é = U+00E9） | 4 | **4** | 5 | 4 |
| `café`（e + 组合记号 U+0301） | 4 | **5** | 6 | 5 |
| 中文 | 2 | 2 | **6** | 2 |
| `😀` | 1 | 1 | 4 | **2** |
| `👨👩👧👦` | **1** | **7** | **25** | 11 |
| `Straße` | 6 | 6 | 7 | 6 |

三个数各说各话：

- **字节**：取决于用哪种编码。UTF-8 里一个汉字 3 字节、一个 emoji 4 字节——**所以「限长 20 字节」和「限长 20 字」是两个完全不同的门**。
- **码点（code point）**：Unicode 给每个字符编的号，`len()` 数的就是这个。本机 `sys.maxunicode = 0x10ffff`（宽构建），所以 `😀` 是 1 个，不是 2。
- **字素簇（grapheme cluster）**：**用户眼里的「一个字」**。`👨👩👧👦` 是 4 个 emoji + 3 个连字号（ZWJ，`U+200D`）拼出来的——7 个码点，**1 个字素簇**。

那 7 个码点当场验一下：

```text
family code points: ['0x1f468', '0x200d', '0x1f469', '0x200d', '0x1f467', '0x200d', '0x1f466']
```

四个「人」，中间夹三个不可见的 `U+200D`。**你在屏幕上看到的一个字，底层是七个码点手拉手。**

### 二、「长得一样」≠「相等」：两张表在这里分叉

上面那两行 `café` 长得**一模一样**，但：

```text
café(预合成)  ==  café(e+记号)  →  False
NFC(前者)     ==  NFC(后者)      →  True
```

一个是「é」这个字本身（U+00E9），另一个是「e」后面跟一个组合重音（`U+0301`）。渲染出来没有任何差别，**可字节不同、`len()` 不同、`==` 直接判 False**。修法只有一条：**在比较、查重、入库之前先做一次 Unicode 规范化（NFC）。** 顺手量了它的代价——对 5000 个字符做一次 NFC，本机约 **77.6 µs**。对于「几百字的用户名/设备名」这种量级，是亚微秒——**比一次数据库查询便宜两三个数量级。**

还有更阴的：`paypal.com` 和 `paypaı.com`（最后那个 `i` 是土耳其无点 `ı`，`U+0131`）——**肉眼几乎分不出，`==` 判 False，编码成一串字节也完全不同**。这就是 IDN 钓鱼的原理：**你以为你在比字符串，其实你在比字节。** 任何「看起来像就不许过」的场景（用户名重复、敏感词、白名单），靠 `==` 都不够。

### 三、大小写转换，会改变长度

这是最反直觉的一类，因为它连「长度守恒」都不保证：

```text
'ß'.upper()      →  'SS'       len 1 → 2     ← 一个字母变成两个
'İ'.lower()      →  'i̇'        len 1 → 2     ← 一个字母变成两个
'Straße'.upper() →  'STRASSE'  len 6 → 7
```

`Straße` 转大写之后**多了整整一个字符**。如果你有个字段假设「upper 之后长度不变」——比如先 `upper()` 再按固定长度对齐、或者先转大写再截断——**它的预算就错了。**

再往下一层：**「转小写」不够，要做「大小写折叠」（casefold）。**

```text
'Straße'.casefold()              →  'strasse'
'STRASSE'.casefold() == 'Straße'.casefold()  →  True     ← 折叠后对上了
'STRASSE'.lower()    == 'Straße'.lower()     →  False    ← 小写化对不上
```

搜索、去重、唯一索引的键，都应该用 `casefold()` 而不是 `lower()`——**`lower` 是给显示用的，`casefold` 是给比较用的。**

### 四、切字符串 = 拆乐高：`s[:n]` 是在切码点，不是切字

`len()` 之外，**切片也按码点走**，于是它会毫不犹豫地把你眼前的一个字劈成两半：

```text
👨👩👧👦abc  [0:1]  →  '👨'                ← 只剩一个男人，家没了，还留了个悬空的 ZWJ
cafe\u0301   反转   →  '\u0301efac'        ← 重音跑到最前面去了
```

第一行：按码点切会留下一个**末尾挂着 ZWJ 的残片**——渲染时可能跟下一个字粘连，或显示成两个孤立的 emoji。第二行更直白：**倒序一个带组合记号的字符串，重音不会跟着字母走**，它会掉在字符串开头。

按字节切更狠：

```text
'中文abc'.encode('utf-8')          = b'\xe4\xb8\xad\xe6\x96\x87abc'
raw[:2].decode('utf-8')  →  UnicodeDecodeError: unexpected end of data
raw[:4].decode('utf-8')  →  UnicodeDecodeError: byte 0xe6 in position 3
```

**一刀切在字节中间，解出来就是坏数据。** HTTP 报文、日志、文件按字节截断时踩的就是这个。

还有个容易忽略的：**`😀` 的 UTF-16 只有 2 个码元**（`0xD83D 0xDE00`，一对代理对）。这不是学术细节——**JavaScript 的 `"😀".length === 2`、HTML 的 `maxlength` 数的就是这一层。** 一个文本框 `maxlength="10"`，用户打 **5 个 emoji** 就被卡住了，而中文能打 10 个。**前端说「最多 10 个字」，跟后端说的不是同一件事。**

### 五、排序：码点序不是人眼序

```text
sorted(['Zebra','apple','Äpfel','banane'])              →  ['Zebra','apple','banane','Äpfel']
sorted(['Zebra','apple','Äpfel','banane'], key=str.casefold) →  ['apple','banane','Zebra','Äpfel']
```

`Ä` 的码点（U+00C4＝196）比 `a`（97）大，于是「Äpfel」被扔到了最后——**人眼看是 A 打头，机器眼里排在所有小写字母后面。** 想按「人的顺序」排，得显式给一个 locale 感知的比较器或 `casefold` 键。**「排好了」这个词，同样有两副面孔。**

### 六、和手上的东西对上

- **`rp_server` 的 `AT+HEAD` 和名字类字段。** 设备名、路径、别名如果存进配置又拿出来比对，**入库前必须 NFC**——否则「同一个名字」会因为你从哪个输入法、哪台机器复制而来，变成两个不同的字符串，查重失效。
- **日志和报文的「截断」。** 日志里截前 N 个**字节**，正好可能切断一个汉字的 UTF-8 / 一个 emoji——排出来的日志要么是乱码，要么触发解码异常。**按字截的是 `visible_len`，按空间截的才是字节，两个都别混用。**
- **UDP 9000 的报文长度字段。** 长度字段是**字节数**，而业务上说的「几个字符」是**码点/字素**——协议两端如果不是同一套口径，中文/emoji 一进去就对不上。
- **`daily-notes` 这个仓库本身。** 文件名、frontmatter、正文里都有中文和 emoji。**「今天写了几行的标题」「文件名长度」** 这类脚本，用 `len()` 会在 emoji 上翻车；真要稳，先 `NFC` 再按字素数。
- **前端输入框。** 我那个控制 App 里的输入限制，如果照的是 JS 的 `maxlength`，**它卡的是 UTF-16 码元，不是字**——中文/emoji 的可用额度跟你想的不一样。
- **一条判断标准：** 凡是要「数、切、比」字符串的地方，先问一句——**我要的是字节、码点，还是人眼那个字？** 三个问题，三种答案，用错就是偶发的、只在中文字符上炸的 bug。

### 七、一句必须说清楚的诚实

上面代码里那个「人眼看到的字」，我是**近似**着数的：它会把「基字符 + 组合记号」和「ZWJ 家族」合成一簇，但**不处理国旗（两个区域指示符配对）、肤色修饰、键帽 emoji** 这些更复杂的情况——那需要完整的 UAX #29 切分表。**真正要精确，得用专门的库**（Python 生态里有 `regex` 的 `\X`、或 `grapheme` 之类）。我这版的价值是：**把「长度不止一个」这件事，用能跑的数字摆到你面前**，而不是声称自己是个合规的切分器。

## 🧩 今日代码片段：`grapheme.py` — 三个长度，三种写法

三个函数：`visible_len` 数人眼里的字（近似字素簇）、`safe_truncate` 按字截断绝不劈开 emoji、`norm_key` 造比较用的规范键（NFC + casefold）。下面是真跑的输出。

```python
# -*- coding: utf-8 -*-
"""grapheme.py —— 三个「长度」各归各位：按人眼切、按语义比、按码点存"""
import unicodedata

ZWJ = "\u200d"
FAMILY = "\U0001F468\u200d\U0001F469\u200d\U0001F467\u200d\U0001F466"  # 👨👩👧👦


def _clusters(s):
    """把字符串切成「人眼看得见的一个个单元」（近似字素簇）。

    规则：基字符 + 紧跟其后的组合记号 / 连字号(ZWJ) 串，算一簇。
    不处理区域指示符（国旗）配对——那需要更完整的 UAX #29 表。
    """
    out, cur, join_next = [], "", False
    for ch in s:
        if cur and (unicodedata.combining(ch) or ch == ZWJ or join_next):
            cur += ch
        else:
            if cur:
                out.append(cur)
            cur = ch
        join_next = (ch == ZWJ)
    if cur:
        out.append(cur)
    return out


def visible_len(s):
    """用户眼里的「几个字」。"""
    return len(_clusters(s))


def safe_truncate(s, n):
    """按人眼单元截断，绝不把组合记号或 emoji 家族劈成两半。"""
    return "".join(_clusters(s)[:n])


def norm_key(s):
    """比较/搜索用的规范键：先合成(NFC)，再大小写折叠(casefold)。"""
    return unicodedata.normalize("NFC", s).casefold()
```

实测输出（Windows 11 / Python 3.14.9）：

```text
样本(首码点)          len  utf8  visible
0x63                   4    5     4        ← café 预合成
0x63                   5    6     4        ← café e+记号：len 差 1，字一样多
0x4e2d                 2    6     2        ← 中文
0x1f600                1    4     1        ← 😀
0x1f468                7    25    1        ← 👨👩👧👦：7 码点 / 25 字节 / 1 个字

family+abc  len=10 visible=4
safe_truncate(...,1) = '👨\u200d👩\u200d👧\u200d👦'   ← 一家人整整齐齐
原生 fam[:1]         = '👨'                            ← 只留下一个男人，家没了

norm_key('café') == norm_key('cafe\u0301') ?   True
norm_key('Straße') == norm_key('STRASSE') ?    True
```

四个值得说的细节：

- **`_clusters` 用「往后看一个」来粘 ZWJ。** 单独遇到 `U+200D` 只把它挂到当前簇，**还要立一个 `join_next` 旗标**，好让紧跟的那个 emoji（它本身不是组合记号）也粘进来。少了这个旗标，`👨👩👧👦` 会数成 4 而不是 1。
- **`safe_truncate` 先切簇、再拼接，而不是 `s[:n]`。** 因为它切的是「单元」，所以**永远不会在组合记号或 emoji 家族中间下刀**。上面那行就是证据：按字切留下完整的家，按码点切只剩一个男人。
- **`norm_key` 把「规范化」和「大小写折叠」缝在一起。** 比较用的键就该是一次性的：**先 NFC 消掉「同形异码」，再 casefold 消掉「大小写」。** 顺序无所谓，但两件都得做——只做一件，另一半坑还在（`Straße` 靠的是 casefold，`café` 靠的是 NFC）。
- **它是「近似」，不是「规范」。** 国旗 `🇨🇳`（两个区域指示符）我这版会数成 2；肤色、键帽 emoji 同理。**我在函数名和 docstring 里都写了这是近似**——因为在字符串处理里，**最危险的不是「不知道」，是「以为自己数对了」。**

一句话收这段：**别写 `len(s) > 20` 这种判断，除非你已经想清楚——你要挡的是 20 个字节、20 个码点，还是用户眼里的 20 个字。** 三个门，放进来的是三拨人。

## ✨ 今日一句

> 一个字符串有三种「长度」：它占几字节、它有几个码点、以及人眼看它是几个字。
>
> 你眼睛数出来的那个，机器一个都不认；机器数的那个，用户一个都不认——而 bug，永远藏在两个「都不认」之间的缝里。
