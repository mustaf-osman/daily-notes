# 📅 2026年11月03日 日报

## 💭 技术随想：你的校验和，到底能抓住几种错

一段串口协议，帧尾是 `sum(data) & 0xFF`。跑了半年没出过事，直到换了一根长一点的线：偶尔会看到一个温度值跳到 300 多度，重发一次就好。

一开始怀疑是解析错位，后来发现错位会立刻炸（长度字段对不上）。再后来把原始字节打出来，才看出真相：**报文里有两个字节的值被交换了，和校验一模一样。**

那一刻挺不舒服的——因为"和"这个算法，从一开始就没打算管顺序。它不是"偶尔失效"，它是**在结构上对所有排列组合免疫**。

于是花了一天把常见的六种校验放到同一张桌子上量：`sum8`、`xor8`、`sum16`、`fletcher16`、`crc8`、`crc16-ccitt`。结论比预想的干脆：**校验和不是"能查错"，是"能查某一类错"。不知道它漏哪一类，等于没校验。**

环境：Windows 11 / Python 3.11.15。所有数字都是本地跑出来的，绝对值换机器会变，比例关系不会。

### 一、实验怎么做的

固定负载 **16 字节 = 128 位**（典型的传感器帧/控制帧大小），随机生成报文，然后：

1. 在报文里随机翻转 k 个位；
2. 独立算出六种校验值，跟原报文比；
3. 校验值相同 → 记为**漏检**（接收端会认为这帧没问题，把错数据交给上层）。

每组 40 万次。

| 算法 | 1 位 | 2 位 | 3 位 | 4 位 |
|---|---|---|---|---|
| `sum8` 求和 | 0 | **6.68e-2** | 1.12e-2 | 1.52e-2 |
| `xor8` 异或 | 0 | **1.18e-1** | 0 | 3.94e-2 |
| `sum16` 求和 | 0 | **5.92e-2** | 9.84e-3 | 1.22e-2 |
| `fletcher16` | 0 | 0 | 3.05e-4 | 2.00e-4 |
| `crc8` | 0 | 1.17e-4 | 0 | 7.96e-3 |
| `crc16-ccitt` | 0 | 0 | 0 | 5.50e-5 |

四件事：

- **1 位错误，六种全抓。** 这就是校验和能活这么多年的原因——真实链路上"只翻一位"确实最常见。但它是这六种算法唯一意见一致的一列。
- **2 位错误开始分家。** `xor8` 漏 11.8%，也就是说**每九个双位错误就有一个被当成好帧**。这个数字不是玄学，下面能一行行算出来。
- **`fletcher16` 在 2 位和 3 位上明显强于两种"和"**，成本只贵了 6 倍（1.2 µs 对 0.19 µs）。
- **`crc16` 在 40 万次里只漏了 22 个 4 位错误**，`crc8` 漏了 3186 个。8 位和 16 位校验的差距，不是"好一点"，是**两个量级**。

### 二、`sum` 和 `xor` 的漏检率，是可以手算的

128 位里随机打两个洞，总共有 $C(128,2) = 8128$ 种位置组合。问：哪些组合会让校验值不变？

**`xor8`**：按位异或，两个洞落在**同一个位位置**（同一个字节内第 r 位，但在不同字节里）时，一升一降、或者一升一升……不对，异或不管方向，同一个位置翻两次就是原值。所以判据只有一个：两个洞的位位置相同。

同位置的对有多少？8 个位位置 × 16 个字节里选 2 个 = $8 \times 120 = 960$。

$$960 / 8128 = 11.81\%$$

实测 11.8%。**`xor8` 的 2 位漏检率不是测出来的，是算出来的，一位不差。**

**`sum8`**：加法要考虑方向。同位置的两次翻转，一升一降正好抵消（6.68% 里的主要部分），但一升一升会变成 $+2^{r+1}$，只有 r=7 时 $128+128 = 256 \equiv 0 \pmod{256}$ 才又抵消。所以：

$$(960/2 + 120/2) / 8128 = 540/8128 = 6.64\%$$

实测 6.68%，差的那点是抽样抖动。**`sum8` 比 `xor8` 好，是因为"进位"顺手挡住了"同方向"的那一半——不是因为加比异或更聪明。**

**`sum16`**：和变成 16 位，$2^{r+1}$ 不再回绕到 0，所以只剩"同位置一升一降"那一半：

$$480 / 8128 = 5.90\%$$

实测 5.92%。三行算式对上三行实测，这张表就没有玄学成分了。

### 三、更难看的一张表：交换两个字节

同上面一样随机生成 16 字节报文，随机挑两个**值不同**的字节交换位置，20 万次：

| 算法 | 漏检率 | 说明 |
|---|---|---|
| `sum8` | **1.0000** | 一个都抓不住 |
| `xor8` | **1.0000** | 一个都抓不住 |
| `sum16` | **1.0000** | 一个都抓不住 |
| `fletcher16` | 4.8e-3 | 靠"位置加权"挡住大部分 |
| `crc8` | 3.7e-3 | 有盲点，见第五节 |
| `crc16-ccitt` | **0** | 20 万次，一个不漏 |

`sum` 和 `xor` 都是**可交换**的运算，交换字节之后和不变、异或也不变——**100% 漏检，不是概率问题，是定义问题**。

这一条比"2 位错误漏 6%"要致命得多：字节交换、字段顺序错乱、缓冲区错位一格、DMA 把两个字段搬反——这些在真实系统里全都不是"翻一位"，而"和"校验对它们**完全瞎**。

我那段协议里的 300 度，就是这么来的。

`fletcher16` 能挡住大部分，是因为它给每个字节加了位置权重（$s_2 = \sum (n-i+1) \cdot b_i$）；但权重是**模 255** 算的，所以还有第五节那个坑。

### 四、CRC 为什么不一样：把报文当成一个多项式

CRC 不是"另一种和"，它是另一个思路：**把报文的一串比特当成一个 GF(2) 上的多项式，除以一个固定的生成多项式，余数就是校验值。**

举例，报文比特 `1011` 就是 $x^3 + x + 1$。发出去的是报文 + 余数，收端再除一次，余数不为 0 就扔。

于是漏检有了精确的判据：

> 漏检 ⟺ 错误多项式 $E(x)$ 能被生成多项式 $g(x)$ 整除。

不是"可能漏"，是**可判定**。而 $g(x)$ 的代数性质决定了它漏什么：

- $g$ 含因子 $(x+1)$ → 它能抓住所有**奇数个**位错误（奇数项多项式在 x=1 处求值为 1，不可能被 $(x+1)$ 整除）。
- $g$ 的周期是 P → 它能抓住所有**距离小于 P** 的两位错误（$1 + x^d$ 只有在 d 是 P 的倍数时才被整除）。
- $g$ 的次数是 16 → 它能抓住所有**长度 ≤ 16 位的突发错误**（这是定理，不是经验）。

所以 CRC 的能力是一张可以查表的设计参数，而不是"用起来感觉挺靠谱"。

回头解释表里三列看起来可疑的 **0**：`xor8` 和 `crc8` 的 3 位漏检率都是 0，原因各不相同——

- `xor8`：奇数个位永远无法互相抵消（某个位置被翻两次会消掉，但总数是奇数，剩下的那个一定还在）。
- `crc8`：多项式含 $(x+1)$ 因子，**奇数个位错误一律抓得住**，跟位置无关。这也是为什么它在"2 位"那列反而有漏（1.17e-4）——偶数个位才是它的弱项。
- `crc16-ccitt`：CCITT 多项式在 32767 位以内最小距离是 4，所有 ≤3 位错误全抓，所以 3 位那一格是**定理上的 0**，不是运气。

### 五、CRC-8 的两个盲点（实测，不是传说）

CRC-8/ATM 的生成多项式是 $x^8 + x^2 + x + 1$（0x107）。它**不是不可约的**：

$$x^8 + x^2 + x + 1 = (x+1)(x^7+x^6+x^5+x^4+x^3+x^2+1)$$

右边那个 7 次因子，系数是 `11111101` = **0xFD**。这带来两个具体后果，我都验了一遍：

**盲点一：位距 127 的两位错误。** 穷举 16 字节（128 位）帧里全部 8128 种两位组合，**只有 1 个漏检**：第 0 位和第 127 位，也就是**首尾两个比特**。因为 7 次因子的周期正好是 127，$1 + x^{127}$ 被它整除。

一个 8 位校验，在 128 位帧上只漏一个两位错——这是设计得相当好的结果。**但也说明：帧再长一点，盲点就开始变多。** CRC-8 只适合几十字节以内的短帧，不是"随便多长都行"。

**盲点二：两个字节差 0xFD 时，交换位置看不出来。** 穷举 16 字节帧里所有"取两个字节、分别换成 a 和 b"的组合（共 7,833,600 种），漏检 **30,720 个**，而它们**全部满足 a ^ b == 0xFD**。

30720 = 120 × 256，一个不多一个不少——每个字节对、每个 a 值各一个。原因就是上面的分解：值差正好等于那个 7 次因子，$h \cdot (1 + x^d)$ 里 $(x+1)$ 部分对所有 d 都成立（$1 + 1^d = 0$），于是整体被 $g$ 整除。

这条挺实用：**"校验通过了"从来不等于"数据对了"，它只等于"数据不属于这个校验函数的零空间"。**

顺便一个同类的坑，同样实测出来了——`fletcher16` 对"整字节翻转"有盲区，而盲区**只有两个值**：

```text
fletcher16：8 位对齐、整字节取反，按原字节值统计漏检
  漏检的原始字节值：[0, 255]   共 2/256 个值
```

因为它是模 255 的：`0x00` 和 `0xFF` 分别贡献 0 和 255，而 255 ≡ 0。**一个全零的字节被整字节翻成全 FF，`fletcher16` 完全看不出来。** 这就是教科书里说的"Fletcher 分不清两个零"。

### 六、突发错误：结果与位置无关，只与长度有关

现实中干扰往往不是散点，而是一段连续的位被一起打歪（电源毛刺、RS-485 上的一个尖峰）。测法：在 128 位里随机选起点，连续翻 k 位，每条 20 万次。

| 算法 | 4 位 | 8 位 | 12 位 | 16 位 | 24 位 |
|---|---|---|---|---|---|
| `sum8` | 0 | 0 | 744 | 1588 | 0 |
| `xor8` | 0 | 0 | 0 | **200000** | 0 |
| `sum16` | 0 | 0 | 381 | 779 | 0 |
| `fletcher16` | 0 | 214 | 0 | 12 | 5 |
| `crc8` | 0 | 0 | 0 | 0 | 0 |
| `crc16-ccitt` | 0 | 0 | 0 | 0 | 0 |

三件事，一件比一件值得记：

1. **`xor8` 对 16 位连续突发 100% 免疫，32 位也一样。** 20 万次，全漏。把长度从 8 扫到 40，规律干净得可怕（每条 2 万次）：

   | 突发长度 | 8 | 12 | 16 | 20 | 24 | 28 | 32 | 36 | 40 |
   |---|---|---|---|---|---|---|---|---|---|
   | 漏检率 | 0 | 0 | **1.00** | 0 | 0 | 0 | **1.00** | 0 | 0 |

   **长度是 16 的倍数就全漏，其余全抓。** 因为异或比的是"每个字节的变化量"：16 个连续的 1 切到字节上，不管从哪一位起步，那三段掩码异或起来正好是 0。于是 `xor8` 的真实能力得这么描述——"能抓长度为非 16 倍数的连续突发"。**一个需要这么描述的能力，本身就是不该出现在协议里的理由。**

2. **CRC 那一列全是 0，而且是确定性的 0。** 连续 k 位的错误多项式永远是 $x^s(1 + x^k)$，起点 s 只是个平移、不影响整除性。所以对 CRC 来说，**"会不会漏"只由 k 决定，跟错误落在哪儿完全无关**。这也是为什么 CRC 的能力能用"检测所有 ≤ 16 位突发"这样一句话来描述。

3. **`sum` 和 `fletcher16` 那一列会"忽高忽低"**——12 位漏 744，24 位又漏 0。因为这俩依赖数据的**具体值**（加法要知道是升还是降），不像 CRC 只看掩码。忽高忽低的另一面是：**你没法用一句话描述它的能力，也就没法为它做保证。**

顺带说，`sum8` 那个"24 位突发漏检 0"不是它变强了，是这组的取样刚好没撞上；`sum8` 在 12 位突发上漏 0.37%，已经足够说明它撑不住。

### 七、代价

16 字节一帧，跑 100 万次的单帧耗时：

| 算法 | µs/帧 | 吞吐 |
|---|---|---|
| `sum8` | 0.164 | 97.6 MB/s |
| `sum16` | 0.192 | 83.2 MB/s |
| `xor8` | 0.526 | 30.4 MB/s |
| `crc8` | 0.590 | 27.1 MB/s |
| `fletcher16` | 1.221 | 13.1 MB/s |
| `crc16-ccitt` | 1.918 | 8.3 MB/s |

`crc16` 是 `sum8` 的 **11.7 倍**。听起来很多，换算一下就知道根本不是问题：

- 1 Mbps 的 CAN，一帧 16 字节大约占 150 位 ≈ **150 µs** 的线时间。CRC16 花 1.9 µs，占 **1.3%**。
- 460800 的串口，16 字节 ≈ 347 µs。CRC16 占 **0.5%**。

**校验不是瓶颈，带宽才是。** 为了省 1.5 µs 把 crc16 换成 sum8，等于用"漏掉 6% 的双位错误 + 100% 的字节错序"去换 1.5 微秒——这笔交易怎么算都亏。

（另外：真机上这段 Python 只是对照。ARMv8 有 CRC32 硬件指令，nRF53 系列有可配多项式的 CRC 外设，几百纳秒到几微秒一帧，比表格里的数字还要再低一到两个数量级。）

### 八、选型，四句话

1. **只有一位可能错，且帧很短** → `sum8` 勉强能用（比如某些老的红外遥控、单字节命令）。超出这个前提就是在赌。
2. **几字节到几十字节、要便宜** → `crc8`。但记住它的盲区：位距 127、值差 0xFD。
3. **几十字节到几百字节、通用** → `crc16-ccitt`（0x1021）或 Modbus 的 `0xA001`。检测所有 ≤16 位突发、所有 1/2/3 位错误，成本仍然可以忽略。
4. **任何"不信任的链路"** → CRC 只是最后一道。前面必须有：**帧头 + 长度 + 序列号**。CRC 保证"这一帧没被打坏"，长度保证"这一帧是完整的"，序列号保证"这一帧没丢也没重复"。这三件事 CRC 一个都不管。

最后一条最容易漏：**CRC 不纠错、不重传、不管顺序、不管丢帧。** 它只回答一个问题——"我收到的这串字节，是不是发送方当时算出来的那一串？"

### 九、和手上的东西对上

- **rp_server 的串口/CAN 帧**：如果现在帧尾是 `sum & 0xFF` 或异或，先改 CRC16。昨天那种"偶发跳到荒谬值"的现象，八成不是驱动问题，是校验太弱。
- **CAN 本身用 CRC-15**（多项式 0x4599），能抓所有 ≤15 位突发和所有 5 位以内随机错误。自定义协议跑在 CAN 上时，上层再加 CRC16 是重复的，该加的是**长度和序列号**。
- **头部舵机 `AT+HEAD=<pan>,<tilt>`**：文本协议天生有 `\n` 结尾，解析靠行边界，其实比二进制帧稳；但如果要传浮点或数组，还是换成带 CRC 的二进制帧更省事。
- **nRF5340 上的实现**：用硬件 CRC 外设（多项式可配），别在主循环里跑软件 CRC；真要软件实现，就一定用查表法（今天这版），逐位移位那版慢 8 倍。
- **解析器必须能重同步**：脏数据里出现 `A5 5A` 的概率不为零，靠 CRC 判假帧头、一个字节一个字节往后挪——今天代码片段里的 `unpack` 就是干这个的。**没有重同步的解析器，一个假帧头能让后面的数据流永远错位。**

一句话收今天：**校验值不为 0 的错误你能看见；校验值撞上的错误，你只会看见"数据是对的，但事情不对"。**

## 🧩 今日代码片段：带 CRC16 的帧 + 能重同步的解析器

打包、解析、跳过脏字节、识别假帧头、坏帧丢弃但后面的好帧照收——这四件事是一个串口协议栈最低限度该有的。下面这段是真跑过的。

```python
# -*- coding: utf-8 -*-
"""带 CRC16 的串口帧：打包 / 解析 / 脏数据重同步"""
HEAD = b"\xA5\x5A"
MAX_PAYLOAD = 64

_CRC16 = []
for i in range(256):
    c = i << 8
    for _ in range(8):
        c = ((c << 1) ^ 0x1021) & 0xFFFF if c & 0x8000 else (c << 1) & 0xFFFF
    _CRC16.append(c)


def crc16(data, crc=0xFFFF):
    for v in data:
        crc = ((crc << 8) & 0xFFFF) ^ _CRC16[((crc >> 8) ^ v) & 0xFF]
    return crc


def pack(payload):
    if len(payload) > MAX_PAYLOAD:
        raise ValueError("payload 太长: %d > %d" % (len(payload), MAX_PAYLOAD))
    body = bytes([len(payload)]) + payload
    return HEAD + body + crc16(body).to_bytes(2, "little")


def unpack(stream):
    """从字节流里逐帧取出。脏字节、假帧头、坏帧都能跳过，不吐半个帧。"""
    frames, dropped, i = [], 0, 0
    while True:
        k = stream.find(HEAD, i)
        if k < 0:
            dropped += len(stream) - i
            i = len(stream)
            break
        dropped += k - i
        if len(stream) < k + 4:
            i = k
            break
        n = stream[k + 2]
        if n > MAX_PAYLOAD:
            i, dropped = k + 1, dropped + 3
            continue
        end = k + 3 + n + 2
        if len(stream) < end:
            i = k
            break
        body = stream[k + 2:end - 2]
        if crc16(body) != int.from_bytes(stream[end - 2:end], "little"):
            i, dropped = k + 1, dropped + 3          # 假帧头，挪一个字节再找
            continue
        frames.append(stream[k + 3:end - 2])
        i = end
    return frames, stream[i:], dropped
```

实测输出：

```text
帧 a 的字节： a5 5a 0d 41 54 2b 48 45 41 44 3d 31 30 2c 2d 35 a3 ff
解析结果： [b'AT+HEAD=10,-5', b'hello', b'\x00\x01\x02\x03\x04\x05\x06\x07\x08\t'] | 剩余 0 字节 | 丢弃 7 字节
翻一位后： [b'hello'] | 坏帧被拦下，后面的好帧照收
```

这段输入里故意塞了两处脏东西：开头两个垃圾字节，中间一个 `A5 5A FF` 的假帧头。解析器把整段流还原成了三帧，一个字节没错位。

四个值得说的细节：

- **长度字段在校验范围之内。** `body = len + payload`，CRC 覆盖两者。如果长度不在 CRC 里，攻击面（或者说故障面）就变成了"长度被改但 CRC 对"——直接读到缓冲区外面去。
- **`from_bytes(..., "little")` 要和打包时的 `to_bytes(2, "little")` 一致。** 大小端错一次，你会得到"所有帧都 CRC 错"这种一看就知道的 bug；但如果是**只在某些字节值上错**（因为长度字段的高低字节换了位置），那就是最难查的那种。
- **坏帧不丢整条流，只挪一个字节。** `i = k + 1` 而不是 `i = end`：万一这个 `A5 5A` 只是载荷里碰巧出现的两个字节，真正的帧头还在后面几个字节处。**这是"粘包/假帧头"问题的标准解法，代价是 O(n) 的重扫，收益是永远不会永久错位。**
- **`unpack` 会返回"没消费完的尾巴"，调用方必须把它和下一次读到的字节拼起来。** 也就是 `buf = rest + recv()`。丢掉这个尾巴，表现就是"每隔一段时间丢一帧"，而且永远复现不了——因为取决于 TCP/串口怎么切包。

## ✨ 今日一句

> 校验和不会让错误消失，它只会让错误变成"二进制里的一位数"。撞上了，你看到的是"数据是对的，但事情不对"。
