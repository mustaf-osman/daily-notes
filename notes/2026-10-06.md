## 💭 技术随想：内存对齐——结构体为什么比你想的胖，排排座还能瘦三分之一

先来猜一个数：C 里写 `struct { char a; int b; char c; }`，`sizeof` 是多少？料很明白：1+4+1 = 6 个字节。但真去打印，编译器会告诉你 **12**。更妙的是，同样这三个字段，只是换个顺序（`int` 先坐），就变回 **8**——什么都没删，白胖了 4 个字节；什么都没加，就瘦了三分之一。而且同样这堆料，换成"紧凑打包"模式，答案是 **6**。

一个结构体三个答案，都不是 bug。这是计算机给内存定下的一条排版规矩在收租：**内存对齐（alignment）**，以及为它服务的**填充（padding）**。

为什么要有这条规矩？因为 CPU 读内存不是一字节一字节"零售"，而是按**格**批发：一次搬一个机器字——32 位是 4 字节、64 位是 8 字节；到了缓存那一层，更是按 64 字节的缓存行整块搬。于是就有了一条硬约束：一个 4 字节的 `int`，如果存放位置骑在两格的交界线上，硬件一次搬不完——要么拆成两次搬（慢一点，x86 基本都这么容忍），要么干脆翻脸报错（不少 ARM 场合如此）。为了"一次搬完"，编译器和 CPU 早就约定好：**每个字段的起始地址，必须是它对齐要求的整数倍**——`int` 只能坐 4 的倍数号座位，`double` 只能坐 8 的倍数号，`char` 随便坐。坐不满的格子怎么办？空着。这些空隙有个正经名字：**填充（padding）**——不装数据，只买"整齐"。

把 `char a; int b; char c;` 摆一遍就全明白了：a 坐 0 号；轮到 b 时 1、2、3 号虽然空着也坐不了（4 字节的屁股必须落在 4 的倍数上），于是 b 坐 4 号；c 坐 8 号。到这里一共用了 9 格——还没完：结构体是要组数组的，如果总长是 9，第二个元素从头数起，它的 b 就落在 13 号，又骑到格线上了。所以总长还得向上取整到"最大字段的对齐"（4 的倍数），一路补到 **12**。6 字节的数据，配了 6 字节的留白。

换个座位顺序让 `int` 先坐：b@0、a@4、c@5，6 格刚够，向上取整到 **8**。同样三个字段，省下的就是那 4 个字节——这就是那句老口诀的来历：**结构体字段从大到小排**。不是因为编译器喜欢大块头，而是"大件先挑座位，小件填缝"，空隙自然最少。

总结成两条排版规则：**① 每个字段的起点，向上对齐到自己的对齐要求，中间的空隙用填充补；② 结构体整体也要对齐（取最大的成员对齐），总长向上取整。** 第②条常常被忽略——它不是为结构体自己，而是为"结构体数组里每个元素都还站在格线上"服务的。不信就把 packed（紧凑打包）的结构体组个数组：步长只有 6 字节，第二个元素的 int 起点是 7，直接骑线——省了内存，坑了搬运。

顺便打消一个念头：不要背"某某类型对齐几字节"。这个数字是平台、编译器、甚至编译选项的函数：32 位和 64 位不一样（指针和 `double` 是重灾区），MSVC 和 GCC 个别类型也有分歧。通用的是**规则**，确切数字交给工具报账——C 里用 `sizeof`、`offsetof`，Python 里用 `ctypes` 对拍，一行都不用手算。

这套规矩不只属于 C。Python 的 `struct` 模块有两条路线：`'@'` 跟本机 C 布局走（字段之间补填充），`'<'`/`'='` 用标准尺寸、一个填充不留。今天的实验还抓到一个非常犀利的小坑：`struct.calcsize('@bic')` 是 **9**，不是 C 的 **12**——因为 Python 只在"字段之间"补填充，**末尾那一截它不补**（它不管你要不要组数组）。跨语言对帧时这就分家了：成员偏移两边能对上，"一条记录多长"不一定对得上。所以对帧先问三件事：**字节序、字段偏移、记录总长**——缺一条，早晚在半夜三点找你。

落到嵌入式现场，这条规矩有三副面孔。**第一副是"报不报错"**：Cortex-M0 这类极简内核对未对齐访问的容忍度极低，多字节访问歪了很容易直接 HardFault；Cortex-M3/M4/M33 宽容一些，普通 LDR/STR 能歪着搬，但 LDM/STM、LDRD/STRD 这类"整批搬运"依旧要求整齐，而且可以配置 `CCR.UNALIGN_TRP` 让它"一律不许歪"。别人递给你一个地址让你取 int，先问一句：它 4 字节对齐吗？**第二副是"你亲手制造的歪"**：为了贴合协议帧，嵌入式常用 packed 结构体（`__attribute__((packed))` / `#pragma pack(1)`）把填充全挤掉——省了字节，代价是字段集体变成未对齐。此时对 packed 字段直接取地址、直接参与复杂运算就是在刀尖上跳舞；标准姿势是**先 memcpy 到对齐的局部变量再用**，这段拷贝编译器保证安全。**第三副是"硬件自己的合同"**：很多 DMA 要求缓冲区按 4 字节甚至缓存行对齐（按行做 clean/invalidate 的实现依赖它）；Cortex-M 的 MPU region 大小必须是 2 的幂、基址按大小对齐。这些数字不会明写在代码里，但都明写在芯片手册里。

还有一条最容易流血的经验：**不要把 C 结构体原样当二进制协议用**。你往结构体中间加一个字段，后面所有字段集体后移——之前抓的包、写进 flash 的数据、对面设备里的解析代码，全部错位。它昨天还好好的。要么把协议和内存解耦（显式序列化：手写 pack/unpack，或 protobuf 这类工具），要么至少给协议帧固定版本。字段顺序、大小、对齐，这三样一起变，才是"二进制兼容"四个字的完整含义。

最后留一句性能账：对齐还管到缓存行（通常 64 字节）这一层。热点结构体如果"劈开两条缓存行"，每次访问都要动两条线；多核时代更隐蔽的是**伪共享**——两个线程各写各自的变量，可惜两个变量住在同一条缓存行里，缓存行在核间来回弹射，两边看起来都无害的写入互相拖慢几十倍。解法也直白：把"大家都爱写的热点"分别对齐到缓存行（`alignas(64)`、填充隔离），物理上分开住。

回头看，内存对齐其实就一件事：**执行一份"整齐"的排版契约**。字段的座位按类型对齐；结构体的总长照顾数组里的后来人；分配器给你的地址永远踩在格线上；协议帧里每个偏移都是排版工算出来的。之前那篇字节序讲的是"多字节数字的字节谁在前"，这篇补上另一半——"结构体的字段各坐哪里"。合起来，你才算能读懂"一块内存长什么样"。下次再有人问 `sizeof` 为什么不是加法，你就从座位表开始讲起。

## 🧩 今日代码片段：六组实验 + 两路复核——把"排版内幕"翻个底朝天

主体是 stdlib-only 的六组实验：① 同料三排——12 / 8 / 6，填充可视化；② Python `struct` 的 `'@'` 与标准模式，外加 9 vs 12 的末尾坑；③ 跨"搬运格"计数；④ 数组步长；⑤ `double` 版本（24 vs 16）+ 分配器地址表；⑥ 把排版规则写成十行公式，把上面每个数字复现一遍。最后两路外部复核收口：让 C 编译器（WSL gcc）亲手报账，再用 numpy 的 `align=True` 交叉验证。

```python
# -*- coding: utf-8 -*-
"""内存对齐现场勘查：结构体为什么比你想的大（真实可运行）

实验1：两种字段顺序，sizeof 12 vs 8；padding 可视化 + 偏移对照
实验2：struct 模块两套规矩——'@' 字段之间补、末尾不补；'='/ '<' 一律不补
实验3：跨"搬运格"计数——对齐的字段搬一次，骑在格线上的搬两次
实验4：数组步长——stride = 补齐后的 sizeof，让每个元素都站在格线上
实验5：double 版本更夸张（24 vs 16）+ 分配器给的地址
实验6：把排版规则写成 10 行公式，复现上面每一个数字
"""
import ctypes
import struct
import sys

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

W = 4  # 搬运单元：4 字节（32 位机器字，方便画格子）


def layout_map(S):
    """把每个字节标上归属：字段首字母 or '.' 填充"""
    n = ctypes.sizeof(S)
    own = {}
    for fn, ft in S._fields_:
        off = getattr(S, fn).offset
        for i in range(off, off + ctypes.sizeof(ft)):
            own[i] = fn[0].lower()
    s = "".join(own.get(i, ".") for i in range(n))
    return " | ".join(s[i:i + W].ljust(W) for i in range(0, n, W))


def show(name, S, note=""):
    n = ctypes.sizeof(S)
    used = sum(ctypes.sizeof(ft) for _, ft in S._fields_)
    print(f"{name}: sizeof = {n} 字节（字段实际共占 {used}，填空隙 {n - used}）{note}")
    for fn, ft in S._fields_:
        off = getattr(S, fn).offset
        print(f"    {fn:<3} 起始 @{off:>2}   占 {ctypes.sizeof(ft)} 字节")
    print(f"    布局: [{layout_map(S)}]")
    print("          （字母 = 字段占的字节，. = 编译器塞的填充）")
    print()


class A(ctypes.Structure):
    _fields_ = [("a", ctypes.c_char), ("b", ctypes.c_int), ("c", ctypes.c_char)]


class B(ctypes.Structure):
    _fields_ = [("b", ctypes.c_int), ("a", ctypes.c_char), ("c", ctypes.c_char)]


class AP(ctypes.Structure):
    _pack_ = 1
    _fields_ = [("a", ctypes.c_char), ("b", ctypes.c_int), ("c", ctypes.c_char)]


class C1(ctypes.Structure):
    _fields_ = [("c1", ctypes.c_char), ("d", ctypes.c_double), ("c2", ctypes.c_char)]


class C2(ctypes.Structure):
    _fields_ = [("d", ctypes.c_double), ("c1", ctypes.c_char), ("c2", ctypes.c_char)]


print("=" * 78)
print("实验1：同样三个字段，排排座——12 字节变 8 字节")
print("=" * 78)
show("A（char, int, char）", A)
show("B（int, char, char）", B)
show("AP（char, int, char，紧凑打包 _pack_=1）", AP)
print("  → 同样 6 字节的料：A 占 12，B 占 8，AP 占 6（但 AP 的 b 骑在格线上，见实验3）")
print()

print("=" * 78)
print("实验2：struct 模块两套规矩——'@' 字段之间补、末尾不补；'='/ '<' 一律不补")
print("=" * 78)
for fmt, desc in [
    ("@bic", "本机布局：char,int,char（字段间补齐）"),
    ("@icb", "本机布局：int,char,char（大件先坐）"),
    ("=bic", "标准尺寸，不补 = 6"),
    ("<bic", "小端标准，不补 = 6"),
    ("@cdc", "本机布局：char,double,char"),
    ("@dcc", "本机布局：double,char,char"),
    ("=dcc", "标准尺寸，不补 = 10"),
]:
    print(f"  calcsize('{fmt}') = {struct.calcsize(fmt):>2}    {desc}")
print()
print("  坑就在末尾：C 的同款结构体 sizeof = 12（数组里每个元素都得站上 4 的格线），")
print("  而 '@bic' = 9 —— Python struct 只补'字段之间'，最后那一截它不管。")
print("  跨语言对帧时，成员偏移能对上，'总长'不一定对得上。")
print()


def words_touched(off, sz, w=W):
    """字段 [off, off+sz) 横跨几个 w 字节的搬运格"""
    return (off + sz - 1) // w - off // w + 1


print("=" * 78)
print("实验3：一次搬 4 字节——站在格线上搬 1 次，骑在格线上搬 2 次")
print("=" * 78)
print(f"  {'字段':<24}{'横跨搬运格数':>10}   说明")
checks = [
    ("A.a  @0..0  (1 字节)", 0, 1, "本来就一格内"),
    ("A.b  @4..7  (4 字节)", 4, 4, "整整齐齐占满一格"),
    ("AP.b @1..4  (4 字节)", 1, 4, "骑在 0/4 的界上 → 要动两格"),
    ("B.b  @0..3  (4 字节)", 0, 4, "整整齐齐占满一格"),
    ("A.c  @8..8  (1 字节)", 8, 1, "一格内"),
]
for tag, off, sz, note in checks:
    print(f"  {tag:<24}{words_touched(off, sz):>10}   {note}")
print("  → 未对齐的 4 字节字段：硬件要么拆成两次搬，要么直接报错（看架构脸色）")
print()

print("=" * 78)
print("实验4：数组步长——元素之间的间隔就是补齐后的 sizeof")
print("=" * 78)
arrA = (A * 2)()
arrB = (B * 2)()
arrAP = (AP * 2)()
strideA = ctypes.addressof(arrA[1]) - ctypes.addressof(arrA[0])
strideB = ctypes.addressof(arrB[1]) - ctypes.addressof(arrB[0])
strideAP = ctypes.addressof(arrAP[1]) - ctypes.addressof(arrAP[0])
print(f"  A  数组步长 = {strideA:>2} 字节 → 第 2 个元素的 b 起始 = {strideA}+4 = {strideA + 4}，能被 4 整除吗: {((strideA + 4) % 4 == 0)}")
print(f"  B  数组步长 = {strideB:>2} 字节 → 第 2 个元素的 b 起始 = {strideB}+0 = {strideB}，能被 4 整除吗: {(strideB % 4 == 0)}")
print(f"  AP 数组步长 = {strideAP:>2} 字节 → 第 2 个元素的 b 起始 = {strideAP}+1 = {strideAP + 1}，能被 4 整除吗: {((strideAP + 1) % 4 == 0)}")
print("  → 末尾补齐不只是'为当前这个结构体'：是为整个数组的每个元素都站上格线服务的")
print()

print("=" * 78)
print("实验5：double 版本更夸张——24 vs 16；外加分配器给的地址")
print("=" * 78)
show("C1（char, double, char）", C1)
show("C2（double, char, char）", C2)
print("  现代分配器给的地址（无论要多大，低 3 位永远是 0）：")
print("     请求字节数   addr % 16   addr % 8")
for sz in (8, 13, 16, 17, 64, 1024):
    buf = ctypes.create_string_buffer(sz)
    addr = ctypes.addressof(buf)
    print(f"     {sz:>6}        {addr % 16:>6}      {addr % 8:>6}")
print("  → 小块落在 8 的格线上、稍大就升到 16：分配器和 CPU 早有契约，绝不给你歪地址")
print()

print("=" * 78)
print("实验6：把排版规则写成 10 行公式，复现上面每一个数字")
print("=" * 78)


def align_up(n, a):
    """向上取整到 a 的倍数：a=4 时 1→4、5→8、9→12"""
    return (n + a - 1) // a * a


def layout(fields, tail_round=True):
    off, out = 0, []
    for name, sz, al in fields:
        start = align_up(off, al)
        out.append((name, start))
        off = start + sz
    if tail_round:
        off = align_up(off, max(al for _, _, al in fields))
    return out, off


F = [("a", 1, 1), ("b", 4, 4), ("c", 1, 1)]
offs, total = layout(F)
print(f"  规则版（末尾向上取整，模拟 C）:        a@{offs[0][1]}  b@{offs[1][1]}  c@{offs[2][1]}   总长 {total}   ← 对上 ctypes 的 A=12")
offs2, total2 = layout(F, tail_round=False)
print(f"  规则版（末尾不补，模拟 Python struct）: a@{offs2[0][1]}  b@{offs2[1][1]}  c@{offs2[2][1]}   总长 {total2}   ← 对上 calcsize('@bic')=9")
print("  一句话：字段起点 = '不小于当前末位的最小对齐倍数'；总长 = 两种收尾（补/不补）")
print()
print("一句话总结：内存不是一条随便切的绳，是一本已经画好格线的作业本——")
print("            每个字段要么整段落进某段格线以内，要么被硬塞进下一段的开头。")
```

  A  数组步长 = 12 字节 → 第 2 个元素的 b 起始 = 12+4 = 16，能被 4 整除吗: True
  B  数组步长 =  8 字节 → 第 2 个元素的 b 起始 = 8+0 = 8，能被 4 整除吗: True
  AP 数组步长 =  6 字节 → 第 2 个元素的 b 起始 = 6+1 = 7，能被 4 整除吗: False
  → 末尾补齐不只是'为当前这个结构体'：是为整个数组的每个元素都站上格线服务的

==============================================================================
实验5：double 版本更夸张——24 vs 16；外加分配器给的地址
==============================================================================
C1（char, double, char）: sizeof = 24 字节（字段实际共占 10，填空隙 14）
    c1  起始 @ 0   占 1 字节
    d   起始 @ 8   占 8 字节
    c2  起始 @16   占 1 字节
    布局: [c... | .... | dddd | dddd | c... | ....]
          （字母 = 字段占的字节，. = 编译器塞的填充）

C2（double, char, char）: sizeof = 16 字节（字段实际共占 10，填空隙 6）
    d   起始 @ 0   占 8 字节
    c1  起始 @ 8   占 1 字节
    c2  起始 @ 9   占 1 字节
    布局: [dddd | dddd | cc.. | ....]
          （字母 = 字段占的字节，. = 编译器塞的填充）

  现代分配器给的地址（无论要多大，低 3 位永远是 0）：
     请求字节数   addr % 16   addr % 8
          8             8           0
         13             8           0
         16             8           0
         17             0           0
         64             0           0
       1024             0           0
  → 小块落在 8 的格线上、稍大就升到 16：分配器和 CPU 早有契约，绝不给你歪地址

实验6：把排版规则写成 10 行公式，复现上面每一个数字
==============================================================================
  规则版（末尾向上取整，模拟 C）:        a@0  b@4  c@8   总长 12   ← 对上 ctypes 的 A=12
  规则版（末尾不补，模拟 Python struct）: a@0  b@4  c@8   总长 9   ← 对上 calcsize('@bic')=9
  一句话：字段起点 = '不小于当前末位的最小对齐倍数'；总长 = 两种收尾（补/不补）

一句话总结：内存不是一条随便切的绳，是一本已经画好格线的作业本——
            每个字段要么整段落进某段格线以内，要么被硬塞进下一段的开头。

**交叉复核 1：让 C 编译器亲自报账（WSL Ubuntu, gcc 13.3, x86-64）**

```c
#include <stdio.h>
#include <stddef.h>

struct A  { char a; int b; char c; };
struct B  { int b; char a; char c; };
struct __attribute__((packed)) AP { char a; int b; char c; };
struct C1 { char c1; double d; char c2; };
struct C2 { double d; char c1; char c2; };

int main(void) {
    printf("A : sizeof=%2zu   a@%zu  b@%zu  c@%zu\n",
           sizeof(struct A), offsetof(struct A, a), offsetof(struct A, b), offsetof(struct A, c));
    printf("B : sizeof=%2zu   b@%zu  a@%zu  c@%zu\n",
           sizeof(struct B), offsetof(struct B, b), offsetof(struct B, a), offsetof(struct B, c));
    printf("AP: sizeof=%2zu   a@%zu  b@%zu  c@%zu   (packed)\n",
           sizeof(struct AP), offsetof(struct AP, a), offsetof(struct AP, b), offsetof(struct AP, c));
    printf("C1: sizeof=%2zu   c1@%zu  d@%zu  c2@%zu\n",
           sizeof(struct C1), offsetof(struct C1, c1), offsetof(struct C1, d), offsetof(struct C1, c2));
    printf("C2: sizeof=%2zu   d@%zu  c1@%zu  c2@%zu\n",
           sizeof(struct C2), offsetof(struct C2, d), offsetof(struct C2, c1), offsetof(struct C2, c2));

    printf("对齐要求: struct A=%zu, struct C1=%zu, double=%zu, int=%zu\n",
           _Alignof(struct A), _Alignof(struct C1), _Alignof(double), _Alignof(int));

    struct A arr[2];
    char *p0 = (char *)&arr[0];
    char *p1 = (char *)&arr[1];
    printf("A 数组步长 = %td 字节；arr[1].b 相对 arr[0] 偏移 %td，%%4 = %td\n",
           p1 - p0, (p1 - p0) + offsetof(struct A, b), ((p1 - p0) + offsetof(struct A, b)) % 4);
    return 0;
}
```

B : sizeof= 8   b@0  a@4  c@5
AP: sizeof= 6   a@0  b@1  c@5   (packed)
C1: sizeof=24   c1@0  d@8  c2@16
C2: sizeof=16   d@0  c1@8  c2@9
对齐要求: struct A=4, struct C1=8, double=8, int=4
A 数组步长 = 12 字节；arr[1].b 相对 arr[0] 偏移 16，%4 = 0

**交叉复核 2：numpy 的 align=True——同一套规矩的现代面孔（uv 隔离环境，numpy 2.4.3）**

```python
import numpy as np
dt  = np.dtype([("a", "u1"), ("b", "<i4"), ("c", "u1")])
dta = np.dtype([("a", "u1"), ("b", "<i4"), ("c", "u1")], align=True)
print("numpy", np.__version__)
print("align=False itemsize:", dt.itemsize)
print("align=True itemsize:", dta.itemsize, "b offset:", dta.fields["b"][1])
```

```
numpy 2.4.3
align=False itemsize: 6
align=True itemsize: 12 b offset: 4
```

**说明：**

- **一个结构体三个答案**：C 编译器 12、Python `struct.calcsize('@bic')` 9、packed 6——6 字节的料，三种"体重"。C 的 12 里有一半是填充；重排成 `int, char, char` 后 8 字节，**整整省下三分之一**。这就是"字段从大到小排"口诀的全部来历。
- **两条规则的公式版**（实验6 十行复现）：字段起点 = "不小于当前末位的最小对齐倍数"；总长 = 向上取整到最大对齐（C）或就此打住（Python `'@'`）。一句话：**对齐是字段的规则，补齐是结构体（和数组）的规则**。
- **实验3 的"搬运格"**是教学示意图：现实里缓存行 64 字节、总线按块——原理相同：跨格的访问要么拆两次（x86 基本容忍，可能变慢；SSE 的 `movdqa` 这类指定对齐指令地址不齐直接异常），要么报错（不少 ARM 场合）。**对齐的访问一次到位**，这就是对齐存在的物理原因。
- **数组视角**（实验4）：步长永远等于补齐后的 `sizeof`。A 的步长 12 → 第二个元素 `b` 落在 16，%4=0；packed 步长 6 → 落在 7，骑线。**末尾那几字节填充是替"数组里的后来人"交的保险费**。
- **Python struct 的末尾坑**（实验2）：文档明说填充只加在相邻成员"之间"，头尾都不加。于是 `'@bic'` = 9 ≠ C 的 12：成员偏移两边一致，总长不一致。**对帧三件套**——字节序、字段偏移、记录总长——一个都别省；跨设备协议一律建议 `'<'` 定宽 + 显式长度。
- **C 复核**（gcc 13.3）：A=12、B=8、packed=6 全部对得上；`_Alignof` 报账：struct A=4、struct C1=8、double=8、int=4；数组步长 12、`arr[1].b` 偏移 %4=0。**跨编译器数字可能不同（尤其 32 位、MSVC/GCC 个别类型），但规则不变**——要数字就让编译器算。
- **numpy 复核**：`align=True`（12、b@4）与 C 布局逐位对应；`align=False`（6）与 packed/标准模式对应。**结构化数组、内存映射文件、和 C 交互的场景**，先想清楚要过哪种日子。
- **分配器地址表**（实验5）：无论请求多大，地址低 3 位恒为 0——≥8 对齐是底线，块一大升到 16。malloc 的"契约"就这么来的：**你永远拿不到歪地址，所以你也要还别人整齐**。
- **嵌入式清单**：① Cortex-M0 对未对齐多字节访问极易 HardFault；M3/M4/M33 上 LDR/STR 可容忍，LDM/STM、LDRD/STRD 要求整齐，`CCR.UNALIGN_TRP` 可配置成一律陷阱；② packed 结构体省字节但字段未对齐——**先 memcpy 到对齐局部变量再用**；③ DMA 缓冲区、MPU region 有各自的对齐合同（大小必须 2 的幂、基址按大小对齐），查手册别猜。
- **协议与 ABI**：别把结构体原样当二进制协议——中间插一个字段，后面全体错位，老数据和对面设备全乱。要么显式序列化（手写 pack/unpack / protobuf），要么固定版本。库边界两边编译选项（pack 与否）要一致，否则同一个头文件长出两种布局。
- **性能账**：跨缓存行访问动两条线；多核时代注意**伪共享**——两个线程的热点变量住进同一条缓存行，会来回弹射互相拖慢。热点用 `alignas(64)` 分开住。
- **落地五条**：① 字段从大到小排（省内存不花一分钱）；② 数字不背——用 `sizeof`/`offsetof`/`_Static_assert`（C）、`ctypes` 对拍（Python）；③ 跨语言/跨设备：显式序列化或 packed + memcpy，长度单独算；④ 嵌入式先对齐三问：地址对齐没？DMA/MPU 要求几字节？手册怎么规定？⑤ 结构体改字段＝改二进制接口，改之前先想谁在看你。

## ✨ 今日一句

> 内存是一本画好格线的作业本，编译器是不肯将就的排版工——宁可留白，也绝不让任何一个字段把腿伸到格线外面。你嫌它胖的那些字节，都是付给"整齐"的房租。
