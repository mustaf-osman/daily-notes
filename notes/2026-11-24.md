# 📅 2026年11月24日 日报

## 💭 技术随想：`01 00` 是 1，也是 256

前几天调一个串口帧，上位机说「长度 1」，下位机按「256」去读，然后一直等不齐那一帧，超时、重发、CRC 对不上。第一反应是线松了、波特率不对、干扰大——查了一圈，线是好的。问题出在两个字节的先后顺序上：同一条报文，两边读出了两个数。

**字节是事实，数是解释。** 同样两个字节 `01 00`，按小端读是 1，按大端读是 256。谁都没撒谎，只是各自按自己的约定解释了一遍。今天把这件事从头到尾在这台机器上跑了一遍（Windows 11 / AMD64 / Python 3.14.9），下面每个十六进制和数字都是刚刚打出来的。

### 一、同一串字节，可以读出三个完全不同的东西

取四个字节 `40 42 0F 00`：

```text
按 u32 小端读 : 1000000
按 u32 大端读 : 1078071040
按 f32 小端读 : 1.401298464324817e-39
```

同一块内存，同一串比特，一个是「一百万」，一个是「十亿多」，一个是「几乎为零」。**没有哪个是错的**——错的只有「没写清楚用哪种读法」这件事。

昨天说 `0.1` 在二进制里存不准；今天补一刀：**就算它存准了，摆进字节的顺序还能再骗你一次。** 精度和字节序是两个独立的坑，一个在「值」上，一个在「摆放」上。

### 二、一个 16 位数，两种摆法

`0x0102` 这个数，占用两个字节。小端把**低位字节放前面**，大端把**高位字节放前面**：

```text
0x0102  小端（<H）: 02 01
0x0102  大端（>H）: 01 02

0x12345678  小端（<I）: 78 56 34 12
0x12345678  大端（>I）: 12 34 56 78

1（64 位）  小端（<Q）: 01 00 00 00 00 00 00 00
1（64 位）  大端（>Q）: 00 00 00 00 00 00 00 01
```

记法很简单：**小端 = 小尾巴在前**，最低有效字节（LSB）放在最低地址。名字里的「端」指的是「尾端」，不是「端点」。

浮点数也一样，只是更不直观：

```text
1.5 的 f32  小端: 00 00 c0 3f      大端: 3f c0 00 00
0.1 的 f64  小端: 9a 99 99 99 99 99 b9 3f
0.1 的 f64  大端: 3f b9 99 99 99 99 99 9a
```

那个 `3f` 跑到哪一头，就是字节序在动手。**浮点数没有「特殊的字节序」**，它只是把 8 个字节按同样规则翻了个面。

### 三、谁大谁小：这不是习惯问题，是两套约定

一张能直接背下来的表：

| 场合 | 字节序 | 说明 |
|---|---|---|
| x86-64（这台机器） | 小端 | `sys.byteorder` 实测 `little` |
| ARM Cortex-M（nRF5340） | 小端 | 芯片复位后默认小端 |
| ARM Cortex-A（RK3588，AArch64） | 小端 | 实际运行的系统都是 LE |
| TCP/IP 头、端口、长度 | **大端** | 所以叫「网络字节序」 |
| Modbus 寄存器 | **大端** | 协议规定 |
| PNG / JPEG 的长度字段 | **大端** | 文件格式规定 |
| BMP | 小端 | Windows 出身 |
| UTF-16 文本 | 看 BOM | `FF FE` 小端，`FE FF` 大端 |

「网络字节序」这四个字容易让人以为「网络上跑的都是大端」——准确的说法是：**协议里那些多字节整数按大端写**，字节本身当然还是按顺序发。所以在这台小端机器上：

```text
socket.htons(0x0102) = 0x201          ← 真的翻了
socket.htonl(1)      = 0x1000000      ← 1 变成了 16777216
struct.pack('!H', 0x0102) = 01 02     ← '!' 就是大端
```

`htons` 的名字是「host to network short」。**host 是本地习惯，network 是协议规定。** 两个不一样的时候，协议赢——因为对端可能是一台大端设备，也可能是一段三十年前定下的报文格式，它不会为你改。

UTF-16 的 BOM 是个活例子：

```text
'A' 按 utf-16-le 编码: 41 00
'A' 按 utf-16-be 编码: 00 41
'A' 按 utf-16   编码: ff fe 41 00    ← 前面两个字节就是在说「我是小端」
```

`FF FE` 这个「字节序标记」本身就是个精心设计的巧合：它在大端下读出来是 `FFFE`，不是合法字符，所以两种读法都能立刻分辨。**这就是「把约定写进数据里」的典范**——比在文档里写一句「默认小端」可靠得多。

### 四、Python 里怎么把话说死

`int.to_bytes` / `int.from_bytes` 都要求（或允许）显式给字节序。**这里有个 3.11 之后才出现的静默坑：**

```text
Python 3.10 及以前: int.from_bytes(b'\x01\x00')  -> TypeError（必须写 byteorder）
Python 3.11 起    : int.from_bytes(b'\x01\x00')  -> 256（默认 'big'）
```

实测这台 3.14.9 上就是 `256`。**「少写一个参数」的代价，是把小端数据按大端读了。** 老代码如果依赖过「必须传参」的报错来提醒自己，升级后会安静地拿到一个错数。所以我的规矩是：**只要跨进程、跨设备、跨语言，字节序永远显式写出来，一个都不省。**

`struct` 的前缀更值得抄在便签上：

| 前缀 | 含义 |
|---|---|
| `<` | 小端，标准大小，不填充 |
| `>` | 大端，标准大小，不填充 |
| `!` | 网络字节序（= 大端），标准大小 |
| `=` | 本机字节序，标准大小，不填充 |
| `@` | 本机字节序，**本机对齐**（默认） |

`@` 是默认值，也是最多人无意中用的那个。它除了字节序，还会**按 C 结构体的规则插入填充字节**：

```text
struct.calcsize('@bi') = 8      ← char 1 字节 + 3 字节填充 + int 4 字节
struct.calcsize('=bi') = 5      ← 1 + 4，挤得干干净净
struct.calcsize('<bi') = 5
```

`b` 一个字节、`i` 四个字节，加起来该是 5，`@` 却给你 8。**这三个填充字节不会出现在你的字段定义里，但会出现在报文里。** 对端如果按「5 字节」解析，从第二个字段开始全部错位——而且错得很有规律，看起来像「值都乘了个系数」。跨设备协议里用 `@`，等于把编译器的对齐策略也一起发给了对方。**一律用 `<` 或 `>`。**

### 五、字节序是「字节之间」，位序是「字节之内」

这是两个正交的维度，但调试时经常被混成一句话：「顺序反了」。

- **字节序**：多个字节之间，谁在前。
- **位序**：一个字节内部，8 个比特谁先上线。

约定也不一样：

```text
UART: 先发 LSB（最低位先走）
SPI:  先发 MSB（最高位先走，多数器件）
I2C:  先发 MSB
```

所以 `0x01`（二进制 `00000001`）在 UART 线上按时间顺序看是这样的：

```text
数据位: █ · · · · · · ·      ← 那个 1 最先出现
```

示波器上看到「先高后低」，不代表这个字节是 `0x80`——**它可能只是 LSB 先发**。位反转函数长这样：

```text
rev8(0x01) = 0x80
rev8(0x80) = 0x01
rev8(0x0F) = 0xF0
```

这个区分在调试里非常实用：**如果整段数据「每个字节都像被镜像了」，那是位序；如果「每两个/四个字节一组互相调了个头」，那是字节序。** 两种错的形状完全不同，别用一种修法去治另一种病。把 `rev8` 套在字节序错误上，只会得到第三份错数据。

### 六、CAN 信号：字节对齐时是字节序，不对齐时是 bit 编号

CAN 报文里一个信号可能只占 12 位、10 位，跨着字节边界。DBC 文件里用两种格式描述它：

- **Intel**：小端，低位字节在前
- **Motorola**：大端，高位字节在前

字节对齐的时候，这条还算好懂。取数据 `12 34 56 78`，一个 16 位信号从第 0 字节开始：

```text
Intel（小端）    : 0x3412 = 13330
Motorola（大端） : 0x1234 = 4660
```

同一个信号，两种解释差了将近三倍。**这种错最阴的地方在于它不报错**：电机不会立刻飞车，只是速度环的反馈一直是错的，然后你开始怀疑 PID 参数。

更麻烦的是**非字节对齐**的情况。DBC 里 Motorola 信号的起始位用的是「锯齿形」编号：起始位指的是信号的最高位，而且跨字节时编号不是线性的。**这个我手算过两次，两次都错。** 正确做法只有一个：拿 `cantools` 之类的库把 DBC 解析出来，或者用厂商工具看解码结果，别拿纸笔推。**下面诚实一节会写明：这部分是文档结论，我今天没有真实 CAN 环境去实测。**

### 七、解析帧：先对账，再相信长度字段

回到开头那个 bug。帧格式是 `AA 55 | 长度(2) | 载荷 | CRC(1)`，实收：

```text
AA 55 | 01 00 | 0A | 3F
```

长度字段 `01 00`：

```text
按小端读: 1     ← 发送方的意思：后面有 1 字节载荷
按大端读: 256   ← 接收方的理解：后面有 256 字节
```

按 256 去读，就会一直等 255 个永远不来的字节。**这时候超时重发只会让问题更隐蔽**——每一帧都在等，每一帧都等不齐。

正确的顺序是**先对账，再解析**：

```text
1. 看帧头对不对（AA 55）
2. 按约定读长度 n
3. 检查 5 + n 是否等于实际收到的字节数
4. 不等就整帧丢掉，不要「先读一点试试」
```

第 3 步是关键。**永远不要相信报文里的长度字段，先用 `len(buf)` 给它对一次账。** 长度字段可能是恶意构造的、可能是字节序读错的、可能是上一版协议残留的——三种情况都表现为「数字看起来很合理」。而对账只要一行比较，代价几乎为零。

反过来，发送方也有一条：**读多少写多少。** 用 `to_bytes` 时宽度写死，值放不下就让它抛 `OverflowError`，别用掩码悄悄截断。`300` 塞进两个字节没问题，`70000` 塞进两个字节就该报错——静默截断会变成「偶尔有一帧数据不对」，这是最难查的一类 bug。

### 八、对着手上的东西看

- **nRF5340 ↔ RK3588 的 SPI。** 芯片手册里写「MSB first」，说的是**位序**，不是字节序。多字节寄存器先传高字节还是低字节，要看具体外设的框图，不能从「MSB first」推出来。
- **PMIC 的 16 位寄存器。** 手册的时序图里通常标了 MSB/LSB 在哪一端，那就是权威。别按「我觉得应该」写。
- **电机 CAN 帧。** 先确认 DBC 里是 Intel 还是 Motorola，再确认信号是否字节对齐。两个都确认完，再去调参数。
- **Modbus。** 寄存器是大端；32 位浮点跨两个寄存器时，还有厂商相关的「字交换」（两个 16 位寄存器的先后）。这不是协议能保证的，必须看设备文档。
- **日志。** 收到原始字节就打一份 hex，解析后的值另打一份。**只打解析值，等于把「解释」当成了「事实」**——等发现解释错了，原始数据已经没了。
- **写协议文档。** 别写「LSB first」这种有歧义的句子，写「小端：字节 0 是最低有效字节」。一句话能省掉对面半天的调试。

### 九、一句必须说清楚的诚实

- **属于规范/文档的**：`struct` 各前缀的含义与对齐规则；TCP/IP 用大端；DBC 的 Intel/Motorola 定义；UTF-16 BOM 的取值；Python 3.11 起 `int.from_bytes` 的 `byteorder` 默认 `'big'`。
- **属于这台机器这一次实测的**：上面所有十六进制、`calcsize` 的 8 与 5、`htons` 的结果、`40 42 0F 00` 的三种读数（Windows 11 / AMD64 / Python 3.14.9）。
- **没有实测的**：真实 CAN 总线上的非对齐信号解码——手上没有 CAN 分析仪和现成 DBC，所以第五节那部分是文档结论；实际动手前请用 `cantools` 验证一遍。
- **最要紧的一句**：字节序错误**不会抛异常**。它会安安静静给你一个「看起来合理」的数，然后你在下游查三天。所以它不是「小心一点」能解决的问题，得靠**显式约定 + 对账**从结构上堵住。

## 🧩 今日代码片段：`wirefmt.py` —— 把「字节怎么变成数」说死

`detect_endian` 不查文档直接看内存，`get_u` / `put_u` 把宽度和字节序都变成必填项，`read_frame` 先对账再解析，`can_intel` / `can_motorola` 把两种 CAN 信号格式摆在一起，`rev8` 处理位序。

```python
# -*- coding: utf-8 -*-
"""wirefmt.py —— 把「字节怎么变成数」这件事说死"""
import struct
import sys


def detect_endian() -> str:
    """不查文档、不问 sys.byteorder，直接看内存里 1 长什么样。"""
    return "little" if struct.pack("<I", 1)[0] == 1 else "big"


def get_u(buf: bytes, off: int, n: int, endian: str = "little") -> int:
    """从 buf[off:off+n] 读一个无符号整数，越界立刻报错，不静默截断。"""
    if off < 0 or n <= 0 or off + n > len(buf):
        raise ValueError(f"越界: off={off} n={n} len={len(buf)}")
    return int.from_bytes(buf[off:off + n], endian)


def put_u(value: int, n: int, endian: str = "little") -> bytes:
    """写出去时显式给宽度和字节序；放不下就抛 OverflowError，不悄悄截断。"""
    return value.to_bytes(n, endian, signed=False)


def read_frame(buf: bytes) -> dict:
    """AA 55 | len(2, little) | payload | crc(1)
    绝不相信 len 字段：先按实际字节数对账，再决定要不要继续解析。"""
    if len(buf) < 5:
        raise ValueError("帧太短")
    if buf[0:2] != b"\xAA\x55":
        raise ValueError(f"帧头不对: {buf[0:2].hex(' ')}")
    n = int.from_bytes(buf[2:4], "little")
    if 5 + n != len(buf):
        raise ValueError(f"长度字段说 {n} 字节，实际收到 {len(buf) - 5} 字节")
    return {"len": n, "payload": buf[4:4 + n], "crc": buf[4 + n]}


def can_intel(data: bytes, start_byte: int, nbytes: int) -> int:
    """CAN 'Intel'（小端）：低位字节在前。只处理字节对齐的信号。"""
    chunk = data[start_byte:start_byte + nbytes]
    if len(chunk) != nbytes:
        raise ValueError("信号超出数据长度")
    return int.from_bytes(chunk, "little")


def can_motorola(data: bytes, start_byte: int, nbytes: int) -> int:
    """CAN 'Motorola'（大端）：高位字节在前。同样只处理字节对齐。"""
    chunk = data[start_byte:start_byte + nbytes]
    if len(chunk) != nbytes:
        raise ValueError("信号超出数据长度")
    return int.from_bytes(chunk, "big")


def rev8(b: int) -> int:
    """位序反转。UART 先发 LSB、SPI 先发 MSB，接反了就靠它救。"""
    r = 0
    for _ in range(8):
        r = (r << 1) | (b & 1)
        b >>= 1
    return r


if __name__ == "__main__":
    print("本机字节序:", detect_endian(), "| sys.byteorder:", sys.byteorder)

    print("0x0102 两种摆法:",
          "little =", put_u(0x0102, 2, "little").hex(" "),
          "| big =", put_u(0x0102, 2, "big").hex(" "))

    print("struct 对齐: '@bi' =", struct.calcsize("@bi"), "字节 | '=bi' =", struct.calcsize("=bi"), "字节")

    frame = bytes.fromhex("AA 55 01 00 0A 3F")
    print("正常帧:", read_frame(frame))
    try:
        read_frame(bytes.fromhex("AA 55 01 00 0A"))
    except ValueError as e:
        print("截断帧被拦:", e)

    data = bytes.fromhex("12 34 56 78")
    print("同一段字节: Intel =", can_intel(data, 0, 2), "| Motorola =", can_motorola(data, 0, 2))

    print("0x01 的位序: 正常", f"{0x01:08b}", "| 反转", f"{rev8(0x01):08b}")

    try:
        get_u(b"\x01", 0, 2)
    except ValueError as e:
        print("越界被拦:", e)

    raw = bytes.fromhex("40 42 0F 00")
    print("四个字节三种读法: u32 little =", int.from_bytes(raw, "little"),
          "| u32 big =", int.from_bytes(raw, "big"),
          "| f32 little =", struct.unpack("<f", raw)[0])
```

实测输出（Windows 11 / AMD64 / Python 3.14.9）：

```text
本机字节序: little | sys.byteorder: little
0x0102 两种摆法: little = 02 01 | big = 01 02
struct 对齐: '@bi' = 8 字节 | '=bi' = 5 字节
正常帧: {'len': 1, 'payload': b'\n', 'crc': 63}
截断帧被拦: 长度字段说 1 字节，实际收到 0 字节
同一段字节: Intel = 13330 | Motorola = 4660
0x01 的位序: 正常 00000001 | 反转 10000000
越界被拦: 越界: off=0 n=2 len=1
四个字节三种读法: u32 little = 1000000 | u32 big = 1078071040 | f32 little = 1.401298464324817e-39
```

五个值得单独说的细节：

- **`detect_endian` 没有调 `sys.byteorder`，而是真的打了一个数看内存。** 文档和运行时可能不一致（交叉编译、模拟器、序列化的字节流），一行实测比一句假设可靠。当然，日常用 `sys.byteorder` 就够了——这个函数的意义是「证明」，不是「查询」。
- **`read_frame` 里 `5 + n != len(buf)` 这一行是整套的核心。** 注意它没有尝试「读 n 个字节，不够就返回部分」——**部分帧比完整帧更危险**，因为它会一路混进解析逻辑。宁可整帧丢掉。
- **`get_u` 故意把越界写成异常。** `int.from_bytes` 本身对切片长度是宽容的：你给它 1 个字节说读 2 个，它不报错，只是少读一个。这类「静默少读」在循环解析里会变成错位，错位又会让后面的 CRC 校验失败，最后你追到 CRC 头上。
- **`can_intel` / `can_motorola` 只处理字节对齐的信号，这是刻意的。** 非对齐信号需要按位拼接，而 Motorola 的起始位语义和普通大端不是一回事。**与其写一个「大概率对」的解码器，不如把限制写在函数名和文档里**——它会逼你在调用处确认信号是否真的字节对齐。
- **`rev8` 是这五个函数里唯一「治另一种病」的。** 它不碰字节的先后，只翻字节内部的位。调试时先用它确认「是不是位序问题」，再决定要不要动字节序——两个都改，只会让现象更乱。

一句话收这段：**字节序不是存储格式，是解释权。谁写的报文，谁就有权规定按哪种读法；读的人如果没拿到这份规定，读出来的每一个数都只是猜测。**

## ✨ 今日一句

> 两个字节 `01 00`，一个人读出 1，一个人读出 256。**他们看的不是同一份数据，是同一份数据加各自的约定。**
>
> 字节序的可怕之处不是它难，是它错了也不报错——它只会给你一个「看起来挺合理」的数，让你去怀疑线缆、怀疑干扰、怀疑 PID。
