## 💭 技术随想：慢查询不是玄学——学会读 EXPLAIN，SQL 调优就入门了

大多数后端性能问题，追到最后都是同一个答案：一条本该走索引的查询，走了全表扫描。数据库不会自己喊疼，它只会默默地把 500 万行数据扫一遍，然后你的接口从 50ms 变成 3 秒。

**判断一个 SQL 写得好不好，不要靠"感觉"，要学会看执行计划。** MySQL 里就是 `EXPLAIN`，PostgreSQL 里是 `EXPLAIN ANALYZE`。几个真正重要的信号：

1. **`type` 列**（MySQL）：从好到坏依次是 `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。看到 `ALL`（全表扫描）或 `index`（全索引扫描，等于把整棵索引树扫一遍）就该警觉。目标是至少达到 `range`，最好 `ref` 以上。

2. **`rows` 列**：估算要扫描的行数。如果查询最终只返回 10 行，但 `rows` 显示 50 万，说明索引选择性差，数据库在大量无用行上浪费了时间。

3. **`Using filesort` / `Using temporary`**：出现这两个，说明 `ORDER BY` 或 `GROUP BY` 没能利用索引的有序性，数据库被迫在内存/磁盘上额外排序——数据量大时是性能杀手。

**最常见的三个坑：**

- **对索引列做函数运算或隐式类型转换。** `WHERE DATE(created_at) = '2026-08-13'` 用不上 `created_at` 的索引（函数包裹了列）；`WHERE phone = 13800138000` 而 `phone` 是 `VARCHAR` 时，隐式转换同样让索引失效。正确写法：`WHERE created_at >= '2026-08-13' AND created_at < '2026-08-14'`，phone 比较时带引号。
- **联合索引不遵循最左前缀原则。** 建了 `(user_id, status, created_at)` 联合索引，查询却只按 `status` 过滤——索引的第一个列 `user_id` 没出现在 WHERE 里，整个索引就用不上。联合索引的顺序应该按"等值查询列在前、范围查询列在后"来设计。
- **`SELECT *` + 大字段。** 分页列表非要 `SELECT *`，把 `TEXT`/`BLOB` 大字段也拉出来。优化方式：列表查询只取需要的列（必要时用覆盖索引），详情页再去取完整数据。

**心法：** 索引的本质是"用空间换时间"的有序数据结构，它只对"前缀匹配、等值、范围"友好。每次写 SQL 前多想一步——这条查询会怎么用索引？再配合 `EXPLAIN` 验证，你就从"凭感觉优化"进入了"看证据优化"的阶段。

## 🧩 今日代码片段：用 Python + EXPLAIN 快速分析一条 SQL 的执行计划

```python
import pymysql

def explain_query(conn, sql: str) -> dict:
    """
    返回一条 SQL 的执行计划摘要。
    重点关注: type / key / rows / Extra
    """
    with conn.cursor(pymysql.cursors.DictCursor) as cur:
        cur.execute(f"EXPLAIN {sql}")
        plan = cur.fetchone()

    # 红绿灯判断
    type_rank = {
        "system": 0, "const": 1, "eq_ref": 2, "ref": 3,
        "range": 4, "index": 5, "ALL": 6,
    }
    scan_type = plan.get("type", "ALL")
    rank = type_rank.get(scan_type, 6)

    if rank <= 3:
        verdict = "✅ 优：走了索引精确查找"
    elif rank == 4:
        verdict = "🟡 中：范围扫描，注意 rows 数量"
    else:
        verdict = "❌ 差：全表/全索引扫描，需要加索引"

    return {
        "verdict": verdict,
        "type": scan_type,
        "key": plan.get("key"),            # 实际使用的索引（NULL = 没走索引！）
        "possible_keys": plan.get("possible_keys"),
        "rows": plan.get("rows"),          # 估算扫描行数
        "extra": plan.get("Extra"),        # 看到 Using filesort/temporary 要警惕
    }

# 用法示例
conn = pymysql.connect(host="127.0.0.1", user="root",
                       password="***", database="shop")

# 反面教材：函数包裹索引列，type=ALL，key=NULL
bad_sql = "SELECT * FROM orders WHERE DATE(created_at) = '2026-08-13'"
print(explain_query(conn, bad_sql))

# 正面写法：区间条件，type=range，key=idx_created_at
good_sql = ("SELECT * FROM orders "
            "WHERE created_at >= '2026-08-13' AND created_at < '2026-08-14'")
print(explain_query(conn, good_sql))
```

**说明：**
- `key` 为 `NULL` 而 `possible_keys` 非空，说明优化器认为"用索引还不如全表扫"或索引根本用不上——这是最值得深挖的信号。
- `EXPLAIN ANALYZE`（MySQL 8.0.18+ / PostgreSQL）会真实执行查询并给出每一步的耗时，比普通 `EXPLAIN` 的估算值更可靠。
- 这个小函数可以做成 CI 里的"慢查询哨兵"：对核心 SQL 跑一遍，`type` 掉到 `index`/`ALL` 或 `rows` 超过阈值就报警。
