## 💭 技术随想：asyncio 的正确打开方式——并发不是并行，但用对了能提速百倍

写了几年同步 Python 的人，第一次接触 `async/await` 时往往有两类反应：一类觉得"不就是在函数前加个关键字嘛"，另一类被事件循环、协程、Future、Task 这些概念劝退。其实 asyncio 的核心思想一句话就能说清：**它用单线程模拟并发，靠"在等待 I/O 时切换任务"来榨干时间。**

理解这个本质，很多坑就不踩了：

**1. 它只对 I/O 密集任务有效。** 一个网络请求要等 100ms，其中 99.9ms 都在等服务器响应——CPU 是闲着的。asyncio 的思路是：等待期间去干别的活，100 个请求的 100ms 等待时间重叠起来，总耗时就从 10 秒压到接近 1 秒。但如果你的任务是在算斐波那契数列（CPU 密集），`async def` 救不了你，那得用 `multiprocessing` 或 C 扩展释放 GIL。

**2. 最大的坑：在协程里调用阻塞函数。** `requests.get()`、`time.sleep()`、慢 SQL 驱动——任何一个阻塞调用都会卡死整个事件循环，所有协程全部瘫痪。这就是"代码看着是异步的，跑起来比同步还慢"的经典原因。规则很简单：网络 I/O 用 `httpx`/`aiohttp`，睡眠用 `asyncio.sleep`，实在绕不开的阻塞调用丢进 `loop.run_in_executor()` 线程池。

**3. `gather` 不是万能的，无限流等于自爆。** `asyncio.gather(*[fetch(url) for url in urls])` 对 1000 个 URL 同时发请求，对端服务器和你的带宽都会被打爆，还可能触发限流封禁。正确做法是用 `asyncio.Semaphore` 做令牌桶限流，把并发控制在 20-50 个。

**4. 协程没有被 `await` 就是没执行。** `asyncio.create_task(coro())` 之后不 `await` 任务会跑，但裸写一行 `coro()` 只会得到一个"从未被等待"的警告——任务静默丢失。同理，`gather` 里一个任务抛异常默认会取消其他任务，记得传 `return_exceptions=True`，或者用 `asyncio.wait(..., return_when=FIRST_EXCEPTION)` 精细控制。

**心法：** 把 asyncio 想象成一个"效率极高的服务员"——他一个人同时服务十桌客人，秘诀不是在客人点菜时跑得飞快，而是把每道菜交给厨房后立刻去下一桌，绝不站在厨房门口干等。你的每行 `await` 都在告诉事件循环："我这边要等一会儿，你先去忙别人的。"写得越多，越明白性能瓶颈从来不是 CPU 不够快，而是等待的方式太浪费。

## 🧩 今日代码片段：带限流、超时、重试的异步批量请求器

```python
import asyncio
import httpx
from typing import Iterable

async def fetch_with_retry(
    client: httpx.AsyncClient,
    url: str,
    sem: asyncio.Semaphore,
    retries: int = 3,
) -> tuple[str, int | str]:
    """带信号量限流 + 指数退避重试的抓取函数"""
    async with sem:  # 关键：信号量在这里才真正限制并发
        for attempt in range(retries):
            try:
                resp = await client.get(url, timeout=10)
                return url, resp.status_code
            except (httpx.TimeoutException, httpx.TransportError) as e:
                if attempt == retries - 1:
                    return url, f"失败: {e.__class__.__name__}"
                await asyncio.sleep(2 ** attempt)  # 1s, 2s, 4s 退避
        return url, "失败: 重试耗尽"  # pragma: no cover


async def batch_fetch(urls: Iterable[str], concurrency: int = 20):
    """批量请求入口：并发 20，单个超时 10s，整体兜底 60s"""
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient() as client:
        tasks = [fetch_with_retry(client, u, sem) for u in urls]
        # return_exceptions=True：一个任务挂了不拖垮整批
        results = await asyncio.wait_for(
            asyncio.gather(*tasks, return_exceptions=True), timeout=60
        )
    return results


async def main():
    urls = [f"https://httpbin.org/delay/1?id={i}" for i in range(100)]
    results = await batch_fetch(urls, concurrency=20)
    ok = sum(1 for _, code in results if isinstance(code, int) and code < 400)
    print(f"100 个请求（各延迟 1s）→ {len(results)} 个返回，成功 {ok} 个")


if __name__ == "__main__":
    asyncio.run(main())
```

**说明：**

- 100 个各延迟 1 秒的请求，同步写法要 100 秒；上面这段并发 20，理论上 5 秒左右跑完——**等待时间被重叠了，CPU 全程只跑一个线程**。
- `Semaphore` 放在函数最外层，保证"拿到令牌才开始发请求"，而不是协程创建时抢占。
- 生产环境把 `httpx.TimeoutException` 换成 `httpx.HTTPStatusError` 组合使用，5xx 也值得重试（注意幂等性）。
- 快速自测：把 `asyncio.run(main())` 前的函数换成 `time.sleep` 版本对比一下，你会立刻理解"并发"和"并行"的区别。
