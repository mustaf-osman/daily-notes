## 💭 技术随想：一个写者，锁住整个文件——SQLite 的并发到底卡在哪

起因很小：一个落库的进程里起了两个线程，各自开一条连接，往同一张表里写。日志里开始零星出现 `database is locked`，重试三次就好了，于是被归成"偶发"。今天把这件事量了一遍，结论不是"偶发"，是**结构性的**。

先说环境，免得把数字当普适真理：Windows 11 / NTFS / Python 3.11.15 / SQLite 3.53.1，杀毒软件实时扫描开着。所以下面的绝对耗时偏慢，换到 ext4 会好看一些；但**比例关系**（批量 vs 逐行、WAL vs journal）是结构决定的，换机器也还在。

再声明一句：下面每个数字都是本机一次真实运行的结果，同一台机器重跑会在一定范围里浮动（逐行提交 17.6~19.2 秒、C 的 p99 在 109~141 ms 之间都出现过），读次数那一列还跟测量窗口长短有关。**看数量级和比例，别把个位数当基准。**

### 一、先算一次 commit 的价钱

同一张表、每次提交插入一行、各跑 300 次：

| 模式 | 一次提交 | 折算上限 |
|---|---|---|
| journal（DELETE）+ synchronous=FULL | **3.255 ms** | 307 次/秒 |
| journal（DELETE）+ synchronous=NORMAL | 2.964 ms | 337 次/秒 |
| WAL + synchronous=FULL | 0.599 ms | 1670 次/秒 |
| WAL + synchronous=NORMAL | **0.026 ms** | 39104 次/秒 |
| WAL + synchronous=OFF | 0.024 ms | 42439 次/秒 |

第一行就是默认配置。**默认的 SQLite，一秒钟最多提交三百来次**——不是插入慢，是提交慢。

journal 模式下每次提交要做完一整套：写 journal 文件 → fsync → 改主库 → fsync → 删 journal。注意第二行：把 `synchronous` 从 FULL 降到 NORMAL，只从 3.255 ms 变成 2.964 ms，**差不到 10%**。说明在这台机器上，瓶颈不只是 fsync，还有"每提交一次就创建、再删除一个 journal 文件"的元数据开销。这条在 ext4 上不一定成立，别照搬。

WAL 换了个思路：不覆盖主库，往 `-wal` 文件末尾追加，一次提交不碰主库。但看第三行——**WAL + FULL 仍然要 0.599 ms，只比 journal 快 5 倍多**。真正快的是第四行：WAL + NORMAL，0.026 ms，比默认快 **125 倍**。所以"我开了 WAL 怎么还是慢"的人，多半 `synchronous` 还停在 FULL——WAL 省的是"改主库"的随机写，不是 fsync。

代价要说清楚：WAL + NORMAL 下，掉电会丢最近若干次提交，但**库不会坏**（这是 WAL 的设计目标）；FULL 是连最近一次都不丢。日志、流水这类数据，NORMAL 是合理的；账本要较真就 FULL，但你得接受 23 倍的成本。

### 二、批量：5000 行，17.575 秒 vs 0.009 秒

| 写法 | 耗时 | 行/秒 |
|---|---|---|
| journal，逐行 commit | **17.575 s** | 284 |
| journal，单事务 | 0.009 s | 581085 |
| journal，单事务 + sync=OFF | 0.008 s | 591681 |
| WAL，逐行 commit | 0.145 s | 34540 |
| WAL，单事务 | 0.012 s | 413678 |
| WAL，单事务 + sync=OFF | 0.007 s | 744668 |

最快和最慢差 **2618 倍**。同样 5000 行、同样的机器、同样的表。

再看提交间隔的曲线（3000 行，journal + FULL）：

| commit 间隔 | 总耗时 | 相对逐行 |
|---|---|---|
| 每行 | 10.524 s | 1.0x |
| 每 10 行 | 1.176 s | 8.9x |
| 每 100 行 | 0.101 s | **104.6x** |
| 每 1000 行 | 0.016 s | **677x** |
| 每 10000 行 / 一次事务 | 0.008 s | 1374x |

（3000 行的实验里，"每 10000 行"和"一次事务"是同一件事，都只提交一次，两行数字一样不奇怪。）

曲线的形状比数字更有用：**从每行到每 100 行，拿到了 105 倍里的绝大部分；从 100 到 1000 又拿了 6 倍；再往上就平了。** 因为收益的来源是"少做 fsync"，一秒钟能做的 fsync 次数是固定的，摊到 1000 行上已经接近于零。

但批量和并发是对立的：批越大，写锁持得越久，别人等得越久。这就是下一节。

### 三、两个写者：600 次写，152 次失败

两个线程、各自一条连接、各写 300 次：

| 配置 | 成功 | 失败 | 总耗时 | 单次最长等待 |
|---|---|---|---|---|
| journal，无 busy_timeout | 448 | **152（25%）** | 2.10 s | 34 ms |
| journal，busy_timeout=5s | 600 | 0 | 3.05 s | **265 ms** |
| WAL，busy_timeout=5s | 600 | 0 | **0.98 s** | 63 ms |

第一行不是"偶尔失败"，是四分之一失败。第二行把错误变成了等待：全部成功，但代价是单次最长等 265 ms。第三行两个都要：全成功，总时间还是最短。

原因一句话：**SQLite 的写锁是库级的。** 不是行锁，也不是表锁——一个连接在写，整个库就只有一个写者，别人要么等，要么失败。这不是实现偷懒，是文件锁这个机制只能锁到文件。

这里有个特别容易踩的坑，我实测确认了：**Python 的 `sqlite3.connect()` 默认 `timeout=5.0`，也就是 `busy_timeout` 默认就是 5000 ms。** 所以绝大多数人根本看不到 `database is locked`，看到的是"这个接口偶尔卡五秒"。比报错难查得多——报错至少指向锁，卡五秒只会被归到"网络抖动"。

```python
# 默认：卡 5 秒再报错
sqlite3.connect(path)
# 想快速失败：显式调小，让问题暴露在日志里
sqlite3.connect(path, timeout=0.2)
```

### 四、读会不会被写堵住

这是 WAL 真正值钱的地方。一个线程不停地开小事务写（每次写一行、立刻提交），另一个线程在同一时间不停 `SELECT count(*)`，`busy_timeout=200ms`：

| 模式 | 空闲 p50 | 写入时 p50 | p99 | 最大 | 同一窗口内完成的读 |
|---|---|---|---|---|---|
| journal（DELETE） | 0.160 ms | 0.538 ms | **109.67 ms** | 109.67 ms | **32 次** |
| WAL | 0.007 ms | **0.005 ms** | 0.02 ms | 5.28 ms | **31239 次** |

左边那一列：读一次的平均值看着还行（0.5 ms），但 p99 直接跳到 109 ms——**平均是给报告看的，p99 是给用户看的**。右边那一列更直接：WAL 下写入时读到 0.005 ms，比空闲时还快一点点（噪音），因为读的人根本不看写的人在干什么。

再看"同一窗口内完成的读"：32 次 vs 31239 次。这三十二次和三点一万次之间，不是"快一点"，是**能不能用**。

机制值得说明白：

- journal 模式：读者拿 SHARED 锁，写者提交时要 EXCLUSIVE 锁，两者互斥。写者提交得越勤，读者越容易被挡在门外，而且等待是**睡眠重试**，不是被唤醒——所以延迟是台阶状的，一卡就是几十上百毫秒。
- WAL 模式：写者往 `-wal` 追加，读者看自己那个快照，两边不碰同一把锁。**读不挡写，写不挡读**——但写和写仍然互斥，WAL 没有把"单写者"变成"多写者"。

这条对机器人系统很实用：状态/日志表一直有人写，前端和调试接口要随时读。journal 模式下，前端刷新会被巡检任务拖成幻灯片；WAL 下互不干扰。

### 五、WAL 的两笔账：文件会长，checkpoint 得有人干

关掉 `wal_autocheckpoint`，一路插入并提交：

| 已提交行数 | `-wal` 大小 | 主库大小 |
|---|---|---|
| 5000 | 0.12 MB | 0.00 MB |
| 10000 | 0.22 MB | 0.00 MB |
| 15000 | 0.33 MB | 0.00 MB |
| 20000 | 0.44 MB | 0.00 MB |

`checkpoint(TRUNCATE)` 之后：`-wal` 0.00 MB，主库 0.39 MB。

每行大概 22 字节的 WAL 开销，线性增长——**这不是泄漏，是账还没结**。数据全都躺在 `-wal` 里，主库还是空的。自动 checkpoint 默认是开着的（1000 页触发一次），关掉它只是为了让这件事显形。

两件真事：

1. **WAL 会被长读卡住。** checkpoint 只能把"所有读者都已经不看的那部分"回写主库。一个开了读事务、然后跑去算十分钟报表的连接，会让 `-wal` 在这十分钟里只长不缩。文档里写得很清楚，我这里没造这个场景。
2. **WAL 依赖共享内存和文件锁**，要求所有连接在同一台机器上。把库放到 NFS/SMB 共享盘上跑 WAL，是自找麻烦——这点也是文档说的，不是我在共享盘上踩出来的。

### 六、备份：拷出来一个 4096 字节的空库

这是今天最值得记住的一条。WAL 模式下写 5000 行、连接保持打开：

```text
主库 h.db      : 4096 字节
WAL  h.db-wal  : 94792 字节
新连接读到的行数: 5000（数据在 WAL 里，读得到）
```

然后按最朴素的方式备份——只拷 `h.db`：

```text
h_copy.db 大小  : 4096 字节
拷出来的内容    : 读表失败：no such table: t  ← 丢了 5000 行
```

**不是丢了最近的几千行，是一张表都没有。** 因为建表语句本身也还在 WAL 里没回写。用 `backup` API 拷：5000 行，一行不少。连接关闭之后再看，WAL 已消失、主库变成 86016 字节——最后一个连接关闭时会顺手做一次 checkpoint，所以"关掉再拷"看着是好的，这就更能骗人。

正确的备份只有三条路：SQLite 的 backup API（Python 里是 `conn.backup(dst)`）、`VACUUM INTO 'file.db'`、或者先停写、`wal_checkpoint(TRUNCATE)` 之后再拷。**只拷 `.db`，在 WAL 模式下等于备份了个寂寞。**

### 七、顺带：索引不是优化，是能不能用

10 万行，按名字查 `count(*)`：

| | 每次查询 | 执行计划 |
|---|---|---|
| 无索引 | **6.516 ms** | `SCAN big` |
| 有索引 | **0.194 ms** | `SEARCH big USING COVERING INDEX idx_name` |

33 倍，建索引花了 45 ms。单看 6.5 ms 好像能忍，但每秒 100 次查询就是 65% 的一个核——不是"慢一点"，是把 CPU 预算吃光了。

### 八、PRAGMA 谁记得住，谁记不住

实测，同一个库，换一条新连接：

| PRAGMA | 重新连接后 | 说明 |
|---|---|---|
| `journal_mode` | **wal**（保留） | 写进库文件头，一次设置，永久生效 |
| `synchronous` | 2 = FULL（回默认） | 每条连接自己的 |
| `busy_timeout` | 5000（回默认） | 每条连接自己的 |

这条能解释一类幽灵 bug：在初始化函数里设了 `synchronous=NORMAL`，后来某个后台线程新开了一条连接，忘了设——那条连接悄悄按 FULL 跑，慢得莫名其妙，而你查初始化代码怎么看都对。**建连接的函数只有一个，所有 PRAGMA 都在里面设，别散落。**

### 九、能抄走的部分

1. **写多读少的本地库：`journal_mode=WAL` + `synchronous=NORMAL` + 显式 `busy_timeout`。** 三个都要，少一个都会在某个场景下退化成默认值。
2. **批量提交，100~1000 行一批。** 5000 行上这是 17.575 s 和 0.009 s 的差别；曲线在 100 行之后就开始平了，别为了省最后一点把事务拖成几秒的长锁。
3. **一个写者。** 所有写操作排进一个队列，由一条线程/一个连接消费。不是"给每个线程一条连接"，那只是把锁竞争从进程内挪到文件锁上。
4. **读用另一条连接，别和写共用。** 共用连接会把读也拖进写事务，而且 Python 的 `sqlite3` 连接默认不允许跨线程用。
5. **`database is locked` 不是靠加重试解决的。** 先看模式、看谁在写、事务有多长；盲目重试是在给已经堵住的锁再加一层负载。
6. **`timeout` 要么调小让它暴露，要么调大但要记指标。** 默认 5 秒的等待最坏：错误被藏起来，延迟被摊到业务上。
7. **备份用 `conn.backup()` 或 `VACUUM INTO`。** WAL 模式下只拷 `.db`，拷到的是空库——今天亲眼看到 5000 行变成 0 行。
8. **别把库放网络盘。** WAL 要共享内存和 POSIX 文件锁，NFS/SMB 上语义不成立。
9. **查询路径上的列建索引，写多的表算清代价。** 建索引 45 ms、查询快 33 倍，这笔账很好算；但每个索引都会让写入变慢一点。
10. **打点四个数：提交耗时 p99、busy 重试次数、`-wal` 大小、每批行数。** 这四个数比"数据库好像有点慢"有用一万倍。

### 十、和手上的东西对上

- **rp_server 的日志/状态表**：写多、读少、单机 → WAL + NORMAL + 单写线程 + 批量提交。前端轮询状态时，不会再被巡检写事务拖住。
- **生鲜超市的 POS 流水导入**：一天几千行，如果逐行提交，就是"导入转圈十几秒"；一个事务包完，几十毫秒。这不是优化，这是同一个操作在两种写法下的两个量级。
- **反过来，别过度批量**：一次事务塞十万行，WAL 会涨、checkpoint 会变重、别的写者会等更久。批大小是"吞吐 / 延迟"的旋钮，不是越大越好。

一句话总结今天量到的东西：**SQLite 的锁不在行上，也不在表上，在整个文件上；它的快慢不取决于你插得多快，而取决于你把多少次 fsync 摊到了多少行上。**

## 🧩 今日代码片段：SQLite 并发实验室 + 一个只让一个线程写的队列

前半段是能把上面每个数字重新跑一遍的实验脚本（A 五种插入写法、B 两个写者、C 写压下的读延迟、D WAL 增长、H 只拷 .db 的备份）；后半段是可以直接抄进项目的 `BatchWriter`：一个写线程、一个队列、按行数或时间攒批、WAL + NORMAL、只在真 busy 时退避。

```python
# -*- coding: utf-8 -*-
"""SQLite 并发实验室：一库一写者

A 五种插入写法（journal/WAL × 逐行/单事务），5000 行
B 两个线程同时写，各 300 次：无 busy_timeout / journal+timeout / WAL+timeout
C 写压不停时读的延迟分布：journal vs WAL
D 关掉 autocheckpoint，看 -wal 长多大，再 checkpoint
H WAL 下只拷 .db 的备份，会丢多少
"""
import os
import shutil
import sqlite3
import sys
import threading
import time

try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass

LINE = "=" * 78
DIR = os.path.dirname(os.path.abspath(__file__))
N = 5000


def pad(s, w):
    import unicodedata
    ww = sum(2 if unicodedata.east_asian_width(c) in "WF" else 1 for c in s)
    return s + " " * max(0, w - ww)


def fresh(name):
    p = os.path.join(DIR, name)
    for suf in ("", "-wal", "-shm", "-journal"):
        try:
            os.remove(p + suf)
        except OSError:
            pass
    return p


def connect(p, mode=None, sync=None, timeout=5.0):
    c = sqlite3.connect(p, timeout=timeout)      # isolation_level 用默认值：DML 前隐式 BEGIN
    if mode:
        c.execute("PRAGMA journal_mode=%s" % mode)
    if sync:
        c.execute("PRAGMA synchronous=%s" % sync)
    return c


def make_table(c):
    c.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, ts REAL, name TEXT, val REAL)")


def insert(c, n, commit_every=None):
    for i in range(n):
        c.execute("INSERT INTO t (ts,name,val) VALUES (?,?,?)",
                  (time.time(), "sensor_%d" % (i % 37), i * 0.001))
        if commit_every and (i + 1) % commit_every == 0:
            c.commit()
    c.commit()


def size_of(p):
    total = 0
    for suf in ("", "-wal", "-shm"):
        try:
            total += os.path.getsize(p + suf)
        except OSError:
            pass
    return total


# ------------------------------------------------------------------ A
def exp_a():
    cases = [
        ("journal, 逐行 commit", "DELETE", "FULL", 1),
        ("journal, 单事务", "DELETE", "FULL", None),
        ("journal, 单事务 + sync=OFF", "DELETE", "OFF", None),
        ("WAL, 逐行 commit", "WAL", "NORMAL", 1),
        ("WAL, 单事务", "WAL", "NORMAL", None),
        ("WAL, 单事务 + sync=OFF", "WAL", "OFF", None),
    ]
    for i, (label, mode, sync, ce) in enumerate(cases):
        p = fresh("a%d.db" % i)
        c = connect(p, mode, sync)
        make_table(c)
        t0 = time.perf_counter()
        insert(c, N, commit_every=ce)
        dt = time.perf_counter() - t0
        c.close()
        print("  " + pad(label, 26) + pad("%.3f s" % dt, 10)
              + pad("%.0f 行/秒" % (N / dt), 14) + "%.1f MB" % (size_of(p) / 1e6))


# ------------------------------------------------------------------ B
def exp_b():
    for idx, (label, mode, timeout) in enumerate([
            ("journal, 无 busy_timeout", "DELETE", 0.0),
            ("journal, busy_timeout=5s", "DELETE", 5.0),
            ("WAL, busy_timeout=5s", "WAL", 5.0)]):
        p = fresh("b%d.db" % idx)
        s = sqlite3.connect(p)
        s.execute("PRAGMA journal_mode=%s" % mode)
        make_table(s)
        s.commit()
        s.close()

        ok, bad, errs, mw = [0, 0], [0, 0], [], [0.0, 0.0]

        def worker(k):
            conn = sqlite3.connect(p, timeout=timeout)
            for i in range(300):
                t0 = time.perf_counter()
                try:
                    conn.execute("INSERT INTO t (ts,name,val) VALUES (?,?,?)",
                                 (time.time(), "w%d_%d" % (k, i), 1.0))
                    conn.commit()
                    ok[k] += 1
                except sqlite3.OperationalError as e:
                    bad[k] += 1
                    errs.append(str(e))
                mw[k] = max(mw[k], time.perf_counter() - t0)
                time.sleep(0.0005)
            conn.close()

        t0 = time.perf_counter()
        ts = [threading.Thread(target=worker, args=(k,)) for k in range(2)]
        [t.start() for t in ts]
        [t.join() for t in ts]
        print("  " + pad(label, 26) + pad("成功 %d" % sum(ok), 12)
              + pad("失败 %d" % sum(bad), 10) + pad("%.2f s" % (time.perf_counter() - t0), 10)
              + "最长 %.0f ms" % (max(mw) * 1e3))
        if errs:
            print("      首个错误：%s" % errs[0])


# ------------------------------------------------------------------ C
def pct(v, p):
    s = sorted(v)
    k = int(round((len(s) - 1) * p / 100.0))
    return s[max(0, min(k, len(s) - 1))]


def exp_c():
    for i, (label, mode, sync) in enumerate([("journal (DELETE)", "DELETE", "FULL"),
                                             ("WAL", "WAL", "NORMAL")]):
        p = fresh("c%d.db" % i)
        w = sqlite3.connect(p, timeout=5.0, isolation_level=None)
        w.execute("PRAGMA journal_mode=%s" % mode)
        w.execute("PRAGMA synchronous=%s" % sync)
        w.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, v TEXT)")
        w.execute("BEGIN")
        for k in range(1000):
            w.execute("INSERT INTO t (v) VALUES (?)", ("row%d" % k,))
        w.execute("COMMIT")
        w.close()

        r = sqlite3.connect(p, timeout=0.2)
        r.execute("PRAGMA busy_timeout=200")
        base = []
        for _ in range(20):
            t0 = time.perf_counter()
            r.execute("SELECT count(*) FROM t").fetchone()
            base.append(time.perf_counter() - t0)

        stop, reads, busy = threading.Event(), [], 0

        def writer():
            c = sqlite3.connect(p, timeout=5.0, isolation_level=None)
            c.execute("PRAGMA journal_mode=%s" % mode)
            for k in range(150):
                c.execute("BEGIN IMMEDIATE")
                c.execute("INSERT INTO t (v) VALUES (?)", ("w%d" % k,))
                c.execute("COMMIT")
            c.close()
            stop.set()

        th = threading.Thread(target=writer)
        th.start()
        while not stop.is_set():
            t0 = time.perf_counter()
            try:
                r.execute("SELECT count(*) FROM t").fetchone()
            except sqlite3.OperationalError:
                busy += 1
            reads.append(time.perf_counter() - t0)
        th.join()
        r.close()
        print("  " + pad(label, 20) + pad("空闲 p50 %.3f ms" % (pct(base, 50) * 1e3), 22)
              + pad("写入时 p50 %.3f ms" % (pct(reads, 50) * 1e3), 24)
              + pad("p99 %.2f ms" % (pct(reads, 99) * 1e3), 16)
              + "读 %d 次，busy %d 次" % (len(reads), busy))
```

然后是写队列。所有写都进队列，只有这一个线程碰数据库：

```python
# -*- coding: utf-8 -*-
"""BatchWriter：一个写线程，按行数/时间攒批，WAL + NORMAL"""
import queue
import sqlite3
import threading
import time


class BatchWriter:
    def __init__(self, path, sql, batch=200, max_delay=0.5):
        self.path, self.sql = path, sql
        self.batch, self.max_delay = batch, max_delay
        self.q = queue.Queue()
        self.stats = {"rows": 0, "batches": 0, "busy": 0}
        self.t = threading.Thread(target=self._run, daemon=True)
        self.t.start()

    def put(self, row):
        self.q.put(row)

    def _connect(self):
        c = sqlite3.connect(self.path, timeout=1.0)
        c.execute("PRAGMA journal_mode=WAL")       # 持久设置，但仍在这里声明，语义清楚
        c.execute("PRAGMA synchronous=NORMAL")     # 每条连接都要设
        c.execute("PRAGMA busy_timeout=1000")      # 每条连接都要设
        return c

    def _run(self):
        conn = self._connect()
        while True:
            rows, stop = [], False
            first = self.q.get()
            if first is None:
                conn.close()
                return
            rows.append(first)
            deadline = time.monotonic() + self.max_delay
            while len(rows) < self.batch:           # 攒够一批，或者等够 max_delay
                left = deadline - time.monotonic()
                if left <= 0:
                    break
                try:
                    item = self.q.get(timeout=left)
                except queue.Empty:
                    break
                if item is None:                    # 关停信号可能夹在数据中间
                    stop = True
                    break
                rows.append(item)

            while True:                             # busy 是暂时的：退避重试，不丢行
                try:
                    conn.execute("BEGIN IMMEDIATE")
                    conn.executemany(self.sql, rows)
                    conn.execute("COMMIT")
                    self.stats["rows"] += len(rows)
                    self.stats["batches"] += 1
                    break
                except sqlite3.OperationalError as e:
                    if "locked" not in str(e) and "busy" not in str(e):
                        raise
                    self.stats["busy"] += 1
                    conn.rollback()                 # COMMIT 抢锁失败时事务还开着，不收掉下次 BEGIN 会报错
                    time.sleep(min(0.05 * (2 ** min(self.stats["busy"], 5)), 1.0))

            if stop:
                conn.close()
                return

    def close(self, timeout=5.0):
        self.q.put(None)
        self.t.join(timeout)
```

`BEGIN IMMEDIATE` 这一句不能省：它让"拿写锁"这件事发生在事务开头，而不是在最后 COMMIT 时才去抢。抢不到就在开头失败、重试，不会把整个事务白跑一遍，也不会出现"读到一半才发现写不进去"。

## ✨ 今日一句

> SQLite 的锁不在行上，也不在表上，在整个文件上——所以并发问题从来不是"多加几次重试"，而是"想清楚谁负责写"。
