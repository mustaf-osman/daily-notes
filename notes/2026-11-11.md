# 📅 2026年11月11日 日报

## 💭 技术随想：一个 25 字符的字符串，让正则跑了 15 秒

前几天在日志里看到一条「解析失败」的报文，顺手拿 `^(a+)+$` 这种写法去校验，前 20 个字符毫秒级返回，我以为是好的。加到第 24 个字符，一个请求卡了 2 秒。我第一反应是偶发、是机器忙——**查下去发现：不是偶发，是数学。每多一个字符，这个正则的耗时翻一倍。**

这就是「灾难性回溯」（catastrophic backtracking），安全圈有个名字叫 ReDoS（正则拒绝服务）。它最反直觉的地方在于：**正则引擎没写错，你的输入也完全合法，代码逻辑找不到任何 bug——它只是在"诚实"地、一个不落地枚举所有可能的匹配方式。而那个可能性的数量，随输入长度指数增长。**

今天在本机（Windows 11 / Python 3.11.15）把这条指数曲线的每一个点都量了一遍，数字都是真跑出来的。

### 一、爆炸的样子：每加一个字符，时间翻一倍

正则 `^(a+)+$`，输入是 `"a"*n + "b"`（末尾那个 `b` 让它**必定匹配失败**）。逐点实测：

| n（a 的个数） | 耗时 | 相对上一个 |
|---|---|---|
| 16 | 6.95 ms | — |
| 17 | 13.9 ms | ×2.0 |
| 18 | 29.3 ms | ×2.1 |
| 19 | 51.1 ms | ×1.7 |
| 20 | 101 ms | ×2.0 |
| 21 | 236 ms | ×2.3 |
| 22 | 433 ms | ×1.8 |
| 23 | 906 ms | ×2.1 |
| 24 | 2.06 s | ×2.3 |
| 25 | 4.03 s | ×2.0 |
| 26 | 7.24 s | ×1.8 |
| 27 | **15.2 s** | ×2.1 |

**每一行几乎都是上一行的两倍。** 这就是指数增长的指纹：不是「有点慢」，是「多打一个字，时间翻番」。n=27 已经是 15 秒，n=30 大约两分钟，n=35 就是几个小时——**而 35 个 `a` + 一个 `b`，只是一个 36 字节的字符串，随便一个用户就能造出来。**

同样是 n=28，换成另外两种写法：

```text
n=28  ^(a+)+$       32722 ms      ← 32.7 秒
n=28  ^(?>a+)+$        13.6 µs     ← 原子组
n=28  ^a++$             2.7 µs     ← 占有量词
```

从 32.7 秒到 2.7 微秒，**差了一千多万倍**。而这三个正则，对「是否是若干个 a」这个问题，给出的是**完全相同的答案**。

### 二、为什么是 2 的 n 次方：数一数「分法」

`(a+)+` 这个结构里，内层 `a+` 和外层 `+` 都能「切分」。对 `"aaaa"` 来说，引擎可以把这 4 个 a 分成：

```text
[a][a][a][a]
[a][a][aa]
[a][aa][a]
[aa][a][a]
[a][aaa]
[aaa][a]
[aa][aa]
[aaaa]
```

**8 种分法。** 一个 n 个 a 的串，分成若干段的分法数正好是 $2^{n-1}$（每个字符后面「切/不切」，最后一位不用决定）：

| n | 分法数 $2^{n-1}$ |
|---|---|
| 20 | 524,288 |
| 23 | 8,388,608 |
| 27 | 134,217,728 |

所以 n=27 时，引擎要试着把 1.3 亿种分法挨个走一遍，每种都走到末尾、撞上那个 `b`、发现不行、再退回来。**它不是在算一个正则，它在做一个 1.3 亿项的全排列。** 而这 1.3 亿项里，前 1.3 亿减一项都是白干的——它们全都指向同一个失败的结局。

关键点：**引擎没法「看出来」这些分法等价。** 它只有一个机制——「这条路不行就退回去，试下一条」。嵌套量词 `(x+)+`、`(x*)*`、`(x+)*` 就是把「下一条路」的条数变成了指数级。

### 三、「几乎匹配成功」才是扳机

最坑的一点：**能快速匹配成功的输入，永远是快的；真正放血的是「差一点点就成功」的输入。** 实测（同样是 24 个字符）：

| 输入 | 结果 | 耗时 |
|---|---|---|
| `"a"*24` | 匹配成功 | **0.001 ms** |
| `"a"*24 + "b"` | 匹配失败 | **1602 ms** |

差一个字符，差六个数级。原因很直白：**成功时引擎一找到路就停；失败时它必须把每条路都走到底，才能确认"确实没有"。** 而「末尾多一个非法字符」正是最坏情况——前缀全部合法，把引擎一路骗到最后一位才翻车，于是前面所有分法全部被完整枚举一遍。

这就是为什么这种 bug 在测试里抓不到：单元测试里放几个正常长度的字符串，全部秒过；上线后碰到一个「长度接近上限、内容几乎合法」的脏输入，服务线程就挂在那儿了。**测试测的是「正常」，攻击用的是「几乎正常」。**

### 四、换成真实点的正则，一样炸

`^(a+)+$` 看着像玩具，但真实世界里的写法有同样的形状。经典的一个是 `^(\w+\s?)*$`（「一串单词、空格可选」，很多人拿它校验用户名/标签）。把它喂给 `"a"*n + "!"`：

| n | `^(\w+\s?)*$` | 改写成原子组 `^(?>\w+\s?)*$` |
|---|---|---|
| 16 | 12.8 ms | 0.013 ms |
| 20 | 195 ms | 0.012 ms |
| 24 | 3.43 s | 0.023 ms |
| 26 | **16.6 s** | 0.018 ms |

而同样长度的输入，只要末尾**没有**那个 `!`（也就是能顺利匹配成功），耗时是 **0.006 ms**。又是那句：**病根不在模式本身，在「模式 × 一条几乎合法但最终失败的输入」。**

`\w+` 和 `\w+\w+` 可以有无穷多种切分，外层再来一个 `*`，指数就又回来了。凡是「量词套量词」，形状都一样。

### 五、怎么修：三条路，从最省事到最彻底

**1. 用原子组 / 占有量词，关掉「重试」这个开关（Python 3.11+）。**

- 占有量词：`a+` 后面跟一个 `+` → `a++`。意思是「一次吃到底，**绝不吐回来**」。
- 原子组：`(?>...)`。意思是「进了这个组，就锁死里面的选择，**不再回头**」。

对 `(a+)+` 来说，加了原子组之后：「把连续的 a 一口气全吃掉，吃掉就不还了」，分法从 2 的 n 次方塌缩成 1 条路。**上面表里那个从 32.7 秒到 13.6 微秒，就是这 5 个字符的功劳。**

**2. 把嵌套量词拍平。** 这是最优解：`^(a+)+$` 和 `^a+$` 完全等价，`(\w+\s?)*` 在很多场景下也能拆成 `\w+(\s+\w+)*`（**把可选的 `\s?` 改成必须的、把单层重复改成"分隔符 + 内容"的交替**）。改完既没有嵌套量词，也不需要靠引擎的扩展语法——**跨语言、跨引擎都安全。**

**3. 卡住输入长度。** 爆炸只在长输入上发生，**把闸门设在正则之前**：超过 4096 字节的字段，在 `re.search` 之前就拒掉。这一条挡住了绝大多数 ReDoS——因为攻击载荷必须够长才有威力。

补一句「治标」的选项：第三方 `regex` 模块支持 `regex.search(pattern, text, timeout=0.1)`，超时直接抛异常。但本机没装这个模块（我确认过，`import regex` 报错），而且**超时是兜底、不是修复**——它把「卡死」变成「抛错」，真正的病根（那个嵌套量词）还在。

### 六、顺便说一下：这门语法 Python 3.11 才进标准库

占有量词 `a++`、`a*+`、`a?+` 和原子组 `(?>...)`，在 `re` 模块里是 **Python 3.11 才加进来的**（更早的版本 `re` 不认，只有第三方 `regex` 认）。本机是 3.11.15，实测都能编译。

这条有个现实后果：**同一段正则，在 3.10 的机器上会直接 `re.error` 报「multiple repeat」，在 3.11 上正常运行。** 部署到 RK3588 那种系统 Python 版本偏老的板子上之前，先确认解释器版本——否则你以为的「优化」，到了现场是一场启动即崩溃。

### 七、和手上的东西对上

- **`rp_server` 的命令解析**：`AT+HEAD=<pan>,<tilt>` 这类是纯 ASCII、能用 `split` 搞定，没问题；但任何「用正则校验一整个字段」的地方（设备名、路径、配置行），只要模式里有**组内量词 + 组外量词**，就等于给每个字段开了一个指数爆炸的入口。**UDP 9000 上谁都能发包，这就是一个现成的 ReDoS 面。**
- **日志/协议行的提取**：`^(\w+\s?)*$` 这种「宽松校验」在日志里到处都是。日志行长度不可控（而且经常整段贴进来），正好是「长输入 + 几乎合法」的温床。
- **用户输入就是攻击输入**：App、Web 表单、聊天机器人收到的字符串，长度和内容都不由你控制。**任何直接对着用户输入跑的正则，都要先过长度闸门。**
- **nRF5340 / 嵌入式上的「轻量正则」**：很多嵌入式 RTOS 用精简正则库，回溯策略和 PC 端不同（有的直接不支持嵌套量词，有的用 NFA 无回溯实现，**天生免疫**）。别把 PC 上测出来的耗时当准——**换个引擎，这条曲线的形状可能完全不同。**
- **一条判断经验**：**看到 `(x+)+`、`(x*)*`、`(x+)*`、（更隐蔽的）`(\w+\s?)*` 这类「量词套量词」，第一反应就该是"这里会爆炸"**。绝大多数业务正则根本不需要嵌套量词——写出来的时候顺手拍平，成本为零。

一句话收今天：**正则引擎不是在"匹配"，它是在"枚举所有可能匹配的方式"；而嵌套量词，就是让这个枚举集合从线性变成指数的那一个括号。** 病根不在输入，在你的模式多写的那一层 `+`。

## 🧩 今日代码片段：`redos.py` — 一个检测 + 一个闸门

两个函数：`is_risky()` 认出「量词套量词」的危险形状，`safe_search()` 在正则之前先把长度卡住。下面的输出是真跑出来的。

```python
# -*- coding: utf-8 -*-
"""redos.py —— 给正则加两道防线：识别嵌套量词 + 卡住输入长度"""
import re

# 组内带 * 或 +，组外又跟一个 * 或 + ：(x+)+  (x*)*  (x+)* 这类嵌套量词
# (?!\?>) 是为了不误伤原子组 (?>...) —— 它本身就是安全写法
_NESTED = re.compile(r"\((?!\?>)[^()]*[*+][^()]*\)[*+]")


def is_risky(pattern: str) -> bool:
    """粗检这个正则有没有可能指数回溯（有嵌套量词就报警）。"""
    return bool(_NESTED.search(pattern))


def safe_search(pattern: str, text: str, max_len: int = 4096):
    """带长度闸门的匹配：爆炸只发生在长输入上，短输入永远安全。"""
    if len(text) > max_len:
        raise ValueError("输入太长(%d > %d)，拒绝直接丢给正则" % (len(text), max_len))
    return re.compile(pattern).search(text)


if __name__ == "__main__":
    for p in [r"^(a+)+$", r"^(\w+\s?)*$", r"^(?>a+)+$", r"^\w+$", r"^(\d{4})-(\d{2})$"]:
        print("%-18s risky=%s" % (p, is_risky(p)))
    try:
        safe_search(r"^(a+)+$", "a" * 5000 + "b")
    except ValueError as e:
        print("safe_search ->", e)
```

实测输出（Windows 11 / Python 3.11.15）：

```text
^(a+)+$            risky=True
^(\w+\s?)*$        risky=True
^(?>a+)+$          risky=False
^\w+$              risky=False
^(\d{4})-(\d{2})$  risky=False
safe_search -> 输入太长(5001 > 4096)，拒绝直接丢给正则
```

四个值得说的细节：

- **`is_risky` 是「粗检」，不是「证明」。** 它只看**一层**括号：组内有没有 `*`/`+`、组外有没有再跟一个。它能抓住最常见的 `(x+)+`、`(\w+\s?)*`，但抓不住「两层以上嵌套」，也看不懂「多个组互相配合造成的歧义」。**它的作用是"提醒你去人工看一眼"，不是"扫过就安全"。**
- **`(?!\?>)` 这一小段是故意的。** 原子组 `(?>a+)+` 的形状和危险模式一模一样，但它恰恰是**解药**——所以检测器要把它排除掉，否则会对已经修好的代码误报。**「看起来危险」和「真的危险」，在这里差的就是那两个字符。**
- **闸门放在 `re.compile` 之前。** 顺序很重要：先量长度，再编译匹配。反过来写（先 compile 再查长度）也行，但把最简单、最便宜的那道检查放最前面，是原则——**最坏的输入应该死在最便宜的那行代码上。**
- **`safe_search` 抛异常而不是返回 `None`。** 「输入太长」和「匹配失败」是两件完全不同的事：前者是**输入不合法/可疑**，后者是**输入合法但不符合模式**。把它们混成同一个返回值，调用方就没法区分「用户填错了」和「有人正在攻击我」。

再补一句为什么不禁用正则、也不手写解析器：**正则在「短、结构规整」的输入上依然是最好的工具**，`^\d{4}-\d{2}-\d{2}$` 这种校验又清晰又快。问题只出在嵌套量词上。**修一个 `+` 的成本，远低于换一套解析框架。**

## ✨ 今日一句

> 正则引擎不是「一眼看出该不该匹配」，它是一个不落地的枚举器——嵌套量词就是让它的枚举表从一行涨到一整个宇宙的那对括号。
>
> 而这一切的启动键，往往只是用户输入里那个「几乎合法」的最后一个字符。
