## 💭 技术随想：状态机——把"想干嘛就干嘛"改成"该干嘛才干嘛"

遥控机器人时有个经典隐患：**按键没有上下文**。同一个 B 键，在"电机还没上电"时按，和在"正在大步走"时按，含义完全不同——前者是"开始"，后者可能是"再下发一次指令、把正在走的步态生生打断"。控制逻辑如果没有一套"现在处于什么阶段、此刻允许做什么"的规矩，早晚会在某个组合里翻车：还没初始化就推理、急停解除的瞬间自动起步、迟到的旧指令把新指令覆盖……这类 bug 的共同解药是**有限状态机（FSM）**。

大白话：状态机就是红绿灯，而散落各处的 if/elif 是没装红绿灯的路口。绿灯不会直接跳成红灯——必须经过黄灯；红灯亮了谁也别想走。你先把"有哪些灯、什么条件下能切换"写死成一张规则表，**表里查不到的切换一律拒绝、保持原状态**，路口就永远不会出现"两个方向同时绿灯"。机器人控制里同理：状态集合就那四五个（待机、就绪、行走、急停），按键是事件，迁移表是规矩——剩下的交给默认拒绝。

为什么推荐一张表而不是一堆 if？

- **看得全**：状态和迁移收敛在一处，review 时一眼能看出哪条路忘了堵，而不是在几十个函数里找"这个分支有没有写 else"；
- **默认安全**：表里查不到 = 拒绝，非法操作不用每个分支单独防御；
- **测得到**：测试清单就是迁移表本身，按表逐条打勾，比人肉穷举代码路径靠谱一个量级。

再配上三条工程心得：① **迁移要设守卫（guard）**——表里允许不代表一定放行，比如"就绪→行走"前还要确认所有电机使能正常；② **急停必须全局可达**——STOP 事件要从任何状态都能进安全态，代码上就是一行循环给所有状态铺上；③ **急停解除只回"起点"**——解除后回到待机而不是直接回到行走，逼着你重新走"初始化→推理"全流程，防止刚急停完又带着旧状态跑起来。

## 🧩 今日代码片段：一个 60 行的状态机骨架，演示双足机器人控制链

场景取自真实遥控逻辑：按键 X 初始化 / B 开始推理 / A 复位。注意看哪几次按键被"默认拒绝"了——那不是 bug，是规矩在工作。

```python
# ── 一个 60 行的状态机骨架:把"规矩"写进一张表,而不是散落在 if/elif 里 ──

class FSM:
    """states: 合法状态集合; table: {(当前状态, 事件): (下一状态, 动作)}"""
    def __init__(self, states, initial, table):
        self.states, self.state, self.table = states, initial, table

    def fire(self, event, *args):
        key = (self.state, event)
        if key not in self.table:
            return f"拒绝:{self.state} 状态下无法响应 {event!r}(表里没有这条迁移)", None
        nxt, act = self.table[key]
        old, self.state = self.state, nxt
        return f"{old} --{event}--> {self.state}", act

# ── 遥控按键对应的动作(真实项目里是发 CAN 帧/调电机 API)──
def do_init(): print("      · 执行:电机上电,关节回零,等待就绪")
def do_run():  print("      · 执行:下发步态指令,开始行走")
def do_stop(): print("      · 执行:急停刹车,切断使能!")

# ── 迁移表:双足机器人控制链(键 X 初始化 / B 推理 / A 复位)──
S = ["IDLE", "READY", "RUNNING", "SAFE"]      # 状态全集:待机/就绪/行走/急停
T = {
    ("IDLE",   "X"): ("READY",   do_init),    # 只有待机态允许初始化
    ("READY",  "B"): ("RUNNING", do_run),     # 只有就绪后才能开走
    ("RUNNING","A"): ("IDLE",    None),       # 行走中按 A:主动停下回待机
    ("READY",  "A"): ("IDLE",    None),
    ("IDLE",   "A"): ("IDLE",    None),
}
for st in S:                                  # 急停:从任何状态都能进 SAFE
    T[(st, "STOP")] = ("SAFE", do_stop)
T[("SAFE", "A")] = ("IDLE", None)             # 急停后只能按 A 解除,且回到
                                              # IDLE → 必须重新初始化才能再跑

fsm = FSM(S, "IDLE", T)
for ev in ["X", "B", "A", "X", "B", "B", "STOP", "B", "A", "B"]:
    line, act = fsm.fire(ev)
    print(f"按键 {ev:>4} → {line}")
    if act:
        act()
```

**实际运行输出（本机 Python 3.11，逐条真实打印）：**

```
按键    X → IDLE --X--> READY
      · 执行:电机上电,关节回零,等待就绪
按键    B → READY --B--> RUNNING
      · 执行:下发步态指令,开始行走
按键    A → RUNNING --A--> IDLE
按键    X → IDLE --X--> READY
      · 执行:电机上电,关节回零,等待就绪
按键    B → READY --B--> RUNNING
      · 执行:下发步态指令,开始行走
按键    B → 拒绝:RUNNING 状态下无法响应 'B'(表里没有这条迁移)
按键 STOP → RUNNING --STOP--> SAFE
      · 执行:急停刹车,切断使能!
按键    B → 拒绝:SAFE 状态下无法响应 'B'(表里没有这条迁移)
按键    A → SAFE --A--> IDLE
按键    B → 拒绝:IDLE 状态下无法响应 'B'(表里没有这条迁移)
```

**说明：**

- 第 8 行：机器人已经在 RUNNING 里大步走，此时再按 B 被拒绝——**防止重复下发指令打断正在执行的步态**。不用写一行防御代码，表里没有就是没有。
- 第 9~10 行：STOP 从行走态直接进 SAFE——急停之所以"从哪儿都能按"，是因为前面那个 `for st in S` 循环把 `(任何状态, STOP)` 都铺进了表里。**写一行循环，而不是在每个分支里都记得调急停**，这就是迁移表的红利。
- 第 11 行：急停锁定（SAFE）后按 B 被拒绝——此时电机已断电，任何推理指令都不该被执行。这就是"默认拒绝 = 默认安全"。
- 第 12~13 行：SAFE 里按 A 解除急停，但只回到 IDLE 而不是直接回 RUNNING——想再走，必须重新走 X（初始化）→ B（推理）全流程。**急停复位后禁止带旧状态直接续跑**，这是写控制逻辑的人最容易漏的一环。
- 代码里动作（`do_init/do_run/do_stop`）是"进入新状态后执行的函数"（entry action），和迁移表分离——状态机框架只负责"查表 + 换状态"，业务动作全部挂在表上，想换动作只改表不改框架。
- 真实项目补强：① 迁移前加守卫，如 `READY--B` 还须检查所有电机使能、IMU 姿态正常；② 动作执行失败要能回滚或主动进 SAFE，别让状态换了事没办成；③ 多线程环境别裸奔共享状态——放进单线程事件循环，或用锁包住 `fire`；④ 状态多了可以上现成库（Python 的 `transitions`），但核心永远是那张表：**状态全集 × 事件 → 迁移表，写清楚，剩下的交给拒绝**。
