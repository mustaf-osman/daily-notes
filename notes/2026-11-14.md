# 📅 2026年11月14日 日报

## 💭 技术随想：时间有两副面孔，混着用就是 bug

我脑子里一直只有「一个时间」——`time()` 给你的那个浮点数，越大越新，相减就是时长。今天写一个「每天几点跑」的定时器，顺手把这句话拆开，发现它其实是**两个完全不同的量，只是恰好共用一个类型**：

- 一个是**流逝的时间**（duration）：从 A 到 B 过去了多少，永远向前、均匀、不会被谁改。
- 一个是**日历上的时间**（wall clock）：现在是几号几点，给人看的，会被 NTP 拨、被夏令时拨、被时区改写。

**代码里的时间 bug，绝大多数不是「算错了」，而是「拿其中的一个，去当了另一个。」** 今天在本机（Windows 11 / Python 3.11.15）把这条链上的东西挨个量了一遍，数字都是真跑出来的。

### 一、三个时钟，三种粒度

同一台机器上，Python 给了三个「时钟」，而它们的精度差了一个数量级还不止。连续采几十万次，统计每次读数的最小跳变：

| 时钟 | 实测最小步进 | 说明 |
|---|---|---|
| `time.time()` | **≈ 1 ms** | 墙上时间，会被系统改 |
| `time.monotonic()` | **≈ 15.6 ms** | 单调，但本机粒度最粗 |
| `time.perf_counter()` | **≈ 1 µs（直到亚微秒）** | 单调 + 最高精度 |

`time.monotonic()` 在这台机器上**只有两种步进值：0.015 和 0.016 秒**——也就是经典的 15.6 ms 时钟节拍。`perf_counter` 那边，20 万次采样里 20 万次都落在 1 微秒的格子（200 多种细粒度），差了两个数量级。

调用开销也顺手量了（每 20 万次的平均）：

```text
time.time()             86 ns/call
time.monotonic()        70 ns/call
time.perf_counter()    143 ns/call
datetime.now()         345 ns/call
datetime.now(tz)       553 ns/call   ← 带时区的贵了近一倍
```

### 二、`monotonic` 其实最「钝」——这很反直觉

平时都说「计时要 monotonic」，但本机实测，用它量一段 0.3 秒的忙循环：

```text
忙循环 ~0.3s：
  perf_counter = 0.300023 s
  time.time    = 0.300052 s
  monotonic    = 0.297000 s   ← 少了 3 ms
```

`monotonic` 把结果四舍五入到了 15.6 ms 的格子上，**离真值差了 3 毫秒**——比它想避免的误差还大。所以在 Windows 上：

- 量**毫秒级、亚毫秒级**的代码 → 用 `perf_counter`；
- 量**秒级、分钟级**的时长（重试间隔、超时）→ `monotonic` 够用，胜在「绝不倒退」；
- `time.time()` → **只用来打时间戳、写日志、给人看**，绝不用于计时。

一句话：**单调性管的是「不会倒退」，精度管的是「量得准」，这是两件事，别用一个词糊过去。**

### 三、日历时间的两个大坑，全在今天实测撞上

下面每个结论都是真跑出来的（`zoneinfo` + 北美东部时区，2026 年春季调时是 3 月 8 日）。

**坑一：`+ timedelta(hours=24)` 根本不是「24 小时后」。**

```text
d = 2026-03-07 12:00 -05:00        （调时前一天）
d + timedelta(hours=24) = 2026-03-08 12:00 -04:00
d + timedelta(days=1)   = 2026-03-08 12:00 -04:00
两者相等？ True
```

`hours=24` 和 `days=1` 给出了**一模一样的结果**。因为 aware datetime 上的 `+ timedelta` 是**墙上时间算术**：它先按钟面加，再加回时区，于是「昨天中午 + 24 小时」变成了「今天中午」——而今天中午到昨天中午，真实只过去了 **23 小时**（少了一小时，春天调时）。想要「真实 24 小时后」，必须绕一圈 UTC：

```text
(d → UTC, +24h, → 回本地) = 2026-03-08 13:00 -04:00   ← 这才是对的
```

**坑二：同一个时区的两个 aware datetime 相减，给的是墙钟差，不是真实时长。**

```text
(d + 1天 - d).total_seconds()                          = 86400 s
(d+1天 换成UTC - d 换成UTC).total_seconds()            = 82800 s   ← 真值 23h
```

第一个数是**错的**（差了一小时）。CPython 有个优化：两个 datetime 的 `tzinfo` 是同一个对象时，相减会**跳过偏移量换算**，直接拿钟面数字减。它省了一次转换，代价是跨夏令时的时候偷偷给你一个错答案。**要真实时长，先 `.astimezone(UTC)` 再相减。**

### 四、回拨那一小时：两个不同的瞬间，`==` 说它们相等

秋季回拨时，01:30 会在一夜里出现两次。把「第一次」和「第二次」两个瞬间拿来比：

```text
x0 = 2026-11-01 01:30 -04:00    （回拨前）
x1 = 2026-11-01 01:30 -05:00    （回拨后）
x0 == x1          →  True        ← 相等？！
x0.timestamp()    →  1793511000
x1.timestamp()    →  1793514600  ← 差了 3600 秒
```

**两个真实时刻差了整整一小时，`==` 却说是同一个。** 还是那个优化——同 `tzinfo` 时不看偏移量、不看 `fold`，直接比钟面。修法只有一条：**判「是不是同一瞬间」永远用 `.timestamp()`（或都换成 UTC），别用 `==`。**

### 五、naive 的 `.timestamp()`，偷偷用了本机时区

一个「没带时区」的 datetime，你叫它 `.timestamp()`，它不会报错，也**不会告诉你在猜**——它按**运行机器的本地时区**去猜。本机在中国：

```text
naive 2026-01-01 00:00 .timestamp()      = 1767196800
同一时刻按 UTC 算                        = 1767225600
差 (小时)                                = -8.0
```

八小时。同一份代码，搬到一台设成 UTC 的服务器上，这个数就变了；搬到欧美，再变。**所以凡是存进数据库、发给别人、写进报文的时间，一律带时区；`datetime.utcnow()`（无时区、且已标记废弃）就是这类事故的老巢。**

### 六、对着手上的东西看

- **我的定时日报任务。** 「每天几点跑」是日历问题（要带时区、要处理调时）；「上次跑到现在多久了」是时长问题（要 monotonic）。**这两件事不能用同一个时钟算**——用 `time.time()` 存上次运行时刻，一次 NTP 校时就可能让它提前或推迟一整轮。
- **`rp_server` 的控制循环周期。** 每拍「睡 20 ms」用 `time.time()` 卡 deadline，一次校时拨快 1 秒，就会**连跑 50 拍补进度**，电机那边就是一下抽动。周期抖动、超时、重试间隔，全部用 `monotonic`。
- **日志时间戳 vs 耗时。** 日志里打的那一列是「日历时间」（要能跟别处的日志对上，所以必须带时区、最好是 UTC）；而 `cost=12ms` 那列是「流逝时间」（必须 `perf_counter`）。**把 `cost` 用墙上时钟算出来，日志一排全是坑。**
- **`AT+HEAD` 报文里的时间字段。** App 和板子的时钟不可能永远一致，两块表对出来的差是「时区 + 漂移」，别拿绝对时间来判先后——**要先比时间戳来源，再谈越界。**
- **协议超时。** UDP 9000 上重传/超时用 `time.time()`，遇到校时就是「提前超时」或「永远不超时」。**超时是时长，不是日期。**
- **nRF5340 / Zephyr。** 那边的「滴答」是 `k_uptime_get()`（单调，从开机算），本来就没有墙上时间；想要日期得另配 RTC。**别指望嵌入式给你一个「现在几点」——它给的是「开机以来过了多久」，这恰恰是量时长最该用的那个时钟。**
- **`git commit` 的时间。** 它是「日历时间」，而且取决于**你机器的时钟**——这就是为什么同一个仓库里会冒出「未来时间」的提交。想让它可信，得靠签名和外部时间源，而不是相信本地那行 `Date:`。

一句话收今天：**"流逝"和"日历"是两个量。前者只会向前、均匀、不被打扰；后者随时会被 NTP、夏令时、时区改写。把后者的差值当成了前者，代码会给出一个看起来完全合理、却错了一小时的答案——而且一年只在两天里错。**

## 🧩 今日代码片段：`clock.py` — 把两个时间分开用

四个小工具：计时器（用 `perf_counter`）、加「真实时长」（绕过墙上算术）、算「真实间隔」（先换 UTC）、判「同一瞬间」（靠 `timestamp()`）。下面的输出是真跑出来的。

```python
# -*- coding: utf-8 -*-
"""clock.py —— 把「流逝的时间」和「日历上的时间」分清楚"""
import time
from datetime import datetime as dt, timedelta, timezone

UTC = timezone.utc


class Stopwatch:
    """量一段代码跑了多久。用 perf_counter：单调、且在本机粒度到微秒。"""

    def __init__(self):
        self._t0 = time.perf_counter()

    def elapsed(self):
        return time.perf_counter() - self._t0


def add_absolute(d, **kw):
    """在 aware datetime 上加「真实流逝的时间」（小时/分钟/秒）。

    直接 d + timedelta 是「墙上时间」算术：跨夏令时会少走/多走一小时。
    """
    return (d.astimezone(UTC) + timedelta(**kw)).astimezone(d.tzinfo)


def real_elapsed(a, b):
    """两个 aware datetime 之间真实流逝了多少秒（先换到 UTC 再相减）。"""
    return (a.astimezone(UTC) - b.astimezone(UTC)).total_seconds()


def same_instant(a, b):
    """两个瞬间是不是同一时刻。别用 ==，夏令时回拨那小时会骗你。"""
    return a.timestamp() == b.timestamp()
```

实测输出（Windows 11 / Python 3.11.15，`zoneinfo` 北美东部）：

```text
Stopwatch(perf_counter)    = 0.245792 s
d + timedelta(hours=24)    = 2026-03-08T12:00:00-04:00   ← 墙上算术，错了
add_absolute(d, hours=24)  = 2026-03-08T13:00:00-04:00   ← 真实 24h
(a - d) 墙钟差             = 86400.0                     ← 错的
real_elapsed               = 82800.0                     ← 真值 23h
x0 == x1        : True     same_instant: False           ← == 骗人，timestamp 不骗
```

四个值得说的细节：

- **`Stopwatch` 默认用 `perf_counter` 而不是 `monotonic`。** 因为在 Windows 上 `monotonic` 只有 15.6 ms 粒度，量「这段代码花了多久」会直接丢掉几毫秒；而 `perf_counter` 单调性和精度兼备。**只有当你不需要亚秒精度、且想省那 70 纳秒时，才退回 `monotonic`。**
- **`add_absolute` 必须绕道 UTC。** 不能写成 `d + timedelta(hours=24)`——那是墙上算术。绕一圈虽然多两行，但它让「加的是真实时长」这件事在代码里看得见，而不是藏在一行「看起来没问题」的加法里。
- **`real_elapsed` 显式 `.astimezone(UTC)`。** 这不是多余——它专门用来绕开 CPython「同 tzinfo 就跳过换算」的优化。少了这一步，跨夏令时的间隔就会少一小时。
- **`same_instant` 不返回 `a == b`。** 因为那个 `==` 在回拨那一小时会撒谎。用 `.timestamp()` 比对，是把「你问的是不是同一瞬间」这个问题问对了。**函数名本身就该是文档：`same_instant` 和 `same_wall_reading` 是两件事。**

再补一句为什么不禁用 aware datetime、全用 UTC：**UTC 适合存、适合传，但不适合显示。** 给用户看「明天早上 8 点」，必须是本地钟面；存进数据库，必须是 UTC。**真正的规则不是「统一用某个」，而是「在边界上换、在显示时换，中间的算术一律选对那副面孔」。**

## ✨ 今日一句

> 时间有两个：一个只向前、均匀、谁也改不动；一个会被拨、会调时、会在一夜里重复一小时。
>
> 拿前者去记日期，你的表会错；拿后者去算时长，你的表会错——而且一年只在两天里错，错得让人以为是玄学。
