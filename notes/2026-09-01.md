## 💭 技术随想：大小端——同一个数字的两种"睡姿"

写上层应用的人很少想字节序，但一碰串口、CAN、I2C、Socket 这些"字节流协议"，大小端（endianness）就会立刻跳出来咬人：明明上位机发的是 `0x1234`，下位机解出来却是 `0x3412`，电机转速直接翻 256 倍。这类 bug 的共同根源是——**数字在内存里是一串字节，而"高位在前还是低位在前"并没有唯一答案**。

以 32 位整数 `0x12345678` 为例，它在内存里的 4 个字节有两种排法：**大端（big-endian）**按人类书写习惯，高位字节 `0x12` 放在低地址；**小端（little-endian）**反过来，低位字节 `0x78` 放在低地址。x86/ARM（大多数模式）是小端，网络协议和很多工业/汽车总线约定是大端——所以跨设备通信时，"协议文档里写的是什么端"必须成为第一确认项，而不是默认"跟我机器一样"。

Python 的 `struct` 模块是把字节流翻译成数字的标准工具，核心就一条规则：**格式串的第一个字符决定字节序**——`>` 大端、`<` 小端、`@` 用本机默认（最坑，别用）。`>I` 和 `<I` 解同一个字节串会得到完全不同的数，这就是"解出来是 3412"的完整解释。

再往深一层，`struct` 的 `pack/unpack` 只是"翻译"，真正的协议解析还要自己搭帧结构：**帧头（同步字）+ 长度 + 载荷 + 校验**。校验和常用 CRC 或简单累加和，它的意义是让接收方区分"传错了"和"没这回事"——串口在电磁干扰下丢字节、错字节是常态，没有校验的协议在机器人工地上就是裸奔。

**心法：** 字节序没有对错，只有"约定"。凡是跨设备、跨语言的字节流，先在协议文档里写死"大端/小端 + 帧格式 + 校验算法"三件事，再用 `struct` 一行行对齐。协议定清楚，剩下都是翻译活。

## 🧩 今日代码片段：struct 解帧实战——带校验和的迷你串口协议

```python
import struct

# 一个自制的迷你协议帧：
# | 0xAA 0x55 (帧头) | uint8 长度(不含帧头与长度本身) | uint16 转速(小端) | int16 温度(小端) | uint8 累加校验 |
def make_frame(rpm: int, temp: int) -> bytes:
    payload = struct.pack("<Hh", rpm, temp)          # 小端打包：转速(无符号) + 温度(有符号)
    body = bytes([len(payload)]) + payload
    checksum = sum(body) & 0xFF                       # 简单累加和，取低 8 位
    return b"\xAA\x55" + body + bytes([checksum])

def parse_frame(buf: bytes):
    if len(buf) < 8 or buf[:2] != b"\xAA\x55":
        raise ValueError("帧头错误或长度不足")
    length, rpm, temp, checksum = struct.unpack("<BHhB", buf[2:8])
    if sum(buf[2:7]) & 0xFF != checksum:              # 校验不过：丢帧或传输出错
        raise ValueError(f"校验和错误: 期望 {sum(buf[2:7]) & 0xFF}, 收到 {checksum}")
    return rpm, temp

frame = make_frame(1234, -20)
print("原始字节 :", frame.hex(" "))
print("解出      :", parse_frame(frame))

# 字节序实验：同一串字节，大端/小端解出完全不同的数
raw = bytes.fromhex("d204")                           # 0x04d2 = 1234 的小端表示
print("小端 0xd204 ->", struct.unpack("<H", raw)[0], "| 大端 ->", struct.unpack(">H", raw)[0])
print("大端打包    ->", struct.pack(">H", 1234).hex(" "))

# 顺手：hex() 把二进制帧转成日志里可读的十六进制串
bad = bytearray(frame); bad[5] ^= 0xFF                # 篡改一个字节，模拟传输干扰
try:
    parse_frame(bytes(bad))
except ValueError as e:
    print("篡改后被拦截:", e)
```

**实际运行输出（本机 Python 3.x）：**

```
原始字节 : aa 55 04 d2 04 ec ff c5
解出      : (1234, -20)
小端 0xd204 -> 1234 | 大端 -> 53764
大端打包    -> 04 d2
篡改后被拦截: 校验和错误: 期望 236, 收到 197
```

**说明：**

- 帧结构一目了然：`aa 55` 帧头 → `04` 长度（载荷 4 字节）→ `d2 04`（1234 小端）→ `ec ff`（-20 小端）→ `c5` 校验和。接收端靠帧头同步、靠长度切分、靠校验和兜底，三层防线缺一不可。注意校验范围是"长度+载荷"5 个字节（`buf[2:7]`），别把校验字节自己也加进去——这是初学者最容易写错的切片。
- 格式串对照：`<H` 小端无符号 2 字节（0~65535），`<h` 小端有符号 2 字节（-32768~32767），`B` 单字节。温度用 `h` 而不是 `H`——零下温度必须能表示负数，否则 -20 会解成 65516。
- `0xd204` 这个字节串，小端解出来是 1234，大端解出来是 53764——**字节没变，结果差 43 倍**，这就是"转速翻 256 倍"类事故的微观现场。
- 篡改一个字节后校验和立刻对不上，接收方主动拒收而不是拿错误数据去驱动电机——**校验和不是为了修数据，是为了让你知道数据不能信**。
- 真实项目里累加和可以换成 CRC16/CRC32（`binascii.crc32` 一行搞定），抗干扰能力更强；帧头建议用 2~4 字节且载荷里不可能出现的序列，降低误同步概率。
