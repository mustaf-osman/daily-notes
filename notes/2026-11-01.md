# 📅 2026年11月01日 日报

## 💭 技术随想：一行 `+=`，26 毫秒和 174 秒的距离

起因是两件小事撞在一起。

第一件：导出一天的 POS 流水，用循环拼 CSV 行，几万行，几十毫秒，没问题。
第二件：给串口日志加个缓冲，每来一行就 `self.buf += line`，跑了半分钟还没结束。

两处都是一行 `+=`，写得一模一样。今天把这件事拆开量了一遍，结论不是"`+=` 很慢"，而是：**`+=` 快不快，取决于还有没有第二个人拿着这个字符串。** 代码里看不出差别，运行时差 6518 倍。

环境：Windows 11 / Python 3.11.15 / CPython。绝对值换机器会变，比例关系是解释器的结构决定的。

### 一、先看成绩单

20 万个 `"ab"` 拼成一个 40 万字符的串：

| 写法 | 耗时 | 相对 |
|---|---|---|
| `"".join(parts)` | **0.618 ms** | 1.0x |
| `list.append` + `join` | 7.271 ms | 11.8x |
| `io.StringIO().write` | 8.659 ms | 14.0x |
| `s = s + p`（局部变量） | 12.098 ms | 19.6x |
| `s += p`（局部变量） | 12.802 ms | 20.7x |

先看两个容易误判的地方：

- **`+=` 和 `s = s + p` 一样快。** "加号慢、`+=` 快"这个说法在这里不成立——编译器把这两种形状认成同一件事。
- **`+=` 只比 `join` 慢 20 倍，不是慢几千倍。** 如果真的是教科书上那个 O(n²)，20 万次拼接要几分钟。它只用了 12 毫秒，说明它**根本没有在每次拼接时复制整个串**。

那 20 倍的差距是什么？是循环本身：20 万次迭代、20 万次字节码分派。`join` 把这些活全交给了 C 层的一个循环，所以它快在"不用回解释器"。

### 二、真正决定价钱的是"有没有第二个人拿着它"

下面这张表是我今天最想让人看的东西。同一行 `+=`，只改"这个串还有没有别人引用"：

| N（拼接次数） | `join` | `+=` 局部 | `+=` 但每步存副本 | `+=` 挂在对象属性上 | 副本/局部 |
|---|---|---|---|---|---|
| 50,000 | 0.31 ms | 3.37 ms | **2726.49 ms** | 246.56 ms | 809x |
| 100,000 | 0.86 ms | 10.41 ms | **17260.58 ms** | 710.58 ms | 1659x |
| 200,000 | 1.49 ms | 26.71 ms | **174070.17 ms** | 6111.61 ms | 6518x |

读这张表要注意三件事：

1. **局部变量的 `+=` 近乎线性**：数据翻倍，时间从 3.37 → 10.41 → 26.71 ms，涨 3.1 倍和 2.6 倍，不是 4 倍。
2. **一旦每步都存副本，立刻变二次**：2726 → 17260 → 174070，涨 6.3 倍和 10.1 倍。数据翻一倍，时间涨六到十倍。
3. **挂在对象属性上的 `+=` 也在二次那一侧**：6111 ms，比局部慢 229 倍。这正是我那个串口日志缓冲的写法——`self.buf += line`。

机制说出来很短：**CPython 的字符串是不可变对象。**`s += p` 正常情况下要新分配一块内存、把老的拷过去、再把新的拷进去——每一步的代价正比于"当前已经有多长"，所以总代价是所有前缀长度之和，也就是 O(n²)。

但 CPython 有一个例外：如果左边那个串**只有一个人拿着**（引用计数为 1），它可以直接在你脚底下把这块内存扩容、把新内容追加到末尾，不用复制。这时候 `+=` 就变成了均摊 O(n)。

**"每步存副本"破坏的正是这个条件。** `keep.append(s)` 之后，每个中间串都被列表拿着，引用计数变成 2，扩容这条路走不通，只能老老实实每一步复制一遍。200k 的那次运行，第一轮直接 `MemoryError`——因为它同时在内存里留了 20 万个长度从 2 到 40 万不等的串，加起来几十 GB。

挂属性的道理一样：`self.buf += line` 展开是"读属性 → 拼接 → 写回属性"，在拼接那一刻，属性本身还指着老串，引用计数不是 1。

一句话记住：**`+=` 的复杂度不是语法决定的，是别名决定的。** 而你写 `self.xxx +=` 的时候，它天生就有别名。

### 三、字符串有多重：CPython 的存储会变宽

拼接近似线性，还有第二个容易忽略的成本：内存。

CPython 的 `str` 不是"一个字节一个字符"。它按这条串里**最大的那个码点**选单位宽度：全是 ASCII 用 1 字节/字符，有一个字符在 BMP 之外就用 4 字节/字符。

| 字符串 | 字符数 | `sys.getsizeof` | 每字符 |
|---|---|---|---|
| 空串 | 0 | 51 | — |
| `"hello"` | 5 | 54 | 0.6 |
| `"中文"` | 2 | 78 | 13.5 |
| `"😀"` | 1 | 80 | 29.0 |
| `"a" * 10` | 10 | 59 | 0.8 |
| `"中" * 10` | 10 | 94 | 4.3 |
| 纯 ASCII 1000 字符 | 1000 | **1049** | 1.00 |
| 中英混排 1000 字符 | 1000 | **2074** | 2.02 |

最后两行是关键。同样 1000 个字符：

```text
"a" * 1000            1049 字节
"a" * 999 + "中"      2074 字节   (+1025，翻倍)
"a" * 999 + "😀"      4076 字节   (+3027，四倍)
```

**末尾加一个汉字，整条串的内存翻倍；加一个 emoji，翻四倍。** 不是那一个字符占了两三个字节，是**整条串的存储单位被抬高了**——前 999 个 ASCII 字符也跟着从 1 字节变成 2 字节或 4 字节。

这条对机器人系统很实在：日志缓冲、状态 JSON、串口回包，只要中间混进一个中文设备名，整个缓冲的内存就翻倍。不是"中文占三个字节"，是"有中文的串，每个字符都按宽字符存"。

（顺带解释清楚另一个常见困惑：UTF-8 里中文是 3 字节，但 CPython 内存里不是按 UTF-8 存的。磁盘上是 UTF-8，内存里是定宽 UCS。这是两套账，别混着算。）

### 四、`len`、字节数、显示宽度，是三件不同的事

这三件事混在一起，是所有中文排版 bug 的源头。

| 样本 | `len()` | UTF-8 字节 | UTF-16 单元 | 显示宽度 |
|---|---|---|---|---|
| `"hello"` | 5 | 5 | 5 | 5 |
| `"中文"` | 2 | 6 | 2 | **4** |
| `"重新"` | 2 | 6 | 2 | 4 |
| `"，。"` | 2 | 6 | 2 | 4 |
| `"😀"` | 1 | **4** | 2 | 2 |
| `"👨‍👩‍👧"` | **5** | **18** | 8 | 8 |
| `"e" + 组合符` | 2 | 3 | 2 | 2 |
| `"é"`（NFC 合成） | 1 | 2 | 1 | 1 |
| `"Tiếng Việt"` | 10 | 14 | 10 | 10 |

几个值得单独拎出来的：

- **`"中文"` 的 `len()` 是 2，不是 6。** Python 3 的 `len` 数的是码点，不是字节。想数字节得 `len(s.encode())`。
- **`"👨‍👩‍👧"` 的 `len()` 是 5。** 一家三口在屏幕上是一个图形，在内存里是 5 个码点：三个 emoji + 两个零宽连接符（ZWJ）。`len` 数的是码点，不是"人看到的字符"。
- **`"e" + "\u0301"` 和 `"\u00e9"` 不相等。** 前者是两个码点（e + 组合重音），后者是一个。`==` 比较的是码点序列，眼睛看着一样不算。要比较得先 `unicodedata.normalize("NFC", s)`。
- **`"ß".upper()` 是 `"SS"`。** 长度从 1 变成 2。任何"转大写不会改变长度"的假设都是错的，越南语、德语、土耳其语都能把它打穿。

### 五、按字节截断：中文断在半路

这是最容易在生产里出事的一处。`"生鲜超市流水：苹果 3.5 元"` 一共 24 个字符、52 个字节。按字节上限砍：

```text
砍到 12 → '生鲜超市'                      （正好落在边界）
砍到 13 → UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe6 in position 12
砍到 20 → UnicodeDecodeError: can't decode bytes in position 18-19
砍到 21 → '生鲜超市流水：'
```

**砍在中间不会给你半个字，它会直接抛异常。** 抛异常还算好的——如果这段代码在某处被 `errors="ignore"` 兜住，你会静默丢掉一个字符；如果它写进了文件，就是一个坏字节序列，后面所有工具都读不了。

正确做法只有一条：**先编码、砍字节、往前退到合法边界、再解码。** 最多退 3 次（UTF-8 一个字符最多 4 字节），代价可以忽略。实测：

```text
安全砍到 12 → '生鲜超市'（12 字节）
安全砍到 13 → '生鲜超市'（12 字节）   ← 退了一个字节
安全砍到 20 → '生鲜超市流水'（18 字节）
安全砍到 21 → '生鲜超市流水：'（21 字节）
```

注意第 13 字节那行：它没有给你 13 字节，给的是 12 字节。**"不超过 N 字节"和"正好 N 字节"是两件事**，协议里如果写了定长字段，得自己补空格。

### 六、大小写折叠：一个中文字，让 `lower()` 慢 20 倍

日志解析里太常见了：每行 `line.lower()` 然后找关键字。测了一下 84 KB 的文本：

| 文本 | 字节 | `.lower()` 一次 |
|---|---|---|
| 纯 ASCII，已全小写 | 78,000 | **18.69 µs** |
| 纯 ASCII，全大写 | 78,000 | **19.17 µs** |
| 中英混排（有大小写要改） | 84,000 | **461.81 µs** |
| 纯中文（根本没有大小写这回事） | 90,000 | **356.20 µs** |
| 中英混排但已全小写 | — | **390.27 µs** |

看最后两行：**纯中文的串，一个字母都没有，`.lower()` 还是要 356 微秒。** 所以慢的不是"改字符"，是这条串的存储类别——只要混进一个非 ASCII 字符，整条串就从 UCS-1 变成 UCS-2，折叠时每个字符都要查一次 Unicode 大小写表，而不是走那条针对 ASCII 的快路径。

前两行更直接：中英混排那份只比纯 ASCII 多 7.7% 的字节，时间多了 **24.7 倍**。这不是"多一点数据多花一点时间"，是换了一条执行路径。

于是最贵的写法是这样：

```python
for line in lines:                 # 2000 行
    if "temp" in line.lower():     # 每行都折叠一次
        ...
```

如果这些行里有中文，折叠成本是纯 ASCII 的 20 倍，而且**每行折一遍、折完就扔**。

两件事说清楚：

1. **折叠本身不是必须的。** 如果关键字是固定的、大小写已知，直接 `in` 就行，不要为了"万一"每行折一遍。
2. **如果非要折叠，折一次，别折 N 次。** 对整段文本折一次再搜，比逐行折快 1.5 倍（实测 383 µs vs 559 µs）；如果搜索要重复很多次，折一次再多次搜，差距更大。

### 七、查找：命中位置决定 500 倍

这一项我第一轮测错了，量出来"0.000 ms"，看着像 `in` 神速。复查才发现：那个词在第一行第 15 个字符就命中了，**它提前返回了**，根本没扫完。

重测，90000 字节的日志，找 `"温度"`：

| 命中位置 | `"温度" in text` | `text.find()` | 预编译 `re.search` |
|---|---|---|---|
| 第 1 行 | **0.06 µs** | 0.16 µs | 0.26 µs |
| 最后一行 | 29.44 µs | 27.53 µs | 23.76 µs |
| 完全不存在 | 26.19 µs | 28.70 µs | **23.86 µs** |

三件事：

- **最好和最坏差 490 倍。** 报"我的查找很快"之前，先确认测的是命中还是未命中。最坏情况永远是"不存在"——它必须扫完全部字节。
- **正则不比 `in` 慢。** 预编译的 `re.search` 在未命中时 23.86 µs，`in` 是 26.19 µs。这 9% 的差距可能一半是噪声，没有重跑验证，但至少说明一件事：**"正则一定慢"是个偏见**——贵的是回溯型的复杂模式，纯字面量搜索的开销和 `in` 在同一档。
- **中文每个字 3 字节，扫的是字节不是字符。** 90000 字节里找 6 字节的 `"温度"`，实际比对的是 6 字节窗口，不是 2 个字符。

### 八、格式化：语法不是成本，转换才是

50 万次，每次都生成同样内容的一行日志：

| 写法 | 每次 | 相对 |
|---|---|---|
| `f"[{ts:.3f}] {name}={val:.2f}"` | 765.3 ns | 1.00x |
| `"[%.3f] %s=%.2f" % (...)` | **650.6 ns** | 0.85x |
| `"[{:.3f}] {}={:.2f}".format(...)` | 682.2 ns | 0.89x |
| 先转好字符串，再 `+` 拼 | **249.8 ns** | 0.33x |
| 先转好字符串，再 `join` | 455.3 ns | 0.59x |
| 先转好字符串，`+=` 逐步拼 | 254.8 ns | 0.33x |

这张表要反着读：

- **三种模板语法差不到 20%。** f-string 在这儿甚至比 `%` 慢 18%——所以"f-string 永远最快"是个不准确的流行说法，至少在 3.11 的浮点格式化上不成立。为这点差异改一整个代码库，不值得。
- **真正贵的是"转换"。** 前三行每次都在做 `float → string` 加补齐；后三行把这一步提到循环外，立刻快 3 倍。**热循环里能把转换提出去就提出去，这比挑语法重要得多。**
- **`join` 在只有 6 个片段时反而慢。** 它要先建列表、再算总长、再拷一遍；片段这么少，`+` 直接拼更快。`join` 的优势在"片段多且已知总数"的时候才显出来，比如第一节那个 20 万。

### 九、CSV 与 BOM：为什么导出的中文在 Excel 里是乱码

| 编码 | 前 12 字节 | 总长 |
|---|---|---|
| `utf-8` | `e6 97 a5 e6 9c 9f 2c e5 95 86 e5 93` | 78 |
| `utf-8-sig` | **`ef bb bf** e6 97 a5 e6 9c 9f 2c e5 95` | 81 |
| `gbk` | `c8 d5 c6 da 2c c9 cc c6 b7 2c b5 a5` | 66 |

`utf-8-sig` 多的那 3 个字节 `EF BB BF` 是 BOM（字节序标记）。Excel 打开 CSV 时不会猜编码，它按系统区域设置来——简体中文 Windows 就用 GBK 去解 UTF-8 的字节，中文全乱。**带上 BOM，Excel 才认得出这是 UTF-8。**

三条实用结论：

1. **给 Excel 的就用 `utf-8-sig`**，给程序读的用 `utf-8`。BOM 会让某些解析器把第一个字段名读成 `"\ufeff日期"`，所以别两处混用。
2. **别用 GBK 存新数据**。它是"在 Windows 上看着正常"的陷阱，一到 Mac/Linux/手机就废，而且生僻字直接编码不了。
3. **读别人的 CSV 要容错**：`utf-8-sig` 能同时吃带 BOM 和不带 BOM 的 UTF-8，这是它比 `utf-8` 更适合当"读入默认值"的原因。

### 十、能抄走的部分

1. **循环里拼字符串，用 `"".join(parts)`，别用 `+=`。** 20 万次上是 20 倍。片段少于 5 个时无所谓，`+` 甚至更快，但别养成习惯。
2. **绝对不要在循环里 `self.buf += x`。** 属性天生带别名，这个写法稳定落在 O(n²) 那一侧。200k 时 6.1 秒，而 `join` 是 1.5 毫秒。
3. **`+=` 的复杂度看别名，不看语法。** 只要有人跟你共享那个串（存进列表、挂到对象、作为返回值提前保存），原地扩容就失效。
4. **`"".join()` 之前先收集，别边拼边用。** 一个 `list` + 一次 `join`，内存峰值也最低。
5. **`len()` 是码点，不是字节，也不是显示宽度。** 三件事分开算：`len(s)`、`len(s.encode())`、`sum(2 if 全角 else 1)`。
6. **按字节截断必须退到字符边界。** 编码→砍→退→解码，退最多 3 次，别用 `errors="ignore"` 糊过去。
7. **别假设 `upper()` / `lower()` 不改变长度。** `"ß" → "SS"`。凡是长度会变的地方，都要按"结果可能比原来长"来留空间。
8. **比较用户输入的字符串前先 `normalize("NFC")`。** 否则 `"café"` 两种写法永远不相等，而且看着一模一样，查都查不出来。
9. **折叠只做一次。** 逐行 `lower()` 在含中文的文本上是纯 ASCII 的 20 倍；整段折一次再搜，比逐行折快 1.5 倍。
10. **测字符串性能，一定要分开测"命中"和"未命中"。** 我第一轮就是被"第一个字符就命中"骗了，量出来比实际快 490 倍。
11. **导出给 Excel 用 `utf-8-sig`。** 差的 3 个字节决定了中文是正常还是乱码。
12. **热循环里把 `float → str` 的转换提到循环外。** 3 倍，比换格式化语法有效得多。

### 十一、和手上的东西对上

- **rp_server 的 HTTP 响应体**：用列表收集片段再一次 `join`，别用 `resp += chunk`。后者在几 MB 的响应上是二次的，而且在 ASGI 里每拼一次还多一次对象分配。
- **串口 / AT 指令的日志缓冲**：`self.buf += line` 就是今天第二节表里那 6.1 秒。换成 `list` + 定期 `join` 或 `collections.deque(maxlen=N)`，行为不变，成本从二次变线性。
- **POS 流水导出**：写 CSV 用 `utf-8-sig` 给 Excel，用 `utf-8` 给程序；金额一律整数分（和 10-30 那篇对上了）。列宽对齐用显示宽度算，不用 `len`——中文算 2 格，`pad_display` 里那 8 格宽的表在终端里才真的齐。
- **中文路径 / 文件名**：`os.listdir` 在 Windows 上返回的是 `str`，不是 `bytes`；一旦传给只吃字节的 C 扩展或子进程，编码就按区域设置走。要稳定就全程 `str` + 显式 `encoding="utf-8"`。
- **nRF5340 上的 C**：`strcat` 每次都要从头找结尾，是标准的 O(n²)；正确写法是维护一个写指针，`memcpy(buf + off, s, n); off += n;`。和 Python 里"留一个长度"是同一个思路——**别让程序每次重新数一遍已经数过的东西。**
- **前端表格**：中文按 2 格算宽度，`len` 算不出来；这也是"看起来对齐了、实际歪了"的常见原因。

一句话总结今天量到的东西：**字符串看起来是一个值，其实是一条存储策略——它有多宽、有没有人跟你抢、以及你是复制还是追加，这三件事决定了它的价钱；而这三件事，一行代码里全看不见。**

## 🧩 今日代码片段：textkit — 五个能直接抄走的小工具

`ChunkWriter`（替代 `+=` 的追加器）、`cut_bytes`（按字节安全截断）、`cut_display` / `pad_display`（按显示宽度对齐中英混排）、`fold_key` / `icontains`（大小写与归一化比较）、`csv_bytes`（带 BOM 的 CSV）。下面这段是真跑过的，输出贴在后面。

```python
# -*- coding: utf-8 -*-
"""textkit：拼接、截断、宽度、大小写、CSV 编码，五个能直接抄走的小工具"""
import csv
import io
import unicodedata


# ---------------------------------------------------------------- 1 拼接
class ChunkWriter:
    """替代 s += line。内部只 append，取结果时一次 join。

    无论外面循环多少次，都只有一次分配和一次拷贝。
    """

    __slots__ = ("_parts", "_size")

    def __init__(self):
        self._parts = []
        self._size = 0

    def write(self, s):
        self._parts.append(s)
        self._size += len(s)
        return self

    def __len__(self):
        return self._size

    def getvalue(self):
        return "".join(self._parts)

    def clear(self):
        self._parts.clear()
        self._size = 0


# ---------------------------------------------------------------- 2 字节截断
def cut_bytes(text, nbytes, encoding="utf-8"):
    """按字节上限截断，绝不切在多字节字符中间。

    先编码 → 砍字节 → 往前退到合法边界 → 解码。
    退到边界最多 3 次（UTF-8 一个字符最多 4 字节），代价可以忽略。
    """
    raw = text.encode(encoding)[:nbytes]
    while raw:
        try:
            return raw.decode(encoding)
        except UnicodeDecodeError:
            raw = raw[:-1]
    return ""


# ---------------------------------------------------------------- 3 显示宽度
def char_width(c):
    """终端里的显示宽度：CJK 全角 2，其余 1。

    组合符（Mn/Me）宽度 0——它和前一个字符叠在一起。
    """
    if unicodedata.combining(c):
        return 0
    return 2 if unicodedata.east_asian_width(c) in "WF" else 1


def vis_width(text):
    return sum(char_width(c) for c in text)


def cut_display(text, width, ellipsis="…"):
    """按显示宽度截断，中文算 2 格。超出就补省略号。"""
    if vis_width(text) <= width:
        return text
    limit = width - vis_width(ellipsis)
    out, w = [], 0
    for c in text:
        cw = char_width(c)
        if w + cw > limit:
            break
        out.append(c)
        w += cw
    return "".join(out) + ellipsis


def pad_display(text, width, align="-"):
    """按显示宽度补齐，用来对齐中英混排的表格。"""
    w = vis_width(text)
    if w >= width:
        return text
    gap = width - w
    if align == ">":
        return " " * gap + text
    if align == "^":
        left = gap // 2
        return " " * left + text + " " * (gap - left)
    return text + " " * gap


# ---------------------------------------------------------------- 4 大小写
def fold_key(text):
    """大小写不敏感的比较键：先折叠，再归一化。

    - casefold() 比 lower() 更彻底（ß → ss）
    - NFC 把 'e' + 声调合成一个字符，否则两边永远不相等
    """
    return unicodedata.normalize("NFC", text.casefold())


def icontains(haystack, needle):
    """大小写不敏感包含。折叠只做一次，别在循环里对同一段文本反复折叠。"""
    return fold_key(needle) in fold_key(haystack)


# ---------------------------------------------------------------- 5 CSV
def csv_bytes(rows, header=None, encoding="utf-8-sig"):
    """生成 CSV 字节。默认 utf-8-sig：带 BOM，Excel 双击才不乱码。

    utf-8      → Excel 按本地编码（简体中文是 GBK）解，中文全乱
    utf-8-sig  → 开头 3 字节 BOM，Excel 认出来是 UTF-8
    gbk        → Windows 原生看着正常，跨系统就废
    """
    buf = io.StringIO()
    w = csv.writer(buf, lineterminator="\n")
    if header:
        w.writerow(header)
    w.writerows(rows)
    return buf.getvalue().encode(encoding)
```

三个值得说的细节：

- **`İstanbul` 那行是 `False`，而且这是对的。** 土耳其语的大写 İ（U+0130）折叠后是 `"i" + 组合点`，展开成两个码点，和普通的 `i` 不相等。`casefold()` 不是万能归一，它只做"大小写"这一层；语言相关的特殊规则得自己处理。这条我原本以为会 `True`，实测打脸，但结论反而更该记住：**别指望一个函数解决所有等价性。**
- **`cut_bytes` 的 13 字节给了 12 字节。** 它保证的是"不超过"，不是"正好"。协议里要定长字段，自己补空格。
- **`pad_display` 那四行在终端里是真的对齐的。** `"商品"` 两个字符、显示 4 格，补到 8 格是 4 个空格；`"Banana"` 6 个字符显示 6 格，补到 8 格是 2 个空格。两者在等宽字体下右边界重合——用 `str.ljust(8)` 就做不到，因为它是按字符数补的。
