# 📅 2026年11月25日 日报

## 💭 技术随想：`café` 有两个，`==` 说它们不相等

起因是一个笔记文件名。Obsidian 里我明明只建了一个「café」，索引里却出现两条，点进去内容还不一样。翻到十六进制才看清：**磁盘上是两份不同的字节，屏幕上是一模一样的七个字母。**

```text
café.txt   ->  63 61 66 c3 a9 2e 74 78 74        （e+acute 合成成一个码点）
café.txt   ->  63 61 66 65 cc 81 2e 74 78 74     （e 和 一个「重音符」两个码点）
```

两行看着完全相同，字节差了 2 个。这是同一杯咖啡的两种写法：**一种把 `é` 存成一个字符，一种存成 `e` 加一个「贴上去的重音」**。

17 号那篇说过 `is` 和 `==` 不是一回事。今天再补一刀：**连 `==` 本身都不够用**，因为「同一个字」在这个层面还没有定义。

以下每个数字都是刚刚在这台机器上打出来的（Windows 11 / Python 3.14.9 / unicodedata 16.0.0，`maxunicode = 0x10ffff`）。

### 一、一个字符，可以是一串码点

我原来以为字符和码点是一对一的。不是。

```text
'é'          ->  1 个码点  U+00E9               同一种写法：合成式（composed）
'e' + U+0301 ->  2 个码点  U+0065 U+0301        另一种写法：分解式（decomposed）
```

打印出来一模一样，`==` 给你 `False`，`len()` 给你 4 和 5：

```text
>>> a, b = "café", "cafe\u0301"
>>> a == b
False
>>> len(a), len(b)
4 5
```

更狠的是韩文。一个 `가` 是 1 个码点 `U+AC00`，拆开是 2 个码点 `U+1100 U+1161`（初声 ㄱ + 中声 ㅏ）。中文倒是基本一对一——汉字没有「合成/分解」两套写法，这也是我在这件事上迟钝了这么多年的原因：**我的母语恰好待在 Unicode 最规矩的那块地里。**

### 二、`len()` 数的是码点，不是「一个字」

`café` 的 `len` 是 4 还是 5，取决于它是怎么进来的。放到 emoji 上更夸张：

```text
👨‍👩‍👧‍👦   7 个码点，11 个 UTF-16 码元，屏幕上 1 个「字」
👍🏽        2 个码点（拇指 + 肤色），4 个 UTF-16 码元
🇨🇳        2 个码点（两个区域指示符）
```

一家四口是「爸爸 + 零宽连接符 + 妈妈 + 零宽连接符 + 女儿 + 零宽连接符 + 儿子」，共 7 个码点。用户眼里的 1 个字符，`len()` 说 7。所以：

- **「限制 20 个字」的输入框**，用 `len(s) <= 20` 拦不住 20 个 emoji（那其实是 140 个码点）；
- **「最多 100 字符」的数据库列**，用 `s[:100]` 截断可能正好切在一家四口中间，留下一个悬空的连接符；
- **「按字数算钱」的功能**，得先说清算的是码点、字素还是字节。

`len()` 给我的从来不是「几个字」，是「几个码点」。这两件事在过去三十年里恰好相等，现在不等了。

### 三、四种归一化，只有两种该用

Unicode 给了四个函数把它们互相折叠：

| 形式 | 做什么 | 结果 |
|---|---|---|
| NFD | 拆到最细（分解） | `é` → `e` + U+0301，`가` → `U+1100 U+1161` |
| NFC | 合成到最短（**存储用**） | 反过来，两个码点合成一个 |
| NFKD | 分解 + 兼容等价 | `①` → `1`，`Ａ` → `A` |
| NFKC | 合成 + 兼容等价（**搜索用**） | 同上，但再合成一次 |

实测的几行，前两个是「无损」，后几个是「有损」：

```text
'é'      NFC 'é'            NFKC 'é'
'①'      NFC '①'           NFKC '1'          ← 圆圈没了
'１'      NFC '１'          NFKC '1'          ← 全角变半角
'Ａ'      NFC 'Ａ'          NFKC 'A'
'Ⅳ'      NFC 'Ⅳ'          NFKC 'IV'         ← 1 个变 2 个
'½'      NFC '½'          NFKC '1⁄2'        ← 1 个变 3 个（带分数斜杠 U+2044）
'㈱'      NFC '㈱'          NFKC '(株)'       ← 1 个变 3 个
'ﬁ'      NFC 'ﬁ'          NFKC 'fi'         ← 连字拆开
```

NFC 是**无损**的：`é` 拆开再合回来，还是原来那个 `é`。NFKC 是**有损**的：`①` 变成 `1` 之后，再也回不到 `①`——它把「字符的样子」和「字符的意思」混为一谈了。

所以规矩很简单：

```text
存储、比较、文件名、数据库主键  ->  NFC
搜索、过滤、模糊匹配、去重      ->  NFKC + casefold（丢了就丢了，反正只是用来找）
```

反过来用就出事：**用 NFKC 存用户的昵称**，用户输入 `㈱` 你给他存成 `(株)`；**用 NFC 做搜索**，用户搜全角 `Ａ` 找不到半角 `A`。

还有一条今天顺手验了：归一化是**幂等**的，`NFC(NFC(x)) == NFC(x)`；`NFC(NFD(x)) == NFC(x)` 也成立。所以「先归一，再比较」永远安全，重复调用不会滚雪球。而且它很便宜——对 100 字符的串跑 20000 次 NFC，3 毫秒。**该归一的地方就归一，别省这点。**

### 四、`lower()` 会改长度，`casefold()` 才叫折叠

11 月 21 号那篇说到排序时提过土耳其语 `i` 和德语 `ß`，当时只是引了一句文档。今天把它们钉到实测上：

```text
'Straße'.lower()      -> 'straße'      长度 6 -> 6
'Straße'.casefold()   -> 'strasse'     长度 6 -> 7      ← ß 变成两个 s
'ß'.lower() == 'ss'   -> False
'ß'.casefold() == 'ss'-> True
'K'（开尔文符号 U+212A）.casefold() -> 'k'
'ς'（词尾 sigma）.upper() -> 'Σ'
'İ'（土耳其大写 I）.lower() -> 'i̇'      长度 1 -> 2      ← i 加一个点
'ß'.upper()           -> 'SS'          长度 1 -> 2
```

这几行说明一件事：**大小写变换不是「一个字符换一个字符」，它可以是 1→2、2→1，甚至跟位置有关**（希腊语的词尾 `ς` 和词中 `σ` 是两个码点，折叠后才统一）。

这直接埋了一个我踩过的 bug：

```text
s   = 'İstanbul-5'        len 10
low = s.lower()           len 11        'i̇stanbul-5'
i   = low.find('stanbul')  -> 2
s[i:i+7]                   -> 'tanbul-'  ← 想切 'stanbul'，切成了 'tanbul-'
s.find('stanbul')          -> 1          ← 原串里其实在 1
```

**用 `lower()` 之后的下标去切原串，差一位。** 任何「先变小写再高亮匹配位置」的代码都有这个洞——搜索词从 `İ` 开头就偏。

结论：做**比较**用 `casefold()`（它比 `lower()` 彻底，专门为「不分大小写地判等」设计）；做**变换下标**时别碰大小写，或者干脆只在下标空间里操作（只对 `low` 切片，别回头切 `s`）。

### 五、同一个文件夹里，两个 `café` 真的能共存

这是今天最反直觉的一条。我在 `C:\ut\unitest` 里分别用 NFC 和 NFD 的名字各建了一个文件：

```text
md 文件列表:
  café.txt   63 61 66 65 cc 81 2e 74 78 74    （NFD，5 个字符）
  café.txt   63 61 66 c3 a9 2e 74 78 74       （NFC，4 个字符）
os.path.samefile(两个名字) -> False
```

**Windows 的 NTFS 不归一化。** 它把这两串字节当成两个名字，两个文件并排躺着。同一个文件夹里，用户看到两个一模一样的图标。

而它对**大小写**反而是折叠的：

```text
创建 'A.txt'  -> OK
创建 'a.txt'  -> OK（没报错）
listdir       -> ['A.txt']          ← 只有一个
samefile('A.txt','a.txt') -> True
```

第二次 `open(..., 'w')` 悄悄打开了同一个文件，把内容覆盖了。**同一个文件系统，对大小写装傻，对归一化认死理。**

这个差异在 git 里会变成事故。我在一个临时仓库里把两个 `café.md` 都提交：

```text
$ git ls-files
"cafe\314\201.md"      ← NFD，git 用八进制转义显示不可见差异
"caf\303\251.md"       ← NFC
$ git ls-files | wc -l
2
$ git ls-files -z | xxd
00000000: 6361 6665 cc81 2e6d 6400 6361 66c3 a92e  cafe...md.caf...
```

**两个文件都进了仓库。** 在 Windows 上一切正常，拉下来还是两个。但到了 macOS 上（APFS 在比较时做归一化，HFS+ 干脆存储时就转 NFD），这两个名字会指向同一个文件——一个被覆盖，另一个永远检不出来。**git 存的是字节，它不纠正你。** 这种 bug 只在「换了一台机器」的时候出现，本地测试永远绿。

这就是为什么现在很多工具链在写盘前先归一次 NFC：不是洁癖，是**让「文件名」这个概念在不同系统上至少指的是同一件事**。

### 六、长度限制按 UTF-16 码元算，124 个 emoji 就到顶

顺手把 Windows 的路径长度也量了一遍，因为这里也藏着「字符数 ≠ 实际存的单位数」。

在 `C:\ut`（长度 5）下试文件名：

```text
纯 ascii 'a'*249 + '.txt'   -> path 259  OK
纯 ascii 'a'*250 + '.txt'   -> path 260  FAIL
'😀'*124 + '.txt'           -> utf16 path 258  OK
'😀'*125 + '.txt'           -> utf16 path 260  FAIL
```

边界卡在 **259 过、260 不过**——经典的 `MAX_PATH`。关键是第二组：**124 个 emoji 就撞墙了，而纯英文能写到 249。** 因为 Windows 数的是 UTF-16 码元，一个 emoji 占 2 个。

最坑的是报错信息。这个失败在 Python 里长这样：

```text
'😀'*125  ->  OSError: No such file or directory
```

**它说「没有这个目录」。** 目录好好的，问题在名字太长。在 `C:\` 根目录试 256 个字符的文件名，报的是 `Invalid argument`；257 个以上又变回 `No such file or directory`。同一个根因，三种报错，没有一种是「名字太长」。

所以「把用户输入的文件名截到 100 字符」这种代码，遇到 emoji 仍然会炸——**它得按码元预算裁，不是按 `len()` 裁。**

### 七、截断要按「字素」切，不然切出半个字

前面说的悬空连接符，实测长这样：

```text
👨‍👩‍👧‍👦  [:2]  ->  '👨\u200d'         ← 爸爸 + 一个连接符，后面什么都没有
🇨🇳      [:1]  ->  '🇨'              ← 半个国旗，渲染成一个方框里的 C
```

`[:2]` 和 `[:1]` 都是合法的 Python 字符串，都是**非法的人类文字**。屏幕上会显示一个孤零零的连接符（多数渲染器直接吞掉），或者一个豆腐块。

正确的切法是按**字素簇**（grapheme cluster）切：组合符、零宽连接符、肤色修饰符、区域指示符配对，都得跟着它的主字符走。这就是 `unikey.py` 里 `_clusters` 干的事。

### 八、同形异码：归一化救不了它

```text
拉丁 'a'   U+0061
西里尔 'а' U+0430      看起来一样，== 给 False
NFKC 之后仍然不一样（它俩不是「同一个字符的两种写法」，是两个不同的字符）
'раураl' 的文字集: ['CYRILLIC', 'LATIN']    ← 混写
'apple'  的文字集: ['LATIN']
```

这个不是 bug，也没有「正确的修法」。归一化处理的是「同一个字符的不同编码」，同形异码处理的是「不同字符长得一样」——后者只能靠**混写检测**（一个标识符里同时出现两种文字就报警）或者 Unicode 的 confusables 表。

值得警惕的场景：域名、包名（`pypi` 上抢注同形包）、评论区的 `@аdmin`（西里尔 а）、以及我自己的文件名去重逻辑——**两个看起来一样的名字，`==` 说不等，去重逻辑会放行第二个。**

### 九、对着手上的东西看

- **笔记文件名 / 索引**（今天这个坑的源头）。索引第一件事就该是 `NFC(name)`，否则同一篇笔记可能以两种写法各进一次索引。Obsidian 的链接匹配、`[[...]]` 里的双链，全走的是字符串精确匹配。
- **git 仓库里的中文/带重音文件名。** 提交前统一 NFC；`core.quotepath` 打开时非 ASCII 会显示成 `"caf\303\251.md"`，看着像乱码，其实是好的——**乱码说明它老实告诉你有不可见差异**。
- **CSV / JSON 的键。** 我那份生鲜流水的表头如果有重音，两条「同名」列就永远合不上。`json.dumps` 默认 `ensure_ascii=True`，会写成 `"\u540d"`，读回来是对的——但**键的归一化它不管**。
- **搜索框。** 用 `fold()`（NFKC + casefold）建索引键，用原串做展示。中文没影响，全角/半角、大小写、`ß`/`ss` 都能对上。
- **任何 `s[:n]`。** 出现在用户可见文案上就是红旗，换成按字素切。
- **任何 `len(s)` 做限制。** 出现在输入校验、数据库列宽、文件名上也是红旗，先想清楚数的是码点、码元还是字节。
- **日志。** 收到外部字符串先打一份 `repr()`。`print()` 会把 `e` + 重音显示成 `é`，**把「有差异」这件事藏起来**；`repr()` 才老实。

### 十、一句必须说清楚的诚实

- **属于标准/文档的**：NFC/NFD/NFKC/NFKD 的定义；NFKC 的兼容分解是有损且不可逆；`casefold` 是「为判等设计」的大小写折叠；NTFS 不归一化；HFS+ 存储时转 NFD、APFS 保留字节但比较时归一化（**这两个是文档结论，这台机器没有 macOS 可验**）。
- **属于这台机器这一次实测的**：上面所有十六进制、`len` 4/5、`git ls-files` 的两条记录、`samefile` 的 True/False、`259 过 260 不过`、`124 个 emoji 顶到 MAX_PATH`、`'İstanbul-5'` 的下标偏一位、20000 次 NFC 3 毫秒。
- **没有实测的**：Linux（ext4）上的文件名行为——按理它跟 NTFS 一样纯字节、不归一化，但我没开那台 RK3588 去验；完整的 UAX #29 字素切分——`_clusters` 是我的近似实现，只覆盖了组合符/ZWJ/肤色/国旗这四类，**印地语、泰语的复杂连字它不管**；真正的同形异码检测需要 Unicode confusables 表或 `confusable_homoglyphs` 库，我也没装。
- **最要紧的一句**：`==` 判的是「码点序列是否相同」，而「是不是同一个字」是一个**需要先做决定**的问题——决定用哪种归一化形式、决定丢掉哪些区别。你没做这个决定，`==` 就替你做了一个，通常还是错的那个。

## 🧩 今日代码片段：`unikey.py` —— 把「看起来一样的字」变成「真的同一个键」

`nfc` 管存储，`fold` 管搜索，`same` 把这两件事合起来回答「是不是同一个」，`_clusters` / `cut` 按字素截断，`utf16_units` / `fit` 按 Windows 的账算长度，`scripts` 揪出混写。

```python
# -*- coding: utf-8 -*-
"""unikey.py —— 把「看起来一样的字」变成「真的同一个键」"""
import unicodedata

ZW = {"\u200b", "\u200c", "\u200d", "\ufeff"}          # 零宽字符
SKIN = range(0x1F3FB, 0x1F400)                          # 肤色修饰符


def nfc(s):
    """存储用：合成成最短形式。同一个字，只有一种写法进库。"""
    return unicodedata.normalize("NFC", s)


def fold(s):
    """检索用：兼容归一 + 大小写折叠 + 干掉零宽。会丢信息，只用于比对。"""
    s = unicodedata.normalize("NFKC", s)          # ① -> 1，Ａ -> A，ﬁ -> fi
    s = s.casefold()                              # ß -> ss，比 lower() 更彻底
    return "".join(c for c in s if c not in ZW)


def same(a, b):
    """「这两个字符串是不是同一个」——不要用 ==，先用用它。"""
    return fold(a) == fold(b)


def _is_ri(c):
    return 0x1F1E6 <= ord(c) <= 0x1F1FF


def _clusters(s):
    """粗粒度字素切分：不做完整 UAX #29，只保证不把组合符/ZWJ/肤色/国旗切开。"""
    out = []
    for c in s:
        cp = ord(c)
        attach = bool(out) and (
            unicodedata.combining(c)
            or cp in (0x200D, 0xFE0E, 0xFE0F)
            or cp in SKIN
            or out[-1][-1] == "\u200d"
            or (_is_ri(c) and len(out[-1]) == 1 and _is_ri(out[-1]))
        )
        if attach:
            out[-1] += c
        else:
            out.append(c)
    return out


def cut(s, n):
    """截断到 n 个字素，绝不留下悬空的组合符或 ZWJ。"""
    return "".join(_clusters(s)[:n])


def utf16_units(s):
    """Windows 文件名/MAX_PATH 数的是 UTF-16 码元：一个 emoji 算 2。"""
    return len(s.encode("utf-16-le")) // 2


def fit(s, budget):
    """按 UTF-16 码元预算裁剪，保证落盘不炸。"""
    s = nfc(s)
    while s and utf16_units(s) > budget:
        s = "".join(_clusters(s)[:-1])
    return s


def scripts(s):
    """看看一串字符里混了几种文字 —— 混了就可能是在钓鱼。"""
    seen = set()
    for c in s:
        if not c.isalpha():
            continue
        name = unicodedata.name(c, "")
        if name:
            seen.add(name.split()[0])
    return sorted(seen)


def strip_marks(s):
    """去掉所有变音符。只有「搜英文/拼音」这种场景才敢用，中文没问题，越南语会哭。"""
    return "".join(c for c in unicodedata.normalize("NFD", s) if not unicodedata.combining(c))


if __name__ == "__main__":
    a = "café"
    b = "cafe\u0301"
    print("1) 同一杯咖啡两种写法:", a == b, "| same():", same(a, b))
    print("   len:", len(a), len(b), "| NFC 后:", nfc(a) == nfc(b), len(nfc(b)))

    print("2) 检索键:", repr(fold("ＡＢＣ①ﬁ")), "|", repr(fold("Straße")), "|", repr(fold("İstanbul")))
    print("   fold+strip:", repr(strip_marks(fold("İstanbul"))), "| == 'istanbul':",
          strip_marks(fold("İstanbul")) == "istanbul")

    fam = "👨\u200d👩\u200d👧\u200d👦"
    print("3) 一家四口 len:", len(fam), "码点 | UTF-16 码元:", utf16_units(fam))
    print("   硬切 2 个码点:", repr(fam[:2]), "（悬空 ZWJ）| 切两个家庭:",
          repr(cut(fam * 2, 2)))
    flag = "🇨🇳"
    print("   国旗 len:", len(flag), "| 硬切一半:", repr(flag[:1]), "| cut(1):", repr(cut(flag, 1)))

    name = "😀" * 200
    print("4) 200 个 emoji: 码点", len(name), "码元", utf16_units(name), "-> fit(240):", utf16_units(fit(name, 240)))

    print("5) 混写检查:", scripts("раураl"), "|", scripts("apple"), "| same('аpple','apple'):",
          same("\u0430pple", "apple"))
```

```text
   fold+strip: 'istanbul' | == 'istanbul': True
3) 一家四口 len: 7 码点 | UTF-16 码元: 11
   硬切 2 个码点: '👨\u200d' （悬空 ZWJ）| 切两个家庭: '👨‍👩‍👧‍👦👨‍👩‍👧‍👦'
   国旗 len: 2 | 硬切一半: '🇨' | cut(1): '🇨🇳'
4) 200 个 emoji: 码点 200 码元 400 -> fit(240): 240
5) 混写检查: ['CYRILLIC', 'LATIN'] | ['LATIN'] | same('аpple','apple'): False
```

五个值得单独说的细节：

- **`fold` 里两步的顺序不能换，我扫了一遍全字符集：有 689 个码点在两种顺序下结果不同。** 举个最直白的：`ᴬ`（U+1D2C，上标大写 A）——先 NFKC 再 casefold 得 `'a'`，先 casefold 再 NFKC 得 `'A'`：**因为 casefold 根本不认识这个「修饰符字母」，它的折叠表里没有它，于是大写漏了过去**。必须先把兼容字符还原成真正的大写字母，折叠才认得。另一种偏差是形态：`ǰ`（U+01F0）先归一后折叠得 `'ǰ'`（分解式），反过来得 `'ǰ'`（合成式）——**两个键不相等，同样的字符串在两种实现下进不了同一个桶。** 标准里的 `NFKC_Casefold` 其实是三步（NFKC → casefold → NFKC），第三步是给「折叠后展开成组合序列」补一次合成；我这两步够用是因为后面只做比较，不拿它输出。
- **`fold` 是「有损」的，所以只能用来比对。** `'abc1fi'` 这个键你拿去做展示，`①` 和 `①` 就分不开了。**永远保留原串做展示，只把 `fold` 的结果当索引用**——这和「密码只存哈希、原文不存」是同一个思路。
- **`same()` 里藏着一个残忍的事实：`'раураl'` 和 `'paypal'` 归一化之后仍然不同。** 这不是 `same` 写错了，是**归一层管不到攻击层**。要防同形异码，得在 `same` 之外再加一道 `scripts()` 检查（混写就拒绝或告警）。
- **`fit()` 的预算单位是 UTF-16 码元，不是字符。** 这是它跟 `cut()` 的分工：`cut` 回答「人类能读到几个字」，`fit` 回答「Windows 肯收几个字节」。两个都要，缺一个就会在某个文件系统上炸。
- **`utf16_units` 用 `utf-16-le` 编码数长度，别用 `len(s.encode('utf-16'))`。** 后者会带 BOM（2 个额外码元）且默认走大端，算出来的数永远多 2。这种「差一点」的量法在边界上就是「过/不过」。

一句话收这段：**`==` 判的是「码点序列是否相同」，而「是不是同一个字」是一个需要先做决定的问题——决定用哪套归一化、决定丢掉哪一层区别。你没做这个决定，`==` 就替你做了一个，通常还是错的那个。**

## ✨ 今日一句

> `café` 和 `café` 看上去一样，`==` 说不是，`samefile` 也说是两个文件——**它俩都对，因为它们回答的是两个不同的问题。**
>
> 真正的问题不是「它们相等吗」，而是「你打算把哪一层差异当成不存在」。这个决定你一旦不做，`sorted()`、`==`、git、文件系统就会各自替你做一个，而且四个答案互不相同。
