# 📅 2026年11月21日 日报

## 💭 技术随想：排序不是一个「顺序」，是四个问题

`sorted(x)` 看起来像一句话：「把这些东西排好」。可真盯着它看，它在同时回答四个互不相干的问题：

1. **谁该在谁前面** —— 比较规则（只有 `key` 这一个入口是你可控的）
2. **相等的人怎么站** —— 稳定性（谁先来谁靠前，还是一片乱）
3. **乱序到什么程度** —— 输入的形状决定速度，能差二十倍
4. **你到底要哪个** —— 全序，还是只要前几个

这四个问题里任何一个答错，代码都不会报错，只会给你一份「看起来很整齐」的错数据。今天全在这台机器上跑了一遍（Windows 11 / Python 3.14.9 / MSYS bash），下面每个数字都是刚跑出来的。

### 一、`sorted` 只认一个符号：`<`

这是今天最颠覆我直觉的一条。排序算法内部**不问你「a 和 b 谁大」**，它只反复问一个布尔问题：`a < b` 吗？

所以当列表里混进一个 `NaN`：

```text
原始        : [3, nan, 1, 2]
sorted(raw) : [3, nan, 1, 2]        ← 一个元素都没动
再排一次    : [3, nan, 1, 2]        ← 还是没动
相邻对 a<=b 不成立的数量: 2 / 3
```

`sorted()` **安安静静地把一份完全没排序的列表还给了我**，不抛异常、不警告。原因就三行：

```text
nan != nan  -> True
nan <  1    -> False
1   <  nan  -> False
```

对 `NaN` 的任何比较都是 `False`。Timsort 扫一遍列表，每个相邻对都「看起来没乱」，于是它得出「已经有序」的结论，原样返回。

**这意味着 `sorted()` 的返回值需要验，不能假设。** 判断方式不是看它有没有抛错，而是看相邻元素：

```python
for a, b in zip(s, s[1:]):
    assert a <= b          # NaN 会在这里被抓住，因为 nan <= x 是 False
```

修法是把 `NaN`（还有 `None`）用一个 key 挪到固定位置，让它变成「一个确定的值」而不是「一个比较不出来的值」：

```text
挪走 NaN 后: [1, 2, 3, nan]   ← 第一个乱序位置: None
```

这个坑在传感器数据上几乎是必然出现的：除以零、`float('inf') - float('inf')`、JSON 里人写进去的 `NaN`——最后都会变成一串「排了但没排」的数据，然后你在下游二分查找，得到随机答案。

### 二、`key` 算一次，`cmp` 算 n·log n 次

给同一个 n=1000 的列表，用两种写法量调用次数：

| 写法 | 调用次数 |
|---|---|
| `sorted(data, key=f)` | **1,000**（每个元素正好一次） |
| `sorted(data, key=cmp_to_key(g))` | **8,640**（≈ n·log₂n = 9,966） |

n=100,000 时 `key` 版仍然是**精确的 100,000 次**。

这条推论比「key 更快」有用得多：**`key` 函数里的东西只会发生一次，所以它允许做重活；`cmp` 函数里的东西会发生十几次，所以它只能做轻活。**

- key 里可以 `re.split()`、可以查字典、可以拼元组 —— 一次性的开销，摊到 n 上很便宜。
- cmp 里做同样的事，就是十几次重复劳动；如果 cmp 里还有 IO 或网络，那就是灾难。
- **更要紧的反面**：key 里别写「有副作用」的东西。因为它只跑一次，你以为「每次比较都会顺手记一笔日志」，实际上只有 n 条，而且顺序跟最终排序无关 —— 这种日志会骗人。

顺带一个容易忽略的事实：Timsort 在**已经排好序**的输入上，`key` 依然会全跑一遍（实测 100,000 次，一次不少）。**省掉的是比较，不是 key。** 所以「数据本来就基本有序」不能成为「key 可以写得很贵」的理由。

### 三、稳定性：五种输入看出两种「倒过来」

拿 `[("a",2), ("b",1), ("c",2), ("d",1), ("e",2)]` 按第二项排：

```text
sorted(key=分数)                -> b d a c e      两分的人按原顺序 a→c→e
sorted(key=分数, reverse=True)  -> a c e b d      ← 也是稳定的：a→c→e 仍然保持
reversed(sorted(key=分数))      -> e c a d b      ← 反了！c 跑到 a 前面
```

**`reverse=True` 不等于「排完再整体倒过来」。** 前者是「用相反的比较规则排序，相等的仍然保持原序」，后者是把已经排好的结果硬翻一遍，**每一组相等的人也跟着被翻了**。

落在代码里长这样：

```python
# 错：同分的顺序被莫名其妙倒过来了
ranked = list(reversed(sorted(rows, key=score)))

# 对：同分保持「谁先来谁靠前」
ranked = sorted(rows, key=score, reverse=True)
```

`bool` 和 `int` 能把这个差别放大到肉眼可见（因为 `True == 1`）：

```text
sorted([True, 0, 1, False])                -> [0, False, True, 1]
sorted([True, 0, 1, False], reverse=True)  -> [True, 1, 0, False]
list(reversed(sorted(...)))                -> [1, True, False, 0]
```

第一行还顺手证明了两件事：**`False` 和 `0` 是「相等」的，所以谁排在前面完全由稳定性决定**（`False` 在后，因为它在原列表里更靠后）；以及 `len({True, 1}) == 1` —— 在集合里它们干脆是同一个元素。

稳定性的真正用法是**两趟排序**：一个 key 做不到「分数降序、同分按名字升序」这种一升一降的组合，两趟可以——

```text
sorted(sorted(people, key=名字), key=分数, reverse=True)
-> [('amy',90), ('cat',90), ('zoe',90), ('bob',80), ('dan',80)]
```

名字先升序排好，再按分数稳定地降序排一遍；分数相同的三个人，顺序**就是上一趟留下的顺序**。这比硬拼一个 `(-分数, 名字)` 元组更灵活：分数那一维是数字可以取负，名字那一维要是字符串就没法取负了 —— 两趟排序绕开了这个限制。

### 四、字符串排的是「码位」，不是「字母」

这条几乎每个人都踩过，但很少人知道它有多彻底：

```text
'Z' < 'a'      -> True            ← 大写字母全在小写前面（码位 0x5A < 0x61）
'é' < 'z'      -> False           ← 0xe9 > 0x7a，带音标的字母跑到 z 后面
sorted(["10","9"]) -> ['10', '9'] ← 字符串比的是逐字符
sorted(["app10","app9","app1"]) -> ['app1', 'app10', 'app9']
sorted(["阿","波","次"]) -> ['次', '波', '阿']   ← 完全不是拼音顺序
```

最后一行值得盯着看：中文的码位顺序跟拼音毫无关系，`阿(0x963F) < 波(0x6CE2) < 次(0x6B21)` 在码位上根本不成立。**你在界面上想做「按名称排序」，`sorted()` 给你的东西在用户眼里就是乱序。**

三个层次的修法，代价递增：

1. **补零/定长**：`app1` → `app001`，字典序就等于数字序。最简单，但要求你能控制数据的生成。
2. **自然排序 key**：按「数字块 / 文本块」切开，数字块转成 `int` 再比。实测把 `['app1','app10','app9']` 变成了 `['app1','app9','app10']`。
3. **真正的语言排序**：拼音、德语 `ß`、土耳其语 `i` —— 需要 locale 数据或 `PyICU`。**Python 内置的 `sorted()` 完全不看 locale**，这条来自文档，今天我也没有环境实测（下面诚实一节里会写明）。

自然排序的 key 有个小细节值得偷：每一段包成 `(0, 数字)` 或 `(1, 文本)` 的元组。这样「数字和文本在同一位置相遇」时，元组先比第一个元素 `0` 和 `1`，**永远不会去比较 `int` 和 `str`**——否则就是一个 `TypeError`：

```text
sorted([1, "1"])    -> TypeError: '<' not supported between instances of 'str' and 'int'
sorted([1, None])   -> TypeError: '<' not supported between instances of 'NoneType' and 'int'
```

同样的错在「元组键」里更隐蔽：`key=lambda d: (d["s"], d["n"])`，只要某个 `n` 是 `None`，就会在**运行到那一对**的时候才炸：

```text
(1, None) 与 (1, 'a') -> TypeError: '<' not supported between instances of 'NoneType' and 'str'
缺字段              -> KeyError: 's'
```

**这里有个要命的非对称**：`sorted()` 不会因为「有两个元素不可比」就提前失败，它会先干活、干到一半才炸。也就是**部分输出已经被修改过了**（`list.sort()` 原地那版尤其危险：列表处于「排了一半」的状态，既不是旧的也不是新的）。跨版本、跨数据的偶发 `TypeError` 大多来自这里。

### 五、输入的形状决定速度：同一份数据，二十倍差

30 万个整数，只改「原来的顺序」：

| 输入 | 耗时 | 相对随机 |
|---|---|---|
| 完全随机 | **50.3 ms** | 1.0× |
| 只有两处对调 | **2.7 ms** | 19× 快 |
| 本来就排好 | **2.1 ms** | 24× 快 |
| 完全倒序 | **2.3 ms** | 22× 快 |

原因不神秘：Timsort 会先在数据里找**天然递增的连续段（run）**，找到就直接用，只对边界做合并。随机数据里 run 平均长度只有 2~3，等于白干；而「排好」和「完全倒序」都只是一条 run（倒序会被识别成「下降 run」再翻过来）。

三条实用推论：

1. **已排好的数据再排一次几乎免费**，所以「每次都排一遍」在多数场景是可以接受的设计——省掉「记住它有没有排过」的复杂度。
2. **但别指望靠先加工数据提速**。想快就得减少比较次数（换 key、分桶），而不是「先打乱一下」。
3. **`sorted()` 会复制一份**：30 万元素的列表，`tracemalloc` 量到峰值多出 **3.4 MB**；原地 `list.sort()` 只多出 O(log n) 的栈。实测同一份数据 `list.sort()` 是 54.8 ms、`sorted()` 是 50~73 ms（`sorted` 要先复制，所以通常略慢，且内存翻倍）。**百万级的列表能原地就原地。**

### 六、要全部，还是要前几个

「取前 5 名」我以前的写法是 `sorted(x)[-5:]`。实测 20 万个浮点数：

| 要几个 | `heapq.nlargest` | 全排再切 | 结论 |
|---|---|---|---|
| 5 | **2.25 ms** | 25.0 ms | 堆快 **11×** |
| 2,000 | **5.12 ms** | 29.8 ms | 堆快 **6×** |
| 100,000 | 189 ms | **27.0 ms** | 堆反而慢 **7×** |

分界线在 k 跟 n 的比例上：堆是 O(n·log k)，排序是 O(n·log n)。**k 小的时候堆几乎只是在「扫一遍」，k 大到接近 n 的时候，它做的无用功比排序还多。**

还有一个小坑：`nlargest` / `nsmallest` 返回的顺序和「全排再切」是反的。`sorted(x)[-5:]` 是**升序**的最后五个，`nlargest(5)` 是**降序**的前五个。集合一样，顺序不一样，拿去做「最近 5 条日志」的时候会安静地倒过来。

### 七、对着手上的东西看

- **CAN / 手柄采样按时间戳排序。** 时间戳来自硬件，出现 `NaN`、`None`、`0` 都不是罕见事。只要有一个，`sorted()` 就可能整段不排。**排序之后加一句「相邻必须有序」的断言**，比相信它便宜得多。
- **日志按时间排。** 如果时间戳是字符串，那排的是字典序：`2026-11-9` 会排在 `2026-11-21` 后面。**统一 ISO 8601 补零（`2026-11-09`）** 就能让字符串序 = 时间序，不用转 datetime。这是最省事的修法。
- **「最新 N 条」别全排。** 20 万条历史日志只为了拿 5 条，用 `deque(maxlen=N)` 顺着读一遍就够了，连堆都不用。
- **优先级队列。** 任务队列「同优先级按到达顺序执行」，靠的正是稳定性；如果你用了 `reversed(sorted(...))` 或者自己写的 `heapq` 元组，公平性会悄悄丢掉 —— 堆**不保证**相等元素的顺序（它只保证父节点不大于子节点）。要公平就把到达序号拼进 key：`(priority, seq)`。
- **`sorted()` 的返回值要验，不要假设。** 不报错 ≠ 排好了。一条 `assert all(a <= b ...)` 在数据边界上救过很多人。
- **中文排序别用 `sorted()` 糊弄。** 界面上「按名称」如果要符合用户直觉，就得自然排序 / 拼音表；码位序是给机器看的。

### 八、一句必须说清楚的诚实

- **属于语言规范（文档保证）的**：`sorted` / `list.sort` 是稳定的；`reverse=True` 也保持稳定；`key` 对每个元素恰好调用一次；最坏 O(n log n)、最好 O(n)。
- **属于这台机器这一次的实测**：50.3 / 2.7 / 2.1 / 2.3 ms 这组数字（倍数会随机器、Python 版本变，**形状的结论不会变**）；`cmp` 在 n=1000 上是 8640 次（跟数据分布有关，不是常数）；`sorted()` 峰值 3.4 MB；k=100,000 时堆慢 7 倍这个交叉点。
- **没有实测的**：locale 相关排序（拼音、`ß`、土耳其语 `i`）——这台机器没有 `PyICU` 和 locale 数据，所以上面「内置 `sorted()` 不看 locale」是来自文档的结论，不是今天的实验数据。真的要做多语言排序，先装 `PyICU` 实测再下结论。
- 所以今天这四条要分开记：**比较规则（你写的 key）、稳定性（语言保证）、速度（输入形状 + 实现）、要几个（算法选择）**。混在一起看，就会得到「我明明排过了啊」和「为什么同分的人顺序变了」这两种最难查的 bug。

## 🧩 今日代码片段：`sortkit.py` —— 四个把「排序」问清楚的小工具

`natural_key` 解决「字符串序不是人眼序」，`nan_safe_key` 解决「`sorted` 静默不排」，`is_sorted` 负责**验货**，`top_k` 解决「只要前几个」，`two_pass` 用稳定性做一升一降。

```python
# -*- coding: utf-8 -*-
"""sortkit.py —— 四个把「排序」问清楚的小工具"""
import heapq
import re


def natural_key(s):
    """'app10' 排在 'app9' 后面。按「数字块 / 文本块」切开再比。
    每一段都包成 (0, 数字) 或 (1, 文本) 的元组：类型不同也不会撞车，
    因为元组先比第一个元素，0 和 1 已经把「数字」和「文本」分开了。"""
    parts = re.split(r"(\d+)", s)
    return [(0, int(p)) if p.isdigit() else (1, p.lower()) for p in parts if p]


def nan_safe_key(x):
    """NaN / None 挪到末尾，其余按原值。sorted 只认 `<`，
    而 NaN 的每一次 `<` 都是 False —— 它会把整个列表当成「已经有序」。"""
    if x is None or x != x:
        return (1, 0.0)
    return (0, x)


def is_sorted(seq, key=lambda x: x):
    """sorted() 不报错，不代表结果有序。用 `a <= b` 验证，NaN 会在这里现形。
    返回第一个「不听话」的下标，全对就返回 None。"""
    for i in range(len(seq) - 1):
        if not (key(seq[i]) <= key(seq[i + 1])):
            return i
    return None


def top_k(seq, k, key=lambda x: x, largest=True):
    """只要前 k 个就别全排：k 小的时候堆快一个数量级，k 大了反而慢。
    注意 nlargest/nsmallest 返回的顺序：降序 / 升序，跟 sorted 的切法不同。"""
    if k <= 0:
        return []
    fn = heapq.nlargest if largest else heapq.nsmallest
    return fn(k, seq, key=key)


def two_pass(rows, primary, secondary):
    """分数降序、同分按名字升序 —— 一个 key 做不到「一升一降」，两趟可以。
    靠的是稳定性：第二趟只在 primary 相等时才「保留第一趟留下的顺序」。"""
    return sorted(sorted(rows, key=secondary), key=primary, reverse=True)


if __name__ == "__main__":
    print("自然排序:", sorted(["app10", "app9", "app1", "App2"], key=natural_key))

    raw = [3, float("nan"), 1, 2]
    print("原始      :", raw)
    print("直接排    :", sorted(raw), "| 第一个乱序位置:", is_sorted(sorted(raw)))
    fixed = sorted(raw, key=nan_safe_key)
    print("挪走 NaN  :", fixed, "| 第一个乱序位置:", is_sorted(fixed, nan_safe_key))

    rows = [("a", 2), ("b", 1), ("c", 2), ("d", 1), ("e", 2)]
    print("reverse=True :", [r[0] for r in sorted(rows, key=lambda r: r[1], reverse=True)])
    print("排完再倒过来 :", [r[0] for r in reversed(sorted(rows, key=lambda r: r[1]))])

    people = [("zoe", 90), ("amy", 90), ("bob", 80), ("cat", 90), ("dan", 80)]
    print("两趟排序     :", two_pass(people, lambda p: p[1], lambda p: p[0]))

    scores = [88, 95, 70, 95, 61, 100]
    print("top3 高分    :", top_k(scores, 3))
    print("末 2 名      :", top_k(scores, 2, largest=False))
```

实测输出（Windows 11 / Python 3.14.9）：

```text
自然排序: ['app1', 'App2', 'app9', 'app10']
原始      : [3, nan, 1, 2]
直接排    : [3, nan, 1, 2] | 第一个乱序位置: 0
挪走 NaN  : [1, 2, 3, nan] | 第一个乱序位置: None
reverse=True : ['a', 'c', 'e', 'b', 'd']
排完再倒过来 : ['e', 'c', 'a', 'd', 'b']
两趟排序     : [('amy', 90), ('cat', 90), ('zoe', 90), ('bob', 80), ('dan', 80)]
top3 高分    : [100, 95, 95]
末 2 名      : [61, 70]
```

四个值得说的细节：

- **`is_sorted` 是这套里最该被抄走的一个。** `sorted()` 的失败是「静默的」——它不抛异常、不打日志，只是给你一份没排的数据。而 `is_sorted` 用 `<=` 而不是 `<` 检查（`a <= b` 对 NaN 返回 `False`，正好把「不可比」抓出来），代价只有一次线性扫描。
- **`nan_safe_key` 返回的是元组，不是数字。** 用 `(1, 0.0)` 把 NaN 钉在最后，用 `(0, x)` 放正常值。**代价是任何拿这份「排好的列表」去做二分查找的地方，都得用同一个 key** —— `bisect` 系列支持 `key=` 参数（3.10+），但一旦你忘了传，它会在 tuple 和 int 之间报 `TypeError`，比查出错数据要好，但足够让人困惑一次。
- **`reverse=True` 和 `reversed()` 的差别不是风格问题。** 上面的输出里 `c` 和 `a` 换了位置——这就是「同分的人顺序被悄悄改掉」，在排行榜、日志合并、diff 展示里都是肉眼能看见的错误。
- **`two_pass` 的两次排序看着笨，其实是一次性的。** 第一趟是 n log n，第二趟在「已经按名字排好」的数据上会命中 Timsort 的 run 检测 —— 但注意，**第二趟的 key 仍然全跑一遍**（今天量过：100,000 次一次不少），省的是比较不是 key。所以如果 primary 的 key 很贵，宁可拼一个复合 key，别依赖两趟。

一句话收这段：**`sorted()` 只认 `<`，`NaN` 让所有 `<` 变成 `False`，于是它把乱序当成有序还给你；而稳定性让「相等的人」有记忆——`reverse=True` 记得，`reversed()` 不记得。**

## ✨ 今日一句

> 排序算法从来没问过你「谁大」，它只反复问一句 **「a 小于 b 吗」**。所以当某个元素连这个问题都答不上来（`NaN`），它不会停下来问你——它会把「没有答案」理解成「不用交换」，然后微笑着把原来的顺序还给你。
>
> 这也是为什么「排过了」和「有序」是两件事：**前者是调用了一个函数，后者需要有人验一遍。**
